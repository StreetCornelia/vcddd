# 业务挖掘说明

**阅读身份：** 主控使用本文连接业务挖掘 Agent 和登记结果成熟度；用户直接调用的业务挖掘 Agent 使用本文确定工作范围并在当前对话工作。主控不执行其中的专业工作。

业务挖掘可以独立调用。通常建议先使用它打开目标空间；用户也可以从其他能力开始，在后续发现缺口时再回来使用。

## 阶段目标

与用户共同找出“这件事在宏观层面最终能做什么、带来什么效果”。AI 必须主动联想相关角色、场景、边界和可能能力，用候选场景帮助用户打开思路；用户决定哪些进入本次目标。

阶段结果包含宏观目标、已选 User Stories、范围和开放项。

## 主专业角色

用户可以在当前对话直接加载 [业务挖掘 Agent](01-interactive-discovery/business-discovery-agent.md)，也可以由主控创建或恢复用户可见的专业对话。两种方式都由用户直接与业务挖掘 Agent 反复讨论，直到宏观目标、多个简要 User Stories、范围和非目标得到确认。

无论输入是一个想法、若干文字、完整或不完整文档，还是已有原型，第一阶段都使用同一个主专业角色。输入形式不会产生另一条业务挖掘路线。

## 对已有素材的处理边界

如果用户的描述已经足以复述“为谁改变什么、最终能做什么、达到什么效果”，第一阶段不要打开已有素材；只登记素材入口，等待用户确认宏观目标后交给业务确立。

只有宏观目标本身仍不清楚时，第一阶段才从素材中做最小范围查看：

- 文档通常只查看标题、目录、摘要、关键入口和用户指出的段落；
- 原型通常只查看入口、主要角色、一级导航和能够直接说明整体效果的页面或截图；
- 一旦能够向用户提出可确认的宏观目标，就停止继续读取素材。

不要为了形成第一阶段结果而完整遍历文档、逐页盘点原型、还原业务规则或设计业务线。素材中真正有价值的参与者、行为、判断、状态变化和结果，由“业务确立”的业务定义 Agent 直接读取，或按需委派素材证据角色深入分析。

如果仅靠快速查看仍无法理解宏观目标，可以扩大读取范围，但必须在执行记录中写明未回答的问题、实际读取范围和停止条件。不得把这种例外固化成默认的全量素材分析。

## 产出要求

业务挖掘 Agent 必须按照 [业务挖掘.md 模板](../../../assets/templates/vcddd-obsidian/01-business-discovery/<goal-id>/业务挖掘.md) 产生一份由用户确认的业务挖掘结果，包含：

- 一段完整的宏观业务目标；
- 参与者与他们能获得的效果；
- 本次选择的多个 User Stories；
- 本次范围；
- 明确非目标；
- 延后、拒绝或仍开放的候选项；
- 推荐由“业务确立”能力继续回答的问题；
- 宏观判断来源和建议留给业务确立深读的素材入口。

正式事实固定写入：

```text
vcddd-obsidian/01-business-discovery/<goal-id>/
├── 业务挖掘.md
└── 候选场景池.md
```

执行记录写入 `vcddd-obsidian/work/<work-id>/执行记录/`，并从本地记录链接上述正式事实。正式事实不反向链接执行记录。

候选场景池是用户选择范围的依据，不是其他能力的默认全量上下文。其他能力通常先加载当前结果和素材入口，再按问题读取原始素材或业务确立证据。

## 不在本阶段

- 详细业务规则和术语完备性验证；
- Domain、架构、模块、API、数据库设计；
- 技术选型和代码实现；
- 语言验证 Agent；
- 把所有 AI 建议自动纳入范围。

## 确认结果的条件

- 产出要求全部满足；
- 业务挖掘进度点全部完成；
- 用户明确确认本阶段结果；
- 结果状态为 `confirmed`；
- 执行记录指向确认内容、能力衔接建议和开放问题。

这些条件只决定能否把业务挖掘结果称为 `confirmed`，不决定其他能力能否启动。条件未满足时，保持真实成熟度并标注假设、缺口和可能返工范围。
