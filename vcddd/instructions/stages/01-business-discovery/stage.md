# 业务挖掘阶段合同

**阅读身份：** 主控用本合同选择业务挖掘路线和登记结果成熟度；业务挖掘能力的主专业 Agent 用本合同约束工作边界。主控不执行其中的专业工作。

业务挖掘是一个可独立调用的能力域，不是业务确立或 Coding 的强制前置。通常建议先使用它打开目标空间，但用户可以从其他能力开始，也可以在后续发现缺口时再回来使用。

## 阶段目标

与用户共同找出“这件事在宏观层面最终能做什么、带来什么效果”。AI 必须主动联想相关角色、场景、边界和可能能力，用候选场景帮助用户打开思路；用户决定哪些进入本次目标。

阶段结果不是完整业务规则、语言模型、系统设计或实现方案。

## 两条路线

### 路线一：交互式业务挖掘

满足任一条件时使用：

- 只有初步想法或文字；
- 原型尚未代表已确认的宏观能力；
- 现有材料不足以直接确定本次能力范围。

主控创建同级专业对话并加载 [业务挖掘 Agent](01-interactive-discovery/business-discovery-agent.md)。用户直接与其反复讨论。

### 路线二：原型能力提取

必须同时满足：

- 用户明确确认原型已经代表宏观层面的目标能力；
- 原型可运行，或有足够可靠的截图、录屏和操作说明；
- 可以用视觉与交互证据观察能力。

主控创建同级专业对话并加载 [原型能力提取 Agent](02-prototype-capability-extraction/prototype-capability-agent.md)。

不得通过阅读业务实现代码来反推原型能力。允许为启动原型最低限度读取运行命令、环境配置或入口说明，但这些内容不能作为能力证据。

## 共同产出合同

两条路线最终都必须产生一份由用户确认的 [业务挖掘结果](../../../assets/templates/01-business-discovery/business-discovery-result-template.md)，包含：

- 一段完整的宏观业务目标；
- 参与者与他们能获得的效果；
- 本次选择的多个 User Stories；
- 本次范围；
- 明确非目标；
- 延后、拒绝或仍开放的候选项；
- 推荐由“业务确立”能力继续回答的问题；
- 对应执行记录与来源链接。

候选场景或原型证据是结果的依据，不是其他能力的默认全量上下文。其他能力通常先加载当前结果，并按其成熟度记录假设；需要追溯时才按链接读取证据。

## 不在本阶段

- 详细业务规则和术语完备性验证；
- Domain、架构、模块、API、数据库设计；
- 技术选型和代码实现；
- 语言验证 Agent；
- 把所有 AI 建议自动纳入范围。

## 路线切换

路线选择错误时可以切换，但必须：

1. 在执行记录中写明原因；
2. 保留已有材料及状态；
3. 新建或恢复正确路线的专业对话；
4. 不将未经用户确认的旧路线结论视为正式结果。

原型暂时无法运行时，不得自动切到“读代码推断”。优先修复启动条件，或请用户提供可靠视觉材料；仍无法获得视觉证据时，将“从原型提取能力”这一具体动作标记为 `limited`，同时说明其他能力仍可使用的材料。

## 确认结果的条件

- 共同产出合同全部满足；
- 用于确认本结果的路线进度点全部完成；
- 用户明确确认本阶段结果；
- 结果状态为 `confirmed`；
- 执行记录指向确认内容、能力衔接建议和开放问题。

这些条件只决定能否把业务挖掘结果称为 `confirmed`，不决定其他能力能否启动。条件未满足时，保持真实成熟度并标注假设、缺口和可能返工范围。
