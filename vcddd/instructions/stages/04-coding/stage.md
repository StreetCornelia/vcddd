# Coding 说明

**阅读身份：** VCDDD 主控、用户直接调用的开发 Leader 能力，以及后续实际开发与集成人物。

## Coding 负责

Coding 把已经形成的业务、Domain 和 Pre-Coding 设计落成真实运行的代码。它负责：

- 从当前目标直接定位并修改相关代码；
- 只在公共规则缺失或多个任务存在真实依赖时补充编码规范或任务图；
- 直接在当前任务适用的工作区完成生产代码、迁移、装配和过程日志；
- 围绕当前失败可能与已有证据动态安排验证和集成；
- 根据代码、测试和运行证据返回需要修正的任务或上游设计；
- 让实现、验证、审核和集成按交付需要穿插，不默认追加收尾流程。

业务、Domain 和业务组合由业务确立拥有。系统、模块、API、逐 API 内部执行流程和数据库由 Pre-Coding 拥有。Coding 可以用实现证据指出这些事实的问题，不能在代码中静默改变它们。

## 当前可以直接使用的人物与能力

| 当前目标 | 人物或能力 | 工作结果 |
|---|---|---|
| 把一个明确系统的当前开发范围拆成小而完整的任务，形成任务依赖图和每个任务的开发说明 | 开发 Leader 的[开发任务拆分能力](../../roles/development-leader/capabilities/task-decomposition.md) | 该系统的 `开发任务图.md` 与 `tasks/<task-id>-<task-name>/任务.md` |
| 调查一个明确系统的已有代码，或为该系统形成开发和集成审查共同使用的编码规则 | 开发 Leader 的 [Coding Style 能力](../../roles/development-leader/capabilities/coding-style.md) | 该系统的 `编码规范.md` |
| 完成一个明确开发范围的真实代码、日志和按需验证 | [开发人员](../../roles/developer/role.md)的[开发任务实现能力](../../roles/developer/capabilities/task-implementation.md) | 生产代码与适用的运行或验证证据 |
| 为当前交付补充有价值的独立验证结论 | [测试人员](../../roles/tester/role.md)的[候选验证能力](../../roles/tester/capabilities/candidate-verification.md) | 可定位到 baseline 的验证结论 |
| 处理当前交付的合并、组合行为或集成审查 | [集成人员](../../roles/integrator/role.md)的[候选审查与集成能力](../../roles/integrator/capabilities/candidate-integration.md) | 可定位到 baseline 的集成结论 |

规划能力只在对应问题真实存在时使用。不要为了让 Coding Style 与任务拆分并行而创建 Agent；若公共规则变化确实影响任务边界，只复核受影响的任务和依赖。

默认直接执行当前明确范围的开发工作。主控动态判断由谁在何时实施、测试、审核或集成最能促进真实交付，不套用固定风险档位或角色套餐。用户可以直接指定任一人物或能力；状态只在跨对话或多人协作确有恢复价值时维护。

多人 Coding 时，VCDDD 的质量结构由主控动态组织，不成为每个子 Agent 的办事清单。主控提供可用 baseline、精确范围、必要事实、真实依赖、预期结果、证据目标和接入方式；执行者只做当前人物的核心专业工作。测试或集成人员可以基于明确 baseline 穿插工作，其结论只影响相关结果。

## 系统边界

需要 Coding 规划时，以一个明确系统为主要范围，并在有助于定位与接入时记录：

- 系统 ID 与系统名称；
- 该系统对应的代码仓库或代码根目录；
- 必要时用于隔离或复现的 Commit；
- 本轮涉及的模块和需要形成的可运行能力。

用户只说业务名或项目名，而系统设计中存在多个系统时，主控先调查最可能相关的范围，并在不同选择会改变交付时请求用户决定；调查、定位及其他不依赖该决定的工作继续。正式规划使用真实系统身份，不以业务名、产品名、仓库名或工作区名称代替，也不创建覆盖所有系统的规划文档。

只有确实创建了规划文档时，不同系统才分别维护自己的编码规范、任务图和任务文档。普通开发不创建 Coding 状态、开发队列或集成队列。跨系统依赖只记录当前任务实际使用的外部能力，不复制另一系统的内部任务。

## 小而完整的开发任务

一个开发任务在其已知依赖允许实施时，能够完整实现一项能力。它不按 Controller、Service、Repository、数据库、日志或测试等技术层拆分，也不把形式化验证或集成当作每个任务的默认门槛。

每个任务按实际需要包含：

- API、命令、消息、后台任务或其他真实入口；
- 应用编排和 Domain 行为；
- 数据库迁移、数据访问和事务；
- 外部组件真实接入；
- 配置、注册和启动装配；
- 正常结果、拒绝、失败和恢复；
- 与运行环境和风险相称的可观测性；
- 能支持当前交付结论的自检、测试或实际运行证据。

任务不需要机械包含不存在的对象。删除某个候选任务后，如果当前能力仍然完整，说明该任务不应独立存在。拆开后任一部分只能形成半成品时，把这些代码责任放回同一个任务。

以下行为不能作为任务完成结果：

- 固定返回成功、`true`、空集合或示例数据；
- 空方法、空适配器、只定义接口或永远不会失败的实现；
- 捕获错误后返回成功或默认值；
- 用 fallback、测试替身或本地假实现掩盖主路径未完成；
- 只完成数据库、日志、测试或装配中的一部分，把其余内容留给未声明的后续工作；
- 当前交付结论承诺真实路径可用，却只通过编译或 mock 测试。

已经由设计明确的降级行为可以实现，但主路径必须真实完成，降级触发、结果和日志必须清楚；验证围绕当前结论与证据缺口安排。

## 按需使用 Coding Style 与可观测性

现有仓库规则足以指导当前修改时直接遵循，不先生成或修订 `编码规范.md`。主控在形成公共规则能减少当前返工、冲突或歧义时穿插使用 Coding Style 能力，不把规范完成设为实现前置。

可观测性只覆盖当前能力真正需要观察的关键操作、失败和外部调用，并服从运行环境：服务端可以使用控制台、结构化日志、平台日志或日志文件；浏览器可以使用诊断信息与遥测；Serverless 可以使用平台日志与追踪。不得泄露密钥、Token、完整 Key 或其他敏感信息。不要为了满足模板而新增日志文件、轮转、保留或关联字段。

## 依赖与按需集成

依赖图用于表达真实代码依赖、baseline 关系和合并影响。某项工作缺少真实依赖时，主控限制或重排受影响动作，同时继续其他能够形成交付或证据的工作。

实现者、测试人员、审核者和集成人员可以围绕当前失败可能与证据缺口动态穿插。主控不预设固定风险套餐、候选串行队列或一律先实现后测试的顺序；验证或合并发现问题时更新受影响实现、baseline 与结论，不阻塞无关工作。

跨对话或多人协作需要恢复时，可以在本地 `work/<work-id>-<work-name>/Coding 状态.md` 记录必要的 baseline、负责人、依赖、风险、外部输入和未完成事项。内容保持最小，只服务于当前协作。

## 缺少真实运行条件

任务拆分时尽量提前列出可能需要用户提供的 Provider Key、API Key、测试账号、沙箱地址、证书、授权范围和受控环境。到达真实实现或验证时点后，如果这些内容尚未提供：

- 开发人员、测试人员或集成人员立即通知主控；直接角色方式直接询问用户；
- 请求说明准确名称、用途、配置入口、目标环境、最低权限、受影响动作和仍可继续的工作；
- 跨对话或多人协作时，主控把请求交给用户并记录必要状态；
- 不依赖该输入的工作可以继续；
- 真实输入可用后，主控依据仍缺少的交付证据安排受影响工作。

敏感值只通过环境变量、项目已有 Secret 机制或用户指定方式注入。代码、Git、Obsidian、执行记录、命令输出和日志中不得出现真实值。任何角色都不能使用固定成功、假 Provider、mock、替代服务、静默跳过或 fallback 掩盖缺少真实输入。

## 正式文档位置

```text
vcddd-obsidian/04-coding/systems/<system-id>-<system-name>/
├── 开发任务图.md
├── 编码规范.md
└── tasks/
    └── <task-id>-<task-name>/
        └── 任务.md
```

仅在任务图、编码规范或任务文档本身是所需长期结果时创建正式文档并进入 Git。当前工作、Agent 执行记录、讨论材料和临时投影只在确有恢复需要时放在 `vcddd-obsidian/work/<work-id>-<work-name>/`，不进入 Git。

正式文档只写当前规则、任务、依赖和完成要求。调查过程、备选拆法、被否决方案、对话历史和 Agent 推理留在对话与执行记录。

跨对话或多人协作时，主控的必要状态和外部输入请求可写入本地 `Coding 状态.md`，不进入 Git。验证和运行证据按交付、复现与交接需要保留，并定位到对应 baseline。

原型、技术 POC、最小端到端实现或其他验证性实现需要作为系统级长期证据保留时，使用 `vcddd-obsidian/03-pre-coding/systems/<system-id>-<system-name>/validation/<validation-id>-<validation-name>/`，把计划、验证源码、运行记录、产物和结论放在同一验证项中。普通生产代码测试仍遵循目标仓库自身的测试目录，不迁入该验证工作空间。
