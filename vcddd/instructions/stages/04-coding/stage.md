# Coding 说明

**阅读身份：** VCDDD 主控、用户直接调用的开发 Leader 能力，以及后续实际开发与集成人物。

## Coding 负责

Coding 把已经形成的业务、Domain 和 Pre-Coding 设计落成真实运行的代码。它负责：

- 为当前目标系统调查已有代码或形成该系统的编码规范；
- 把当前系统的开发范围拆成小而完整的任务并建立有向依赖图；
- 在隔离工作区完成生产代码、迁移、装配、过程日志和测试；
- 使用串行集成队列持续形成新的可运行 Commit；
- 根据代码、测试和运行证据返回需要修正的任务或上游设计；
- 在全部开发任务闭合后完成系统验证、工程改进和独立审核。

业务、Domain 和业务组合由业务确立拥有。系统、模块、API、逐 API 内部执行流程和数据库由 Pre-Coding 拥有。Coding 可以用实现证据指出这些事实的问题，不能在代码中静默改变它们。

## 当前可以直接使用的人物与能力

| 当前目标 | 人物或能力 | 工作结果 |
|---|---|---|
| 把一个明确系统的当前开发范围拆成小而完整的任务，形成任务依赖图和每个任务的开发说明 | 开发 Leader 的[开发任务拆分能力](../../roles/development-leader/capabilities/task-decomposition.md) | 该系统的 `开发任务图.md` 与 `tasks/<task-id>-<task-name>/任务.md` |
| 调查一个明确系统的已有代码，或为该系统形成开发和集成审查共同使用的编码规则 | 开发 Leader 的 [Coding Style 能力](../../roles/development-leader/capabilities/coding-style.md) | 该系统的 `编码规范.md` |
| 在独立 worktree 中完成一个就绪任务的真实代码、日志、测试和实际运行，形成候选 Commit | [开发人员](../../roles/developer/role.md)的[开发任务实现能力](../../roles/developer/capabilities/task-implementation.md) | 生产代码、候选 Commit 与本地执行记录 |
| 在固定试合并代码树上独立验证任务结果、数据、外部接入和日志 | [测试人员](../../roles/tester/role.md)的[候选验证能力](../../roles/tester/capabilities/candidate-verification.md) | 独立验证记录与可复现证据 |
| 对队首候选完成初审、试合并、组织独立验证、组合结果复审和正式集成 | [集成人员](../../roles/integrator/role.md)的[候选审查与集成能力](../../roles/integrator/capabilities/candidate-integration.md) | 新集成 Commit 或可复现退回记录 |

两个规划能力可以由加载同一开发 Leader 人物说明的不同 Agent 从同一个设计与代码快照并行开始。Coding Style 中会改变目录、共享写入、日志设施、测试方式、迁移方式、代码生成或统一装配的规则形成后，开发任务拆分能力只复核受影响的任务和依赖。

本系统前置任务已经集成且系统外依赖可用的开发任务可以并行启动。每个任务使用自己的开发人员、分支和 worktree；每个候选由独立集成人员审核，并由不参与实现和集成的测试人员验证固定试合并代码树。用户可以直接指定任一人物或能力。主控负责连接、监督、维护当前状态和处理事件，不替专业人员调查、拆分、写代码、测试、修复或审核。

## 系统边界

每次 Coding 规划只处理一个明确系统。开始前记录：

- 系统 ID 与系统名称；
- 该系统对应的代码仓库或代码根目录；
- 固定 Commit；
- 本轮涉及的模块和需要形成的可运行能力。

用户只说业务名或项目名，而系统设计中存在多个系统时，先列出已知系统并确认本次处理对象。不得以业务名、产品名、仓库名或工作区名称代替系统身份，也不得创建覆盖所有系统的 `编码规范.md`、`开发任务图.md` 或任务目录。用户已经明确系统时直接开始，不重复确认。

不同系统分别维护自己的编码规范、任务图、任务文档、Coding 状态、开发队列和集成队列。共享仓库、工具或配置不改变归属：目标系统的文档引用自己实际采用的共享来源和适用范围。一个系统依赖另一个系统的集成结果时，只记录精确的外部任务或结果链接，不把另一个系统的任务复制进当前任务图。

## 小而完整的开发任务

一个开发任务在它声明的本系统前置任务已经集成、系统外依赖已经可用后，能够独立实现、运行、验证和集成一项完整能力。它不按 Controller、Service、Repository、数据库、日志或测试等技术层拆分。

每个任务按实际需要包含：

- API、命令、消息、后台任务或其他真实入口；
- 应用编排和 Domain 行为；
- 数据库迁移、数据访问和事务；
- 外部组件真实接入；
- 配置、注册和启动装配；
- 正常结果、拒绝、失败和恢复；
- 关键过程日志、控制台输出和日志文件；
- 自动化测试和实际运行方式。

任务不需要机械包含不存在的对象。删除某个候选任务后，如果当前能力仍然完整，说明该任务不应独立存在。拆开后任一部分只能形成半成品时，把这些代码责任放回同一个任务。

以下行为不能作为任务完成结果：

- 固定返回成功、`true`、空集合或示例数据；
- 空方法、空适配器、只定义接口或永远不会失败的实现；
- 捕获错误后返回成功或默认值；
- 用 fallback、测试替身或本地假实现掩盖主路径未完成；
- 只完成数据库、日志、测试或装配中的一部分，把其余内容留给未声明的后续工作；
- 只通过编译或 mock 测试，却没有运行当前任务承诺的真实路径。

已经由设计明确的降级行为可以实现，但主路径必须真实完成，降级触发、结果和日志必须清楚，并分别验证。

## Coding Style 的共同要求

所有开发任务和集成审查使用同一系统当前版本的 `编码规范.md`。规范至少说明命名、以 Domain 为主的文件编排、非业务代码位置、过程日志、错误处理、数据访问、外部协作、测试和工具链。

日志具有以下已经确定的核心要求：

- 重要操作具有开始、关键步骤、状态变化、外部调用、结果和失败日志；
- 日志可以在控制台直接看到；
- 日志实际写入可定位的日志文件；
- 日志文件路径可配置，并确定轮转、保留和初始化失败处理；
- 一次操作可以用请求、追踪、任务或业务对象标识串联；
- fallback、重试、拒绝和失败不能静默发生；
- 密钥、Token、完整 Key 和其他敏感信息不能写入日志。

具体日志库、格式、文件位置和轮转方式由使用 Coding Style 能力的开发 Leader 结合当前语言、框架和运行环境提出方案并与用户确认。无法直接写文件的运行环境必须把具体限制和持久日志替代方式交给用户决定，不能自行删除日志文件要求。

## 有向图与串行集成队列

有向图记录当前系统内部真实的开发前置关系。一个任务只有在本系统前置任务已经成功集成、系统外依赖已经验证可用后才可开始；兄弟任务不互相等待，可以并行开发。

开发完成只产生候选 Commit。候选按完成顺序进入同一集成分支的串行队列。集成人员基于最新集成 Commit 完成候选初审和临时试合并，测试人员在固定试合并代码树上形成独立验证记录，集成人员再完成组合结果复审；全部正确后才更新正式集成 Commit。

某个任务集成成功后，主控立即检查它的直接后继。本系统前置任务已经全部集成且系统外依赖已经验证可用的节点可以立即开始，不等待同一层的其他任务完成。审核或验证失败的候选退回原开发人员修正；修正形成新候选后重新进入队尾，其他无关候选继续集成。

本地 `work/<work-id>-<work-name>/Coding 状态.md` 只保存当前集成基线、任务状态、串行队列和外部输入请求。任务状态使用：

- `waiting`：仍有本系统前置任务未集成，或系统外依赖尚不可用；
- `ready`：本系统前置任务已经集成且系统外依赖可用，可以启动开发；
- `developing`：开发人员正在实现或修正；
- `waiting-input`：某项实现或验证等待用户控制的真实运行条件；
- `queued`：候选 Commit 已进入串行集成队列；
- `integrating`：当前候选正在独立集成；
- `returned`：候选已经退回原开发人员；
- `integrated`：候选已经形成新的集成 Commit。

主控只处理已经发生的事件：

1. 本系统前置任务全部集成且系统外依赖可用后，把任务更新为 `ready`，启动或恢复各自开发人员；
2. 开发人员形成候选后，登记候选并加入队尾；
3. 集成分支空闲时，把队首候选交给独立集成人员；
4. 候选被退回时恢复原开发人员，新候选形成后加入队尾；
5. 候选集成成功后登记新集成 Commit，移出队列并立即检查直接后继。

同一集成分支同时只能有一个集成人员。队列只串行化集成分支写入，不阻止其他就绪任务开发。

## 缺少真实运行条件

任务拆分时尽量提前列出可能需要用户提供的 Provider Key、API Key、测试账号、沙箱地址、证书、授权范围和受控环境。到达真实实现或验证时点后，如果这些内容尚未提供：

- 开发人员、测试人员或集成人员立即通知主控；直接角色方式直接询问用户；
- 请求说明准确名称、用途、配置入口、目标环境、最低权限、受影响动作和仍可继续的工作；
- 主控立即把请求交给用户，并在 `Coding 状态.md` 登记状态；
- 不依赖该输入的工作可以继续，依赖该输入的实现或验证记为 `waiting-input`；
- 真实路径没有完成验证前，任务不能形成可集成候选，候选也不能正式集成。

敏感值只通过环境变量、项目已有 Secret 机制或用户指定方式注入。代码、Git、Obsidian、执行记录、命令输出和日志中不得出现真实值。任何角色都不能使用固定成功、假 Provider、mock、替代服务、静默跳过或 fallback 掩盖缺少真实输入。

## 正式文档位置

```text
vcddd-obsidian/04-coding/systems/<system-id>-<system-name>/
├── 开发任务图.md
├── 编码规范.md
└── tasks/
    └── <task-id>-<task-name>/
        └── 任务.md
```

正式文档进入 Git。当前工作、Agent 执行记录、讨论材料和临时投影只放在 `vcddd-obsidian/work/<work-id>-<work-name>/`，不进入 Git。

正式文档只写当前规则、任务、依赖和完成要求。调查过程、备选拆法、被否决方案、对话历史和 Agent 推理留在对话与执行记录。

主控的 Coding 当前状态、队列和外部输入请求只写入本地 `Coding 状态.md`，不进入 Git。候选 Commit、新集成 Commit、测试和运行证据分别写入开发人员、测试人员或集成人员的本地执行记录。
