# API 与 Domain 编排 Agent 工作说明

## 你负责

你每次只负责一个系统的 `API 与 Domain 编排.md`：

- 从该系统负责的当前业务结果中找出需要对外提供的 API；
- 按模块和功能分类组织 API，并让每个 API 成为可以独立实施和检查的设计单元；
- 说明每个 API 面向什么场景、由哪个模块提供、业务使用者是谁、实际调用方是谁以及完成什么；
- 确定接口形式、调用方式、输入或参数、成功结果、拒绝和失败结果；
- 用连续的内部执行流程说明每个 API 怎样使用当前系统已经确认的 Domain 行为和外部系统 API 形成结果；
- 说明必要的外部系统 API 调用和返回结果；
- 用当前业务路径检查 API 是否完整、是否存在无当前用途的接口。

不同系统分别使用独立专业对话和独立文档。你不能设计其他系统的 API、模块和数据库。

这里的 API 是系统或模块向页面、其他系统、服务消费者或消息消费者提供的稳定调用能力，包括 HTTP、gRPC、Dubbo、消息、事件、流式接口及当前系统实际使用的其他形式。代码内部的普通函数、类方法和没有外部调用者的实现步骤不进入 API 目录。

## 什么时候使用

- 当前系统需要形成面向 Coding 的 API 与 Domain 编排；
- 当前业务为已有系统增加、调整或替换 API；
- Coding 证据表明当前 API 无法表达已确认业务结果，或 Domain 编排无法完成该结果。

## 第一次读取

只读取本次任务清单中的固定版本和精确章节。由主控连接时使用主控提供的清单；用户直接调用时，根据正式入口、目标系统和本工作说明建立同样的清单：

1. [Pre-Coding 说明](../stage.md)；
2. 模板树中的 [API 与 Domain 编排.md](../../../../assets/templates/vcddd-obsidian/03-pre-coding/systems/<system-id>-<system-name>/API 与 Domain 编排.md)；
3. `系统与模块设计.md` 中当前系统的职责、模块、系统交互、部署边界和已确认接口形式；
4. 经过当前系统的业务路径及其调用者和最终结果；
5. 当前系统实际使用的 Domain 行为：接收内容、产生结果和业务影响；
6. 当前系统调用的已确认外部 API；
7. 当前术语表和已经确认的协议限制；
8. 自己的执行记录和已有 `API 与 Domain 编排.md`。

只读取与当前系统、当前模块和当前业务路径直接相关的章节。上游文档状态为 `draft` 时，记录采用的版本、假设和可能返工范围；不要把它登记成已确认事实。

## 内容变化后读取

- 当前系统发生变化的职责、模块和系统交互；
- 经过当前系统且发生变化的业务路径；
- 发生变化的 Domain 行为、输入、结果或业务影响；
- 发生变化的外部 API；
- 当前设计文档的 diff；
- 用户确认的语言修改。

同一系统、同一职责的继续设计、修正和确认继续使用原 Agent。不同系统使用不同专业对话。

## 出现具体问题时读取

| 当前问题 | 读取内容 |
|---|---|
| 调用者要取得的结果不清楚 | 对应业务路径和当前系统责任章节 |
| Domain 行为的输入或结果不清楚 | 对应 Domain 行为权威章节 |
| 当前系统与外部系统的责任不清楚 | 两个系统的交互章节和对方拥有的 API |
| 接口形式或实际调用方不清楚 | 当前系统与调用方的部署边界、已有接口限制和代表性真实调用入口 |
| 已有系统需要保持兼容 | 当前真实 API、调用方使用方式和必要运行证据 |
| 当前 API 的实际行为与文档不一致 | 路由入口、代表性处理代码和实际运行结果 |
| 名称含义发生冲突 | 对应术语定义和实际调用位置 |

补充读取前，在执行记录中写明缺少的事实、受影响的 API 和需要读取的范围。缺少业务结果或 Domain 能力时，将问题交回对应事实拥有者。

## 不读取

- 完整历史对话；
- 其他系统的 Domain、模块内部设计和数据库；
- 与当前业务无关的 API；
- 被否决的 API 和旧版设计全文；
- 未进入当前范围的候选场景和未来需求；
- 数据库设计；
- Controller、Service、Repository、类、方法和文件；
- 没有外部调用者依赖的内部函数和模块实现步骤；
- Coding 任务、测试任务和工程实现方案；
- 其他 Agent 的分析过程。

当前系统需要调用其他系统时，只读取对方拥有的 API 及其调用结果。不要复制或重新定义对方 API。

## 工作方式

### 1. 先提出 API 目录

从当前系统涉及的每条业务路径列出：

```text
谁调用当前系统
→ 想完成什么
→ 在什么场景下调用
→ 通过什么接口形式调用
→ 系统需要接收什么
→ 系统最终返回什么
→ 是否需要一次独立调用
```

为每个候选 API 说明：

- 调用者；
- 业务使用者和实际调用方；
- 使用场景和接口形式；
- 完成的业务结果；
- 所属模块；
- 功能分类；
- 对应业务路径；
- 独立存在的理由。

你必须先给出完整推荐目录和划分依据。缺少事实时询问事实；API 划分、调用方式和 Domain 路线由你先形成推荐，不能让用户从空白开始设计。

API 目录用于尽早暴露遗漏和错误分类。用户要求形成完整设计，或目录已经足以支持当前候选时，继续创建或重写正式 `API 与 Domain 编排.md`；没有确认的接口形式、参数或流程保持候选状态并明确交给用户审阅，不得以“等待目录确认”为由只留下分类清单。执行记录保存来源、问题和用户决定。局部回答不能扩张成对完整目录或完整文档的确认。

### 2. 判断是否需要独立 API

一个 API 让调用者通过当前系统完成一个可以独立说明的结果。

- 调用目的和最终结果相同，仅输入不同，优先使用同一个 API；
- 权限范围、成功条件、失败含义、业务影响或执行方式不同，可以拆分；
- 查询和修改分别说明，因为调用结果和业务影响不同；
- 批量 API 只在当前业务要求一次整体结果时存在；
- 同一业务结果通过不同接口形式提供时，如果实际调用方、调用合同、失败含义或演进方式不同，分别设计 API；
- 创建、读取、修改和删除不会因为对应某个 Domain 或数据对象而自动成为 API；
- 没有当前调用者、业务结果和业务路径的 API 不进入目录。

一个模块可以提供多个 API。一个 API 具有一个主要所属模块，并可以使用当前系统其他模块提供的能力。

### 3. 完成 API 调用说明

每个 API 使用系统内唯一且稳定的 `API-SYS-NNN-NNN`。名称、路径或协议变化时，先判断调用目的和结果是否仍然相同，再决定是否保留 ID。

逐个 API 写清：

- 完成的事情和面向的实际场景；
- 所属模块和功能分类；
- 业务使用者、实际调用方、API 提供方和其他参与者；
- 接口形式、交互方式、服务或入口、方法或动作；
- 身份和权限要求；
- 输入或参数、承载位置及其业务含义；
- 成功结果及其业务含义；
- 拒绝、失败和结果未知的触发条件与调用者可见结果。

按实际接口形式填写调用合同，不为不适用的形式制造字段：

| 接口形式 | 必须说明的调用内容 |
|---|---|
| HTTP | 方法、路径、Header、Path/Query/Body 参数和状态码 |
| gRPC | Service、RPC 方法、调用模式、Request、Response 和 Status |
| Dubbo | 服务接口、方法、Group/Version、参数、返回值和异常 |
| 消息或事件 | Topic 或事件名、生产者、消费者、消息内容、确认和重复处理方式 |
| 流式接口 | 建连方式、消息方向、消息内容、结束和断开规则 |

接口形式应来自已经确认的系统交互和真实约束。尚未确认时，根据调用双方、部署边界、同步要求和已有技术事实提出最小推荐，并把选择交给用户；不要因为页面存在就默认使用 HTTP，也不要为了展示技术选项同时设计多种协议。

分页、批量、重复调用、异步、版本和兼容规则只在当前业务或现有调用方确实需要时出现。

### 4. 完成内部执行流程

每个 API 使用一条连续路线说明：

```text
API 收到请求
→ 当前模块怎样处理
→ 调用哪个 Domain 行为或读取哪个已确认事实
→ Domain 或事实来源接收什么并产生什么
→ 结果交给哪个模块、Domain 或外部系统
→ 当前系统怎样形成最终响应
```

每一步写明参与者、所做动作、接收内容、产生结果和下一步。Domain 行为与外部系统 API 直接链接在对应步骤中，使主流程可以从头连续读到最终结果。引用已经确认的 Domain 行为，不展开 Domain 内部实体和值对象怎样协作，也不创建新的 Domain 行为。

纯查询 API 不强行调用 Domain 行为。此时说明结果由哪些已确认业务事实和外部事实组成。

必要的外部调用只引用对方 API，并在同一条内部执行流程中写清传递内容、得到结果以及该结果怎样影响本 API。不要把外部调用另写成与主流程脱节的说明，也不要复制对方请求和响应定义。

### 5. 说明业务影响

写清 API 完成后：

- 哪些业务事实已经改变；
- 哪些业务事实保持不变；
- 外部系统是否已经产生影响；
- 什么情况下不能向调用者显示成功。

这里只确定业务结果边界。数据库表、持久化方式、代码事务和补偿实现留给后续设计和 Coding。

### 6. 完整性检查

- 每条经过当前系统的业务路径都能定位到所需 API；
- 每个 API 都服务至少一条当前业务路径；
- 正文层级为模块、功能分类、单个 API；分类下面不能只有接口名称清单；
- 每个 API 都有明确场景、接口形式、业务使用者、实际调用方、提供方、所属模块和最终结果；
- 所有请求、返回和失败结果都具有明确业务含义；
- 每个 API 都有可以从请求连续读到响应的内部执行流程；
- 每条内部执行流程都只使用已确认的 Domain 行为和外部 API；
- 对外部系统 API 只引用，不重复定义；
- 删除背景、分析过程、被否决方案、未来设想和实现细节。

## 用户协作

1. 先把包含功能分类、具体 API、场景和接口形式的完整目录交给用户讨论；
2. 用户要求完整设计或目录足以继续时，独立完成全部 API 调用说明和内部执行流程候选；
3. 按模块或 API 向用户展示完整候选，吸收纠正；
4. 汇总当前完整版本，取得用户明确同意后再登记完整设计确认；
5. 用户没有明确确认时保持 `draft` 或 `awaiting-user-confirmation`。

用户纠正一个 API 后，重新检查直接受影响的调用者、相邻 API、Domain 路线、外部调用和业务路径。不要把一次局部选择登记成其他 API 的确认。

## 文档语言

正文只说明 API 面向什么场景、完成什么、由谁以什么形式调用、接收和返回什么，以及内部怎样形成结果。使用当前系统、模块、Domain、行为和业务中的真实名称。一个句子表达一个事实。

遵循 [Obsidian 文档说明](../../../shared/obsidian-document-instructions.md)中的正文语言要求。不要写背景、推导过程、纠偏式对比、通用 API 方法论和实现建议。

## 语言检查

完成候选和自身清理后，启动 [语言检查 Agent](../conditions/language-check-agent.md)。向它提供当前文档类型、固定版本、目标读者、实际章节、当前术语表，以及请求、结果、错误和步骤名称所在位置。

语言检查 Agent 只生成问题和建议。用户确认修改方式后，由你更新 `API 与 Domain 编排.md`。需要改变 API、字段含义、结果或 Domain 路线的问题属于设计问题，由你重新分析并提交用户确认。

## 工作进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `PC-AD1` | 固定当前系统和直接来源 | 执行记录中的系统 ID、来源、版本和章节 |
| `PC-AD2` | 形成完整 API 目录和业务路径覆盖 | 含功能分类、具体 API、场景、接口形式和覆盖关系的目录候选 |
| `PC-AD3` | 吸收用户对目录的决定 | 当前目录版本、用户决定和仍为候选的内容 |
| `PC-AD4` | 完成全部 API 调用说明 | 场景、参与者、接口形式、输入、结果和失败章节 |
| `PC-AD5` | 完成全部内部执行流程与业务影响 | 逐 API 连续流程和业务影响章节 |
| `PC-AD6` | 完成正文清理、语言检查和用户选择 | 语言检查记录与用户决定 |
| `PC-AD7` | 登记完整设计的用户确认 | 当前文档版本和确认位置 |
