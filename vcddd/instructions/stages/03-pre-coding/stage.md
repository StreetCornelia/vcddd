# Pre-Coding 说明

**阅读身份：** VCDDD 主控 Agent 使用本文选择 Pre-Coding Agent、准备读取内容和登记产出；用户直接调用的 Pre-Coding 主专业 Agent 使用本文确定工作边界并建立自己的任务上下文。主控不开展专业设计。

## 负责的工作

Pre-Coding 使用当前业务、已确认的 Domain 事实和业务组合，形成 Coding 直接使用的设计文档：

- 系统与模块设计；
- API 与 Domain 编排；
- 数据库设计。

三类设计分别由明确角色负责，不要求每次都新建 Agent。用户直接指定角色时由当前 Agent 加载对应工作说明；主控连接时使用用户可见的专业对话。不同系统分别维护自己的 API 与数据库专业上下文和文档。

## 当前可用角色

| 当前工作 | Agent | 产出 |
|---|---|---|
| 设计整体系统、系统职责、系统交互、系统内部模块和关键业务路径 | [系统与模块设计 Agent](01-system-and-module-design/system-and-module-design-agent.md) | `系统与模块设计.md` |
| 设计一个系统面向页面、其他系统或服务消费者的 API、调用形式、调用结果和逐 API 内部执行流程 | [API 与 Domain 编排 Agent](02-api-and-domain-orchestration/api-and-domain-orchestration-agent.md) | 当前系统的 `API 与 Domain 编排.md` |
| 设计一个系统的 ER、表、字段、类型、约束、索引、关系、事务和数据生命周期 | [数据库设计 Agent](03-database-design/database-design-agent.md) | 当前系统的 `数据库设计.md` |
| 检查指定 Pre-Coding 文档中的名称、句子、字段、表格和图中文字 | [语言检查 Agent](conditions/language-check-agent.md) | 独立语言检查记录 |

系统与模块设计 Agent 负责整体系统和各系统内部模块。每个系统分别维护一份 API 与 Domain 编排角色上下文和一份数据库设计角色上下文；它们可以由用户在当前对话直接启动，也可以由主控连接。不同系统不共用 API、数据库文档和内部设计上下文。语言检查 Agent 在指定设计文档形成后使用，只提交问题和建议，等待用户确认。

## 系统与模块设计需要的内容

本次任务使用固定版本和精确章节链接。由主控连接时由主控提供；用户直接调用时，由系统与模块设计 Agent 根据正式入口和当前目标建立同样的清单：

- 当前宏观业务目标、已选 User Stories 和业务线结果；
- 当前业务使用的已确认能力，包括能力由哪个 Domain 提供、接收什么、产生什么；
- 业务怎样组合这些能力形成结果；
- 已确认的现有系统、外部系统、第三方组件、运行方式和部署边界；
- 当前术语表；
- 系统与模块设计模板。

任务清单不包含完整历史对话、业务与 Domain 的设计过程、被否决方案、未来设想、API、数据库设计和 Coding 任务拆分。

## API 与 Domain 编排需要的内容

每次只处理一个系统，并使用固定版本和精确章节链接。由主控连接时由主控提供；用户直接调用时，由 API 与 Domain 编排 Agent 根据正式入口、目标系统和当前任务建立同样的清单：

- 当前系统在 `系统与模块设计.md` 中的职责、模块和系统交互；
- 经过当前系统的业务路径、调用者和最终结果；
- 当前系统与调用方已经确认的部署边界、接口形式和协议限制；
- 当前系统实际使用的 Domain 行为、输入、结果和业务影响；
- 当前系统需要调用的外部 API；
- 当前术语表和已确认协议限制；
- API 与 Domain 编排模板。

任务清单不包含其他系统的内部设计、数据库、Coding 任务和未来 API。已有系统需要保持兼容或核实真实行为时，由 API 与 Domain 编排 Agent 记录具体问题后读取当前 API、调用方使用方式和最小必要运行证据。

## 数据库设计需要的内容

每次只处理一个系统，并使用固定版本和精确章节链接。由主控连接时由主控提供；用户直接调用时，由数据库设计 Agent 根据正式入口、目标系统和当前任务建立同样的清单：

- 当前系统的职责、边界和与外部系统的数据责任；
- 当前系统必须保存的 Domain 事实、非 Domain 数据、关系和生命周期；
- 会读取或改变数据、要求共同成功、处理并发或面对外部失败的具体 API 内部步骤；
- 当前真实过滤、关联、排序、分页、数据量、保留时间和安全限制；
- 当前系统已经确定的数据库产品、部署方式和技术限制；
- 已有系统当前 Schema、表、字段、约束、索引和迁移结果；
- 数据库设计模板。

业务、Domain 和 API 只帮助数据库设计 Agent 判断需要承载的数据及一致性要求。数据库正式文档只写数据库内部结构，不复制业务目标、流程、API 功能和分析过程。已有系统需要核实结构时，数据库设计 Agent 只读取数据库 Schema、迁移结果、最小数据分布和必要运行证据，不扩张到应用代码分析。

## 文档位置

```text
vcddd-obsidian/03-pre-coding/
├── 系统与模块设计.md
├── 语言检查/
└── systems/
    └── <system-id>/
        ├── API 与 Domain 编排.md
        ├── 数据库设计.md
        └── 语言检查/
```

系统与模块设计事实只写在 `系统与模块设计.md`。每份 API 与 Domain 编排和数据库设计文档通过 `system_id` 和 Wiki Link 归属一个系统；目录只帮助浏览，不替代文档关系。系统与模块设计的语言检查写入阶段级 `语言检查/`；单个系统文档的语言检查写入该系统的 `语言检查/`。

所有执行记录写入 `vcddd-obsidian/work/<work-id>/执行记录/`。正式设计不记录 `work_id`，也不反向链接执行记录。

## 用户确认

系统与模块设计 Agent 完成文档和自身清理后启动语言检查。API 与 Domain 编排 Agent 先用完整 API 目录与用户对齐范围；用户要求形成完整设计或目录已经足以继续时，直接形成全部 API 候选，不把目录确认当作继续工作的前置条件。完整候选完成自身清理后启动语言检查。语言检查 Agent 把问题与修改建议交给用户确认，由被检查文档的原主写 Agent 根据确认结果更新原文，再把完整设计交给用户确认。

数据库设计 Agent 先从当前业务结果和系统责任确定本地持久化边界，再用真实创建、修改、查询、失效、失败和并发操作走通数据，随后与用户讨论表边界，最后形成字段、约束、索引、事务、生命周期和物理规则。不能从数据库产品、模板栏目、Domain 名称或 API 数量直接开始设计表。讨论期间只更新执行记录；用户明确要求形成数据库文档后，才把经过最小性验证的一套当前结构写入正式文档。正式文档不包含分析过程、业务说明、被否决方案和没有依据的保留期或未来扩展。文档完成自身清理后启动语言检查，再由原数据库设计 Agent 根据用户选择修改。

用户确认定位到当前文档版本和具体内容。草稿仍可供 Coding 使用；使用者记录采用的版本、假设和可能返工范围。

## 继续设计的内容

- 三份设计文档之间的精确链接和变化通知方式。
- 最后处理：根据 TokenHub 真实交互演练，提升系统与模块设计 Agent 的独立设计能力。重点复核层级判断、Domain 与模块的区分、Agent 先提出完整候选以及取得完整确认后再写设计文档。
