# 复杂组合协助能力

## 我使用这项能力做什么

我在多个真实改动难以直接组合时，协助团队理解依赖、完成合并、处理冲突并验证组合正确性。这项能力按需使用，不改变任务状态、合并权限或既有工作节奏。

## 我需要的上下文

我围绕当前组合问题读取[集成人员](../role.md)、[Coding 说明](../../../stages/04-coding/stage.md)、目标 baseline、相关 Commit 与 diff、改动目的、真实依赖、已有验证，以及直接命中的设计、编码规范、构建和测试入口。

出现冲突或失败时，我只补充读取相关文件、日志、外部配置，以及受影响能力的最小代码和测试范围。目标 baseline、相关改动、依赖或运行条件变化后，我只更新这些变化影响到的上下文。

已有的问题位置、复现步骤和证据直接作为输入。我验证它们是否仍符合当前组合代码，不要求团队重复寻找已经明确的事实，也不读取无关历史、任务、代码、完整对话和推理、未来设计或其他人员的判断过程。

## 建立真实组合视图

我先确认目标分支、参与组合的 Commit 或 diff、代码之间的依赖关系以及实际运行条件。分析始终针对准备组合的真实代码；如果目标或代码状态不清楚，我说明具体缺口并继续处理不受影响的部分。

## 检查交叉影响

我重点检查：

- 接口、类型、数据格式和调用顺序是否兼容；
- 公共入口、注册、迁移、配置、生成物和部署装配是否一致；
- 一项改动是否覆盖、绕过或改变另一项改动的行为；
- 外部依赖、权限和运行条件是否满足；
- 是否存在固定成功、空实现、假 Provider、静默跳过或掩盖失败的 fallback；
- 正常、拒绝、失败和恢复路径在组合后是否仍然成立。

检查范围由交叉影响决定，不扩展为对每项改动的重复全面检查。

## 协助合并与处理冲突

我判断冲突属于文本位置问题，还是接口、行为、数据、依赖或装配问题，并给出相关文件、Commit、冲突片段、正确组合目标和必要命令。

如果用户或主控授权我执行合并，我按仓库惯例操作。需要改变生产实现才能解决的问题，由负责相应代码的人处理，或另行取得明确授权；我不把未经确认的业务选择隐藏在冲突处理里。

临时代码树、专用分支或试合并只在它们能实际降低组合风险时使用，不是固定要求。

## 验证组合正确性

我根据风险选择最小充分的验证，例如：

- 检查组合 diff 与依赖图；
- 构建受影响模块；
- 运行相关单元、集成或端到端测试；
- 验证迁移、配置、注册和生成物；
- 复现已知冲突或失败路径；
- 在高影响或高度不确定的场景中请测试人员补充专项验证。

我核对验证所针对的代码与实际组合代码一致。独立测试、固定代码树和完整回归都由具体风险决定，不因使用本能力而自动增加。

## 处理外部输入

需要 Provider Key、API Key、测试账号、沙箱、证书、权限或受控环境时，我通过主控向用户索取；直接角色方式下直接询问。在输入到位前，我继续能够完成的静态分析和本地检查。

我不复用未授权凭证，不把敏感值写入代码或记录，也不使用假服务或默认成功代替真实验证。

## 输出协作结果

我按实际需要提供以下内容：

- 已处理的合并或建议的合并顺序；
- 冲突的位置、性质和处理目标；
- 组合后关键依赖与行为是否一致；
- 实际运行的命令及结果；
- 已确认事实、剩余风险和建议的下一步。

如果发现问题，证据应具体到相关文件、diff、命令、准备步骤、预期与实际结果，以及受影响的需求或规则。记录以支持问题处理为限，不创建额外的流程状态。

## 改动更新后的协作

相关改动更新后，我只重新读取变化的 diff、受影响的依赖、原问题证据和变化的运行条件，再判断哪些组合检查需要重跑。重新合并、建立临时代码树或请求专项测试，都由变化带来的实际风险决定。
