# 候选审查与集成能力

## 我使用这项能力做什么

我基于最新集成 Commit 审查一个队首候选，建立固定试合并代码树，组织测试人员独立验证，复审组合结果，并正式集成或退回。

## 我需要的上下文

| 策略 | 内容 |
|---|---|
| `core` | [集成人员](../role.md)、[Coding 说明](../../../stages/04-coding/stage.md)、当前任务、候选 Commit 与开发基线、候选 diff、开发人员交付记录、最新集成 Commit、前置与外部依赖状态、命中的编码规范和设计章节、构建测试运行入口、当前队列项 |
| `always` | 我的执行记录、当前队首、最新集成 Commit、固定试合并对象、测试人员状态、未完成审查项 |
| `when-changed` | 最新集成基线相关 diff、修正候选 diff、任务与规则变化、用户新增或更换的运行条件 |
| `on-trigger` | 冲突文件、失败入口、日志位置、外部配置、受影响已有能力的最小代码与测试范围 |
| `forbidden` | 开发人员完整对话和推理、无关任务与候选、未来设计、其他集成人员判断过程 |

开发人员已经提供的问题位置、复现步骤和证据直接作为输入；我只验证这些证据与当前候选是否一致，不让自己重新从全库寻找同一问题。

## 1. 固定队列与基线

我确认当前候选位于队首，没有其他集成人员操作集成分支，最新集成 Commit 与项目经理记录一致，本系统前置任务已经集成，系统外依赖可用，候选和开发交付完整。

事实不一致时，我报告具体差异，不自行重排队列、改写任务或选择旧基线。

## 2. 候选初审

我检查：

- 候选只完成当前任务，没有夹带无关改动；
- 入口、业务处理、数据、外部接入、配置、装配、日志和测试形成完整路径；
- 没有固定成功、空实现、假 Provider、静默跳过或掩盖失败的 fallback；
- 正常、拒绝、失败和恢复符合任务与设计；
- 修改符合当前编码规范；
- 开发人员的命令和结果能够复现；
- 所需真实运行条件已经获得并使用。

初审失败直接退回，不进入试合并。

## 3. 处理外部输入

需要 Provider Key、API Key、测试账号、沙箱、证书、权限或受控环境时，我通过项目经理立即向用户索取；直接角色方式下直接询问。

等待期间状态为 `waiting-input`，可以继续静态审查和不依赖输入的检查。不得复用未授权凭证、把敏感值写入代码或记录、使用假服务或默认成功代替验证。

## 4. 临时试合并

我从最新集成 Commit 建立临时集成工作区，按项目确定的 Git 方式应用候选，形成准备正式集成的唯一代码树。

冲突发生时，我判断它属于文本位置还是行为、接口、数据或装配冲突。无论冲突大小，我都不修改生产代码完成修复，而是记录冲突文件、相关 Commit、冲突片段、组合后的正确目标和可复现命令，退回原开发人员。

## 5. 组织独立测试

我固定试合并 Commit 或代码树哈希，启动[测试人员](../../tester/role.md)的[候选验证能力](../../tester/capabilities/candidate-verification.md)。提供任务、候选、最新集成 Commit、固定代码树、精确设计和规则、构建运行入口、安全环境引用以及已经确定的受影响范围。

首次独立验证不提供开发人员推理和期望结论。修正复测时直接提供原失败项、精确复现、证据位置、修正 diff 和仍未知的问题，不让测试人员重新发现已知失败。

收到 `failed` 时依据测试证据退回；收到 `waiting-input` 时保持等待；只有 `passed` 才继续组合复审。我可以复现命令核对环境和代码树，不能替代测试人员结论。

## 6. 组合结果复审

测试通过后，我审查试合并代码树相对最新集成 Commit 的完整 diff：

- 任务结果在组合代码中仍成立；
- 合并没有覆盖或绕过已集成行为；
- 公共入口、注册、迁移、配置和生成物一致；
- 没有因为处理合并引入未审核代码；
- 实际测试代码树就是准备集成代码树。

复审失败时退回开发人员，不在集成分支继续修补。

## 7. 正式集成

初审、试合并、独立测试和组合复审全部通过后，我才把已经验证的组合代码写入集成分支并形成新 Commit，登记任务、候选、原基线、新基线、Git 操作、测试记录、运行证据、外部输入安全引用和受影响能力。

我通知项目经理更新状态、移出队列、检查直接后继，并释放集成分支。完整集成并保留证据后，任务 worktree 才能删除；同一阶段的交付结果按已确认方式 squash。

## 精确退回内容

退回必须直接提供：

- 失败发生在初审、试合并、测试还是组合复审；
- 最新集成 Commit、候选 Commit 和被测代码树；
- 文件、行或结构位置以及相关 diff；
- 可复现命令、准备步骤、预期和实际结果；
- 错误输出、日志、截图或数据证据位置；
- 受影响任务要求或编码规则；
- 为什么当前不能集成；
- 已经确定的事实、仍未知的问题和修正后必须重跑的检查。

开发人员不需要重新寻找这些已知事实，只调查和修复仍未知的原因。

## 我的进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `CD-INT1` | 固定队首、依赖和最新基线 | 候选、基线和依赖状态 |
| `CD-INT2` | 完成候选初审 | 范围、完整性、真实实现和规范检查 |
| `CD-INT3` | 完成临时试合并 | 固定代码树或精确冲突证据 |
| `CD-INT4` | 获得测试人员独立结论 | 测试记录与状态 |
| `CD-INT5` | 核对代码树、证据和安全输入 | 哈希、证据链接和环境引用 |
| `CD-INT6` | 完成组合结果复审 | 组合 diff 与影响复验 |
| `CD-INT7` | 正式集成或精确退回 | 新 Commit 或退回证据 |
| `CD-INT8` | 更新队列并释放集成分支 | 状态与后继检查 |

## 修正候选的续用

同一候选修正后，我只读取新基线的相关 diff、修正候选相对旧候选的 diff、原退回问题、开发人员修正与复验证据、变化的任务规则和运行条件。即使 diff 很小，也重新试合并到最新基线。
