# 事实与 POC 验证能力

## 我使用这项能力做什么

我回答一个会影响当前产品或业务判断的明确问题。根据问题选择权威资料核验、代码或原型观察、真实运行，或者一个最小且可丢弃的 POC。小型查询由当前 Agent 直接完成；本能力仅在需要独立性或隔离大量材料、复杂环境时单独使用。

## 使用条件

围绕一个可命名问题直接选择足够的验证方式。缺少受影响判断、来源或运行条件时，先完成可由现有材料回答的部分，并明确缺口和不确定性。

单一来源核验、少量材料查询或简单运行验证不默认创建独立任务。只有独立结论本身有价值，或材料量、交叉引用、运行复杂度会明显挤占主上下文时，才委派本能力。

## 我需要的上下文

围绕当前问题读取必要的来源、代码或页面、运行入口和 POC 环境，记录仍未回答的证据缺口。已知文档、API、错误或入口应优先使用；缺少输入时，从现有材料或可运行入口完成可验证部分，并说明限制。只有越界引用确实是回答当前问题所需时才继续调查，避免无关完整项目、他人结论和期待答案污染验证，也不把 POC 当生产实现。

## 选择验证方法

我优先选择成本最低且证据足够的方法：

1. 第一方文档和直接声明；
2. 现有系统、原型或代码的直接观察；
3. 在批准环境中的真实调用；
4. 只覆盖存疑点的最小 POC。

一个来源已经足以回答时不制作 POC。资料声明与真实行为可能不同，且差异会影响判断时，补充运行验证。

## 最小 POC 边界

POC 必须写明：只证明的问题、输入、环境、步骤、成功与失败判定、证据、没有证明的内容和清理方式。

POC 不进入正式产品路径，不承担完整错误处理、可维护性和生产质量，也不能被后续人员当成可直接上线的实现。需要真实 Key 或账号时向用户索取，不能用假成功代替。

## 形成证据

我区分：

- 来源直接声明；
- 实际观察或运行事实；
- 基于证据的推断；
- 尚无法确认；
- 给事实拥有者的建议。

使用代码时记录精确范围；使用原型或网页时记录入口、步骤和截图；使用外部资料时记录直接来源、访问日期和适用条件；使用 POC 时记录可复现命令和结果。

## 输出

默认形成 `FACT-*` 证据；使用 POC 时在同一证据中增加 `POC-*` 运行记录。输出包含问题、直接回答、证据、实际范围、冲突、置信度、未知和可能影响。

当验证包含需要保留和复现的原型源码、POC、运行脚本或运行产物，并且已经能够归属明确系统时，使用系统验证模板，写入 `vcddd-obsidian/03-pre-coding/systems/<system-id>-<system-name>/validation/<validation-id>-<validation-name>/`。计划、源码、运行记录、产物和结论保存在同一验证项中；小型来源核验或无需长期保存实现的事实查询仍可只形成 `FACT-*` 证据。

证据不自动成为产品范围、业务或 Domain 事实。事实拥有者可在自己的权威文档中采纳并链接证据。
