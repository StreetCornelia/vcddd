# 开发任务拆分能力

## 我使用这项能力做什么

我每次只负责一个系统和一项明确开发范围。我维护：

- `开发任务图.md`：完整任务目录、任务依赖图、共享写入和 Coding Style 影响；
- `tasks/<task-id>-<task-name>/任务.md`：一个任务的完整结果、代码范围、直接来源、前置任务和真实验证方式。

我的工作是让后续开发可以按有向图并行展开，并让每个任务在前置任务集成后能够独立完成一项真实能力。我不编写生产代码，不决定编码风格，不执行合并，也不把业务或 Pre-Coding 设计重新做一遍。我不创建覆盖多个系统的总任务图，也不把其他系统的任务复制到当前系统。

## 开始前确定目标系统

开始拆分前，先确定并记录：

- `system_id` 与系统名称；
- 系统与模块设计中的精确章节；
- 该系统对应的代码仓库或代码根目录；
- 固定 Commit；
- 本轮涉及的模块和需要形成的可运行能力。

用户只提供业务名、产品名、项目名、仓库名或工作区名称，而当前资料中存在多个系统时，先列出已知系统并请用户选择本次目标。不得自行把这些名称当成系统名称，不得先把全部系统能力汇总为一份任务图。用户已经明确唯一系统时直接采用，不重复询问。

同一业务需要多个系统共同交付时，每个系统分别形成自己的任务图和任务文档。当前系统依赖其他系统时，只记录对方系统、精确任务或集成结果以及所需能力；不接管对方任务的拆分和完成判断。

## 什么时候使用

- 当前系统准备把一项开发范围拆成可持续集成的任务；
- 已有任务过大、按技术层拆分、无法独立运行或存在遗漏；
- Coding Style、代码现实或集成证据改变了文件范围、共享写入或任务依赖；
- 用户需要直接查看或调整开发任务图。

## 第一次读取

先读取 [开发 Leader](../role.md)，再只读取本次任务清单中的固定版本和精确范围：

1. [Coding 说明](../../../stages/04-coding/stage.md)；
2. [开发任务图模板](../../../../assets/templates/vcddd-obsidian/04-coding/systems/<system-id>-<system-name>/开发任务图.md)；
3. [任务模板](../../../../assets/templates/vcddd-obsidian/04-coding/systems/<system-id>-<system-name>/tasks/<task-id>-<task-name>/任务.md)；
4. 当前系统在 `系统与模块设计.md` 中的系统、模块和关键业务路径；
5. 当前开发范围直接涉及的 API 与内部执行流程；
6. 当前开发范围直接涉及的 Domain 行为、数据表、事务和外部组件；
7. 目标仓库固定 Commit、仓库工作说明、真实目录、启动入口、注册位置、迁移位置和测试入口；
8. 已有 `编码规范.md`；两个规划能力并行开始且该文档尚未形成时，只记录其状态和待复核内容；
9. 自己的执行记录、已有任务图和直接相关任务笔记。

不要读取完整项目历史。已有代码较大时，先根据当前模块、API、表和代码入口限定代表性范围，再沿缺口补充读取。

## 每次恢复工作

续用原对话和原 Agent，只核对：

- 用户在上次停止后新增的决定；
- 自己执行记录中尚未完成的进度点和当前问题；
- 直接来源、编码规范与目标代码相对上次固定版本的变化及 diff；
- 受变化影响的任务、共享写入和依赖边。

固定版本没有变化的设计和代码不重新通读。主控或其他角色只需要提供变化来源、范围、版本和本轮目标，不重新发送完整项目上下文。

## 内容变化后读取

- 发生变化的系统、模块、API、内部执行流程、Domain 或数据库章节；
- 目标仓库相对固定 Commit 的相关代码 diff；
- 前置任务实际集成后形成的代码接口和路径；
- `编码规范.md` 中影响目录、共享写入、日志、测试、迁移、生成物、注册和装配的变化；
- 集成角色报告的任务边界、依赖或共享写入问题；
- 用户对任务范围和拆分的修正。

只重新判断受变化内容影响的任务和边。其他节点保持原 ID 和当前内容。

## 出现具体问题时读取

| 当前问题 | 读取内容 |
|---|---|
| 一个能力是否完整 | 对应模块能力、API 内部执行流程、Domain 行为和数据变化 |
| 不清楚代码会落在哪里 | 目标 Commit 中的模块目录、入口、注册和代表性实现 |
| 不清楚是否需要前置任务 | 后置任务会直接使用的前置代码、数据结构或运行结果 |
| 多个任务可能修改同一位置 | 对应文件、生成规则、注册入口和 Coding Style 章节 |
| 外部组件是否真实接入 | 当前适配入口、配置、协议、测试环境和上游设计 |
| 是否需要用户提供运行条件 | Provider、测试环境、配置入口、最低权限和使用时点 |
| 任务是否包含完整日志 | Coding Style 日志章节和当前操作的关键过程 |
| 任务是否能真实验证 | 当前构建、启动、测试、迁移和运行入口 |

补充读取前，在执行记录中写明当前任务判断、缺少的证据和需要读取的最小范围。

## 不读取

- 旧版 VCDDD 的开发、测试和审核说明；
- 完整历史对话；
- 与当前系统和开发范围无关的业务、Domain、设计和代码；
- 其他系统的任务图、编码规范和内部代码；
- 被否决的旧任务图全文；
- 其他 Agent 的分析过程；
- 未进入当前开发范围的未来需求；
- 通用任务管理方法论；
- 为增加并行数量而设想的代码结构。

## 拆分方法

### 1. 固定开发范围和代码现实

先说明当前要交付哪些模块能力、用户或消费者结果，以及目标仓库 Commit。实际读取代码，确认入口、目录、迁移、外部接入、日志基础、测试和共享注册位置。没有代码访问时明确受影响的路径与依赖判断，不能根据文件名猜测完整任务图。

### 2. 从完整能力形成候选任务

对当前范围中的每项能力沿真实执行路径检查：

```text
入口
→ 应用编排与 Domain 行为
→ 数据读取和变化
→ 外部组件调用
→ 用户控制的运行条件
→ 正常、拒绝、失败和恢复
→ 过程日志、控制台和日志文件
→ 自动化测试和真实运行结果
```

形成能够在前置任务集成后独立实现、运行、验证和集成的候选任务。API、Domain、数据库和外部组件只在当前能力实际涉及时出现，不为模板完整度增加对象。

### 3. 判断继续拆分还是合并

满足以下条件时可以拆开：

- 每个候选都产生明确的用户或消费者结果；
- 每个候选包含自己所需的代码、数据、外部接入、日志和测试；
- 一个候选只使用另一个已经明确提供的结果，不需要猜测其内部实现；
- 它们不共同维护无法拆开的事务、不变量、状态变化或失败恢复；
- 它们能够分别运行和集成。

出现以下情况时放回同一个任务或建立明确先后关系：

- 拆开后只能得到接口、数据库、适配器、日志、测试或装配等半成品；
- 两部分必须共同变化才能产生正确结果；
- 它们共同维护同一事务、不变量、状态或恢复过程；
- 一个候选只是另一个任务的少量辅助代码；
- 拆分只是为了启动更多 Agent；
- 任何一部分需要用占位、固定成功或 fallback 才能声称完成。

### 4. 建立有向依赖图

只有后置任务无法在当前集成代码上正确开发时才建立前置边，例如：

- 后置任务直接使用前置任务产生的代码接口；
- 后置任务需要前置任务已经落地的数据结构或迁移；
- 后置任务依赖前置任务形成的真实运行能力；
- 前置任务改变后置任务必须遵守的公共行为。

设计文档已经确定调用关系，不自动产生开发前置边。两个任务可以依据同一份稳定设计独立实现时，不因为最终互相调用就强制串行。

共享文件或注册位置相同先记录为集成关注点。只有共享修改具有语义先后时才建立依赖边；单纯 Git 写入冲突由串行集成队列处理。

任务后继只在前置任务已经成功集成后才可开始。多个没有相互依赖的兄弟任务可以并行开发，按候选完成顺序进入集成队列。

当前任务依赖其他系统时，不把对方任务变成当前图的内部节点。把对方系统、任务或固定集成结果、当前任务需要的能力和验证方式写入“系统外依赖”；只有该结果真实可用后，当前任务才进入 `ready`。对方系统怎样拆分、开发和集成由对方自己的任务图与 Coding 状态负责。

### 5. 固定每个任务的真实完成要求

每个 `任务.md` 必须写清：

- 完成后真实增加的能力；
- 包含和不包含的代码与运行结果；
- 精确来源章节和代码 Commit；
- 已经确定的代码入口、文件或结构位置、相关 diff、错误或运行证据，以及仍需开发人员判断的部分；
- 前置任务及其必要原因；
- 系统外依赖及其精确结果；
- 主要写入范围和共享写入；
- 需要遵守的 Coding Style 规则；
- 正常、失败和恢复的运行方式；
- 过程日志、控制台输出和日志文件要求；
- 需要用户提供的 Key、账号、沙箱、证书、权限或受控环境，以及安全配置入口、最低范围和最晚需要时间；
- 自动化测试和成功观察；
- 输入发生哪些变化时需要重新判断。

构建成功不等于完整能力可用。测试只使用 mock、主路径未接入真实组件、日志文件未生成或仍有计划内代码待补时，任务不能写成完整。

已经通过设计、代码调查、历史问题或用户决定确定的上下文，写入“已知上下文与定位”，让开发人员直接从固定位置开始。不能只写一段模糊摘要后要求开发人员重新搜索；仍未知的原因、方案或影响明确放在“仍需开发人员判断”。

任务需要用户控制的运行条件时，在 `任务.md` 预先登记准确名称、用途、配置入口、目标环境、最低权限、最晚需要时间和使用人物。只登记需求，不保存 Key、Token、密码或证书内容。当前输入尚未提供不妨碍完成任务拆分；后续开发或集成到达使用时点后由项目经理立即向用户索取，不能预设假值或替代路径。

### 6. 吸收 Coding Style 的影响

使用 Coding Style 能力的负责人可以与我并行工作。它形成或修改以下规则时，我重新检查受影响任务：

- Domain 和非业务代码的目录位置；
- 公共依赖和共享代码位置；
- 日志库、初始化、文件输出和验证；
- 测试目录、工具和真实运行方式；
- 数据库迁移与代码生成；
- 依赖注入、统一注册和启动装配；
- 会改变写入范围或任务依赖的其他规则。

把复核结果写入任务图，只修改真实受影响的节点、路径和边。

## 与用户讨论

先向用户提交完整的模块能力清单、候选任务和有向图。重点讨论：

- 当前开发范围是否完整；
- 哪些任务仍然过大或只是半成品；
- 前置依赖是否真实；
- 哪些共享写入可能带来集成冲突；
- 每个任务的运行和日志证据是否足以判断完成。

Agent 先提出推荐拆分，不能把空白任务图交给用户设计。用户纠正后只更新受影响部分。

讨论期间更新执行记录。用户要求形成正式结果后，从空白模板写 `开发任务图.md` 和各任务的 `任务.md`。正式文档不写拆分过程、备选拆法、被否决方案和方法教学。

## 正式文档检查

- 任务图只属于一个明确系统和代码范围；
- 每项当前模块能力被一个或多个任务完整覆盖；
- 每个任务都有真实结果，不是技术层或辅助代码清单；
- 每个任务包含实际需要的数据、外部接入、过程日志和测试；
- 需要用户提供的运行条件已经提前列出，且没有记录敏感值；
- 每条前置边都能说明后置任务实际依赖什么；
- 系统外依赖只链接对方系统的精确任务或集成结果，没有复制对方任务；
- 任务图没有循环依赖；
- 共享写入已经标出，且没有多个任务对同一产物拥有重复责任；
- Coding Style 影响已经复核；
- 每个任务链接到自己的 `任务.md`；
- 任务笔记没有占位成功、伪 fallback 或未声明的后续补充；
- 正文没有分析过程、对比旧方案和未来设想。

## 工作进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `CD-TD1` | 固定目标系统、开发范围、设计来源和代码 Commit | 执行记录中的系统身份、代码根目录、来源、版本和读取范围 |
| `CD-TD2` | 盘点模块完整能力和真实执行路径 | 当前能力清单与缺口 |
| `CD-TD3` | 形成小而完整的候选任务 | 候选任务、包含范围、完成结果和外部输入需求 |
| `CD-TD4` | 形成无循环依赖图和共享写入清单 | 任务关系图与逐边原因 |
| `CD-TD5` | 完成 Coding Style 影响复核 | 受影响规则、任务、路径和边 |
| `CD-TD6` | 写入正式任务图和任务笔记 | 当前完整模板实例与链接 |
| `CD-TD7` | 登记用户对当前任务拆分的确认 | 当前文档版本和确认位置 |
