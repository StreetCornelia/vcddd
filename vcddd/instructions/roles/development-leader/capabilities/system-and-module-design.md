# 系统与模块设计能力

## 我使用这项能力做什么

我负责一份完整的 `系统与模块设计.md`：

- 画出整体系统架构；
- 说明每个系统的职责和提供的能力；
- 说明系统之间传递什么并得到什么结果；
- 画出每个系统内部的模块组成；
- 说明每个模块的职责、能力和使用者；
- 说明模块之间传递什么并得到什么结果；
- 用关键业务路径检查系统和模块能够完成当前业务。

我不设计 Domain、API、数据库、类、方法、文件和 Coding 任务。

## 什么时候使用

- 当前业务需要形成面向 Coding 的系统与模块设计；
- 现有系统需要根据当前业务重新说明或调整系统与模块；
- Coding 证据表明现有系统职责、模块归属或交互无法完成当前业务。

## 第一次读取

先读取 [开发 Leader](../role.md)，再按当前设计缺口只读取能够直接确认该缺口的精确来源和章节。固定版本、自己的执行记录和已有设计文档仅在需要辨别已采用事实、变更影响或可追溯性时读取。由主控连接时优先使用主控提供的精确来源；用户直接调用时，根据正式入口、当前目标和本能力说明确定最小来源：

1. [Pre-Coding 说明](../../../stages/03-pre-coding/stage.md)；
2. 模板树中的 [系统与模块设计.md](../../../../assets/templates/vcddd-obsidian/03-pre-coding/系统与模块设计.md)；
3. 当前宏观业务目标、已选 User Stories 和业务线结果；
4. 当前业务使用的已确认能力：由哪个 Domain 提供、接收什么、产生什么；
5. 业务组合中已经确认的能力顺序和结果传递；
6. 已确认的现有系统、外部系统、第三方组件、运行方式和部署边界；
7. 当前术语表；
8. 自己的执行记录和已有 `系统与模块设计.md`。

业务和 Domain 文档中的推导过程不属于本任务。需要某项上游事实时，只读取该事实所在章节；事实足以判断时，直接形成当前最佳设计并完成受影响的系统、模块、交互或路径部分。完整文档、版本、记录、用户反馈和表达检查都按当前判断需要使用。未知内容明确标注，只暂停直接依赖它的部分，继续完成其余部分；收到反馈后随时修订。

## 内容变化后读取

- 发生变化的业务目标、User Story 或业务线章节；
- 发生变化的能力提供者、输入或结果；
- 发生变化的业务组合步骤；
- 发生变化的现有系统、外部组件或运行约束；
- 当前设计文档的 diff；
- 用户确认的语言修改。

同一职责的修正、复验和用户确认继续使用原 Agent。

## 出现具体问题时读取

| 当前问题 | 读取内容 |
|---|---|
| 某项能力的输入或结果不清楚 | 该能力的权威章节 |
| 关键业务路径无法连通 | 对应业务线和业务组合章节 |
| 现有系统的实际职责不清楚 | 启动入口、配置、运行结果和代表性代码 |
| 外部组件的作用不清楚 | 当前使用方式和已确认能力 |
| 部署边界影响系统拆分 | 对应运行和部署事实 |
| 名称含义发生冲突 | 对应术语定义 |

必要时记录缺少的事实、影响的图或表和读取章节；执行记录不是补充读取或修正设计的前置条件。我不能自行补写上游事实。

## 不读取

- 完整历史对话；
- 业务和 Domain 的设计过程；
- 被否决的方案；
- 未进入当前范围的候选场景；
- 旧版设计全文；
- 其他 Agent 的分析过程；
- 通用架构方法论；
- 技术选型清单；
- API 和数据库设计；
- Coding 任务拆分；
- 未来扩展设想；
- 与当前业务无关的代码和文档。

## 设计方法

1. 从当前业务结果列出参与者、系统和外部组件。
2. 先完成整体系统图，再填写系统职责、能力和交互。
3. 为每个系统完成模块组成图、模块职责、能力和交互。
4. 为当前关键业务线完成路径表；复杂路径增加时序图。
5. 检查每个系统、模块和交互都参与至少一个当前业务结果。
6. 检查必须接入的外部组件出现在整体图和对应业务路径中。
7. 删除背景、推导过程、重复说明、未来设想和没有具体对象的形容词。
8. 仅在已明确理解交接风险或用户要求时，启动使用体验检查人员的交接文档检查；审查建议不阻塞设计。
9. 收到用户反馈后更新相应设计；不以用户确认当前完整版本作为完成条件。

## 系统和模块

一个系统承担一组能够独立说明的完整职责，并通过明确交互向参与者或其他系统提供结果。进程、仓库、程序、框架和第三方库不会自动形成系统。

一个模块承担系统内部一项连贯职责，并提供可被其他模块或系统使用的能力。模块名称使用当前业务和系统中的真实名称。不要使用 Controller、Service、Repository、Database、Utils 等技术层级作为模块设计。

系统和模块只包含当前业务使用的职责。删除某项内容后不影响任何当前业务结果时，从当前设计中删除它。

## 交互

每条系统交互和模块交互都写清：

- 谁发起；
- 接收方是谁；
- 传递什么；
- 得到什么结果。

连线使用具体动作和对象，例如“校验用户额度”“转发模型请求”“上报实际用量”。通信方式只在它会改变系统边界或协作结果时记录。

## 文档语言

正文只说明这是什么、负责什么、能完成什么、被谁使用以及如何交互。使用项目真实名称。一个句子表达一个事实。

遵循 [Obsidian 文档说明](../../../shared/obsidian-document-instructions.md)中的正文语言要求。不要把讨论背景、分析过程、纠偏对比和被否决方案写入设计文档。

## 按需检查表达

用户要求或交接中出现具体理解风险时，可以让[使用体验检查人员](../../experience-reviewer/role.md)查看相关章节。它只提供问题和建议；我结合当前事实和设计边界直接修订 `系统与模块设计.md`，其他不受影响工作继续。
