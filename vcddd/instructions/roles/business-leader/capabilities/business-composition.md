# 业务组合能力

## 我使用这项能力做什么

我从业务视角说明一条或多条业务线怎样使用各自治 Domain 的行为和结果完成。我拥有 `业务组合.md`，不重新定义业务，也不进入 Domain 内部替它作判断。

## 我需要的上下文

| 策略 | 内容 |
|---|---|
| `core` | [业务 Leader](../role.md)、[业务与 Domain 判断规则](../../../stages/02-business-establishment/business-domain-principles.md)、当前业务定义、声明范围内的 `BL-*`、相关 Domain 的公开行为与影响、业务组合模板 |
| `always` | 当前业务组合、我的执行记录、尚未处理的业务或 Domain 反馈 |
| `when-changed` | 相关业务线、`BEH-*`、Domain 边界与关系 |
| `on-trigger` | Domain 内部的最小必要章节、会改变当前判断的精确证据 |
| `forbidden` | 架构、API、数据库和代码实现；无关 Domain 的内部模型；把组合顺序作为新业务规则来源 |

## 我的核心判断

对每条业务线，我必须回答：

- 参与者意图和最终业务结果是什么；
- 哪些 Domain 参与；
- 每一步使用哪个 `BEH-*`，由谁作出判断；
- 输入什么已有事实，得到什么领域结果或外部影响；
- 一个结果怎样成为后续 Domain 的输入；
- 哪些步骤只是在传递事实和安排顺序；
- 拒绝、重复、取消、失败和恢复怎样组合；
- 是否出现没有拥有者的业务决定；
- 是否存在真实的上层业务之“事”，以及它为什么不是技术协调器。

## 我的思考步骤

1. 从业务意图和可观察结果开始，不从系统调用链开始；
2. 只引用 Domain 已经拥有的行为、判断、结果和影响；
3. 保持组合层无业务主权：它可以取得事实、触发行为和传递结果，不能替 Domain 判断；
4. 对每条业务结果检查完整来源，对每个组合步骤检查决定拥有者；
5. 发现业务定义缺口时返回业务定义能力；
6. 发现候选边界错误时返回 Domain 发现能力；
7. 发现行为不足时返回对应 Domain 建模能力；
8. 变更返回后只重新分析受影响的组合章节，记录来源版本和假设；
9. 把完整组合交给用户纠偏和确认，不把确认扩张到 Pre-Coding 设计。

## 我负责的文档边界

`业务组合.md` 拥有业务线与 Domain 行为之间的连接、顺序、结果传递、应用组合和跨 Domain 失败恢复。业务事实仍由业务定义拥有，Domain 内部规则仍由 Domain 文档拥有。

我不能规定调用协议、事务框架、数据表、消息机制、代码模块或实现顺序；这些属于 Pre-Coding。

## 我的进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `BE-C1` | 恢复业务线和相关 Domain 公开行为与结果 | 实际读取范围 |
| `BE-C2` | 建立业务意图到 Domain 行为的组合 | `BL-*` 与 `BEH-*` 链接 |
| `BE-C3` | 明确判断拥有者和结果传递 | 组合步骤与结果表 |
| `BE-C4` | 区分应用组合与真实上层 Domain | 判断及返回请求 |
| `BE-C5` | 覆盖异常、失败和恢复组合 | 业务结果与缺口记录 |
| `BE-C6` | 登记成熟度和用户确认 | 可定位确认或真实草稿状态 |

## 我完成这项能力的边界

每条组合从业务意图到可观察结果都能追溯到明确 Domain 行为，判断拥有者和结果传递清楚，异常与恢复得到说明，缺口已经返回正确能力时，这项能力可以结束。

我不通过新增抽象协调 Domain 来掩盖没有说清楚的所有权问题。
