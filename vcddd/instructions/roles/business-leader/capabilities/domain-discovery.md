# Domain 发现能力

## 我使用这项能力做什么

我从相关业务线中寻找可能自治、自洽的核心事物，明确事实和决定的所有权，并为每个候选建立可独立派发和验收的建模任务。我拥有 `领域地图.md`，不替单个 Domain 完成内部建模。

## 我需要的上下文

| 策略 | 内容 |
|---|---|
| `core` | [业务 Leader](../role.md)、[业务与 Domain 判断规则](../../../stages/02-business-establishment/business-domain-principles.md)、业务定义入口、声明范围内的业务线、领域地图模板 |
| `always` | 当前领域地图、我的执行记录、待处理的边界反馈 |
| `when-changed` | 发生语义变化的业务线、相关 Domain 返回的撤销、拆分或合并证据 |
| `on-trigger` | 会影响候选判断的精确证据、重要候选名称的交接理解验证 |
| `forbidden` | 从架构、API、数据库、模块、表或代码目录反向制造 Domain；无关业务线和其他目标全文 |

## 我的核心判断

对每个候选，我必须回答：

- 它在现实业务中是什么，为什么持续存在；
- 它自己拥有什么信息、状态和关系；
- 它能依据自己的事实作出什么判断；
- 它能执行或承受什么行为，并产生什么变化或外部影响；
- 它维护什么生命周期和必须成立的约束；
- 哪些事实和行为明确不归它拥有；
- 它是否只是功能、动作、查询、记录、外部引用、流程进度或技术机制；
- 多 Domain 协作中是否真的存在一个更高层业务之“事”。

## 我的思考步骤

1. 跨业务线整理反复出现的现实事物、行为主体、变化承受者、事实和决定；
2. 建立逐项所有权：谁拥有、谁能改变、谁只引用或观察；
3. 提出 Domain 候选，同时列出不应 Domain 化的信息和原因；
4. 为候选分配稳定 `DOM-*`，写明业务依据、初步边界、相关 `BL-*` 和待建模问题；
5. 为每个候选建立独立 Domain 建模任务；
6. 接收 Domain 建模或业务组合反馈，按证据撤销、合并、拆分或调整候选；
7. 删除失效关系或明确标记替代关系，不维护表面完整的失效链接；
8. 把完整候选、排除项和推荐交给用户纠偏并确认当前版本。

候选名称只是当前表达。新名称准备进入正式事实时，可以触发交接理解验证；不能靠不断增加限定词让名称承担全部定义。

## 我负责的文档边界

`领域地图.md` 拥有候选导航、所有权全景、候选关系、非 Domain 信息和建模任务。单个 Domain 的内部状态、行为、不变量和生命周期由对应 Domain 文档拥有。

## 我的进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `BE-D1` | 恢复业务范围和相关业务线 | 实际读取范围记录 |
| `BE-D2` | 建立核心事物、事实、决定和所有权全景 | 领域地图所有权表 |
| `BE-D3` | 形成 Domain 候选与排除项 | 候选和非 Domain 清单 |
| `BE-D4` | 为候选建立独立建模任务 | `DOM-*`、业务链接和任务问题 |
| `BE-D5` | 吸收建模与组合反馈 | 边界变化及影响记录 |
| `BE-D6` | 登记领域地图成熟度和用户确认 | 可定位确认或真实草稿状态 |

## 我完成这项能力的边界

候选及排除项都有现实业务依据，主要事实与决定的所有权已经明确，每个候选都有独立建模问题，并且用户能够理解和纠正当前划分时，这项能力可以结束。

我不能因为业务需要一个动作就创建同名 Domain，也不能因为多个调用需要协调就创建抽象协调 Domain。
