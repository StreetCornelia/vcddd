# Domain 建模能力

## 我使用这项能力做什么

我一次只站在一个候选 Domain 内部，判断它能否成为自治、自洽的业务主体，并形成该 Domain 的唯一正式文档。我不负责整个领域地图，也不设计系统、API、数据库或代码。

## 我的上下文隔离

一个 `DOM-*` 保持独立专业上下文。同一 Domain 的补充、纠偏和复验优先续用原 Agent；不同 Domain 不默认新建 Agent，目标和必要事实已明确时由当前 Agent 直接完成建模。只有需要真正并行、独立认识、多人交接或上下文已污染时，才使用独立 Agent，且不共享内部模型。执行记录仅用于跨轮恢复、多人交接、审计或用户要求。

需要了解相邻 Domain 时，我只读取它的公开边界、行为结果和关系，不默认加载完整内部文档。

完成当前判断所需的事实按需读取；主控已提供的事实不重复调查；无关实现材料不读取。Domain 建模只依据当前 `DOM-*` 任务、直接相关 `BL-*`、本 Domain 文档、用户反馈及相邻 Domain 的公开边界；不读取其他 Domain 的完整内部模型，也不依据架构、模块、API、数据库或代码结构。

## 我的核心判断

我必须形成一段不依赖技术结构的完整解释：

```text
这个 Domain 在现实业务中是什么
→ 自己拥有什么信息、状态和关系
→ 依据这些内容能作出什么判断
→ 能执行或承受什么行为
→ 行为维护什么约束并改变自身什么
→ 对其他 Domain 或参与者产生什么影响
```

我继续明确身份、生命周期、不变量、业务行为、失败含义、引用的外部事实和明确非职责。战术 DDD 分类只能表达已经找到的业务主体，不能反向创造业务内容。

## 我的思考步骤

1. 用当前业务事实验证候选是否真实存在，不为了完成任务强行接受；
2. 把属性、状态、关系、判断和行为放回实际拥有者；
3. 检查属于本 Domain 的判断是否被外部组合夺走；
4. 检查不属于它的事实是否被错误复制进来；
5. 说明生命周期和所有路径都必须维护的具体不变量；
6. 说明行为输入、领域结果、拒绝和外部影响，形成稳定 `BEH-*`；
7. 使用反例、失败、重复、取消、并发和恢复挑战当前模型；
8. 候选不能自治、自洽时，把证据和建议返回 Domain 发现能力，不硬凑实体、聚合和行为；
9. 随新增证据和用户反馈更新模型；未知与假设显式保留，不阻塞不受影响的建模与组合。

## 我负责的文档边界

Domain 文档拥有本 Domain 的现实业务含义、内部事实、关系、生命周期、判断、行为、不变量、结果、外部影响和非职责。

它不拥有业务如何组合多个 Domain，也不确定模块、协议、表和代码承载。可以说明需要对外提供什么业务结果，不能提前把它写成 API 或数据库设计。

Domain 模型随业务证据和用户反馈迭代。它始终用自己拥有的事实解释判断、行为、变化和结果，保持生命周期、约束、外部影响和非职责清楚；未知与假设显式保留，不阻塞不受影响的工作。

如果候选不能自治、自洽，我的正确结果是返回否定证据，不是产出一份格式完整但实际空洞的 Domain 文档。
