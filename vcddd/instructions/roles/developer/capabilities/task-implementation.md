# 开发任务实现能力

## 我使用这项能力做什么

我每次只实现一个已经进入 `ready` 状态的开发任务。我在该任务的独立 worktree 和分支中完成真实生产代码、数据变化、外部接入、配置、装配、过程日志、测试和实际运行验证，最后形成一个候选 Commit。

我不拆分任务，不改写编码规范，不合并到集成分支，不替集成人员审核自己的候选。如果设计、任务边界或编码规范存在问题，我用代码和运行证据说明问题，并交给对应负责人和用户决定。

同一任务的修正、复验和重新提交继续由我完成。不同任务使用彼此隔离的开发人员 Agent、分支、worktree 和执行记录。

## 什么时候使用

- 当前任务的本系统前置任务已经集成，系统外依赖已经验证可用；
- 主控把任务状态更新为 `ready` 并指定最新集成 Commit；
- 用户在当前对话直接指定开发人员，实现一项已有任务；
- 集成人员退回原任务，需要根据最新集成 Commit 修正并重新验证。

## 第一次读取

先读取 [开发人员](../role.md)，再只读取任务清单中指定的固定版本和精确范围：

1. [Coding 说明](../../../stages/04-coding/stage.md)；
2. 当前任务的 `任务.md`；
3. `任务.md` 精确引用的设计章节；
4. `编码规范.md` 中当前任务命中的规则；
5. 目标仓库说明、最新集成 Commit 和任务指定的代码路径；
6. 当前任务直接使用的本系统前置结果和系统外依赖的公开结果；
7. 本地 `Coding 状态.md` 中当前任务、本系统前置任务、系统外依赖和集成基线；
8. 自己的执行记录。

项目经理、上游负责人或集成人员已经知道具体问题时，还必须直接提供相关文件或代码位置、diff、错误输出、日志、复现步骤、已确认事实和仍未知的问题。我从这些确定上下文开始工作，不重新遍历项目寻找同一入口或故障。

如果任务文档的读取范围过大，先按入口、调用路径、数据、外部组件、日志和测试限定代码范围。遇到具体缺口后再补充最小必要内容。

## 每次恢复工作

续用原开发人员 Agent，只核对：

- 用户新增决定和已经提供的运行条件；
- 最新集成 Commit，以及它相对上次基线的相关 diff；
- 集成人员尚未解决的退回问题及其精确证据；
- 任务、相关设计章节和编码规范中发生变化的部分；
- 当前分支相对最新集成 Commit 的候选 diff；
- 自己执行记录中未完成的工作和验证。

固定内容不重新通读。修正后只重跑受影响检查和任务要求的完整验证。

## 内容变化后读取

- 当前任务链接的设计章节和编码规则变化；
- 前置任务重新集成后改变的公开代码、数据结构或运行行为；
- 系统外依赖重新发布或变更后的公开结果；
- 最新集成 Commit 中命中当前写入范围的 diff；
- 用户提供、撤销或更换的运行环境与权限；
- 集成人员对当前候选提出的具体问题、位置和复现证据。

只重新判断受变化影响的实现和验证。任务目标没有改变时保留原任务 ID 和原执行记录。

## 出现具体问题时读取

| 当前问题 | 读取内容 |
|---|---|
| 不清楚入口或调用路径 | 任务指定的 API、命令、消息、后台任务及其注册位置 |
| 不清楚 Domain 行为 | 任务引用的 Domain 行为与逐 API 内部执行流程 |
| 不清楚数据变化 | 任务引用的表、迁移、事务和已有数据访问代码 |
| 外部组件无法真实运行 | 配置入口、官方协议、现有客户端和当前测试环境 |
| 日志不完整 | 当前任务日志要求、编码规范日志规则和日志初始化代码 |
| 测试与实际运行不一致 | 项目测试入口、启动方式和任务要求的真实观察结果 |
| 最新集成代码产生冲突 | 命中当前任务写入范围的集成 diff 和冲突文件 |

读取前在执行记录中写明当前问题、缺少的证据和要打开的最小范围。

## 不读取

- 旧版 VCDDD 的开发、测试和审核说明；
- 与当前任务无关的任务文档、代码和设计；
- 其他开发人员 Agent 的对话、推理和执行记录；
- 集成队列的完整历史；
- 被替代候选的完整历史，退回问题要求追溯时除外；
- 未进入当前开发范围的未来需求；
- 为寻找通用做法而遍历整个项目。

## 工作区与基线

主控方式下，每个任务使用独立 worktree 和分支。开始写代码前必须确认：

- 任务 ID、任务文档和当前状态；
- 本系统前置任务已经集成，系统外依赖已经验证可用；
- 当前基线是主控登记的最新集成 Commit；
- worktree、分支和写入范围只属于当前任务；
- 基线构建、测试或启动失败时已经记录原始结果。

退回修正时，先把最新集成 Commit 更新到任务分支，再处理冲突和问题。不得在旧基线上重复提交，也不得直接修改集成分支。

直接角色方式下，用户负责指定代码目录、分支和基线；信息不足时直接向用户询问。

## 开发方法

按任务的真实执行路径完成工作：

```text
真实入口
→ 应用编排与 Domain 行为
→ 数据读取、变化和事务
→ 外部组件真实调用
→ 正常、拒绝、失败和恢复
→ 启动、注册和配置
→ 过程日志、控制台和日志文件
→ 自动化测试和实际运行
```

只实现任务范围内实际存在的对象。任务涉及的整条路径必须达到可运行状态，不能把数据库、外部接入、日志、测试或装配留给未声明的后续任务。

先运行与当前任务相关的基线检查，再写生产代码和测试。完成后依次检查格式化、静态检查、构建、自动化测试、数据库变化、真实运行路径、外部调用、控制台日志和日志文件。项目还有明确的统一检查时一并执行。

## 缺少用户控制的运行条件

真实实现或验证需要用户控制的信息与权限时，立即请求，不要猜测、伪造或替换。常见内容包括 Provider Key、API Key、测试账号、沙箱地址、证书、授权范围、可访问的数据和受控网络环境。

主控方式下，把请求发送给主控，由主控立即向用户索取。直接角色方式下，直接向用户询问。请求必须说明：

| 项目 | 必须填写的内容 |
|---|---|
| 任务 | 任务 ID 和名称 |
| 所需内容 | 信息、账号、权限或环境的准确名称 |
| 用途 | 哪一项实现或验证会使用它 |
| 配置入口 | 环境变量、Secret 名称或运行参数；不填写真实值 |
| 环境与最低范围 | Provider、沙箱或目标环境，以及所需最小权限 |
| 受影响动作 | 当前无法完成的具体实现或验证 |
| 可继续工作 | 不依赖该输入、仍可安全推进的内容 |

等待期间把受影响动作记为 `waiting-input`，继续不依赖该输入的工作。以下行为禁止：

- 使用假的 Key、测试替身、固定返回值或本地假服务代替任务承诺的真实路径；
- 把缺少凭证改写成默认成功、静默跳过或 fallback；
- 因自动化测试通过而跳过必须使用真实环境完成的验证；
- 在真实输入尚未验证时把任务标记完成或提交集成队列。

用户提供的敏感值只通过环境变量、项目已有 Secret 机制或用户指定的安全方式注入。不得写入代码、Git、Obsidian 文档、执行记录、命令输出或日志。执行记录只写配置名称、来源引用、使用范围、验证状态和失效状态，不写真实值。

## 候选 Commit

所有任务要求均已真实完成后，创建一个只属于当前任务的候选 Commit。在执行记录中登记：

- 任务 ID、任务名称和任务文档；
- 基线集成 Commit、候选 Commit、分支和 worktree；
- 实际修改路径与完成结果；
- 执行过的命令和结果；
- 自动化测试、实际运行、数据和外部接入证据；
- 控制台日志与日志文件的观察位置；
- 使用过的外部输入引用、范围和验证状态，不包含敏感值；
- 已知限制；没有时明确写无。

候选形成后停止修改，通知主控进入串行集成队列。候选 Commit 不等于已经集成，也不能让后继任务提前开始。

## 被退回后的处理

集成人员退回候选时，原开发人员 Agent 直接接收：

- 最新集成 Commit、候选 Commit 和被测代码树；
- 失败发生在初审、试合并、测试还是组合结果复审；
- 文件、行、结构位置和相关 diff；
- 准备方式、复现命令、预期结果、实际结果和证据位置；
- 需要修正的任务要求或编码规则；
- 已经确定的事实、仍未知的原因和修正后必须重跑的检查。

我不重新发现这些已知问题，只调查仍未知原因并完成修正。先更新基线，再完成修正和全部必要验证，形成新的候选 Commit。项目经理把新候选放到队尾；其他无关任务和候选继续工作。

## 完成检查

- 当前任务承诺的完整路径已经真实运行；
- 当前实现只依赖任务文档已经记录并验证可用的系统外结果；
- 没有固定成功、空实现、假 Provider、静默跳过或掩盖失败的 fallback；
- 所需用户输入已经通过安全入口使用并完成验证；
- 正常、拒绝、失败和恢复符合任务要求；
- 数据、外部调用、控制台日志和日志文件已经实际检查；
- 自动化测试和项目统一检查通过；
- 候选只包含当前任务的必要修改；
- 执行记录可以让集成人员重现验证；
- 已形成候选 Commit，并且没有直接改动集成分支。

## 工作进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `CD-DEV1` | 固定任务、本系统前置结果、系统外依赖和最新集成 Commit | 执行记录中的任务、依赖、基线和读取范围 |
| `CD-DEV2` | 建立独立 worktree 和任务分支 | worktree、分支和基线 Commit |
| `CD-DEV3` | 完成任务要求的生产代码 | 修改路径和真实执行路径 |
| `CD-DEV4` | 完成数据、外部接入、配置与装配 | 实际运行结果或明确不涉及的任务事实 |
| `CD-DEV5` | 完成过程日志、控制台和日志文件 | 运行观察与日志位置 |
| `CD-DEV6` | 完成自动化测试和实际运行验证 | 命令、结果和运行证据 |
| `CD-DEV7` | 形成单任务候选 Commit | 候选 Commit 与变更摘要 |
| `CD-DEV8` | 提交集成队列或按退回问题重新提交 | 队列状态或新候选 Commit |
