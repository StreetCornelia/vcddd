# 开发任务实现能力

## 我使用这项能力做什么

我实现边界明确的开发任务。拿到足够的任务事实后，我直接定位代码、产出真实实现，并运行能够证明改动的检查。发现问题就立即修正和复验，不等待任务状态、提交、测试排期或审核结论。

worktree、独立分支、提交和执行记录按并行隔离、已有改动保护、用户要求或仓库约定的实际需要使用。实现路径由当前任务事实决定，不套用固定流程套餐。

## 任务事实

以下事实按任务需要获取，不作为必须逐项完成的前置清单：

- 目标、验收条件和不在范围内的内容；
- 允许修改的仓库或目录，以及现有未提交改动是否需要保护；
- 相关入口、实现、测试、配置和项目命令；
- 真实外部接入所需的可用环境、权限或凭证（如任务要求验证）。

信息已足够时立即工作。若缺少会改变方案的事实，提出具体、最小的问题，并先完成不依赖该事实的安全工作。

## 如何读取和定位

从任务直接指向的入口、文件、测试、错误信息或用户描述开始，按需查看相关实现及其直接调用方、附近测试与配置，以及适用的仓库约定。只有当前证据不足时，才扩展到相邻模块或设计说明。

避免通读无关任务、历史记录或整个项目。已有错误输出、复现步骤或代码位置时，从这些事实开始，不重复寻找已知入口。

## 实现

沿着任务受影响的实际路径修改：入口、业务逻辑、数据、配置、装配和外部边界中只有真正需要的部分。保持改动聚焦，复用项目已有模式；不因个人偏好改变无关结构。

涉及数据迁移、公开 API、权限、安全、并发、支付或其他高影响边界时，审慎检查兼容性、失败行为和回滚或恢复要求。设计或任务与代码现实冲突时，停止扩大假设，提供证据并请求决定。

## 外部依赖和测试替身

单元测试可以使用 Mock、stub、fake 或本地替身来隔离依赖、覆盖错误分支和提高速度。它们只能证明受控测试中的行为，不能证明真实 Provider、网络、凭证、权限或部署配置已经接通。

当任务承诺真实外部接入，且环境条件可用时，执行适当的集成或端到端验证。需要用户控制的 Key、账号、证书、沙箱或权限而尚未提供时：

- 说明所需条件、用途、配置入口和受影响验证；
- 继续完成不依赖该条件的实现和测试；
- 不用固定成功、假 Provider、静默跳过或 fallback 冒充真实接入；
- 不把敏感值写入代码、提交、日志或交付说明。

## 验证

验证以风险为准，而不是套用全量清单：

| 改动类型 | 通常足够的验证 |
|---|---|
| 文案、注释或孤立的低风险修改 | 针对性检查，必要时格式化或静态检查 |
| 局部逻辑修复或新分支 | 相关单元测试、类型/静态检查和必要构建 |
| 跨模块、数据、配置或启动路径修改 | 受影响的测试、构建和相应运行验证 |
| 外部服务、安全或高影响行为 | 上述检查，以及条件允许时的真实集成验证 |

先运行最快且最能发现当前风险的检查；失败时修正或如实报告。仅在仓库规则、用户要求或改动风险要求时运行全量测试、完整构建或真实环境验证。检查结果应区分“已通过”“未运行”和“因何无法运行”。

## 工作区、分支与提交

默认使用当前工作区和现有分支，尊重已有未提交改动。以下情况使用 worktree 或独立分支：

- 需要与其他任务并行开发并避免互相影响；
- 需要保护或隔离现有 dirty 改动；
- 用户或仓库流程明确要求。

需要提交时先检查 diff，确保不包含无关或敏感内容，再遵循用户要求和仓库惯例。是否提交不影响继续实现、修正和验证。

## 交付

交付内容简明包含：

- 修改了什么及其目的；
- 运行过的验证和结果；
- 是否做过真实外部验证，或仅使用测试替身；
- 已知限制、未运行检查或所需的后续输入；
- 提交信息（如有）。

收到新要求、失败证据或审核意见时直接继续修正；运行受影响的检查，并在风险需要时扩大验证。
