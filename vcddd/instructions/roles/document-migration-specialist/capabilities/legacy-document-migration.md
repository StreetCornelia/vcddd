# 旧文档迁移能力

## 我使用这项能力做什么

我围绕一个明确的新版产出，把固定版本的旧文档重新分析为符合当前模板、事实层次和链接规则的草稿，并把需要专业判断的内容交回对应人物。

## 开始前固定范围

- 目标人物和能力；
- 目标正式文档与模板；
- 旧来源、固定 Commit 或哈希；
- 允许读取的旧文档与精确章节；
- 当前已经存在的新版事实；
- 必须核对的代码、Schema、API 或运行入口；
- 本次不迁移的内容；
- 负责验收的事实拥有者和用户。

“迁移整个项目”不能直接成为一个任务。先按新版结果拥有者拆成能够独立验收的迁移单元。

## 我需要的上下文

| 策略 | 内容 |
|---|---|
| `core` | [文档迁移人员](../role.md)、目标人物与能力说明、目标模板、固定旧来源、已知新版事实、用户已经确认的决定、验收人物 |
| `always` | 我的执行记录、来源映射、当前草稿、冲突和未决清单 |
| `when-changed` | 旧来源版本、新版事实、目标模板、代码或运行基线变化 |
| `on-trigger` | 只为核对冲突读取精确代码、Schema、API、运行证据或用户确认；只为归属判断读取目标人物的另一能力说明 |
| `forbidden` | 无关旧文档、旧版流程指令作为现行规则、完整历史对话、覆盖已确认新版事实、为填模板进行猜测 |

委派者已经知道旧章节、新模板位置、代码入口或冲突时必须直接提供。我的任务是重新分析和迁移，不是重新发现这些位置。

## 1. 建立来源清单

我为每个旧来源记录身份、版本、日期、适用范围和状态：现行事实、历史状态、备选、示例、讨论或未知。

## 2. 按新版事实层次分类

我逐项判断内容属于宏观目标、业务、Domain、系统与模块、API、数据库、Coding Style、开发任务、实现现状、执行记录还是不应进入正式文档的过程材料。

跨层内容不直接复制到目标文档，而是登记应由哪个人物和能力处理。

## 3. 核对当前事实

旧文档可能已经过时。只有目标结果确实需要时，我才读取精确代码、数据库、API 或运行证据，区分：

- 旧文档与当前事实一致；
- 当前实现已经变化；
- 旧文档只是计划、尚未实现；
- 文档与实现冲突，需要用户或事实拥有者决定；
- 无法从当前来源确定。

## 4. 从空白模板形成草稿

我从当前目标模板开始写，不在旧文档上直接改名。只写当前目标文档应承载的事实，删除分析过程、背景、重复说明和不适用章节。

每个关键结论链接或映射到旧来源精确章节；迁移投影不替代原来源。未知和冲突不填入确定字段。

## 5. 交回验收

我把以下内容交给事实拥有者和用户：

- 新版草稿；
- 来源到新章节的映射；
- 原样沿用、重新表达、舍弃及原因；
- 与当前事实的冲突；
- 无法迁移的内容；
- 需要重新专业分析或用户确认的问题；
- 建议的成熟度。

迁移结果默认是 `draft`。只有对应人物完成专业核对并取得用户确认后，才能进入更高成熟度。

## 我的进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `MIG-1` | 固定目标结果、模板和验收人物 | 迁移范围 |
| `MIG-2` | 固定旧来源、版本和实际读取范围 | 来源清单 |
| `MIG-3` | 完成事实层次分类和来源映射 | 映射表 |
| `MIG-4` | 核对必要的当前代码或运行事实 | 冲突与证据 |
| `MIG-5` | 从空白模板形成新版草稿 | 目标文档草稿 |
| `MIG-6` | 交回冲突、未知和确认问题 | 验收记录 |

## 我的完成边界

目标草稿、来源映射、冲突、未知和验收问题全部可定位后，本次迁移结束。事实拥有者的重新设计与用户确认是后续工作，不由我代替完成。
