# 旧文档迁移能力

## 我使用这项能力做什么

我围绕需要更新或复用的内容，把旧文档重新分析为符合当前模板、事实层次和链接规则的内容与修订建议，并把需要专业判断的内容交回对应人物。小范围迁移由当前 Agent 直接完成，不阻塞其他不受影响的工作。

## 所需范围

- 目标人物和能力；
- 目标正式文档与模板；
- 旧来源与相关章节；
- 允许读取的旧文档与精确章节；
- 当前已经存在的新版事实；
- 必须核对的代码、Schema、API 或运行入口；
- 本次不迁移的内容；
- 需要处理冲突或未知的事实拥有者和用户。

## 我需要的上下文

提供目标人物及能力说明、目标模板、旧来源、已知新版事实和已确认的用户决定。需要追溯或处理冲突时，可补充版本信息、来源映射、当前迁移内容以及冲突和未知清单；只为核对冲突读取精确的代码、Schema、API、运行证据或用户确认，只为判断归属读取目标人物的相关能力说明。

不读取无关旧文档、完整历史对话，也不把旧版流程指令当作现行规则；不以填满模板为由猜测，更不以迁移内容覆盖已确认的新版事实。旧材料只作为来源，不能成为新的事实。

委派者已经知道旧章节、新模板位置、代码入口或冲突时必须直接提供。我的任务是重新分析和迁移，不是重新发现这些位置。

## 1. 建立来源清单

我为每个旧来源记录身份、版本、日期、适用范围和状态：现行事实、历史状态、备选、示例、讨论或未知。

## 2. 按新版事实层次分类

我逐项判断内容属于宏观目标、业务、Domain、系统与模块、API、数据库、系统验证、Coding Style、开发任务、实现现状、执行记录还是不应进入正式文档的过程材料。

旧原型、技术 POC、最小端到端实现及其运行材料归属明确系统时，迁移到 `vcddd-obsidian/03-pre-coding/systems/<system-id>-<system-name>/validation/<validation-id>-<validation-name>/`：源码进入 `src/`，可复现输入进入 `fixtures/`，脚本进入 `scripts/`，每次运行的记录与产物进入 `runs/<run-id>/`。只有观察既有原型所得的业务证据进入业务目标的 `证据/原型观察/`；不得把原型源码迁入该证据目录。

跨层内容不直接复制到目标文档，而是登记应由哪个人物和能力处理。

## 3. 核对当前事实

旧文档可能已经过时。只有目标结果确实需要时，我才读取精确代码、数据库、API 或运行证据，区分：

- 旧文档与当前事实一致；
- 当前实现已经变化；
- 旧文档只是计划、尚未实现；
- 文档与实现冲突，需要用户或事实拥有者决定；
- 无法从当前来源确定。

## 4. 从空白模板形成内容

我从当前目标模板开始写，不在旧文档上直接改名。只写当前目标文档应承载的事实，删除分析过程、背景、重复说明和不适用章节。

每个关键结论链接或映射到旧来源精确章节；迁移投影不替代原来源。未知和冲突不填入确定字段。

## 5. 提供问题与建议

我把以下内容交给事实拥有者和用户：

- 新版内容与修订建议；
- 来源到新章节的映射；
- 原样沿用、重新表达、舍弃及原因；
- 与当前事实的冲突；
- 无法迁移的内容；
- 需要重新专业分析或用户确认的问题；

迁移内容、来源映射、冲突、未知和修订建议应当可定位；事实拥有者的重新设计仍由其负责。
