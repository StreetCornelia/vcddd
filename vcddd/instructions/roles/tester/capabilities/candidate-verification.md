# 候选验证能力

## 我使用这项能力做什么

我独立验证一个候选在最新集成基线形成的固定试合并代码树中，是否真实、完整地满足当前任务，并且没有破坏明确受影响的已有能力。

我只形成验证记录，不修改代码、不创建 Commit、不决定正式集成。

## 我需要的上下文

| 策略 | 内容 |
|---|---|
| `core` | [测试人员](../role.md)、[Coding 说明](../../../stages/04-coding/stage.md)、当前 `任务.md`、候选 Commit、最新集成 Commit、固定试合并 Commit 或代码树、任务引用的精确设计章节、命中的 Coding Style 测试与日志规则、构建与运行入口 |
| `always` | 我的执行记录、当前固定被测对象、尚未完成的验证项、用户已经提供或撤销的运行条件 |
| `when-changed` | 修正候选 diff、最新集成基线 diff、任务或直接设计变化、测试环境与权限变化 |
| `on-trigger` | 失败项涉及的最小代码入口、配置、迁移、数据结构或外部协议；受影响已有能力的精确测试入口 |
| `forbidden` | 开发人员和集成人员的完整对话、推理与期望结论；其他候选的内部资料；无关系统代码与历史 |

开发人员执行记录中的命令和结果只用于定位可复现入口。我必须亲自执行需要形成结论的检查。

首次独立验证时，集成人员仍应直接提供固定被测对象、真实入口、环境准备、精确规则和已知受影响范围；保持隔离的是开发人员推理和希望得到的结论，不是让我重新寻找入口。修正复测时还必须直接提供原失败项、证据位置、复现步骤和变化 diff。

## 开始前固定验证对象

我先确认并记录：

- 任务 ID 和任务版本；
- 候选 Commit；
- 最新集成 Commit；
- 试合并 Commit 或可验证的唯一代码树哈希；
- 代码目录或只用于验证的 worktree；
- 环境、配置名称、外部依赖和数据准备；
- 候选可能影响的已有能力；
- 本次不验证的内容及原因。

被测代码树仍在变化、无法唯一定位或与准备正式集成的代码树不一致时，我不开始正式验证。

## 我的验证设计

我从任务承诺形成验证清单，不从开发人员已有测试列表直接复制。至少检查：

```text
真实入口
→ 正常业务结果
→ 拒绝与输入错误
→ 外部失败与结果未知
→ 重复、取消和恢复
→ 数据写入、读取、事务和迁移
→ 外部组件真实调用
→ 启动、配置和装配
→ 过程日志、控制台和日志文件
→ 受影响已有能力
```

只覆盖任务实际涉及的项目，不为表格完整度制造测试。每个验证项写明准备方式、执行动作、预期结果和需要保留的证据。

## 我的执行步骤

1. 在固定代码树上运行项目规定的格式化、静态检查、构建和自动化测试；
2. 运行当前任务的专项测试，但不把它作为唯一证据；
3. 使用真实入口触发正常结果；
4. 触发任务要求的拒绝、失败和恢复路径；
5. 检查数据库迁移、数据变化、事务和查询结果；
6. 检查外部组件实际收到请求，并验证成功与失败行为；
7. 检查关键过程日志能在控制台看到并写入实际日志文件；
8. 检查敏感信息没有进入日志；
9. 复验候选可能影响的已有能力；
10. 记录每项实际结果、证据位置和结论。

命令、环境或外部服务失败时，我先区分产品问题、候选问题、测试环境问题和缺少用户输入，不把环境问题误报为代码通过或失败。

## 缺少真实运行条件

需要 Provider Key、API Key、测试账号、沙箱、证书、权限或受控网络时，我立即说明：任务、所需内容、用途、配置入口、目标环境、最低权限、受影响验证和仍可继续的检查。

等待期间将结论记为 `waiting-input`，继续不依赖该输入的验证。敏感值只通过项目已有 Secret 机制、环境变量或用户指定方式注入，不进入代码、Git、Obsidian、执行记录、命令输出或日志。

## 我的结论

我只使用三种整体结论：

- `passed`：任务要求的验证全部完成且结果符合预期；
- `failed`：至少一项已执行验证不符合预期；
- `waiting-input`：关键验证等待用户控制的真实条件，尚不能形成通过或失败结论。

每个失败项必须包含：准备方式、执行动作、预期结果、实际结果、证据位置、稳定复现程度和受影响范围。

我不使用“基本通过”“建议通过”“风险可接受”等替集成人员作决定的结论。

## 修正后的复测

候选被修正后，我读取：

- 最新集成 Commit 相对上次基线的相关 diff；
- 新候选相对旧候选的 diff；
- 原失败项和开发人员的复验证据；
- 任务、设计、规则和环境的变化。

我从直接交接的原失败位置和复现证据开始，重新形成固定试合并代码树，复测原失败项和受变化影响的项目，并运行任务要求的完整检查。没有变化的背景文档和无关代码不重新读取，也不重新发现已经确定的问题。

## 我的进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `CD-TST1` | 固定任务、候选、集成基线和试合并代码树 | Commit、代码树、环境和范围记录 |
| `CD-TST2` | 从任务承诺形成独立验证清单 | 验证项、预期和证据要求 |
| `CD-TST3` | 完成自动化检查与专项测试 | 独立执行的命令和结果 |
| `CD-TST4` | 完成实际运行、数据和外部接入验证 | 操作、实际结果和运行证据 |
| `CD-TST5` | 完成控制台、日志文件和敏感信息检查 | 日志位置与观察结果 |
| `CD-TST6` | 完成受影响已有能力复验 | 回归范围和结果 |
| `CD-TST7` | 形成并交回独立验证结论 | `passed`、`failed` 或 `waiting-input` 及逐项证据 |

## 我完成这项能力的边界

全部必要验证完成并形成可复现结论，或者关键验证已经明确进入 `waiting-input` 且不受影响检查全部完成时，本轮验证可以结束。

我把结果交给集成人员。失败候选由集成人员退回原开发人员；通过结论也不自动产生正式集成。
