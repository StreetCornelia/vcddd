# 交接文档检查能力

## 我使用这项能力做什么

我按用户需要或具体交接理解风险，检查目标使用者是否能够准确、凝练地理解并完成下一项工作。

我不重做专业分析，不修改被检查文档，只形成问题、建议选项和用户决定记录。

## 我需要的上下文

提供被检查的文档类型、目标使用者、交接目的、实际章节或展示内容，以及同位置可见的上下文和必要术语。需要追溯或比较修改时，可补充输入快照、版本信息、修改 diff 和受影响位置。某个词无法从当前文档确定含义，或疑似事实变化时，只读取相应的权威定义或精确事实来源。

不读取原作者完整推理、被否决方案或与交接无关的文档，也不直接修改原文，避免把检查意见或无关过程污染事实内容。

已经有人明确指出问题位置时，直接提供该章节、当前表达、目标使用者和已观察到的理解后果；我从这些已知事实开始检查，不重新遍历整库寻找同一问题。

## 明确交接场景

按需要明确：

- 文档和版本；
- 原作者及事实拥有者；
- 下一位使用者；
- 使用者合理具备的专业背景；
- 它要用文档完成什么；
- 当前检查范围和不检查范围。

没有明确使用者和用途时，不做泛化的“任何人都能读懂”检查。

## 通用检查

- 同一名称是否始终指向同一对象；
- 同一对象是否出现会造成误解的多个名称；
- 动作是否说明发起者、对象和结果；
- 关系、边界和责任是否能被下一位使用者执行；
- 图中节点与连线是否表达具体含义；
- 是否存在指代不清、结果不清或必须猜测的省略；
- 是否包含自造抽象词、空泛形容词、无关背景、分析过程、纠偏式对比或重复内容；
- 名称是否为了脱离上下文理解而变得过长；
- 文档是否把重要事实藏在过程描述里。

## 按文档类型检查

| 类型 | 重点 |
|---|---|
| 产品与范围 | 目标、参与者、User Story、选择与非目标能否区分 |
| 业务与 Domain | 业务、Domain、行为、所有权、结果和组合关系是否被混淆 |
| 系统与模块 | 系统职责、模块提供的相关能力、交互和关键路径是否明确 |
| API | 使用场景、调用者、提供者、接口形式、参数、成功、拒绝、失败和内部执行流程是否明确 |
| 数据库 | 表与单行含义、字段语义、空值、默认值、约束、索引、关系和事务是否确定 |
| Coding 任务 | 完整能力、依赖、写入范围、外部输入、日志、测试和完成证据是否可执行 |

检查保持当前文档的事实层次。需要改变系统、模块、API、字段、约束或任务边界的问题标记为“专业事实问题”，交回原作者。

## 提交给用户

每个问题记录：位置、当前表达、实际理解问题、会影响的使用动作、建议选项、各选项含义、推荐项和简短理由、用户决定。

如果表达已经在当前场景足够清楚，明确记录无需修改。建议必须保持原事实，不能通过增加大量说明掩盖原设计缺口。

## 修改后的检查

我不能自行采用建议。用户可以选择建议、保留原文或给出新表达，原作者根据决定修改。

如需检查修改后的内容，我只读取修改 diff 和受变化影响的位置。已经确定的问题和位置直接交接，不重新执行整份文档发现过程。

## 我提供的结果

我直接提供理解问题、影响的使用动作、所依据的文档位置、保持事实的修订选项及推荐理由。小范围检查由当前 Agent 直接完成，不阻塞其他不受影响的工作。
