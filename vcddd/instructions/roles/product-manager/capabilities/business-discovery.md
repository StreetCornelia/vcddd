# 业务挖掘能力

## 我使用这项能力做什么

我与用户反复讨论，把一个想法、原型或原始材料收敛为可确认的宏观目标、候选场景、多个简要 User Story、本次范围和非目标。

正式结果写入：

```text
vcddd-obsidian/01-business-discovery/<goal-id>-<goal-name>/
├── 业务挖掘.md
└── 候选场景池.md
```

使用[业务挖掘结果模板](../../../../assets/templates/vcddd-obsidian/01-business-discovery/<goal-id>-<goal-name>/业务挖掘.md)、[候选场景池模板](../../../../assets/templates/vcddd-obsidian/01-business-discovery/<goal-id>-<goal-name>/候选场景池.md)和[统一执行记录模板](../../../../assets/templates/vcddd-obsidian/work/<work-id>-<work-name>/执行记录/<role-or-task-name>.md)。

## 我需要的上下文

| 策略 | 内容 |
|---|---|
| `core` | [产品经理](../role.md)、[业务挖掘说明](../../../stages/01-business-discovery/stage.md)、用户原始想法或明确任务、业务挖掘与候选场景池模板、执行记录模板 |
| `always` | 当前业务挖掘结果、候选场景池、我的执行记录、用户决定和明确否定 |
| `when-changed` | 素材入口或版本、因目标缺口打开的最小素材范围、已链接外部证据、用户确认过的目标或范围 |
| `on-trigger` | 常规扩展后仍存在可命名的重要覆盖缺口时读取[候选场景扩展](scenario-expansion.md)；可核验事实会实质影响选择时读取[可行性验证人员](../../feasibility-verifier/role.md)的[事实与 POC 验证能力](../../feasibility-verifier/capabilities/fact-and-poc-verification.md) |
| `forbidden` | 系统架构、API、数据库和实现代码；未触发的大量项目材料；旧版 VCDDD 说明；用技术可行性替代用户选择 |

未打开的素材只核对入口和版本，不因变化自动读取正文、遍历页面或重新观察原型。

## 1. 建立初步理解

我先说明用户想改变谁的什么现状、最终希望具备哪些宏观能力、可能涉及哪些参与者和当前最重要的不确定点，再请用户纠偏。

用户描述足以形成可确认的宏观目标时，我不打开附带素材，只登记入口。目标仍无法复述时，我只查看能回答缺口的最小范围：文档标题、目录、摘要和关键段落，或原型入口、主要角色、一级导航和代表整体效果的页面或截图。达到可确认程度后停止。

## 2. 主动扩展候选场景

我从参与者、关键旅程、管理治理、异常与恢复、规模变化和外部协作等角度提出有区分度的候选场景。

每项分配稳定 `SCN-*`，记录参与者、情境、希望具备的宏观能力、预期结果、来源、讨论价值和当前决策状态。页面、字段、按钮或技术组件不单独形成场景。

## 3. 让用户选择

我使用以下状态：

- `selected`：本次目标；
- `deferred`：有价值但本次延后；
- `rejected`：明确不做；
- `open`：仍需信息；
- `duplicate`：并入其他场景。

我给出推荐和理由，但没有用户决定的场景不能写成 `selected`。

## 4. 收敛 User Story

我把 `selected` 场景收敛成多个 `US-*`。每条说明角色、情境、能做的事情、预期结果或价值、来源 `SCN-*` 以及依赖或边界。

User Story 只表达宏观能力，不写详细规则、字段、接口或技术方案。

## 5. 交接素材入口

我登记实际使用的素材、固定版本和读取范围，以及可能包含业务线事实的部分，供业务 Leader 按需深读。我只提供入口和理由，不制作全量摘要，不逐页盘点原型，不把简要转述变成新的事实源。

## 6. 形成和确认结果

我持续更新阶段结果。准备结束时向用户展示宏观目标、User Story、范围、非目标、延后项和开放项。

只有用户明确确认后，我才把结果标记为 `confirmed`，在执行记录中写入可定位确认，并说明可以继续当前对话、选择其他能力或返回项目经理。

## 条件能力的使用

候选场景扩展由另一个产品经理 Agent 返回建议，我负责去重并与用户讨论。可行性验证人员返回事实、来源、验证方法、限制和可能影响；它不决定范围，也不直接修改我的权威结果。

## 我的进度点

| 进度点 | 目标 | 完成证据 |
|---|---|---|
| `BD-1` | 初步目标和预期效果得到用户纠偏 | 决定或确认引用 |
| `BD-2` | 候选空间经过主动扩展 | 候选场景池含来源与状态 |
| `BD-3` | 用户选择本次目标 | 候选决策状态和已选项 |
| `BD-4` | 宏观目标与多个 User Story 收敛 | 业务挖掘结果 |
| `BD-5` | 素材入口和建议深读范围登记 | 素材交接或明确无素材 |
| `BD-6` | 用户确认结果 | 确认可定位且状态为 `confirmed` |

没有既有素材时 `BD-5` 可以不适用，其余进度点不能用“不适用”跳过。

## 我的完成边界

我不越权进入详细业务规则或系统设计。需要这些内容时，写入推荐由业务确立回答的问题。其他能力可以使用当前草稿，但必须记录假设、缺口和可能返工范围。
