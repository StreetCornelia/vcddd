# 执行记录说明

**适用身份：** 所有实际参与 VCDDD 工作的 Agent，包括主控、主专业 Agent 和条件 Agent。

## 设计

你与其他角色共用一个执行记录内核，各身份、能力或路线只扩展工作进度点。你只维护自己的执行记录，不替其他角色补写。执行记录用于恢复、能力衔接和审计，不是专业结果本身，也不是逐字聊天记录。

## 稳定内核

你维护的执行记录必须包含：

- 工作、阶段、路线、角色、专业对话 ID；
- 对应结果笔记；
- 本轮目标；
- 启动上下文及固定版本；
- 工作进度点表；
- 关键事件；
- 实际上下文使用；
- 产出与链接；
- 用户确认；
- 当前状态、限制、受影响判断和下一步；
- 能力衔接建议。

使用模板树中的 [执行记录文件](../../assets/templates/vcddd-obsidian/work/<work-id>/执行记录/<角色或任务>.md)。

执行记录固定写入 `vcddd-obsidian/work/<work-id>/执行记录/`，只保存在本地，不进入 Git。执行记录可以链接本轮创建或更新的正式事实；正式事实不得反向链接执行记录，也不得保存 `work_id` 或 Agent 对话 ID。

## 工作进度点扩展

你的 Agent 工作说明或路线说明会定义：

- 进度点代码；
- 产出成熟度判断；
- 所需证据；
- 是否允许标记不适用。

开始工作时，把属于你的进度点复制到统一模板的工作进度点表。进度点不是其他能力的准入条件。不要为自己的身份或路线复制整份执行记录模板。

## 更新时机

只在语义节点更新：

- 路线或目标确认；
- 新的一组候选场景形成；
- 用户作出范围决定；
- 权威文档发生实质更新；
- 进度点完成；
- 出现、变化或解除具体限制；
- 用户确认专业结果；
- 建立或更新能力衔接。

不要在每条消息、每次读取或每个工具调用后更新。

## 上下文使用记录

至少记录：

| 字段 | 内容 |
|---|---|
| 来源 | 文件、章节 ID、页面或证据链接 |
| 固定版本 | Commit、内容哈希或明确快照 |
| 策略 | `core` / `always` / `when-changed` / `on-trigger` |
| 实际读取范围 | 章节、行区间、页面状态或“未读取” |
| 使用原因 | 它支持哪个任务或决定 |

“禁止上下文”只需记录规则和是否遵守，不要为了证明禁止而读取它。

未触发的 `on-trigger` 项可以出现在“启动上下文”清单中，但只记录触发条件和路由名称；不得填写工作说明内容或实际读取范围。在“实际上下文使用”中，其读取范围必须为“未读取”，或直接不建立该行。只有记录了具体触发事实后，才能登记实际读取的工作说明、版本和范围。

## 结果确认记录

你必须亲自根据工作说明、正文与证据判断以下条件，不得交给脚本打分或裁决。主专业 Agent 只有同时满足以下条件，才能把自己的结果登记为 `confirmed`：

- 路线必需进度点完成；
- 阶段结果存在并链接；
- 用户确认内容可定位；
- 未决项、假设、受影响判断和建议动作已记录；
- 实际使用的上下文可追溯。

`confirmed` 描述结果成熟度，不是其他能力的启动许可。未满足这些条件时，结果仍可作为 `draft` 或带假设输入被其他能力使用，但接收方必须记录来源状态和返工风险。

主控和条件 Agent 没有专业结果确认权：

- 主控等待专业对话工作时可将自己的记录标记为 `waiting`，完成本次调度或结果登记后标记为 `completed`；
- 条件 Agent 在产出已按工作说明交回后，将自己的记录标记为 `completed`；
- 它们不得把阶段结果或自己的执行记录标记成用户确认的替代品。
