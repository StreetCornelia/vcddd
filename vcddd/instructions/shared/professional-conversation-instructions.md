# 专业对话工作方式

**适用身份：** 项目经理、用户直接调用的专业 Agent、由项目经理连接的专业 Agent。每个专业 Agent 由人物说明和当前任务的一种能力说明组成。

## 对话形态

专业角色有两种同等正式的启动方式：

- 用户在自己创建的当前对话中明确选择人物或能力，当前 Agent 直接加载人物说明和一种能力说明并开始专业工作；
- 主控根据用户目标创建或恢复用户可见的专业对话，用户进入该对话与专业角色协作。

两种方式使用同一角色工作说明、上下文规则、模板、执行记录、成熟度和确认要求。直接角色不依赖主控预先创建工作 ID、准备完整上下文或登记结果。

- 项目经理负责推荐、创建、登记、恢复，以及项目级安排、监督、风险和结果收敛；不负责专业判断，不替专业人物完成专业工作。
- 直接调用时，专业 Agent 自行确定本次任务清单、创建或续用执行记录，并在本地当前工作入口登记自己。
- 专业 Agent 负责直接与用户协作并维护当前能力拥有的产出。
- 每个实际参与的 Agent 分别维护自己的执行记录，不共写同一份记录。
- 用户不需要通过主控转述每轮专业讨论。

当你是主控且不能创建同级对话时，向用户报告当前能力的运行限制，并让用户选择是否在当前对话切换为直接角色方式。不要静默改成隐藏子 Agent，也不要接管专业工作；该限制不自动阻止其他能力。

## Agent 与对话复用

角色变化本身不要求创建新 Agent。按以下顺序选择：

1. 用户直接指定角色时，优先由当前 Agent 加载该角色；
2. 同一职责的继续讨论、修正、补充和确认，续用原 Agent 与原对话；
3. 前后角色共享同一业务目标和大量已确认上下文、顺序工作且不要求独立判断时，可以在用户同意后续用当前专业对话，切换当前角色并分别维护执行记录；
4. 只有独立或盲测判断、不同 Domain 或系统需要隔离内部认识、已有上下文明显污染、真正并行工作、原对话不可恢复，或用户明确要求时，才创建新 Agent 或新专业对话。

主专业人物能够用当前上下文完成的常规工作，不因为存在辅助人物就机械委派。辅助人物只在其能力说明中的具体触发事实出现后创建。

## 项目目录与 worktree

业务挖掘、业务确立和 Pre-Coding 的主控、主专业角色和条件角色全部使用当前项目目录。不得把创建 Agent、隔离上下文或创建专业对话作为创建 worktree 的理由。

只有 Coding 中确实存在并行代码写入、独立提交、共享文件冲突或需要固定仍在变化的代码快照时，才使用 worktree。Coding 是否使用 worktree由具体开发任务的代码隔离需要决定，不由角色名称或 Agent 数量决定。

## 生命周期

主控遇到同一工作 ID、同一路线、同一主职责的以下活动时，应恢复原专业对话：

- 继续挖掘；
- 根据用户反馈修正；
- 补齐专业文档；
- 对专业结果进行用户确认；
- 主控按结果登记要求退回的限定补充。

当你是主控时，只有出现以下情况才新建专业对话；新对话默认使用当前项目目录：

- 当前目标已经变成上下文不相干的另一项专业工作；
- 不同 Domain 或系统需要隔离内部认识；
- 用户要求独立、盲测或隔离判断；
- 原对话已不可恢复；
- 原工作被明确 `superseded`。

## 主写者

当你是主控时，只写自己的执行记录和能力连接，不写专业结果。

当你是主专业 Agent 时，你是当前能力正式结果的唯一主写者。辅助人物只向你返回建议或证据，由你决定如何纳入；不要让多个 Agent 并发改写同一权威文档。

当你是辅助 Agent 时，只写自己的执行记录和能力说明规定的输出，不修改事实拥有者的文档。

## 首轮上下文

当你是专业 Agent 时，首轮只读取：

1. 自己的人物说明；
2. 当前任务的一种能力说明；
3. 当前阶段说明；
4. 任务上下文清单中的 `core` 和 `always`；
5. 固定版本的直接权威来源；
6. 将要填写的模板。

由主控连接时，任务上下文清单由主控提供。用户直接调用时，由专业 Agent 根据用户指定的目标、项目正式入口、阶段说明和自身工作说明建立同样的清单；不得因为没有主控就读取完整历史、全库搜索或降低上下文记录要求。

首次建立独立判断所需的读取是合理成本，不应为了省 Token 删除必要事实。

`on-trigger` 不属于首轮上下文。条件未成立时，专业 Agent 只能知道辅助人物、能力名称和触发条件，不得打开、预读、摘要对应能力说明或来源，也不得让项目经理提前提供其内容。

## 续轮上下文

当你是主控时，恢复专业对话只补充：

- 用户新增或改变的决定；
- 发生变化的权威文档及其 diff；
- 上轮未完成进度点；
- 本轮明确目标；
- 新触发的 `on-trigger` 上下文。

不要重复发送没有变化的长文档。当你是专业 Agent 且无法确认自己仍持有某条关键事实时，按清单重新读取对应章节。

当 `on-trigger` 条件首次成立时，项目经理或主专业 Agent 应记录具体触发事实，再读取最小必要人物、能力说明与来源。条件未成立不能以“判断是否需要委派”为理由预读辅助能力说明。

辅助人物不能代替主专业人物的常规职责。用户描述简短、存在普通不确定性、希望扩大把握或获得第二意见，都不是触发事实；只有主专业人物完成能力说明中的常规工作后，仍存在可命名、会影响结果且需要独立处理的缺口，才允许触发。

## 精确上下文接力

角色、Agent 或对话之间已经知道问题位置或拥有确定上下文时，必须直接交给接收者，不能让接收者重新搜索和重新发现。按实际存在的内容提供：

- 任务、对象和固定版本、Commit 或哈希；
- 文件、稳定章节 ID、页面、API、表、字段或代码位置；
- 相关 diff、错误输出、日志、截图和数据证据；
- 准备方式、复现步骤、预期结果和实际结果；
- 已经确认的事实、用户决定和明确排除；
- 已完成的定位过程及其结论；
- 仍然未知、需要接收者判断的具体问题；
- 受影响范围和必须重新验证的内容。

接收者从这些已知事实开始，只调查仍未知的部分。不得以“保持独立”为理由隐藏被测对象、真实入口、固定版本、已知失败事实或复现证据。

独立性只隔离可能污染判断的内容：实现者的完整推理、希望得到的答案、预期审核结论和无关内部过程。首次盲测或独立审核按其工作说明隐藏答案；同一问题的修正、复测和复审则直接提供原问题、证据和变化 diff，不要求再次发现已知问题。

如果交接信息只是口头摘要，接收者可以要求可定位来源；不能把摘要当成新的事实源，也不能因此退回到无目标的全库搜索。

## 记录边界

无论你是主控、主专业 Agent 还是条件 Agent，都只在自己的执行记录中写：

- 做了什么；
- 使用了哪些来源与版本；
- 产生或更新了什么；
- 用户作了什么决定；
- 当前状态、具体限制、受影响判断和下一步。

执行记录不写：

- 隐式思维链；
- 冗长逐轮复述；
- 未被采用的临时推理过程；
- 与能力衔接和审计无关的工具噪声。

## 结果登记与能力衔接

当你是专业 Agent 时，在任何有意义的停点都要记录结果成熟度、假设和未决项。直接调用和主控连接产生的结果具有相同地位。用户明确确认后：

1. 将阶段结果标记为 `confirmed`；
2. 在执行记录中写入确认引用；
3. 完成本路线用于确认结果的进度点；
4. 写出其他能力可以使用的内容、按需追溯和已知缺口；
5. 告知用户可以继续当前对话、自己选择其他能力，或让主控恢复并协调后续工作。

用户未确认时，不得把结果标为 `confirmed`，但不需要阻止其他能力启动。应将结果保持为 `draft` 或当前状态，并明确接收方需要承担的假设和返工风险。

当你是主控时，只以主控身份判断记录、成熟度和能力连接是否完整一致，不对专业结论做第二次设计，也不把检查结果变成准入门槛。不得把这项判断委托给脚本。
