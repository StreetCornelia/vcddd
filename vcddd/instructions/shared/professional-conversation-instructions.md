# 专业对话工作方式

**适用身份：** 项目经理、用户直接调用的专业 Agent、由项目经理连接的专业 Agent。每个专业 Agent 由人物说明和当前任务的一种能力说明组成。

## 对话形态

专业角色有两种同等正式的启动方式：

- 用户在自己创建的当前对话中明确选择人物或能力，当前 Agent 直接加载人物说明和一种能力说明并开始专业工作；
- 主控根据用户目标创建或恢复用户可见的专业对话，用户进入该对话与专业角色协作。

两种方式使用同一角色工作说明、上下文规则、事实所有权和按需执行记录。直接角色不依赖主控预先创建工作 ID、准备完整上下文或登记结果。

- 项目经理负责项目级安排、监督、风险和结果收敛；边界明确且当前 Agent 能快速完成的小型调查、汇总、进展说明或修改直接完成，不为角色纯度委派。
- 直接调用时，专业 Agent 自行确定本次任务清单；仅在需要跨轮恢复、持续跟踪、能力交接或审计时创建或续用执行记录，并按需补充本地当前工作入口。
- 专业 Agent 负责直接与用户协作并维护当前能力拥有的产出。
- 每个实际参与且确有记录需要的 Agent 分别维护自己的执行记录，不共写同一份记录；角色切换不等于新 Agent，也不自动产生新记录。
- 用户不需要通过主控转述每轮专业讨论。

当你是主控且不能创建同级对话时，向用户报告当前能力的运行限制，并让用户选择是否在当前对话切换为直接角色方式。不要静默改成隐藏子 Agent，也不要接管专业工作；该限制不自动阻止其他能力。

## Agent 与对话复用

角色变化本身不要求创建新 Agent、专业对话或执行记录。按以下顺序选择：

1. 用户直接指定角色时，优先由当前 Agent 加载该角色；
2. 同一职责的继续讨论、修正、补充和定稿，续用原 Agent 与原对话；
3. 前后角色共享同一业务目标和大量上下文、顺序工作且不要求独立判断时，续用当前对话；角色切换不创建新记录；
4. 只有独立或盲测判断、不同 Domain 或系统需要隔离内部认识、已有上下文明显污染、真正并行工作、原对话不可恢复，或用户明确要求时，才创建新 Agent 或新专业对话。

主专业人物能够用当前上下文完成的常规工作，不因为存在辅助人物就机械委派。出现适合辅助人物独立处理的具体缺口时，再按需创建。

## 项目目录与 worktree

业务挖掘、业务确立和 Pre-Coding 的主控、主专业角色和条件角色全部使用当前项目目录。不得把创建 Agent、隔离上下文或创建专业对话作为创建 worktree 的理由。

只有 Coding 中确实存在并行代码写入、独立提交、共享文件冲突或需要隔离仍在变化的代码快照时，才使用 worktree。Coding 是否使用 worktree 由具体开发任务的代码隔离需要决定，不由角色名称或 Agent 数量决定。

## 生命周期

主控遇到同一工作 ID、同一路线、同一主职责的以下活动时，应恢复原专业对话：

- 继续挖掘；
- 根据用户反馈修正；
- 补齐专业文档；
- 用户继续讨论或调整专业结果；
- 对已有结果作限定补充。

当你是主控时，只有出现以下情况才新建专业对话；新对话默认使用当前项目目录：

- 当前目标已经变成上下文不相干的另一项专业工作；
- 不同 Domain 或系统需要隔离内部认识；
- 用户要求独立、盲测或隔离判断；
- 原对话已不可恢复；
- 原工作已经明确结束，当前目标是另一项不相干的工作。

## 主写者

当你是主控时，可以直接完成边界明确的小型专业结果；只有已经委派给独立负责人的正式结果才不与其并发共写。

当你是主专业 Agent 时，你是当前能力正式结果的唯一主写者。辅助人物只向你返回建议或证据，由你决定如何纳入；不要让多个 Agent 并发改写同一权威文档。

当你是辅助 Agent 时，只修改任务明确授权的输出；没有授权时返回结论，不修改事实拥有者的文档。执行记录仍按需。

## 上下文提供

由主控连接专业 Agent 时，主控直接提供当前任务的最少必要事实：本轮目标、已经定位的对象和位置、与判断有关的变化，以及仍需执行者处理的未决问题。不要为了形式完整发送无关人物说明、阶段说明、模板或历史材料。

后续协作只补充新增或改变的事实、相关 diff 和仍未解决的问题，不重复发送没有变化的长文档。用户直接调用专业角色时，同样从用户目标、已知位置和当前未决问题开始，只读取完成判断真正需要的内容。

执行者从主控或用户已经提供的定位结果开始，只调查仍未知的部分；已经明确的文件、章节、代码位置、复现方式和结论不重新搜索或重新发现。只有现有信息不足以支持判断时，才补读对应来源。

辅助人物不能代替主专业人物的常规职责。出现可命名、会影响结果且适合独立处理的缺口时，项目经理或主专业 Agent 直接提供该缺口的最少必要事实，再按需引入辅助人物。

## 精确上下文接力

角色、Agent 或对话之间已经知道问题位置或拥有确定上下文时，必须直接交给接收者，不能让接收者重新搜索和重新发现。按实际存在的内容提供：

- 任务、对象，以及判断确实依赖的版本、Commit 或哈希；
- 文件、稳定章节 ID、页面、API、表、字段或代码位置；
- 相关 diff、错误输出、日志、截图和数据证据；
- 准备方式、复现步骤、预期结果和实际结果；
- 已经明确的事实、用户决定和明确排除；
- 已完成的定位过程及其结论；
- 仍然未知、需要接收者判断的具体问题；
- 受影响范围和必须重新验证的内容。

接收者从这些已知事实开始，只调查仍未知的部分。不得以“保持独立”为理由隐藏被测对象、真实入口、相关代码状态、已知问题事实或复现证据。

独立性只隔离可能污染判断的内容：实现者的完整推理、希望得到的答案、预期审核结论和无关内部过程。首次盲测或独立审核按其工作说明隐藏答案；同一问题的修正、复测和复审则直接提供原问题、证据和变化 diff，不要求再次发现已知问题。

如果交接信息只是口头摘要，接收者可以要求可定位来源；不能把摘要当成新的事实源，也不能因此退回到无目标的全库搜索。

## 记录边界

执行记录、`当前工作.md` 与 `主控状态.md` 都是按需恢复工具：只有工作跨轮持续、需要主控协调或恢复、存在交接/审计需求，或用户明确要求时才创建或更新。普通单次任务不创建 work 文档；角色切换、加载另一能力说明或在同一 Agent 内继续工作，也不单独触发新 Agent、新工作目录或新记录。

已创建执行记录时，无论你是主控、主专业 Agent 还是条件 Agent，都只在自己的执行记录中写：

- 当前目标；
- 已知事实和使用的来源；
- 结果及其证据；
- 未决项及其影响。

执行记录不写：

- 隐式思维链；
- 冗长逐轮复述；
- 未被采用的临时推理过程；
- 与能力衔接和审计无关的工具噪声。

## 结果与能力衔接

当你是专业 Agent 时，在有意义的停点直接说明当前目标、已知事实、结果、证据和未决项；只在需要长期保存或跨轮恢复时写入正式结果或已有执行记录。直接调用和主控连接产生的结果具有相同地位。

用户的决定和反馈作为事实直接纳入结果。其他能力可以直接使用当前结果；存在假设、证据缺口或可能返工范围时，在交接中明确说明即可。

当你是主控时，只检查事实所有权、结果来源和未决项是否表达清楚，不对专业结论做第二次设计，也不把记录完整度变成开工或交付条件。不得把专业判断委托给脚本。
