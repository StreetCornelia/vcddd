## 文档唯一主轴

`核心接口内部编排.md` 只以 `API设计.md` 中的单个 API 为正文一级单位。读者进入任一 API 章节，必须不跨章节就能回答：

```text
调用者为什么调用
→ 系统先做什么
→ 每一步得到什么结果
→ 依据结果继续到哪一步
→ 什么情况下拒绝或失败
→ 哪些变化一起提交
→ 外部影响发生在何时
→ 最终向调用者返回什么
```

不要建立“API 内部编排 / Domain 方法内部编排”两个并列正文，也不要按业务线、用例、资源类型或“核心 API 组”合并多个接口。业务线只用于检查覆盖；Domain 设计继续拥有行为内部规则、不变量、对象协作和生命周期。

每个 API 在 `API设计.md` 中先取得唯一、稳定且不随路径文案变化的标识：

```text
API 标识：API-<系统内唯一短名>
```

编排文档使用同一个标识，不重新命名接口。

## 每个部分怎样填写

### 接口目录

逐项覆盖 `API设计.md` 的全部 `API 标识`。目录只负责导航和一句话业务结果，不在这里展开流程。

### 业务结果

先用普通话说明调用者意图、成功后谁发生什么变化和接口不负责什么。不要以模块、表、框架或技术动作开头。

### 主流程

这是正文核心。每一步只表达一个可判断的推进：

```text
谁
→ 基于什么已取得事实做什么
→ 得到什么结果
→ 根据结果去哪一步
```

步骤必须从 `S1` 连续编号。执行者使用 API 入口、应用用例、明确 Domain、Repository 或明确外部系统；不要使用“系统”“服务”“处理器”等无法定位责任的泛称。

图只能补充这张表，不能代替它。需要图时，每个 API 默认最多一张时序图；只有分支或恢复无法从表格看懂时再增加一张活动图。

### 分支与失败

所有主流程中的拒绝、冲突、重复、取消、超时、部分完成和结果未知都在这里回到具体步骤。不要另写脱离步骤的大段“异常处理原则”。

### 事务与外部影响

明确本地原子范围、提交点、不可逆外部动作的前后顺序、成功证明和未知结果恢复。事务不是框架用法说明；装饰器、Unit of Work、锁或 Outbox 等技术选择留给工程编码规范和 Coding。

### Domain 调用

只说明当前 API 在哪一步调用哪个已确认 Domain 行为、给它什么事实、取得什么领域结果，并链接 `系统拆分.md` 的权威行为与规则。

不要在本文件重新写一套“Domain 方法内部编排”。如果现有 Domain 设计无法说明行为怎样依据规则产生结果，应先补充并重新确认 `系统拆分.md`，不能把缺失的 Domain 设计藏进接口编排。

### 业务证据与验证

只记录证明重要业务结果、外部影响、恢复或安全审计所必需的日志与关联标识。日志字段、级别、采样、频率和脱敏的系统实现规范属于 `工程编码规范.md`。

验证场景使用业务结果表述，不在这里设计测试框架或测试代码。

## Domain 与技术细节的边界

| 内容 | 权威位置 |
| --- | --- |
| API 请求、响应、协议和错误合同 | `API设计.md` |
| Domain 拥有的行为、规则、不变量、对象协作和生命周期 | `系统拆分.md` |
| 单个 API 怎样依次调用 Domain、Repository 和外部能力并形成结果 | `核心接口内部编排.md` |
| 模块、端口、Adapter 和依赖方向 | `模块拆分.md` |
| 表、字段、约束、索引和数据迁移 | `数据库设计.md` |
| 事务框架、日志 Schema、代码组织和测试实现方式 | `工程编码规范.md` |

编排步骤可以引用这些事实，但不能复制或重新定义它们。

## 可读性边界

- 先写业务结果和主流程，再写事务、证据和验证；
- 一个标题只属于一个确切 API，不使用“创建类 API”“单聚合修改 API”等接口组；
- 一句话只表达一个判断或动作，术语第一次出现时链接权威定义；
- 表格单元格写结果，不塞入多段推理；
- 不把确认过程、调研过程、候选比较或任务恢复信息写进正文；
- 不用图替代文字步骤，不让读者从多张图自行拼装结果；
- 不重复 API 字段、Domain 内部规则、数据库字段或 Coding 机制；
- 一个 API 章节即使单独截取，也能回答正常、拒绝、事务、外部影响和最终返回。

## 完成与确认

候选完成后运行：

```text
python3 <本 Skill 目录>/scripts/validate_project.py <目标仓库根目录> --orchestration-system <中文系统名>
```

结构验证通过以后，再把接口目录和逐 API 章节交给用户审核。确认包按 API 顺序展示每个接口的业务结果、主流程、主要失败、事务与外部影响；不要另写脱离正文的七项、十项或其他总结让用户代替阅读文档。

用户明确确认当前版本后才能标记 `已确认`。API 增删、业务结果、步骤顺序、Domain 判断拥有者、事务提交点、不可逆外部影响或结果未知语义发生实质变化时，恢复为 `待确认`，重新运行结构验证并交给用户确认。
