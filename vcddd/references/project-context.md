## 目标

让没有历史对话的主控或专业 Agent 从少量入口恢复：

- 用户已经建立哪些阶段性业务目标；
- 当前有哪些任务；
- 当前负责角色和讨论对象；
- 哪些文档是事实源、派生基线、证据或按需报告；
- 尚未处理的用户反馈；
- 下一步应该调用谁并读取什么。

项目文档是持久记忆。聊天历史和 Agent 内部上下文都可以丢弃。

入口和任务恢复模板见 [project-document-contracts.md](project-document-contracts.md)。事实文档可以按读者需要组织正文，导航和恢复文档必须遵守固定合同。

## 恢复顺序

主控恢复：

1. 读取 `docs/vcddd/index.md`；
2. 读取 `docs/vcddd/work/index.md`；
3. 用户明确继续或请求只匹配一个任务时，只读取该任务的 `主控状态.md`；
4. 原样转交交互包、反馈或按“下一步”调度专业 Agent。

专业 Agent 恢复：

1. 读取角色 reference、`主控状态.md` 和其中链接的完整任务；
2. 读取任务列出的直接权威文档和证据；
3. 若存在待处理反馈，由当前角色吸收；
4. 开发时读取当前开发基线和本切片直接来源；
5. 审核时只读取任务固定的代码快照、实现记录、开发基线、审核角色 reference 和允许证据路径。

主控不要默认读取完整任务、业务、系统、报告、验证历史或专业 Agent 改动的整份 diff。导航或状态不能说明下一步时，先让当前专业 Agent 修复完整任务和状态文件。

旧任务尚未建立 `主控状态.md` 时，由一次性恢复整理子 Agent 读取旧任务并创建短状态，主控不自己加载整份旧任务。`validate_project.py --recovery-task <任务名>` 只有在短状态、完整任务和入口链接都存在时才认为当前任务可恢复。

首次建档时只创建已经有真实内容的入口和任务，不预建空目标、系统或报告。

## 业务目标与任务

阶段性业务目标表示用户持续推动的业务结果：

- 可跨系统、任务和会话；
- 可与其他目标并行；
- 由用户决定建立、选择、合并、暂停、完成和取消；
- 不因一个任务或一次上线自动结束。

工作任务表示有独立目标和完成条件的实际工作：

- 可以服务多个目标；
- 一个目标可以由多个任务推进；
- 不按文档、Agent 或步骤机械拆任务；
- 用户直接要求梳理、设计、构建、修改或修复，且只匹配一个任务时可以继续；
- 没有匹配任务时主控透明建立中文任务；
- 多个选择会实质改变结果时才请用户选择。

只读解释、审查和状态报告不自动创建任务。

## 事实空间

### `business/`

业务设计 Agent 拥有。正式事实集中在：

```text
business/<阶段性业务目标>/业务设计.md
```

它说明业务目标与范围、业务层系统设计和业务线逻辑。

### `systems/`

系统与开发设计 Agent 拥有单个系统的设计事实：

```text
系统拆分.md
模块拆分.md
API设计.md
核心业务流程.md
数据库设计.md
```

`开发基线.md` 是这些事实和相关业务设计的派生实现入口，不是新的语义源。

`系统拆分.md` 中的完整 Domain、`API设计.md`、`核心业务流程.md` 和 `数据库设计.md` 都先由系统设计 Agent 形成候选，再分别由用户审核。每份文档保存自己的确认状态和依据；`待确认` 候选可以在用户明确要求时支持并行设计，但不具有当前事实权威。四者均确认以后，`开发基线.md` 才可以成为 `当前` 的实现入口。

`核心业务流程.md` 是业务线到实现之间的编排事实：覆盖每条业务线，只展开核心流程，并用稳定步骤把 API、应用层、Domain、事务、外部系统、关键日志、失败恢复和验证连接起来。开发记录和实现符合性审核沿用这些步骤，不从代码反向发明另一套流程。

这些设计文档中的权威图与正文共同构成事实。图的类型、所有权、派生方式和图文冲突处理见 [设计图表达协议](diagramming.md)；更换会话时不需要重建图的含义，只读取权威图及其相邻补充说明。

### 开发与审核记录

开发记录保存代码如何落实开发基线以及独立审核如何判断固定代码快照。它们是实现和审核证据，不会反向成为新的业务或设计权威。

```text
systems/<中文系统名>/开发记录/
├── index.md
└── <开发切片>/
    ├── 实现记录.md
    ├── 审核/
    │   ├── 实现符合性.md
    │   └── 工程质量.md
    └── 审核结论.md
```

- `开发记录/index.md`：列出切片、当前代码快照、实现范围、审核结论和入口；
- `实现记录.md`：开发 Agent 维护设计到代码和验证证据的映射；
- 两份核心审核：相互独立，只对记录的代码快照有效；
- `审核结论.md`：独立审核完成后由新的审核结论 Agent 汇总问题、处理责任、修正快照和复审状态，不替代原审核记录。

安全、性能、前端体验或平台专项审核按风险增加到 `审核/`，不要求所有项目机械创建。

代码变化时保留旧记录的 Git 历史，并让当前入口指向新快照的实现和复审结果。局部修改只影响对应审核；改变 API、Domain、事务、迁移或大范围实现时两个核心审核都需要重新读取。

### `work/`

完整任务 `index.md` 由当前专业 Agent 维护，保存任务目标、读写合同、候选、冲突、影响和恢复判断；`主控状态.md` 由主控与当前专业 Agent 交替写入，保存当前角色、交互、反馈、结果路径和下一步。两者都不替代业务或系统事实。

### 原型、验证与按需报告

- 原型是发现或呈现投影；
- 验证保存可复现证据；
- 报告是用户指定位置的派生阅读视图。

三者都不能和 `business/`、`systems/` 竞争当前事实。

## 任务恢复点

每个任务包含两层恢复点：

```text
work/<中文任务名>/主控状态.md
→ 主控只读的短通信面

work/<中文任务名>/index.md
→ 专业 Agent 的完整任务恢复文档
```

完整任务固定使用 [任务恢复文档模板](project-document-contracts.md#任务恢复文档)。它保存任务定义、角色、读写合同、完整判断、已有产物和恢复动作，但当前交互、待处理反馈和处理结果只链接 `主控状态.md`，避免复制。

两份文件都不保存完整聊天、命令流水或原始推理。用户反馈被专业 Agent 吸收后，状态文件清空待处理区并链接更新后的事实。

判断状态只保存问题、证据、候选、结论、所有者、依赖、状态和影响。重要未决决定不因数量较多而省略；当前决策前沿是其中不依赖其他未决决定、可以立即处理的集合。答案写入正式事实文档后，从任务中的未决判断移除，并重新计算前沿，避免任务记录与事实文档竞争。

## 角色恢复合同

主控调用专业 Agent 前，把角色 reference、当前讨论对象和只属于该任务的待处理用户原话片段写入 `主控状态.md`。一条反馈涉及多个任务时，完整原话只保存在协调任务，由主控切分后分别派发；专业 Agent 不读取其他系统的反馈片段。专业 Agent 从状态文件进入完整任务，读取其中的权威文档、直接证据、允许写入路径、完成条件和全部未决决定。专业 Agent 完成后直接更新事实、完整任务和状态文件；主控不接收完整结果信封。

新专业 Agent 只依赖：

```text
角色 reference
+ 当前任务的主控状态
+ 当前任务恢复文档
+ 任务列出的权威文档和直接证据
```

主控调度消息只包含角色 reference 和主控状态路径，不能拥有项目文档中没有的关键上下文。详细进入和退出动作见 [project-document-contracts.md#角色进入与退出](project-document-contracts.md#角色进入与退出)。

## 状态与替代

事实或投影按需标明：

- `当前`：声明范围内的现行事实或可用投影；
- `待确认`：尚未被用户或证据接受的候选；
- `待重新判断`：来源变化后可能失效的事实；
- `待重新生成`：来源变化后的开发基线或派生报告；
- `已替代`：仅供历史追溯；
- `证据`：观察或实验结果。

同一个问题只能有一个当前事实源。详细文档和开发基线可以并存，但必须明确前者是事实、后者是派生阅读入口。

对 Domain、API、核心业务流程和数据库设计而言，“被用户接受”必须来自当前版本的明确审核确认，不能由 Agent 从用户沉默、文档完成或旧版本确认推断。实质变更会使对应确认失效，并只影响依赖该变化的下游内容。

旧材料依靠版本控制或明确历史导航保存，不继续出现在当前主路径。

## 变化影响

改变事实时：

1. 在当前任务记录变化和证据；
2. 先识别依赖该事实的具体文档、基线、代码、测试、原型和报告；
3. 只把受影响部分标为 `待重新判断` 或 `待重新生成`；
4. 事实拥有者更新源文档；
5. 受影响角色重新读取并局部推导；
6. 开发基线变化时标记受影响代码快照和审核结论；
7. 按需重新生成原型、开发基线、实现记录、审核或用户报告。

不要因一项变化废弃全部下游，也不要让后写代码、报告或原型静默覆盖上游。

多个任务修改同一事实时，主控保存竞争变化并让事实拥有者统一处理；同一文件不并行写入。

## 目录合同

```text
<目标仓库>/
├── docs/vcddd/
│   ├── index.md
│   ├── business/
│   │   ├── index.md
│   │   └── <阶段性业务目标>/
│   │       └── 业务设计.md
│   ├── systems/
│   │   ├── index.md
│   │   └── <中文系统名>/
│   │       ├── index.md
│   │       ├── 系统拆分.md
│   │       ├── 模块拆分.md
│   │       ├── API设计.md
│   │       ├── 核心业务流程.md
│   │       ├── 数据库设计.md
│   │       ├── 开发基线.md
│   │       └── 开发记录/
│   │           ├── index.md
│   │           └── <开发切片>/
│   │               ├── 实现记录.md
│   │               ├── 审核/
│   │               │   ├── 实现符合性.md
│   │               │   └── 工程质量.md
│   │               └── 审核结论.md
│   └── work/
│       ├── index.md
│       └── <中文任务名>/
│           ├── index.md
│           ├── 主控状态.md
│           ├── Domain判定.md（任务进入 Domain 分析时）
│           └── 语言验证/（存在名称或文案盲测时）
├── <用户指定或项目约定的原型位置>/
└── <用户指定的按需报告位置>
```

`docs/vcddd/index.md` 说明项目现实边界、业务/系统/任务入口、当前开发基线、重要冲突以及不同问题的阅读方式。

`business/index.md` 只列用户建立的目标、状态和业务设计入口。

`systems/index.md` 只列系统、责任、状态和入口；系统 `index.md` 只列目的、责任、当前设计文档、开发基线和开发记录入口。

各入口、主控状态和任务恢复文档的最小内容见 [project-document-contracts.md](project-document-contracts.md)。

用户没有要求报告时不创建报告目录或报告文件。简单项目仍保留固定事实责任，但可以在用户明确决定后合并物理文件，并更新验证约定。
