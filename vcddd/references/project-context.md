## 目标

让没有历史对话的主控或专业 Agent 从少量入口恢复：

- 用户已经建立哪些阶段性业务目标；
- 当前有哪些任务；
- 当前负责角色和讨论对象；
- 哪些文档是事实源、派生基线、证据或按需报告；
- 尚未处理的用户反馈；
- 下一步应该调用谁并读取什么。

项目文档是持久记忆。聊天历史和 Agent 内部上下文都可以丢弃。

入口和任务恢复模板见 [project-document-contracts.md](project-document-contracts.md)。事实文档可以按读者需要组织正文，导航和恢复文档必须遵守固定合同。

## 恢复顺序

主控恢复：

1. 读取 `vcddd/index.md`；
2. 读取 `vcddd/work/index.md`；
3. 用户明确继续或请求只匹配一个任务时，只读取该任务的 `主控状态.md`；
4. 原样转交交互包、反馈或按“下一步”调度专业 Agent。

专业 Agent 恢复：

1. 读取角色 reference、`主控状态.md` 和其中链接的完整任务；
2. 读取任务列出的直接权威文档和证据；
3. 若存在待处理反馈，由当前角色吸收；
4. 开发规划时读取当前开发基线、本系统工程编码规范、真实代码快照和任务图模板；
5. 实施任务时读取当前开发任务图中的本节点、前置产物、允许写入范围和直接来源；
6. 统一测试时读取全部生产代码合并后的固定快照、自己的测试角度和允许路径；
7. 工程改进时读取测试结论、固定生产代码与测试快照、开发基线、工程规范和允许证据路径；
8. 审核时只读取任务固定的最终生产代码与测试快照、任务图、集成记录、实施记录、测试结论、开发基线、工程规范、审核角色 reference 和允许路径。

主控不要默认读取完整任务、业务、系统、报告、验证历史或专业 Agent 改动的整份 diff。导航或状态不能说明下一步时，先让当前专业 Agent 修复完整任务和状态文件。

旧任务尚未建立 `主控状态.md` 时，由一次性恢复整理子 Agent 读取旧任务并创建短状态，主控不自己加载整份旧任务。完成恢复整理后执行：

```text
python3 <skill-root>/scripts/sync_indexes.py <repo-root> --write
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --recovery-task <work-id>
```

第一条命令只同步工作索引；第二条只有在短状态、完整任务和入口链接都存在时才通过。脚本不读取旧任务替 Agent 迁移，也不判断任务专业结论是否正确。完整边界见 [脚本执行协议](script-usage.md#恢复或迁移一个工作任务)。

首次建档时只创建已经有真实内容的入口和任务，不预建空目标、系统或报告。

## 业务目标与任务

阶段性业务目标表示用户持续推动的业务结果：

- 可跨系统、任务和会话；
- 可与其他目标并行；
- 由用户决定建立、选择、合并、暂停、完成和取消；
- 不因一个任务或一次上线自动结束。

工作任务表示有独立目标和完成条件的实际工作：

- 可以服务多个目标；
- 一个目标可以由多个任务推进；
- 不按文档、Agent 或步骤机械拆任务；
- 用户直接要求梳理、设计、构建、修改或修复，且只匹配一个任务时可以继续；
- 没有匹配任务时主控透明建立中文任务；
- 多个选择会实质改变结果时才请用户选择。

只读解释、审查和状态报告不自动创建任务。

## 事实空间

### `business/`

业务设计 Agent 拥有。正式事实集中在：

```text
business/<阶段性业务目标>/业务设计.md
```

它说明业务目标与范围、业务层系统设计和业务线逻辑。

### `systems/`

系统与开发设计 Agent 拥有单个系统的设计事实：

```text
系统拆分.md
架构设计.md
模块拆分.md
API设计.md
核心接口内部编排.md
数据库设计.md
```

`开发基线.md` 是这些事实和相关业务设计的派生实现入口，不是新的语义源。

`工程编码规范.md` 由 Coding 角色拥有，保存本系统全部代码共同遵守的当前工程规则、条件规则、允许实现空间、验证方式、例外和存量处理。它不与业务、Domain、架构、模块、API、核心接口内部编排或数据库设计竞争事实权威。Coding Agent 按固定模板从已有代码或当前技术栈最佳实践形成完整候选，由用户确认后才成为当前规范；规则改变业务结果、事务语义、外部合同或数据事实时，必须返回相应设计文档，而不能留在工程规范中。

`系统拆分.md` 中的完整 Domain、`架构设计.md`、`模块拆分.md`、`API设计.md`、`核心接口内部编排.md` 和 `数据库设计.md` 都先由系统设计 Agent 形成候选，再由用户审核。每份文档保存自己的确认状态和依据；`待确认` 候选可以在用户明确要求时支持并行设计，但不具有当前事实权威。六者均确认以后，`开发基线.md` 才可以成为 `当前` 的实现入口；工程编码规范另行确认并成为 `当前` 后才能进入 Coding。

`核心接口内部编排.md` 是 API 到实现之间的连续业务编排事实：接口目录检查 `API设计.md` 是否完整覆盖，正文只以一个确切 API 为一级单位，固定说明业务结果、主流程、分支失败、事务与外部影响、Domain 调用和业务证据。Domain 行为内部规则、不变量和对象协作继续由 `系统拆分.md` 拥有。交付记录和实现符合性审核沿用逐 API 稳定步骤，不从代码反向发明另一套编排。

`数据库设计.md` 是已确认业务与编排的数据承载事实：先说明需要保存什么和为什么保存，再以每张表为单位说明存在意义、单行语义、全部字段、关系、约束、查询、事务、并发和生命周期。DDL、ORM 映射和迁移属于 Coding 实现，不进入设计文档，也不能代替用户审核。

这些设计文档中的权威图与正文共同构成事实。图的类型、所有权、派生方式和图文冲突处理见 [设计图表达协议](diagramming.md)；更换会话时不需要重建图的含义，只读取权威图及其相邻补充说明。

### `validation/`

验证属于被验证系统。原型是 `prototype` 验证方法；技术 PoC、合同检查、源码核对、基准、模拟和最小端到端实现是其他方法。每项验证在 `systems/<system-id>/validation/<VAL-ID>-<slug>/` 同时保存计划、实现代码、运行记录和结论。生产代码不得依赖验证代码。

验证项 `index.md` 是验证状态的唯一拥有者；具体运行状态由 `runs/<RUN-ID>/运行记录.md` 拥有。验证总入口只保存生成的状态投影。

### 开发与审核记录

交付记录保存一个交付单元怎样拆分全部代码、在隔离 worktree 中按依赖实现和集成、代码完成后怎样统一测试、继续工程改进，以及独立审核如何判断最终固定快照。它们是实现演化和审核证据，不会反向成为新的业务或设计权威。

```text
systems/<system-id>/delivery/
├── index.md
└── <delivery-id>/
    ├── index.md
    ├── plan/
    │   └── 开发任务图.md
    ├── stages/
    │   └── <stage-id>/
    │       └── 阶段记录.md
    ├── tasks/
    │   └── <TASK-ID>/
    │       ├── 任务进度.md
    │       └── 实现记录.md
    ├── feedback/design/
    ├── integration/
    │   └── 集成记录.md
    ├── testing/
    │   ├── feedback/
    │   │   └── <测试角度>.md
    │   └── 测试结论.md
    ├── improvement/
    │   └── <轮次>-<分析角度>.md
    └── review/
    │   ├── 实现符合性.md
    │   ├── 工程质量.md
    │   └── 审核结论.md
```

- `delivery/index.md`：列出交付单元及其任务图、阶段、统一代码快照、测试、工程改进和审核状态；
- `开发任务图.md`：开发规划 Agent 维护全部代码产物、任务边界、依赖、并行批次、worktree 基线和共享写入所有权；
- `tasks/*/任务进度.md`：只记录已派发任务的最近事件、代码产物和集成恢复点；
- `tasks/*/实现记录.md`：各开发 Agent 只记录自己的生产代码和提供给后续任务的实际产物，不包含测试结论；
- `stages/*/阶段记录.md`：记录共同起点、等价性、任务输出、唯一阶段 Commit 和用户门禁；
- `integration/集成记录.md`：保存任务 Commit、合并顺序和统一生产代码快照；
- `testing/feedback/`：多个独立测试 Agent在全部生产代码形成以后分别编写测试、运行并反馈，不修改生产代码；
- `测试结论.md`：新的测试结论 Agent 汇总失败责任、修正任务和复测范围；
- `improvement/`：测试结论允许继续以后，多个独立 Agent从单一角度形成分析或授权生产代码修改；至少记录重复与抽象分析；
- 两份核心审核：相互独立，只对记录的代码快照有效；
- `审核结论.md`：独立审核完成后由新的审核结论 Agent 汇总问题、处理责任、修正快照和复审状态，不替代原审核记录。

安全、性能、前端体验或平台专项审核按风险增加到 `review/`，不要求所有项目机械创建。

同批实施任务只有在任务图确认无代码依赖且写入范围不冲突时并行，并使用隔离 worktree。统一测试针对同一生产代码快照并行，工程分析针对同一测试后快照并行；任何阶段修改同一文件或相互依赖代码必须串行。代码变化时保留旧记录并让当前入口指向新快照；改变 API、Domain、事务、迁移、共享基础或大范围实现时重新执行全部受影响测试和两个核心审核。

### `work/`

完整任务 `index.md` 由当前专业 Agent 维护，保存任务目标、读写合同、候选、冲突、影响和恢复判断；`主控状态.md` 由主控与当前专业 Agent 交替写入，保存当前角色、交互、反馈、结果路径和下一步。两者都不替代业务或系统事实。

### 按需报告

报告是用户指定位置的派生阅读视图。验证和原型已经归入各系统 `validation/`；报告和验证都不能与 `business/`、`systems/*/design/` 竞争当前事实。

## 任务恢复点

每个任务包含两层恢复点：

```text
work/<work-id>/主控状态.md
→ 主控只读的短通信面

work/<work-id>/index.md
→ 专业 Agent 的完整任务恢复文档
```

完整任务固定使用 [任务恢复文档模板](project-document-contracts.md#任务恢复文档)。它保存任务定义、角色、读写合同、完整判断、已有产物和恢复动作，但当前交互、待处理反馈和处理结果只链接 `主控状态.md`，避免复制。

两份文件都不保存完整聊天、命令流水或原始推理。用户反馈被专业 Agent 吸收后，状态文件清空待处理区并链接更新后的事实。

判断状态只保存问题、证据、候选、结论、所有者、依赖、状态和影响。重要未决决定不因数量较多而省略；当前决策前沿是其中不依赖其他未决决定、可以立即处理的集合。答案写入正式事实文档后，从任务中的未决判断移除，并重新计算前沿，避免任务记录与事实文档竞争。

## 角色恢复合同

主控调用专业 Agent 前，把角色 reference、当前讨论对象和只属于该任务的待处理用户原话片段写入 `主控状态.md`。一条反馈涉及多个任务时，完整原话只保存在协调任务，由主控切分后分别派发；专业 Agent 不读取其他系统的反馈片段。专业 Agent 从状态文件进入完整任务，读取其中的权威文档、直接证据、允许写入路径、完成条件和全部未决决定。专业 Agent 完成后直接更新事实、完整任务和状态文件；主控不接收完整结果信封。

新专业 Agent 只依赖：

```text
角色 reference
+ 当前任务的主控状态
+ 当前任务恢复文档
+ 任务列出的权威文档和直接证据
```

主控调度消息只包含角色 reference 和主控状态路径，不能拥有项目文档中没有的关键上下文。详细进入和退出动作见 [project-document-contracts.md#角色进入与退出](project-document-contracts.md#角色进入与退出)。

## 状态与替代

事实或投影按需标明：

- `当前`：声明范围内的现行事实或可用投影；
- `待确认`：尚未被用户或证据接受的候选；
- `待重新判断`：来源变化后可能失效的事实；
- `待重新生成`：来源变化后的开发基线或派生报告；
- `已替代`：仅供历史追溯；
- `证据`：观察或实验结果。

同一个问题只能有一个当前事实源。详细文档和开发基线可以并存，但必须明确前者是事实、后者是派生阅读入口。

工程编码规范内部的规则还区分 `当前`、`候选` 和 `已替代`。只有整份规范已经用户确认且状态为 `当前`，其中的当前规则才能约束 Coding；候选规则不得暗中成为实现标准。规范版本变化只影响适用代码与工程审核，不自动使业务设计或开发基线失效。

对 Domain、架构、模块、API、核心接口内部编排、数据库设计和工程编码规范而言，“被用户接受”必须来自当前版本的明确审核确认，不能由 Agent 从用户沉默、代码现状、文档完成或旧版本确认推断。实质变更会使对应确认失效，并只影响依赖该变化的下游内容。

旧材料依靠版本控制或明确历史导航保存，不继续出现在当前主路径。

## 变化影响

改变事实时：

1. 在当前任务记录变化和证据；
2. 先识别依赖该事实的具体文档、基线、代码、测试、原型和报告；
3. 只把受影响部分标为 `待重新判断` 或 `待重新生成`；
4. 事实拥有者更新源文档；
5. 受影响角色重新读取并局部推导；
6. 开发基线或工程编码规范变化时标记受影响代码快照、工程改进和审核结论；
7. 按需重新运行 `prototype` 等系统验证，并重新生成开发基线、实现记录、工程改进、审核或用户报告。

不要因一项变化废弃全部下游，也不要让后写代码、报告或原型静默覆盖上游。

只要上述变化修改了业务、系统、工作、验证或交付状态拥有者，就执行：

```text
python3 <skill-root>/scripts/sync_indexes.py <repo-root> --write
```

目标是更新受控索引投影，不是让脚本决定哪些事实应该改变。

Coding 产生的 SQL、迁移、测试和运行证据可以证明已确认设计在实现现实中存在缺口。此时 Coding 保持建议权而非上游事实写入权：用设计反馈记录提出问题、证据、影响和具体修改意见，由事实拥有者判断并重新进入用户确认。受影响实现等待新基线，不受影响范围继续；既不能用代码静默覆盖设计，也不能用“忠于设计”拒绝反馈新证据。

多个任务修改同一事实时，主控保存竞争变化并让事实拥有者统一处理；同一文件不并行写入。

`vcddd/index.md` 说明项目现实边界、业务/系统/任务入口、当前开发基线、重要冲突以及不同问题的阅读方式。

`business/index.md` 只列用户建立的目标、状态和业务设计入口。

`systems/index.md` 只列系统、责任、状态和入口；系统 `index.md` 只列目的、责任、当前设计、开发输入、验证和交付入口。

目录名使用稳定 ASCII 标识，中文名称保存在标题和正文。验证、交付和工作目录不因状态改变而移动；上层索引由同步脚本从各状态拥有者生成。

各入口、主控状态和任务恢复文档的最小内容见 [project-document-contracts.md](project-document-contracts.md)。

用户没有要求报告时不创建报告目录或报告文件。简单项目可以不创建没有实际内容的可选目录，但已经进入合同的固定事实文档、验证项和交付记录不合并到其他层级。
