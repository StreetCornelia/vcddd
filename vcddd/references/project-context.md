## 目标

让没有历史对话的主控或专业 Agent 从少量入口恢复：

- 用户已经建立哪些阶段性业务目标；
- 当前有哪些任务；
- 当前负责角色和讨论对象；
- 哪些文档是事实源、派生基线、证据或按需报告；
- 尚未处理的用户反馈；
- 下一步应该调用谁并读取什么。

项目文档是持久记忆。聊天历史和 Agent 内部上下文都可以丢弃。

## 恢复顺序

1. 读取 `docs/vcddd/index.md`；
2. 读取 `docs/vcddd/work/index.md`；
3. 用户明确继续或请求只匹配一个任务时读取该任务；
4. 根据当前负责角色读取业务目标或系统入口；
5. 读取任务列出的直接权威文档；
6. 若存在待处理反馈，交给任务记录的角色；
7. 开发时读取当前开发基线和本切片直接来源。
8. 审核时只读取任务固定的代码快照、实现记录、开发基线、审核角色 reference 和允许证据路径。

不要默认读取全部业务、系统、任务、报告和验证历史。导航不能说明直接来源时先修复导航。

首次建档时只创建已经有真实内容的入口和任务，不预建空目标、系统或报告。

## 业务目标与任务

阶段性业务目标表示用户持续推动的业务结果：

- 可跨系统、任务和会话；
- 可与其他目标并行；
- 由用户决定建立、选择、合并、暂停、完成和取消；
- 不因一个任务或一次上线自动结束。

工作任务表示有独立目标和完成条件的实际工作：

- 可以服务多个目标；
- 一个目标可以由多个任务推进；
- 不按文档、Agent 或步骤机械拆任务；
- 用户直接要求梳理、设计、构建、修改或修复，且只匹配一个任务时可以继续；
- 没有匹配任务时主控透明建立中文任务；
- 多个选择会实质改变结果时才请用户选择。

只读解释、审查和状态报告不自动创建任务。

## 事实空间

### `business/`

业务设计 Agent 拥有。正式事实集中在：

```text
business/<阶段性业务目标>/业务设计.md
```

它说明业务目标与范围、业务层系统设计和业务线逻辑。

### `systems/`

系统与开发设计 Agent 拥有单个系统的设计事实：

```text
系统拆分.md
模块拆分.md
API设计.md
数据库设计.md
```

`开发基线.md` 是这些事实和相关业务设计的派生实现入口，不是新的语义源。

### 开发与审核记录

开发记录保存代码如何落实开发基线以及独立审核如何判断固定代码快照。它们是实现和审核证据，不会反向成为新的业务或设计权威。

```text
systems/<中文系统名>/开发记录/
├── index.md
└── <开发切片>/
    ├── 实现记录.md
    ├── 审核/
    │   ├── 业务与设计符合性.md
    │   ├── Domain与数据.md
    │   └── 工程质量.md
    └── 审核结论.md
```

- `开发记录/index.md`：列出切片、当前代码快照、实现范围、审核结论和入口；
- `实现记录.md`：开发 Agent 维护设计到代码和验证证据的映射；
- 三份核心审核：相互独立，只对记录的代码快照有效；
- `审核结论.md`：主控汇总问题、处理责任、修正快照和复审状态，不替代原审核记录。

安全、性能、前端体验或平台专项审核按风险增加到 `审核/`，不要求所有项目机械创建。

代码变化时保留旧记录的 Git 历史，并让当前入口指向新快照的实现和复审结果。局部修改只影响对应审核；改变 API、Domain、事务、迁移或大范围实现时三个核心审核都需要重新读取。

### `work/`

主控拥有。保存任务目标、交互状态、当前角色、候选、冲突、影响和下一步，不替代业务或系统事实。

### 原型、验证与按需报告

- 原型是发现或呈现投影；
- 验证保存可复现证据；
- 报告是用户指定位置的派生阅读视图。

三者都不能和 `business/`、`systems/` 竞争当前事实。

## 任务恢复点

每个 `work/<中文任务名>/index.md` 至少保存：

```text
任务状态：
任务目标：
完成条件：
服务的业务目标与系统：

当前负责角色：
交互状态：等待用户 | 等待 Agent | 无等待
当前讨论对象：
当前权威文档：

已经形成的认识或实现：
当前核心判断及答案：
已触发的条件判断：
补充判断：
尚未确定或存在冲突的判断：
全部重要未决决定及所有者：
决定之间的依赖关系：
当前决策前沿：
正在比较的候选或冲突：
本次准备补充或替换的信息：
可能受影响的其他文档：

最新用户交互包：
尚未处理的用户反馈：
反馈处理结果：

当前工作位置：
当前开发基线与代码快照：
实现记录与审核状态：
恢复动作：
下一步：
```

只保存恢复所需语义，不保存完整聊天、命令流水或原始推理。用户反馈被专业 Agent 吸收后，清空待处理区并链接更新后的事实。

判断状态只保存问题、证据、候选、结论、所有者、依赖、状态和影响。重要未决决定不因数量较多而省略；当前决策前沿是其中不依赖其他未决决定、可以立即处理的集合。答案写入正式事实文档后，从任务中的未决判断移除，并重新计算前沿，避免任务记录与事实文档竞争。

## 状态与替代

事实或投影按需标明：

- `当前`：声明范围内的现行事实或可用投影；
- `待确认`：尚未被用户或证据接受的候选；
- `待重新判断`：来源变化后可能失效的事实；
- `待重新生成`：来源变化后的开发基线或派生报告；
- `已替代`：仅供历史追溯；
- `证据`：观察或实验结果。

同一个问题只能有一个当前事实源。详细文档和开发基线可以并存，但必须明确前者是事实、后者是派生阅读入口。

旧材料依靠版本控制或明确历史导航保存，不继续出现在当前主路径。

## 变化影响

改变事实时：

1. 在当前任务记录变化和证据；
2. 先识别依赖该事实的具体文档、基线、代码、测试、原型和报告；
3. 只把受影响部分标为 `待重新判断` 或 `待重新生成`；
4. 事实拥有者更新源文档；
5. 受影响角色重新读取并局部推导；
6. 开发基线变化时标记受影响代码快照和审核结论；
7. 按需重新生成原型、开发基线、实现记录、审核或用户报告。

不要因一项变化废弃全部下游，也不要让后写代码、报告或原型静默覆盖上游。

多个任务修改同一事实时，主控保存竞争变化并让事实拥有者统一处理；同一文件不并行写入。

## 目录合同

```text
<目标仓库>/
├── docs/vcddd/
│   ├── index.md
│   ├── business/
│   │   ├── index.md
│   │   └── <阶段性业务目标>/
│   │       └── 业务设计.md
│   ├── systems/
│   │   ├── index.md
│   │   └── <中文系统名>/
│   │       ├── index.md
│   │       ├── 系统拆分.md
│   │       ├── 模块拆分.md
│   │       ├── API设计.md
│   │       ├── 数据库设计.md
│   │       ├── 开发基线.md
│   │       └── 开发记录/
│   │           ├── index.md
│   │           └── <开发切片>/
│   │               ├── 实现记录.md
│   │               ├── 审核/
│   │               │   ├── 业务与设计符合性.md
│   │               │   ├── Domain与数据.md
│   │               │   └── 工程质量.md
│   │               └── 审核结论.md
│   └── work/
│       ├── index.md
│       └── <中文任务名>/index.md
├── <用户指定或项目约定的原型位置>/
└── <用户指定的按需报告位置>
```

`docs/vcddd/index.md` 说明项目现实边界、业务/系统/任务入口、当前开发基线、重要冲突以及不同问题的阅读方式。

`business/index.md` 只列用户建立的目标、状态和业务设计入口。

`systems/index.md` 只列系统、责任、状态和入口；系统 `index.md` 只列目的、责任、当前设计文档、开发基线和开发记录入口。

用户没有要求报告时不创建报告目录或报告文件。简单项目仍保留固定事实责任，但可以在用户明确决定后合并物理文件，并更新验证约定。
