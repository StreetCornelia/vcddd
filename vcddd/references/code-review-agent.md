## 共同规则

审核 Agent 对一个固定代码快照形成独立审核事实，不修改代码、设计文档或其他审核记录。

所有核心审核读取相同的：

- 代码 Commit 或不可变补丁；
- 当前开发基线及本切片直接来源；
- 本切片 `实现记录.md`；
- 仓库规范、测试和可复现运行入口。

审核时不得读取其他审核 Agent 的结论。主控在全部独立审核完成后才汇总。

审核不是泛泛寻找“可以更好”的地方。先回答本审核角色的核心判断；只有风险事实触发时再展开条件问题。

## 审核输入

开始前确认：

```text
审核角色：
代码快照：
开发基线：
实现切片：
允许读取的代码与证据路径：
明确不在范围内的内容：
```

代码快照、基线或实现范围无法唯一确定时返回主控，不审核移动中的目标。

## 业务与设计符合性审核

结果使用者需要判断：代码是否实现了声明范围内的业务，而不是只通过了技术测试。

核心判断：

- 每条声明实现的业务线是否产生基线要求的结果；
- 正常、拒绝、冲突、重复、取消、失败和恢复是否与设计一致；
- API 的入口、字段、错误和可观察行为是否符合契约；
- 模块和 Domain 协作是否遗漏或篡改业务决定；
- 实现记录声明的覆盖与真实代码、测试是否一致；
- 是否存在代码新增但上游没有定义的业务行为。

优先使用业务场景到 API、Domain、代码和测试的纵向追踪。只在事实触发时深入权限、金额、批量、外部系统或兼容行为。

## Domain 与数据审核

结果使用者需要判断：业务状态能否在全部生命周期和异常路径中被正确保存。

核心判断：

- Domain 边界、对象所有权和依赖方向是否保持；
- 生命周期、状态转换和不变量是否由代码真实执行；
- 命令、查询和应用编排是否绕过领域规则；
- 表、字段、约束和历史记录是否承载设计中的领域事实；
- 事务、锁、CAS、幂等和恢复是否保持业务正确；
- 迁移、兼容和回退是否会破坏已有数据；
- 外部系统事实是否被错误复制或取得所有权。

并发、迁移、金额精度、历史审计、删除和外部一致性只在相关事实存在时重点展开。

## 工程质量审核

结果使用者需要判断：实现是否能可靠运行、验证和继续演化。

核心判断：

- 模块边界、依赖方向和接口是否清楚且可维护；
- 错误处理、资源释放、超时、取消和重试是否可靠；
- 测试是否覆盖关键行为和风险，而非只覆盖代码路径；
- 日志、指标和追踪是否足以观察重要结果与故障；
- 配置、启动、升级和故障恢复是否可操作；
- 是否存在明确的安全、性能或容量风险；
- 复杂度是否服务当前业务，而不是无依据的未来设计。

安全、性能、容量和平台专项可以由主控按风险增加独立审核，不能替代三个核心审核。

## 问题分级与记录

只记录有证据、可定位并具有实际影响的问题：

```text
问题编号：
级别：阻断 | 重要 | 一般 | 建议
对应核心判断或风险触发器：
代码与运行证据：
违反或未覆盖的业务、设计或工程要求：
影响：
要求达到的修正结果：
需要修改代码还是返回上游设计：
```

- `阻断`：会产生错误业务结果、破坏数据、安全或使关键验证不可信；
- `重要`：当前范围存在明确缺陷，但不一定立即造成不可恢复结果；
- `一般`：局部正确性或维护问题；
- `建议`：不改变当前正确性的改进，不得阻断完成。

不要用偏好冒充缺陷，也不要只给具体补丁而不说明要求达到的结果。

每份审核记录固定包含：

```text
审核对象：
依据的开发基线：
审核范围：
未覆盖范围：
审核结论：通过 | 有条件通过 | 不通过

核心判断结果：
已触发的条件判断：
发现的问题：
验证证据：
```

## 复审

审核结论只对记录的代码快照有效。

- 局部修复：提出问题的审核角色复审受影响范围；
- API、Domain、事务、数据迁移或大范围重写：重新执行三个核心审核；
- 设计事实变化：先由事实拥有者更新设计和开发基线，再形成新代码快照；
- 问题是否关闭由相应审核角色确认，开发 Agent 不能自行宣布审核问题已经解决。

复审记录引用原问题编号、修正 Commit、重新执行的证据和关闭或继续存在的结论。
