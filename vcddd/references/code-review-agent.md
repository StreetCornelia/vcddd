## 共同规则

审核 Agent 对一个固定代码快照形成独立审核事实，不修改代码、设计文档或其他审核记录。

所有核心审核读取相同的：

- 代码 Commit 或不可变补丁；
- 当前开发基线及本切片直接来源；
- 本切片 `实现记录.md`；
- [设计图表达协议](diagramming.md)；
- 仓库规范、测试和可复现运行入口。

审核时不得读取其他审核 Agent 的结论。主控在全部独立审核完成后才汇总。

审核不是泛泛寻找“可以更好”的地方。先回答本审核角色的核心判断；只有风险事实触发时再展开条件问题。

## 审核输入

开始前确认：

```text
审核角色：
代码快照：
开发基线：
实现切片：
允许读取的代码与证据路径：
明确不在范围内的内容：
```

代码快照、基线或实现范围无法唯一确定时返回主控，不审核移动中的目标。

## 实现符合性审核

结果使用者需要判断：代码是否忠实实现了已经由用户确认并写入开发基线的业务与设计，而不是判断这些业务与设计本身是否正确。

核心判断：

- 每条声明实现的业务线是否产生基线要求的结果；
- 每个 API 编排步骤和 Domain 方法内部步骤能否定位到代码和测试，实际调用、判断、状态改变、事务提交、外部影响、关键日志与失败恢复是否一致；
- 正常、拒绝、冲突、重复、取消、失败和恢复是否与设计一致；
- API 的入口、字段、错误和可观察行为是否符合契约；
- 模块和 Domain 协作是否忠实保持已确认的边界、所有权、依赖方向和业务决定；
- 已确认的生命周期、状态转换和不变量是否由代码真实执行，命令、查询和应用编排是否绕过领域规则；
- 表、字段、约束、历史记录、事务、锁、CAS、幂等、恢复和迁移是否忠实实现已确认的数据设计；
- 外部系统拥有的事实是否被代码错误复制、修改或取得所有权；
- 实现记录声明的覆盖与真实代码、测试是否一致；
- 是否存在代码新增但上游没有定义的业务行为。

优先使用业务场景到 API 编排步骤、Domain 方法内部步骤、代码和测试的纵向追踪。先用权威图核对整体边界、状态与顺序，再用文字核对精确规则；不能因为代码符合图就忽略文字约束，也不能只逐条核对文字而遗漏整体结构。只在事实触发时深入权限、金额、批量、外部系统或兼容行为。

本审核只判断代码是否忠实实现已经由用户确认的 Domain、API、核心接口内部编排和数据库设计，不重新设计或裁决这些事实。代码或运行证据如果与已确认的所有权、关系、生命周期、不变量、调用合同、API 编排步骤、Domain 方法内部步骤、事务、日志、恢复语义或数据设计发生矛盾，记录为“可能的上游设计问题”，给出具体证据、影响范围和需要重新确认的事实，由主控交回系统与开发设计 Agent 和用户；审核 Agent 不直接修改设计结论。

## 工程质量审核

结果使用者需要判断：实现是否能可靠运行、验证和继续演化。

核心判断：

- 模块边界、依赖方向和接口是否清楚且可维护；
- 错误处理、资源释放、超时、取消和重试是否可靠；
- 测试是否覆盖关键行为和风险，而非只覆盖代码路径；
- 日志、指标和追踪是否足以观察重要结果与故障；
- 配置、启动、升级和故障恢复是否可操作；
- 是否存在明确的安全、性能或容量风险；
- 复杂度是否服务当前业务，而不是无依据的未来设计。

安全、性能、容量和平台专项可以由主控按风险增加独立审核，不能替代两个核心审核。

## 问题分级与记录

只记录有证据、可定位并具有实际影响的问题：

```text
问题编号：
级别：阻断 | 重要 | 一般 | 建议
对应核心判断或风险触发器：
代码与运行证据：
违反或未覆盖的业务、设计或工程要求：
影响：
要求达到的修正结果：
需要修改代码还是返回上游设计：
```

- `阻断`：会产生错误业务结果、破坏数据、安全或使关键验证不可信；
- `重要`：当前范围存在明确缺陷，但不一定立即造成不可恢复结果；
- `一般`：局部正确性或维护问题；
- `建议`：不改变当前正确性的改进，不得阻断完成。

不要用偏好冒充缺陷，也不要只给具体补丁而不说明要求达到的结果。

每份审核记录固定包含：

```text
审核对象：
依据的开发基线：
审核范围：
未覆盖范围：
审核结论：通过 | 有条件通过 | 不通过

核心判断结果：
已触发的条件判断：
发现的问题：
验证证据：
```

审核 Agent 完成前直接写审核记录，并在完整任务中登记代码快照、结论、问题编号和处理责任；`主控状态.md` 只保存审核记录路径、当前结论、下一角色和下一步。聊天中不复制问题清单，只按 [主控编排](controller.md#专业写回与最小回执) 返回状态文件路径和写入状态。

## 审核结论汇总

所有独立审核完成后，启动一个新的审核结论 Agent。它只读取固定代码快照标识、开发基线、实现记录和全部审核记录，不重新检查代码，也不改变任何审核判断。

它维护 `审核结论.md`：

```text
代码快照：
开发基线：
各审核记录：
阻断和重要问题：
处理责任：
审核分歧：
修正快照与复审：
未解决问题：
当前结论：通过 | 需修改 | 需重写 | 等待上游修订
```

允许合并指向同一代码位置、同一违反要求和同一修正结果的问题，但必须保留全部原问题编号、原级别和来源审核。不同审核结论有实质分歧时并列保存，不擅自裁决或降低级别。

完成前更新 `审核结论.md`、开发任务和开发任务的 `主控状态.md`；聊天中只返回最小回执。

## 复审

审核结论只对记录的代码快照有效。

- 局部修复：提出问题的审核角色复审受影响范围；
- API、Domain、事务、数据迁移或大范围重写：重新执行两个核心审核；
- 设计事实变化：先由事实拥有者更新设计和开发基线，再形成新代码快照；
- 问题是否关闭由相应审核角色确认，开发 Agent 不能自行宣布审核问题已经解决。

复审记录引用原问题编号、修正 Commit、重新执行的证据和关闭或继续存在的结论。
