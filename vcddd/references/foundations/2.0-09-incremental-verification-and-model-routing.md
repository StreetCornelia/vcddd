# VCDDD 2.0 阶段性成果（九）：增量验证、阶段审查与模型路由

> 状态：已进入 VCDDD 2.0 Skill 合同
>
> 日期：2026-07-31

## 1. 问题

把测试和审核全部放在生产代码完成以后，会形成三个累积风险：

1. 一个任务的局部错误要到多个后续任务已经依赖它以后才暴露；
2. 跨任务接线、启动、迁移和环境问题要到最终集成才第一次运行；
3. 最终审核同时面对大量局部缺陷和系统性问题，修正范围难以控制。

“代码已经提交”也不能回答产物是否能构建、启动、运行或产生用户需要的结果。文件存在、Commit 存在和 Agent 完成通知都不是可运行证据。

另一个独立问题是模型继承。主会话为了业务、Domain 和架构判断可能使用最高级模型，但边界清楚的编码、测试、固定记录和局部审查不需要同等推理成本。如果主控省略模型参数，所有子任务继承主会话，会让成本与任务认知难度失去关系。

## 2. 三级反馈闭环

### 2.1 任务级

每个实施任务提交固定 Commit 后立即并行进行：

- 任务验证：按任务图声明的验证合同执行构建、静态检查、启动、关键路径和聚焦测试；
- 任务审查：核对当前任务相对开发基线、工程规范、实施上下文和授权范围的实现符合性与局部工程质量。

两个角色都独立于实施 Agent，也互不读取结论。任何一项失败都返回原任务或上游事实拥有者；两者通过后才允许合并和解除下游依赖。

### 2.2 阶段级

阶段任务汇合以后固定阶段 Commit，再并行进行：

- 阶段运行验证：累计相关测试，真实构建、启动、就绪检查并执行关键路径；
- 阶段审查：检查跨任务接线、共享写入、依赖装配、迁移、错误传播和阶段范围。

两者通过后阶段才进入用户确认或派发依赖阶段。阶段必须声明最低和实际达到的运行层级：

```text
可构建 → 可启动 → 可运行 → 可用
```

第一处承诺用户可观察结果的阶段和最终阶段必须达到“可用”。不能用编译成功替代用户或消费者能够取得结果。

### 2.3 最终级

全部阶段闭合以后仍保留：

- 跨阶段统一测试；
- 工程改进；
- 实现符合性和工程质量最终审核；
- 风险触发的安全、性能、容量或平台专项。

最终流程不再负责第一次发现普通局部错误，而是补齐单任务和单阶段无法发现的组合风险、回归和整体质量问题。

## 3. 证据分层

不同层级的通过不能互相替代：

| 层级 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 任务验证 | 固定任务 Commit 达到本任务最低运行层级 | 阶段接线或完整业务路线可用 |
| 任务审查 | 当前任务忠实且局部工程质量可接受 | 组合运行正确 |
| 阶段运行验证 | 阶段 Commit 能在声明环境运行到指定层级 | 跨阶段系统风险已经覆盖 |
| 阶段审查 | 任务汇合、共享写入和阶段边界成立 | 最终全系统质量 |
| 统一测试与最终审核 | 最终固定快照的组合风险和整体符合性 | 后续变化永远不会引入问题 |

所有记录绑定不可变 Commit、实际环境、命令、退出结果、观察结果和未覆盖范围。

## 4. 模型能力档位

模型按任务的认知难度选择，而不是按主会话继承：

| 档位 | 典型工作 |
| --- | --- |
| `deep` | 业务发现、Domain、总体架构、跨系统与不可逆关键判断 |
| `planning` | API、内部编排、数据库、工程规范、任务图和复杂根因 |
| `review` | 单任务、阶段和最终代码审查 |
| `execution` | 边界明确的编码、测试、修复、原型和验证运行 |
| `mechanical` | 索引、结构检查、状态回写和固定投影 |

主控选择满足档位的最低成本模型并显式设置模型与推理强度。代码量大、文件多或审查条目多不自动升级；跨事实所有权、重大歧义、不可逆风险或连续有证据的能力不足才升级。

## 5. 配置属于目标项目

Skill 只定义发现和校验协议，不保存具体模型列表。每个目标项目在自己的仓库维护：

```text
vcddd/config/agent-models.json
```

首次进入任何专业阶段前，主控检查本机 Codex 与 Claude Code，对当前可访问的环境分别真实发现模型、推理强度和限制，形成五档映射并让用户确认；不可访问的环境只记录原因，不虚构模型。任何阶段发现配置缺失、当前环境段缺失、模型失效或映射未确认时，先回到模型配置，不静默继承主会话。

Codex 使用当前主机创建任务/子 Agent 接口公开的模型元数据；Claude Code 使用当前账号 `/model` 选择器确认真实可见模型，并用 CLI 帮助核对 `--model`、`--effort` 和 fallback 参数。文档示例和模型家族名称不能替代本机账号的可用性证据。

## 6. 可机械校验的门槛

校验器增加三个确定性门槛：

- 基础检查拒绝缺失或未确认的项目模型配置；
- `--task-check` 检查任务实现、验证、审查的快照、层级、结论和 Agent 独立性；
- `--stage-check` 检查阶段 Commit、运行验证、阶段审查和继续条件；
- 最终 `--review-batch` 要求所有任务和阶段增量记录已经闭合，并至少有一个阶段达到“可用”。

脚本仍不判断业务、测试或审查结论本身是否正确。它只保证这些判断在正确时间、由独立角色、针对固定快照并以可恢复形式存在。
