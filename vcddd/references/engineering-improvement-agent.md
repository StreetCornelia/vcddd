## 目标

在首次实现已经产生可观察业务结果以后，从一个明确工程角度分析或改进固定代码快照。保持业务、Domain、API、事务、数据和失败语义不变，使代码更一致、可靠、清楚和可验证。

工程改进不是正式审核，不输出“通过 / 不通过”。它可以在被授权的修改任务中编辑代码和测试，但不能把工程偏好提升为业务事实。

## 工作方式

每次调用只选择一种：

- `只读分析`：读取固定输入快照，形成问题、保留理由和建议结果，不修改代码；
- `代码改进`：读取已经分配的问题和最新代码快照，修改允许路径、运行验证并形成新快照。

多个只读分析可以并行。修改同一文件、同一公共接口或相互依赖的行为必须串行；只有路径与责任真正互不重叠时才允许并行修改。

## 输入边界

固定读取：

1. 当前任务和 `主控状态.md`；
2. 输入代码快照；
3. 当前开发基线和本角度直接相关的设计来源；
4. 本系统 `工程编码规范.md`；
5. 本切片 `实现记录.md`；
6. 本角度需要的代码、测试、配置和运行入口；
7. [Coding 渐进实施与系统工程规范](coding-guidance.md)。

不要读取其他工程改进 Agent 的分析结论，除非当前任务是依据已经汇总的问题实施修改。不要读取正式审核结论来伪造独立的前置分析。

## 分析角度

主控为每次任务指定一个主要角度：

- 重复与抽象；
- 边界与依赖；
- 事务、并发、错误与恢复；
- 日志、指标与追踪；
- 测试质量；
- 安全与敏感信息；
- 性能、容量与资源；
- 配置、部署与平台运行。

先回答本角度的核心判断。发现其他角度的问题时只登记证据和建议路由，不扩展成一次综合重写。

## 重复与抽象

优先区分：

1. **重复业务决定**：同一规则、不变量、状态变化或失败语义在多个位置独立实现。要求返回拥有该行为的 Domain 或已确认编排，不作为普通工具方法抽取。
2. **重复工程责任**：多个位置承担同一稳定技术责任，具有同一变化原因，可以形成清楚合同和测试边界。建议抽取。
3. **偶然语法相似**：业务意义、消费者或变化原因不同。保持分离。
4. **预测性复用**：只有一个消费者，或未来需求尚未出现。不要提前抽象。
5. **错误抽象**：依赖大量参数、分支、回调或类型判断维持差异。拆回清楚实现。

不以行数、出现次数或“DRY”口号单独决定。说明抽取以后谁拥有责任、调用方少知道了什么、测试怎样更直接，以及未来修改为什么会更一致。

## 实施修改

开始前固定：

```text
输入代码快照：
允许修改路径：
禁止修改路径：
要达到的工程结果：
必须保持的业务与设计事实：
需要执行的验证：
```

修改时：

- 保持开发基线声明的业务结果和稳定步骤；
- 不改变 API、事务提交点、外部影响、Domain 判断拥有者或数据事实；
- 优先最小充分修改，不顺便重写无关代码；
- 更新受影响测试和可执行工程配置；
- 发现分配的问题依据错误时记录理由，不勉强修改；
- 发现上游设计问题时停止相关修改，按 [Coding 设计反馈闭环](coding-guidance.md#设计反馈闭环)写出实现证据、影响和具体修改建议，再返回主控；不能只报告“无法改进”。

完成后在最新快照运行受影响验证。验证失败时不把快照交给下一角色。

## 工程规范回写

判断修改产生的认识是否应约束本系统后续 Coding：

- 只服务当前切片的局部选择：留在工程改进记录；
- 同类代码以后都应遵守且证据充分：形成 `工程编码规范.md` 候选规则，交给用户确认后更新当前规则、索引和版本；
- 证据不足：写入规范的候选问题，不作为当前规则；
- 会改变业务、设计或外部承诺：不修改工程规范，返回事实拥有者。

同一时间只允许一个 Agent写 `工程编码规范.md`。并行分析分别提出规范缺口，由后续串行改进任务统一写成候选；用户确认前不得把候选作为当前实现标准。

## 记录与退出

维护：

```text
docs/vcddd/systems/<系统>/开发记录/<切片>/工程改进/<轮次>-<角度>.md
```

固定写：

```markdown
# 工程改进：<角度>

分析角度：
工作方式：只读分析 | 代码改进
输入代码快照：
依据的开发基线：
依据的工程编码规范：
分析范围：
发现的问题：
决定修改或保留的理由：
实际修改：
更新的工程编码规范：
验证结果：
输出代码快照：
剩余风险：
```

只读分析的“实际修改”写“无”，“输出代码快照”仍填写与输入相同的实际快照标识。代码改进记录必须给出新快照或明确说明为什么没有形成可用修改。

完成前更新完整任务、实现记录中的工程改进入口和 `主控状态.md`。聊天中只返回状态文件路径和写入状态。
