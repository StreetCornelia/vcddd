## 原则

用户始终在主会话交互，但专业内容由当前专业 Agent 负责。主控不把专业问题重新概括成模糊摘要，也不替专业 Agent解释用户反馈。

用户需要参与：

- 真实目标、利益和业务意图；
- 材料无法证明的组织现实；
- 多个合理解释之间的选择；
- 高影响承诺、风险接受和价值取舍；
- 原型和实现是否表达了预期结果。

进入面向开发的设计后，用户还需要审核完整 Domain、API、核心接口内部编排和数据库 / SQL 设计。这不是让用户替 Agent 做设计，也不是启动另一个 AI 审核 Agent：系统设计 Agent 先给出完整、连贯、可执行的推荐方案，用户再判断它是否正确表达业务、是否可以成为开发依据。

Agent 先调查和形成完整草案，再集中请用户纠偏；不能把调查、归纳或专业设计推回给用户。

Domain 之后的设计交互遵守 [设计图表达协议](diagramming.md)。交互包必须给出完整文档路径，并指出本轮需要查看的图、每张图回答的问题和仍需结合阅读的补充说明。图与正文冲突、图仍是旧版本或图无法表达当前结论时，不能请求用户确认。

面向用户的内容遵守 [业务语言与建模边界](language-and-modeling.md)：使用用户原话和普通话，只把元关键词当作结构。Domain 交互可以标注 DDD 分类，但每个术语同时给出具体业务含义；不能要求用户先理解行业黑话才能回答。

专业 Agent 必须提交全部会改变业务结果、责任、生命周期、风险承诺或开发正确性的未决决定，不设数量上限。先排除本角色应自行解决的专业判断，只在多个问题确实受同一个上位决定支配时归并。

交互包区分“当前决策前沿”和“等待前置决定”：前沿中的决定全部展示并请求用户回答；依赖其他决定的事项也保持可见，但说明依赖和暂不回答的原因。数量较多时按业务对象或影响范围分组，并给出建议回答顺序，不能截断、隐藏或用任意数量取舍。

## 专业 Agent 生成交互

专业 Agent 把可直接展示的交互包写入当前任务的 `主控状态.md`：

```text
交互类型：展示草案 | 请求纠偏 | 请求决定 | 报告冲突

面向用户的内容：
<完整文本>

为什么需要用户参与：
<无法从证据判断的真实意图或选择>

用户需要回答：
<当前决策前沿的全部最少充分信息>

其他重要未决决定：
<等待哪些前置决定、会影响什么；没有则写“无”>

收到反馈后：
<重新调用哪个角色、读取哪些路径>
```

不要让主控根据专业报告自行发明问题。

## Domain 业务主体确认

系统设计进入 Domain 分析时，先把业务叙述恢复成“什么做了什么，产生了什么”，并由用户明确确认：

- 业务中客观存在的核心事物是什么；
- 每个核心事物拥有什么属性、状态和其他事物；
- 事物之间是什么关系，关系由谁拥有和约束；
- 每个行为由哪个核心事物完成；
- 行为改变和影响了谁，产生什么结果；
- 外部系统事实与本地业务解释怎样区分。

专业 Agent 先调查证据并给出完整推荐认识，主控原样展示。用户确认的是业务世界中的主体、所有权、关系和行为归属，不是 DDD 术语。用户否定任何内容时，由同一角色重新分析全部直接受影响内容后再次确认。

涉及多个系统时，每个系统分别确认。交互包必须明确写出当前系统名称，并把共通事物在本系统中的意义、本地拥有事实和外部权威事实分开；不能用“这个概念已经在另一个系统确认”代替本系统确认。

## Domain 设计确认

业务主体确认后，系统设计 Agent 围绕每个核心事物形成充血、自洽的 Domain，继续完成内部 DDD 设计，再由用户审核完整结果：

- 这个 Domain 在现实业务中是什么核心事物；
- 它自己维护哪些属性、状态和关系；
- 它拥有和执行哪些行为；
- 每个行为依据什么事实和规则作出判断；
- 行为会改变自己什么、影响其他什么并产生什么结果；
- 哪些行为明确不属于它；
- 多个 Domain 参与时，是否存在真实的上层业务之“事”拥有整段过程，还是仅为应用协作。
- Domain 内有哪些实体、值对象和关系对象，它们为什么属于该 Domain；
- 哪些对象必须在同一聚合中维护哪些不变量；
- Domain 的完整生命周期、失败语义以及跨 Domain 合同。

Agent 先用普通话讲清每个完整业务主体，再补充 DDD 分类和实现含义。审核包同时提供 Domain 总览、必要类图和状态图，让用户核对拥有关系、聚合边界和生命周期；文字继续说明不变量、拒绝与异常语义。用户既审核 Domain 是否正确表达业务世界，也审核实体、聚合、不变量和生命周期是否足以指导开发；不需要用户从空白开始提出这些设计。确认前不能把候选 Domain 扩散到模块、API、数据库和开发基线。任何内部 DDD 内容或权威图在确认后发生实质变化，都要重新展示受影响的完整 Domain 并再次确认。

## Domain 核心命名确认

完成 DDD 分类后、用这些名称生成 API 和数据库之前，主控先按 [语言验证 Agent](language-validation-agent.md) 启动一次隔离盲测，把结果交回系统设计 Agent 处理。之后再把 Domain、领域行为、核心对象、关系和业务表的建议名称交给用户确认业务含义。每项先单独展示名称和盲测理解，再展示用户原话或来源、普通话定义、名称所在层次、为什么当前需要单独存在、DDD 分类以及可能造成的误解。

不同层次使用不同判断：Domain 名称应以稳定名词准确指向核心事物，不必承载所有行为；行为名称应清楚表达动作和结果；页面文案在实际页面语境中无歧义；表名说明保存的事实和用途。未确认名称标为临时名称，不能扩散到 API、表和代码。用户修改名称或含义时，重新检查受影响的业务主体、关系、行为、Domain、API 和数据，不做孤立文字替换。

## API 设计审核

系统设计 Agent 完整写出本系统 `API设计.md` 后，将其标记为：

```text
API 设计确认：待确认
API 设计确认依据：无
```

交给用户的审核内容必须足以独立判断：

- 每条业务线和用例由哪些 API 承载；
- 每个独立 API 是否声明系统内唯一且稳定的 `API 标识`，供内部编排、开发和审核持续引用；
- 调用方、权限、方法、路径、版本和业务标识；
- 请求与响应字段的业务含义，而不只是类型；
- 正常、拒绝、冲突、重复、结果未知和查询确认；
- 幂等、并发、事务、超时、取消、重试和流式行为；
- 跨系统调用中的能力假设、成功证明、部分完成、补偿和对账；
- API 与模块、Domain 行为和测试场景的对应。

流式、异步、回调、查询确认或跨系统结果未知等复杂边界必须同时展示调用方可观察的时序图；普通同步接口不为形式完整机械画图。

Agent 负责给出完整推荐合同并解释取舍，不能只把字段清单或一串零散问题丢给用户。用户可以整体确认，也可以纠正任意部分；收到纠正后，Agent 重新检查并展示所有直接受影响的合同。只有用户明确确认当前版本后，Agent 才记录 `API 设计确认：已确认` 和可恢复的确认依据。

默认先完成本系统 API 审核，再开始本系统核心接口内部编排。用户明确要求并行准备时，可以形成标记为候选的编排或数据库草案；另一个系统也可以依据清楚标记的“外部能力需求 / 待确认合同”继续自己的候选设计，但任何 Agent 都不能把未确认 API 当成已经生效的跨系统合同或当前开发事实。

## 核心接口内部编排审核

API 确认后，系统设计 Agent 完整写出本系统 `核心接口内部编排.md`，并将其标记为：

```text
核心接口内部编排确认：待确认
核心接口内部编排确认依据：无
```

交互包使用[核心接口内部编排固定模板](internal-orchestration-template.md)的同一 API 顺序。先展示接口目录，再逐个接口展示正文，不再把内容重新压缩成脱离文档的若干确认结论。

每个 API 的审核入口固定为：

1. `业务结果`：调用者意图、成功后谁发生什么变化和明确非责任；
2. `主流程`：连续步骤中谁做什么、得到什么结果以及下一步；
3. `分支与失败`：每个拒绝、冲突、重复、取消、超时、部分完成和结果未知发生在哪一步；
4. `事务与外部影响`：本地原子范围、提交点、不可逆动作顺序、成功证明和恢复；
5. `Domain 调用`：每一步调用的已确认 Domain 行为、输入、领域结果和权威规则链接；
6. `业务证据与验证`：必要日志、关联标识和必须证明的业务场景。

简单查询或直接映射也使用相同结构，对不适用事项写明原因。一个章节只能对应一个 API，不能把多个接口合成“创建类”“修改类”或其他接口组；用户也不应从宏观业务流程、组件图、Domain 总览或另一套 Domain 方法目录自行拼装某个接口。

候选交互前先运行 `--orchestration-system <系统>`。结构验证未通过时保持 `待确认`，不能把不完整摘要交给用户代替正文。图只补充对应 API 的主流程；默认最多一张时序图，分支或恢复仍难以理解时再增加一张活动图。

Agent 负责提出完整编排，不把技术顺序选择推给用户。用户可以整体确认，也可以纠正任意步骤或关系；收到纠正后，Agent 重新检查所有直接受影响的 API、Domain 调用、事务、外部影响、业务证据和失败语义。Domain 行为内部规则本身有缺口时返回 `系统拆分.md` 修订和重新确认。只有用户明确确认当前版本后，Agent 才记录 `核心接口内部编排确认：已确认` 和可恢复的确认依据。

确认后才默认开始数据库设计，因为数据库要承载编排中已确定的状态、事务、操作证据和恢复需要。用户明确要求并行准备时可以形成数据库候选，但不能让候选表结构反向改写编排，也不能跳过编排审核。

## 数据库设计审核

系统设计 Agent 按[数据库设计固定模板](database-design-template.md)完整写出本系统 `数据库设计.md`，将其标记为：

```text
数据库设计确认：待确认
数据库设计确认依据：无
```

候选交互前先运行 `--database-system <系统>`。结构验证未通过时保持 `待确认`，不能把字段清单、ER 图、DDL 或一段摘要交给用户代替正文。交给用户的审核内容必须足以独立判断：

- 整个系统需要保存哪些事实、为什么需要持久化、由谁拥有以及由哪张表承载；
- 每张表为什么存在、一行记录表示什么、为什么需要独立成表，以及数据库表注释原文；
- Domain 信息与非 Domain 信息为何需要保存、由谁写入和用于什么判断；
- 每个字段为什么存在、保存的事实、事实来源、类型、空值、默认值、范围、变化时机、敏感性和数据库注释原文；
- 身份、主键、业务唯一键、外键、版本、关系和删除语义；
- 状态、不变量、组合约束、数据库与上层责任、索引及其真实查询依据；
- 事务、锁、CAS、并发、回滚、恢复和跨系统结果未知；
- 数据兼容、迁移、回填、清理和回退；
- 设计与 Domain、API、已确认核心接口内部编排和当前业务场景的对应。

关系数据同时展示 ER 图；多种存储参与时展示存储边界图。图负责关系全景，逐表固定章节负责可审核事实。`数据库设计.md` 不包含 SQL 代码块、DDL、ORM 实体或完整迁移；这些由 Coding 在设计确认后落地并验证。

Agent 负责提出完整推荐数据设计，按“数据承载全景 → 表目录 → 逐表意义和字段 → 跨表事务与安全 → 实现交接”的顺序向用户展示。用户审核它能否准确、完整地承载当前业务，不需要阅读建表语句。用户纠正后，Agent 重新检查所有直接受影响的表、字段、关系、约束、事务和生命周期。只有用户明确确认当前版本后，Agent 才记录 `数据库设计确认：已确认` 和可恢复的确认依据；在此之前不能把开发基线标记为 `当前`，也不能进入 Coding。

API、核心接口内部编排和数据库确认都是用户对设计事实的审核，不产生独立 AI 审核记录。确认后的新证据仍可随时触发修订；实质变更先把对应文档恢复为 `待确认`，只让受影响的下游事实失效并重新推导。

## 主控转交

主控只读取 `主控状态.md`，可以添加一句当前角色和进度说明，但交互包的事实、选项、影响和问题必须逐字呈现。主控不读取完整专业报告后重新生成问题，也不把交互包再复制回完整任务；完整任务中的交互字段链接状态文件即可。

## 处理用户反馈

1. 单一任务反馈由主控把尚未处理的用户原话写入该任务的 `主控状态.md`，不附解释；
2. 将该文件路径交回原专业 Agent；
3. 专业 Agent判断它确认、否定或新增了什么；
4. 专业 Agent更新自己拥有的事实文档；
5. 专业 Agent更新完整任务和 `主控状态.md` 中的处理结果、受影响范围和下一轮交互；
6. 专业 Agent清空“待处理用户反馈”，只向主控返回状态文件路径。

一条用户消息涉及多个系统或任务时，先由主控按 [多系统任务隔离](controller.md#多系统任务隔离) 路由：

- 完整原话只在协调任务中保存一次；
- 每个专业任务只收到与自己直接相关的原文片段；
- 共同业务事实先由业务设计 Agent吸收，系统 Agent随后读取更新后的权威文档；
- 片段边界不清时不广播，先请求事实拥有者或用户明确。

用户反馈需要改变其他事实空间时，当前 Agent 只报告影响，不直接修改其他角色文档。

无需永久保存全部原始聊天。反馈被权威文档吸收后，只保留理解决定所需的依据；措辞本身具有证据意义时保留短引文或可恢复链接。

## 跨会话恢复

`主控状态.md` 保存：

```text
当前负责角色：
通信状态：待派发 | Agent 工作中 | 等待用户 | 可继续 | 阻塞 | 完成
当前讨论对象：
专业结果位置：
本轮变更：
用户交互包：
待处理用户反馈：
反馈处理结果：
下一步：
```

完整任务保存权威来源、全部专业判断、未决决定、依赖和恢复动作。新主控只依赖短状态；新专业 Agent 再读取完整任务和权威文档，都不要求重放完整会话。
