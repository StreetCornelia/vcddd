## 原则

用户始终在主会话交互，但专业内容由当前专业 Agent 负责。主控不把专业问题重新概括成模糊摘要，也不替专业 Agent解释用户反馈。

用户需要参与：

- 真实目标、利益和业务意图；
- 材料无法证明的组织现实；
- 多个合理解释之间的选择；
- 高影响承诺、风险接受和价值取舍；
- 原型和实现是否表达了预期结果。

Agent 先调查和形成完整草案，再集中请用户纠偏；不能把调查、归纳或专业设计推回给用户。

## 专业 Agent 生成交互

返回可直接展示的交互包：

```text
交互类型：展示草案 | 请求纠偏 | 请求决定 | 报告冲突

面向用户的内容：
<完整文本>

为什么需要用户参与：
<无法从证据判断的真实意图或选择>

用户需要回答：
<最少充分信息>

收到反馈后：
<重新调用哪个角色、读取哪些路径>
```

不要让主控根据专业报告自行发明问题。

## 主控转交

主控可以添加当前角色和进度说明，但交互包的事实、选项、影响和问题原样呈现。提出问题前，在任务中保存交互包和当前负责角色。

## 处理用户反馈

1. 主控先把尚未处理的用户原话保存到当前任务；
2. 将原话、当前讨论对象和权威路径交回原专业 Agent；
3. 专业 Agent判断它确认、否定或新增了什么；
4. 专业 Agent更新自己拥有的事实文档；
5. 返回处理结果、受影响范围和下一轮交互；
6. 主控清空“待处理反馈”，保存更新后的恢复动作。

用户反馈需要改变其他事实空间时，当前 Agent 只报告影响，不直接修改其他角色文档。

无需永久保存全部原始聊天。反馈被权威文档吸收后，只保留理解决定所需的依据；措辞本身具有证据意义时保留短引文或可恢复链接。

## 跨会话恢复

任务入口保存：

```text
当前负责角色：
交互状态：等待用户 | 等待 Agent | 无等待
当前讨论对象：
当前权威文档：
最新用户交互包：
尚未处理的用户反馈：
反馈处理结果：
恢复动作：
```

新主控或新专业 Agent 只依赖这组状态和当前文档，不要求重放完整会话。
