## 原则

用户始终在主会话交互，但专业内容由当前专业 Agent 负责。主控不把专业问题重新概括成模糊摘要，也不替专业 Agent解释用户反馈。

用户需要参与：

- 真实目标、利益和业务意图；
- 材料无法证明的组织现实；
- 多个合理解释之间的选择；
- 高影响承诺、风险接受和价值取舍；
- 原型和实现是否表达了预期结果。

Agent 先调查和形成完整草案，再集中请用户纠偏；不能把调查、归纳或专业设计推回给用户。

面向用户的内容遵守 [业务语言与建模边界](language-and-modeling.md)：使用用户原话和普通话，只把元关键词当作结构。Domain 交互可以标注 DDD 分类，但每个术语同时给出具体业务含义；不能要求用户先理解行业黑话才能回答。

专业 Agent 必须提交全部会改变业务结果、责任、生命周期、风险承诺或开发正确性的未决决定，不设数量上限。先排除本角色应自行解决的专业判断，只在多个问题确实受同一个上位决定支配时归并。

交互包区分“当前决策前沿”和“等待前置决定”：前沿中的决定全部展示并请求用户回答；依赖其他决定的事项也保持可见，但说明依赖和暂不回答的原因。数量较多时按业务对象或影响范围分组，并给出建议回答顺序，不能截断、隐藏或用任意数量取舍。

## 专业 Agent 生成交互

返回可直接展示的交互包：

```text
交互类型：展示草案 | 请求纠偏 | 请求决定 | 报告冲突

面向用户的内容：
<完整文本>

为什么需要用户参与：
<无法从证据判断的真实意图或选择>

用户需要回答：
<当前决策前沿的全部最少充分信息>

其他重要未决决定：
<等待哪些前置决定、会影响什么；没有则写“无”>

收到反馈后：
<重新调用哪个角色、读取哪些路径>
```

不要让主控根据专业报告自行发明问题。

## Domain 所有权确认

系统设计进入 Domain 分析时，所有权与关系全景必须由用户明确确认。这不是把技术设计推给用户，而是确认：

- 哪个主体拥有哪个业务事实和决定；
- 各主体基于自己拥有的事实、决定和规则具有什么自有能力；
- 事物之间是什么业务关系；
- 关系本身由谁拥有和约束；
- 关系成立后新增、允许或限制什么业务能力；
- 外部系统事实与本地业务解释怎样区分。

专业 Agent 先调查证据并给出完整推荐认识，主控原样展示。确认前任务保持等待用户，不能继续对象分类、聚合、Domain、API 和数据库。用户否定任何基础关系时，由同一角色重新分析完整受影响全景后再次确认。

## Domain 核心命名确认

完成 DDD 分类后、用这些名称生成 API 和数据库之前，主控先按 [语言验证 Agent](language-validation-agent.md) 启动一次隔离盲测，把结果交回系统设计 Agent 处理。之后再把 Domain、核心对象、关系和业务表的建议名称交给用户确认业务含义。每项先单独展示名称和盲测理解，再展示用户原话或来源、普通话定义、为什么当前需要单独存在、DDD 分类以及可能造成的误解。

用户确认的不是技术模式，而是名称是否准确代表业务中的东西、是否不依赖说明即可理解。需要读完定义才能猜到含义的名称不合格。未确认名称标为临时名称，不能扩散到 API、表和代码。用户修改名称或含义时，重新检查受影响的所有权、关系、Domain、API 和数据，不做孤立文字替换。

## 主控转交

主控可以添加当前角色和进度说明，但交互包的事实、选项、影响和问题原样呈现。提出问题前，在任务中保存交互包和当前负责角色。

## 处理用户反馈

1. 主控先把尚未处理的用户原话保存到当前任务；
2. 将原话、当前讨论对象和权威路径交回原专业 Agent；
3. 专业 Agent判断它确认、否定或新增了什么；
4. 专业 Agent更新自己拥有的事实文档；
5. 返回处理结果、受影响范围和下一轮交互；
6. 主控清空“待处理反馈”，保存更新后的恢复动作。

用户反馈需要改变其他事实空间时，当前 Agent 只报告影响，不直接修改其他角色文档。

无需永久保存全部原始聊天。反馈被权威文档吸收后，只保留理解决定所需的依据；措辞本身具有证据意义时保留短引文或可恢复链接。

## 跨会话恢复

任务入口保存：

```text
当前负责角色：
交互状态：等待用户 | 等待 Agent | 无等待
当前讨论对象：
当前权威文档：
最新用户交互包：
尚未处理的用户反馈：
反馈处理结果：
恢复动作：
```

新主控或新专业 Agent 只依赖这组状态和当前文档，不要求重放完整会话。
