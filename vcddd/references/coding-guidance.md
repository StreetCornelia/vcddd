## 目的与边界

把已经确认的业务和设计忠实落成代码，同时允许 Coding 在不改变业务意义的前提下主动解决框架、代码组织、可靠性、可观察性、安全、性能、测试和运行问题。

Coding 对业务语义关闭，对工程实现开放：

- 不重新发明业务、Domain、API、事务结果、数据库事实或失败语义；
- 不把现有代码的方便做法提升为新业务；
- 在开发基线和系统工程规范约束内自主选择框架、类型、方法、公共组件和技术机制；
- 发现设计无法实现或工程事实会改变业务结果时返回事实拥有者；
- 发现可复用的系统级工程认识时先形成候选，经用户确认后更新本系统的 `工程编码规范.md`。

事务在已确认的核心接口内部编排和数据库设计中保存完整业务实现语义。Coding 可以选择事务装饰器、显式 Unit of Work、锁、CAS、Outbox、重试或其他技术机制，但不得改变已确认的原子范围、提交点、外部影响顺序、结果未知和恢复语义。

数据库设计保存表和字段为什么存在、单行语义、约束、查询、事务及生命周期；DDL、ORM 映射、迁移、回填和回退程序由 Coding 产生。实现可以选择具体数据库语法和迁移工具，但必须把设计中的 `数据库表注释原文` 和每个字段的 `数据库注释原文` 落入数据库 COMMENT 或等价元数据，并验证实际 schema 与已确认设计逐项对应。纯 SQL 方言、命名长度、迁移工具或 ORM 表达问题由 Coding 自行解决；如果 SQL 实证表明已确认的数据事实、约束、查询、事务或迁移要求不合理，则进入设计反馈闭环。任何需要改变数据事实、字段含义、约束责任或事务语义的实现便利，都必须返回数据库设计重新确认。

## 渐进加载

不要一次读取全部设计历史、全部代码和全部工程细则。按当前切片逐层扩展：

1. 读取开发 Agent reference、当前任务、已经确认的架构设计和模块拆分、状态为 `当前` 的开发基线；
2. 读取本系统 `工程编码规范.md` 的文档合同、当前规则索引和全部“始终适用”规则；
3. 读取本切片直接关联的业务线、API、逐 API 内部编排、所调用的 Domain 行为、数据库章节和权威图；
4. 检查当前规则索引中的触发条件，只读取被当前事实触发的事务、并发、外部调用、日志、安全、性能、迁移或平台规则；
5. 读取本切片实际涉及的代码入口、仓库可执行规范、测试和运行证据；
6. 只有发生效力不清、设计冲突、存量兼容或复审时，才继续读取历史实现、工程改进或旧审核记录。

`工程编码规范.md` 的当前规则索引必须足以让新 Agent 判断哪些规则始终适用、哪些规则由事实触发。索引缺失、过期或无法定位规则时先修复规范，不依靠 Agent 猜测。

## 系统级工程编码规范

每个进入 Coding 的系统固定维护：

```text
docs/vcddd/systems/<中文系统名>/工程编码规范.md
```

它是 Coding Agent 维护、用户确认的系统级工程事实，不是业务或设计事实，也不是开发基线的复制。不同系统不默认共享规范；同一仓库存在多个系统时，每个系统明确自己的适用代码范围。

首次 Coding 前完整读取并严格使用[工程编码规范形成流程与固定模板](engineering-coding-standard-template.md)。不建立逐开发切片的类、文件和方法计划。

已有代码时固定执行：

```text
识别语言、框架及版本
→ 按固定模板逐项调查代码和配置
→ 提取稳定风格
→ 标记冲突、缺失、不适用和历史例外
→ 为冲突与缺失提出当前最佳实践
→ 用户确认完整候选
→ 规范成为当前
```

完全没有代码时固定执行：

```text
确认语言、框架及版本
→ 按固定模板逐项提出当前最佳实践
→ 说明推荐、依据、替代项和权衡
→ 用户确认完整候选
→ 规范成为当前
```

从已有代码提取规则时，必须实际读取目标仓库，依次使用明确仓库规范与工具配置、核心模块稳定做法、多个模块共同惯例作为证据。单个文件、偶发写法或历史兼容不能直接成为系统规则。代码只能证明当前写法，不能代替用户确认未来规则。没有仓库路径或访问条件时先请求代码入口，不能仅凭用户概述生成完整存量规范。

没有稳定证据或完全没有代码时，针对确定的语言、框架和版本查阅当前官方文档、维护者指南和成熟生态约定。Agent 先给出推荐，不用空问题让用户从零发明；每个重要选择说明为什么适合当前系统、适用版本、至少一个真实替代项和代价。架构设计或模块拆分尚未确认时先返回系统设计，不能直接用工程规范假定它们已经存在，也不能提前交付工程规范候选。

固定模板覆盖架构与代码组织、Domain 与应用编排、命名表达、事务、数据访问、错误、日志可观察性、外部协作、并发异步幂等、配置安全、测试、封装复用重复以及工具链交付。当前不存在的主题写明“不适用、原因和重新触发条件”，不能删除。

只有同时满足以下条件的规则才能约束 Coding：

- 整份规范为 `状态：当前`；
- `规范确认：已确认` 且有可恢复依据；
- 单项规则状态为 `当前`；
- 规则落入当前适用范围或条件已经触发。

Coding 发现规范不足时，先区分局部等价选择和跨模块、跨切片的系统规则。局部选择自主决定；系统规则先调查现有代码，没有稳定做法时提出当前技术栈最佳实践，把规则写为候选并取得用户确认。改变业务结果、API 合同、Domain 责任、事务业务语义或数据事实时停止补规范，返回上游设计。

Lint、格式化、日志 Schema、静态检查和测试脚本作为可执行投影与规则相互链接。新规则影响存量代码时明确立即迁移、触及时迁移、允许例外或暂不迁移，不能默认全仓重写。

## 设计反馈闭环

Coding 忠实实现当前设计，同时有责任用实现证据检验设计能否成立。“已确认”表示当前实现基线，不表示 Coding 必须压下后来发现的问题。

先区分问题层次：

- 具体 SQL 方言、ORM 映射、迁移文件组织、代码结构或框架接法能够在允许实现空间内解决，且不改变数据和业务语义：Coding 自行解决并记录；
- 已确认的总体架构、主要组件或统一机制无法承载当前设计，或者模块责任和依赖边界无法实现：反馈架构设计或模块拆分；
- 表或字段无法表达真实事实、约束不能保持不变量、查询合同在给定数据模型下不可成立、迁移会破坏已确认数据、事务边界无法原子落地：反馈数据库设计或核心接口内部编排；
- Domain 缺少实现当前结果所需的事实或行为，所有权、关系、聚合边界、不变量、生命周期或失败语义彼此矛盾：反馈系统拆分；
- API 或业务结果本身需要变化：反馈对应 API 或业务设计。

Coding 不能只说“设计有问题”或把选择重新推给用户。发现者先完成足以定位问题的调查，可以编写不进入正式业务路径的最小技术验证，然后提出一份推荐修改。每个设计反馈写入：

```text
开发记录/<切片>/设计反馈/<序号>-<事实对象>.md
```

固定包含：

```text
反馈状态：待上游判断 | 已采纳 | 部分采纳 | 不采纳 | 已重新确认
发现阶段：首次实现 | SQL 与迁移 | 测试 | 运行验证 | 工程改进 | 代码审核
问题所在：
对应的权威设计：
实现、SQL 或运行证据：
为什么当前设计不成立或不合理：
影响的业务结果与代码范围：
建议修改：
替代方案与权衡：
建议修改的权威文档和章节：
当前代码处理：停止相关实现 | 仅保留技术验证 | 继续不受影响范围
可以继续的范围：
事实拥有者：
上游处理结果：
重新确认依据：
受影响的下游文档、代码和测试：
```

`建议修改` 给出发现者认为最合理的具体方案，不只列问题；`替代方案与权衡` 只保留确有价值的其他选择。Coding 可以建议怎样调整 Domain、表、字段、约束、索引、事务或迁移，但没有这些事实的写入权，不能直接把建议写成已确认设计。

主控把记录路由给相应事实拥有者。事实拥有者必须独立判断证据和建议，在自己拥有的任务、状态和设计文档中记录采纳、部分采纳、更合适方案或不采纳理由；不能直接改写 Coding 拥有的设计反馈记录。需要改变已确认设计时更新权威文档、使直接依赖的确认与开发基线失效，并重新提交用户确认。新基线生效后，Coding 重新读取上游结果，更新设计反馈的状态、处理结果和重新确认依据，再继续实现。

受影响实现停止在不会制造错误事实的位置；不受影响的切片可以继续。不得为了保持进度，用触发器、额外查询、隐藏状态、临时表、重复业务判断或特殊分支静默修补设计缺口。记录由 `实现记录.md` 的“与设计的偏离”直接链接；问题解决后保留 Git 历史和上游处理结果，不删除反馈。

```text
无条件适用规则：

```

只围绕一个可观察业务结果组织纵向实现。依赖先于引用者，但不要先搭建当前结果没有消费者的通用框架。

## 首次实现

优先形成忠实、清楚、可运行和可测试的最小实现：

- 先实现开发基线声明的正常、拒绝、冲突、重复、失败和恢复结果；
- 让业务判断留在拥有它的 Domain，让应用层只获得外部事实和组织协作；
- 忠实实现已确认的事务、提交、外部影响、日志与恢复顺序；
- 遵守当前工程规范，不用局部便利绕过系统规则；
- 不为未来可能复用的代码提前建立抽象、框架或扩展点；
- 不把“先写清楚”误解为允许复制业务规则。

首次实现允许暂时保留局部技术重复，只要含义清楚、没有分裂同一业务决定、没有违反当前工程规范，并能在后续工程改进中被独立判断。

以下重复必须在首次实现中消除：

- 同一个业务规则在多个入口分别判断；
- 同一个不变量或状态变化被应用层、Domain 和持久化层分别实现；
- 多处代码独立解释同一 API、事务或失败语义；
- 复制会立即造成安全、数据或恢复风险。

不要仅因两段代码语法相似就提取。抽象至少需要证明它们承担同一责任、具有同一变化原因、能形成清楚合同，并确实降低不一致或验证成本。

## 工程改进

首次实现通过自检并形成可重复定位的代码快照后，再进入工程改进。工程改进不是正式审核；它允许修改代码、测试和纯工程规范，目标是把已经正确的业务实现收敛成更可靠、清楚和一致的系统代码。

至少启动独立的“重复与抽象”分析。再按当前事实与规范触发：

- 边界与依赖；
- 事务、并发、错误与恢复；
- 日志、指标与追踪；
- 测试质量；
- 安全与敏感信息；
- 性能、容量与资源；
- 配置、部署和平台运行。

每个分析 Agent 只读取同一输入快照、开发基线、工程规范、实现记录和自己角度需要的代码，不读取其他分析结论。分析可以并行；修改同一文件或相互依赖的代码必须串行。

分析完成后：

1. 把有证据的问题、保留不改的理由、建议结果和规范缺口写入独立工程改进记录；
2. 对互不重叠的修改按代码所有权分配，对重叠修改由一个 Agent 或连续 Agent在最新快照上处理；
3. 每次修改保持业务结果、设计步骤、事务和外部语义不变；
4. 运行受影响测试和必要运行验证；
5. 把可复用的系统级认识写成 `工程编码规范.md` 候选，用户确认后更新当前版本；局部选择留在改进记录；
6. 形成新的代码快照，并让后续改进读取最新快照；
7. 发现需要改变设计时停止修改，由主控返回事实拥有者。

“重复与抽象”使用以下判断：

- 同一业务规则重复：收回拥有该规则的 Domain，不作为普通重构；
- 同一稳定工程责任重复且具有同一变化原因：形成清楚抽象；
- 只是语法相似、业务意义或变化原因不同：保留分离；
- 当前只有一个消费者、仅猜测未来复用：不提前抽象；
- 抽象需要大量参数、分支或回调维持差异：撤销抽象；
- 减少少量行数却增加命名、层级和测试成本：保留清楚的局部实现。

具体角色合同见 [工程改进 Agent](engineering-improvement-agent.md)。

## 形成待审核快照

所有计划内工程改进完成后：

1. 运行声明范围的自动化测试和必要的真实运行验证；
2. 更新工程规范版本及其可执行投影；
3. 更新 `实现记录.md` 的设计映射、工程规范、改进记录、测试和剩余风险；
4. 固定 Commit 或不可变补丁作为待审核快照；
5. 只把最终快照交给相互独立的实现符合性、工程质量和触发的专项审核；
6. 正式审核 Agent只读，不在审核过程中修改移动目标。

审核发现问题后，由开发或工程改进 Agent在新任务中修正，形成新快照并按影响范围复审。

## 发现冲突

按事实所有者返回：

- 业务结果或场景错误：业务设计 Agent；
- Domain、行为、不变量或关系错误：系统与开发设计 Agent；
- 总体架构、主要组件或统一机制错误：架构设计；
- 模块责任或依赖边界错误：模块拆分；
- API、事务、外部影响、关键日志或恢复语义错误：核心接口内部编排；
- 数据结构、约束、迁移或数据库事务承载错误：数据库设计；
- 纯工程规范缺失或不一致：Coding Agent形成规范候选并取得用户确认；
- 现有代码没有遵守当前设计或工程规范：开发或工程改进 Agent修正；
- 平台能力尚未被证明：技术验证。
