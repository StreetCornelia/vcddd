## 目的与边界

把已确认业务和设计忠实落成全部生产代码，同时允许 Coding 在不改变业务意义的前提下主动解决框架、代码组织、可靠性、可观察性、安全、性能和运行问题。

Coding 对业务语义关闭，对工程实现开放：

- 不重新发明业务、Domain、API、事务结果、数据库事实或失败语义；
- 不要求所有代码任务都涉及业务结果、API 或 Domain；
- 在开发基线和系统工程规范内自主选择类型、方法、局部组件和技术机制；
- 发现设计无法实现或工程事实会改变业务结果时返回事实拥有者；
- 系统级工程规则经用户确认后写入本系统 `工程编码规范.md`；
- 先完成全部生产代码，再由多个独立测试 Agent 统一编写测试并反馈。

事务的业务语义来自已确认编排和数据库设计。Coding 可以选择装饰器、Unit of Work、锁、CAS、Outbox、重试等技术机制，但不得改变原子范围、提交点、外部影响顺序、结果未知和恢复语义。

数据库设计保存表和字段为什么存在、单行语义、约束、查询、事务及生命周期；DDL、ORM、迁移、回填和回退程序由 Coding 产生。实现必须落地数据库表与字段注释原文。SQL 实证表明数据事实、约束、查询、事务或迁移要求不成立时进入设计反馈，不用实现便利静默改变事实。

## 渐进加载

不要一次读取全部历史。按工作类型加载：

### 开发规划

1. 读取当前任务、当前开发基线和已经确认的架构与模块；
2. 读取 `工程编码规范.md` 的固定合同、规则索引和全部核心规则；
3. 读取当前批次涉及的 API、编排、数据库和权威图；
4. 调查真实代码目录、注册入口、共享文件、构建和版本快照；
5. 按 [开发任务图固定模板](implementation-task-graph-template.md)盘点全部代码产物。

### 单个实施任务

1. 读取状态为 `当前` 的任务图和自己的节点；
2. 读取节点直接来源、前置产物、工程规则和允许写入范围；
3. 读取任务 worktree 中的实际代码；
4. 只在发生效力冲突、存量兼容或设计问题时扩展证据。

### 统一测试、工程改进和审核

分别读取固定统一生产代码快照、自己的角色 reference、开发基线、工程规范和明确允许的代码与记录。独立 Agent 不读取同阶段其他 Agent 的结论。

## 系统级工程编码规范

每个进入 Coding 的系统维护：

```text
docs/vcddd/systems/<中文系统名>/工程编码规范.md
```

首次 Coding 前完整使用[工程编码规范形成流程与固定模板](engineering-coding-standard-template.md)。

已有代码时：

```text
识别语言、框架和版本
→ 按固定模板逐项调查代码与配置
→ 提取稳定风格
→ 标记冲突、缺失、不适用和历史例外
→ 提出推荐与替代
→ 用户确认
```

没有代码时：

```text
确认语言、框架和版本
→ 根据当前官方资料和成熟实践逐项提出推荐
→ 说明依据、替代和权衡
→ 用户确认
```

没有仓库访问时不能仅凭概述生成存量规范。架构或模块未确认时不能用规范提前假定它们。

当前规范固定覆盖架构与代码组织、Domain 与应用编排、命名、事务、数据访问、错误、日志、外部协作、并发异步幂等、配置安全、测试、封装复用以及工具链交付。不存在的主题写明不适用、原因和重新触发条件。

只有整份规范为 `当前`、用户确认有可恢复依据、单项规则为 `当前` 且适用条件成立时，规则才能约束 Coding。局部等价选择由实施 Agent 决定；跨模块、跨任务的规则先形成候选并取得用户确认。

## 开发任务图

生产代码开始前必须建立：

```text
开发记录/<开发批次>/开发任务图.md
```

任务图不是逐层代码翻译，而是全部代码产物的责任和依赖图。严格使用[开发任务图固定模板](implementation-task-graph-template.md)：

```text
代码产物盘点
→ 提供者与消费者
→ 写入范围与共享位置
→ 合并或拆分责任
→ 真实依赖与冲突
→ 并行批次
→ worktree 基线
→ 用户确认
```

禁止：

- 把 Controller、Service、Repository 或 Domain 当成固定一级任务；
- 给不存在的 API、Domain、数据库或外部系统补占位任务；
- 按期望子 Agent 数量拆分；
- 为未来复用建立没有当前消费者的基础任务；
- 把测试与正确性验证塞进实施节点。

任务图只有状态为 `当前`、用户确认且结构校验通过后才能创建编码 worktree。

## 并行编码与集成

实施任务按任务图执行：

- 无未完成前置依赖且写入范围不冲突的任务并行；
- 同批任务从同一 Commit 建立隔离分支和 worktree；
- 每个 Agent 只修改自己的授权范围并提交；
- 前置任务合并后，依赖任务从新的合并 Commit 开始；
- 同一共享文件只有一个写入者；
- 任务完成只表示代码已形成，不表示已通过测试。

开发任务可以是工程基础、数据迁移、查询、接口、业务代码、外部集成、后台任务、系统能力、装配或存量改造。它只引用实际来源，不强制形成纵向业务切片。

生产代码实施允许暂时保留局部技术重复，但不能重复实现同一业务规则、不变量、事务或失败语义。公共抽象只有在当前存在多个真实消费者、责任相同、变化原因相同且合同清楚时才成立；其他情况留给统一工程改进判断。

全部任务按依赖顺序合并后建立：

```text
开发记录/<开发批次>/集成记录.md
```

固定说明：

```text
开发任务图：
起始代码快照：
已合并任务及 Commit：
合并顺序：
共享写入处理：
未合并或未实现事项：
统一生产代码快照：
测试状态：未开始 | 进行中 | 需修正 | 完成
工程改进状态：未开始 | 进行中 | 完成
最终待审核快照：
```

集成阶段不编写测试，不声明生产代码正确。

## 统一测试

全部生产代码形成统一快照后，按 [统一测试 Agent](testing-agent.md)启动多个测试任务。测试角度由实际代码和风险触发，不机械要求 Domain、API 或数据库测试。

每个测试 Agent：

- 从同一生产代码快照建立独立 worktree；
- 只写自己范围内的测试代码和测试反馈；
- 不修改生产代码；
- 运行测试并提供失败证据；
- 把生产代码、测试代码、工程规范、上游设计或平台责任分开；
- 不读取其他测试 Agent 结论。

全部测试反馈由新的测试结论 Agent 汇总。失败返回对应实施任务或事实拥有者；修正形成新统一代码快照后按影响范围复测。只有测试结论为 `可进入工程改进` 才继续。

测试是在代码完成后的统一反馈阶段，不属于每个开发任务的编码完成边界。

## 工程改进与审核

统一测试形成可复现测试代码后，再以当前生产代码和测试快照进入工程改进：

- 至少执行独立的重复与抽象分析；
- 按风险追加边界依赖、事务可靠性、可观察性、安全、性能或平台分析；
- 多个只读分析可以并行；
- 生产代码修改按所有权分配，重叠修改串行；
- 代码改进必须运行受影响的统一测试；
- 发现设计问题时返回事实拥有者；
- 系统级规则变化形成工程规范候选并由用户确认。

工程改进完成并复测以后，固定最终生产代码与测试快照，再启动只读的实现符合性、工程质量和风险专项审核。审核只判断固定目标，不在审核中修改代码。

## 设计反馈闭环

Coding 发现问题时先区分：

- 具体语言、框架、ORM、迁移文件或局部代码组织能保持已确认语义：自行解决；
- 架构或模块责任无法承载实现：返回架构或模块拆分；
- 表、字段、约束、查询、事务或迁移无法成立：返回数据库设计或核心接口内部编排；
- Domain 所有权、行为、不变量或生命周期矛盾：返回系统拆分；
- API 或业务结果需要变化：返回 API 或业务设计；
- 任务边界、依赖、并行或共享写入判断错误：返回开发规划 Agent；
- 系统工程规则不足：形成规范候选。

发现者先调查足以定位问题的代码、SQL、测试或运行证据，并提出推荐修改。每个反馈写入：

```text
开发记录/<开发批次>/设计反馈/<序号>-<事实对象>.md
```

固定包含：

```text
反馈状态：待上游判断 | 已采纳 | 部分采纳 | 不采纳 | 已重新确认
发现阶段：任务规划 | 生产代码实现 | SQL 与迁移 | 统一测试 | 工程改进 | 代码审核
问题所在：
对应的权威设计：
代码、SQL、测试或运行证据：
为什么当前设计不成立或不合理：
影响的任务与代码范围：
建议修改：
替代方案与权衡：
建议修改的权威文档和章节：
当前代码处理：停止相关实现 | 仅保留技术验证 | 继续不受影响范围
可以继续的范围：
事实拥有者：
上游处理结果：
重新确认依据：
受影响的任务、代码和测试：
```

主控把反馈路由给事实拥有者。事实拥有者独立判断采纳、部分采纳、替代或不采纳；需要改变已确认设计时更新权威文档、使受影响基线和任务图失效并重新交给用户确认。

## 记录合同

每个开发批次维护：

```text
开发记录/<开发批次>/
├── 开发任务图.md
├── 实施任务/
│   └── <TASK-标识>/
│       └── 实现记录.md
├── 集成记录.md
├── 设计反馈/（实际发生时）
├── 测试反馈/
│   └── <测试角度>.md
├── 测试结论.md
├── 工程改进/
│   └── <轮次>-<分析角度>.md
├── 审核/
│   ├── 实现符合性.md
│   └── 工程质量.md
└── 审核结论.md
```

`开发任务图.md` 拥有代码产物、任务依赖、并行批次和 worktree 调度。`实现记录.md` 只记录单个任务实际生产代码。`集成记录.md` 拥有统一生产代码快照和阶段状态。`测试反馈/` 和 `测试结论.md` 保存统一测试证据。`工程改进/` 保存测试以后发生的工程分析与修改。正式审核只读取最终固定生产代码与测试快照。
