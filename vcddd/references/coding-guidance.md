## 目的与边界

把已经确认的业务和设计忠实落成代码，同时允许 Coding 在不改变业务意义的前提下主动解决框架、代码组织、可靠性、可观察性、安全、性能、测试和运行问题。

Coding 对业务语义关闭，对工程实现开放：

- 不重新发明业务、Domain、API、事务结果、数据库事实或失败语义；
- 不把现有代码的方便做法提升为新业务；
- 在开发基线和系统工程规范约束内自主选择框架、类型、方法、公共组件和技术机制；
- 发现设计无法实现或工程事实会改变业务结果时返回事实拥有者；
- 发现可复用的系统级工程认识时更新本系统的 `工程编码规范.md`。

事务在已确认的核心接口内部编排和数据库设计中保存完整业务实现语义。Coding 可以选择事务装饰器、显式 Unit of Work、锁、CAS、Outbox、重试或其他技术机制，但不得改变已确认的原子范围、提交点、外部影响顺序、结果未知和恢复语义。

数据库设计保存表和字段为什么存在、单行语义、约束、查询、事务及生命周期；DDL、ORM 映射、迁移、回填和回退程序由 Coding 产生。实现可以选择具体数据库语法和迁移工具，但必须把设计中的 `数据库表注释原文` 和每个字段的 `数据库注释原文` 落入数据库 COMMENT 或等价元数据，并验证实际 schema 与已确认设计逐项对应。任何需要改变数据事实、字段含义、约束责任或事务语义的实现便利，都必须返回数据库设计重新确认。

## 渐进加载

不要一次读取全部设计历史、全部代码和全部工程细则。按当前切片逐层扩展：

1. 读取开发 Agent reference、当前任务、状态为 `当前` 的开发基线；
2. 读取本系统 `工程编码规范.md` 的文档合同、当前规则索引和全部“始终适用”规则；
3. 读取本切片直接关联的业务线、API、逐 API 内部编排、所调用的 Domain 行为、数据库章节和权威图；
4. 检查当前规则索引中的触发条件，只读取被当前事实触发的事务、并发、外部调用、日志、安全、性能、迁移或平台规则；
5. 读取本切片实际涉及的代码入口、仓库可执行规范、测试和运行证据；
6. 只有发生效力不清、设计冲突、存量兼容或复审时，才继续读取历史实现、工程改进或旧审核记录。

`工程编码规范.md` 的当前规则索引必须足以让新 Agent 判断哪些规则始终适用、哪些规则由事实触发。索引缺失、过期或无法定位规则时先修复规范，不依靠 Agent 猜测。

## 系统级工程编码规范

每个进入 Coding 的系统固定维护：

```text
docs/vcddd/systems/<中文系统名>/工程编码规范.md
```

它是 Coding Agent 拥有的系统级工程事实，不是业务或设计事实，也不是开发基线的复制。不同系统不默认共享规范；同一仓库存在多个系统时，每个系统明确自己的适用代码范围。

首次 Coding 前，从仓库规范、当前代码和已确认设计形成最小可用版本。不要把现有代码一律当作正确规范；区分继续采用的惯例、已知违规、临时兼容和准备形成的新规则。

固定使用：

```markdown
# <系统名>工程编码规范

状态：待建立 | 当前 | 待重新判断
适用系统：
适用代码范围：
规范版本：
生效代码快照：
维护角色：Coding Agent

## 使用与演化规则

## 当前规则索引

| 规则标识 | 级别 | 适用或触发条件 | 内容与位置 |
| --- | --- | --- | --- |

## 当前系统工程约束

## 当前编码规则

## 例外与存量处理

## 尚未形成规范的问题

## 重要演化
```

规则级别固定为：

- `核心`：所有本系统 Coding 无条件读取和遵守；
- `条件`：索引声明触发事实，当前切片命中时读取和遵守；
- `补充`：不改变当前正确性的偏好，只在核心和条件规则稳定后处理。

每项规则固定说明：

```text
规则标识：
状态：当前 | 候选 | 已替代
级别：核心 | 条件 | 补充
适用范围或触发条件：
必须满足的要求：
采用原因：
允许的实现空间：
禁止行为：
验证方式：
允许例外：
存量代码处理：
关联配置、代码或替代规则：
```

只让状态为 `当前` 的规则约束 Coding。候选规则保留问题和证据，但不能暗中指导实现。

`当前编码规则` 按系统真实需要维护架构与依赖、Domain 编码、应用用例、事务与并发、错误与恢复、日志指标追踪、数据与迁移、外部协作、安全、性能容量、配置依赖、测试、基础代码表达和运行交付。不要为尚未出现的技术形态预建空规则。

最小可用版本不是空模板。首次进入 Coding 时至少回答：

- 模块、目录和依赖方向怎样保持，哪些层可以调用哪些层；
- 业务判断由哪个 Domain 拥有，应用层怎样忠实排列已确认步骤；
- 已确认事务语义在当前框架中统一使用什么机制，怎样处理并发、失败和恢复；
- 错误怎样分类、转换和返回，哪些位置允许捕获或重试；
- 日志采用什么结构与字段，在业务结果、状态变化、外部协作和异常的什么时机记录，以什么频率记录或抑制，怎样关联请求、业务对象与重试，并怎样脱敏；
- 测试分别怎样证明 Domain 规则、应用编排、事务数据和外部边界；
- 当前怎样判断重复业务决定、合理技术重复、应当封装和过度封装；
- 配置、迁移、静态检查和交付入口怎样形成可重复验证。

某项在当前系统中确实不存在时明确写“不适用及原因”，不要凭空形成技术方案；一旦相关事实出现，再把它变成条件规则或核心规则。

Coding 发现规范不足时：

1. 判断它是本切片局部选择，还是以后同类代码都应遵守的系统规则；
2. 局部选择只写实现或工程改进记录；
3. 纯工程且证据充分的系统规则由 Coding Agent写入规范、更新索引和版本；
4. 证据不足的规则写为候选，不约束当前代码；
5. 改变业务结果、API 合同、Domain 责任、事务语义或数据事实时停止补规范，返回上游设计；
6. 新规则影响存量代码时明确“立即迁移、触及时迁移、允许例外或暂不迁移”，不能默认全仓重写；
7. Lint、格式化、日志 Schema、静态检查和测试脚本作为可执行投影与规则相互链接；发生冲突时暴露并统一，不任选方便的一方。

## 进入开发切片

先建立：

```text
切片业务结果：
开发基线范围：
适用的工程规范版本：
无条件适用规则：
当前事实触发的条件规则：
关联 API 与稳定编排步骤：
关联 Domain 方法与稳定内部步骤：
事务、数据、外部协作和日志要求：
现有代码与平台约束：
测试和可观察完成证据：
```

只围绕一个可观察业务结果组织纵向实现。依赖先于引用者，但不要先搭建当前结果没有消费者的通用框架。

## 首次实现

优先形成忠实、清楚、可运行和可测试的最小实现：

- 先实现开发基线声明的正常、拒绝、冲突、重复、失败和恢复结果；
- 让业务判断留在拥有它的 Domain，让应用层只获得外部事实和组织协作；
- 忠实实现已确认的事务、提交、外部影响、日志与恢复顺序；
- 遵守当前工程规范，不用局部便利绕过系统规则；
- 不为未来可能复用的代码提前建立抽象、框架或扩展点；
- 不把“先写清楚”误解为允许复制业务规则。

首次实现允许暂时保留局部技术重复，只要含义清楚、没有分裂同一业务决定、没有违反当前工程规范，并能在后续工程改进中被独立判断。

以下重复必须在首次实现中消除：

- 同一个业务规则在多个入口分别判断；
- 同一个不变量或状态变化被应用层、Domain 和持久化层分别实现；
- 多处代码独立解释同一 API、事务或失败语义；
- 复制会立即造成安全、数据或恢复风险。

不要仅因两段代码语法相似就提取。抽象至少需要证明它们承担同一责任、具有同一变化原因、能形成清楚合同，并确实降低不一致或验证成本。

## 工程改进

首次实现通过自检并形成可重复定位的代码快照后，再进入工程改进。工程改进不是正式审核；它允许修改代码、测试和纯工程规范，目标是把已经正确的业务实现收敛成更可靠、清楚和一致的系统代码。

至少启动独立的“重复与抽象”分析。再按当前事实与规范触发：

- 边界与依赖；
- 事务、并发、错误与恢复；
- 日志、指标与追踪；
- 测试质量；
- 安全与敏感信息；
- 性能、容量与资源；
- 配置、部署和平台运行。

每个分析 Agent 只读取同一输入快照、开发基线、工程规范、实现记录和自己角度需要的代码，不读取其他分析结论。分析可以并行；修改同一文件或相互依赖的代码必须串行。

分析完成后：

1. 把有证据的问题、保留不改的理由、建议结果和规范缺口写入独立工程改进记录；
2. 对互不重叠的修改按代码所有权分配，对重叠修改由一个 Agent 或连续 Agent在最新快照上处理；
3. 每次修改保持业务结果、设计步骤、事务和外部语义不变；
4. 运行受影响测试和必要运行验证；
5. 把可复用的系统级认识更新到 `工程编码规范.md`，局部选择留在改进记录；
6. 形成新的代码快照，并让后续改进读取最新快照；
7. 发现需要改变设计时停止修改，由主控返回事实拥有者。

“重复与抽象”使用以下判断：

- 同一业务规则重复：收回拥有该规则的 Domain，不作为普通重构；
- 同一稳定工程责任重复且具有同一变化原因：形成清楚抽象；
- 只是语法相似、业务意义或变化原因不同：保留分离；
- 当前只有一个消费者、仅猜测未来复用：不提前抽象；
- 抽象需要大量参数、分支或回调维持差异：撤销抽象；
- 减少少量行数却增加命名、层级和测试成本：保留清楚的局部实现。

具体角色合同见 [工程改进 Agent](engineering-improvement-agent.md)。

## 形成待审核快照

所有计划内工程改进完成后：

1. 运行声明范围的自动化测试和必要的真实运行验证；
2. 更新工程规范版本及其可执行投影；
3. 更新 `实现记录.md` 的设计映射、工程规范、改进记录、测试和剩余风险；
4. 固定 Commit 或不可变补丁作为待审核快照；
5. 只把最终快照交给相互独立的实现符合性、工程质量和触发的专项审核；
6. 正式审核 Agent只读，不在审核过程中修改移动目标。

审核发现问题后，由开发或工程改进 Agent在新任务中修正，形成新快照并按影响范围复审。

## 发现冲突

按事实所有者返回：

- 业务结果或场景错误：业务设计 Agent；
- Domain、行为、不变量或关系错误：系统与开发设计 Agent；
- API、事务、外部影响、关键日志或恢复语义错误：核心接口内部编排；
- 数据结构、约束、迁移或数据库事务承载错误：数据库设计；
- 纯工程规范缺失或不一致：Coding Agent更新 `工程编码规范.md`；
- 现有代码没有遵守当前设计或工程规范：开发或工程改进 Agent修正；
- 平台能力尚未被证明：技术验证。

报告问题位置、代码或运行证据、影响范围、当前切片是否可继续以及需要重新确认或重新生成的内容。不要在代码中用新的业务结果绕过冲突。
