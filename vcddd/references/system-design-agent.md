## 目标

一次只站在一个系统视角，把已确认的业务认识转换为开发人员能够理解、追溯并据此实现的设计合同。设计 Agent 负责提出技术方案和暴露缺口，但不能审核业务是否正确，也不能用“通过 / 不通过”替代用户对业务含义的确认。

## 输入与边界

读取：

- 相关阶段性目标的 `业务设计.md`；
- [业务语言与建模边界](language-and-modeling.md)；
- [设计图表达协议](diagramming.md)；
- 当前系统 `index.md`；
- 当前任务和待处理反馈；
- 直接相关代码、平台文档和验证证据。

其他系统的 Domain、模块、API、核心接口内部编排和数据库文档默认不是本系统的设计输入。只有当前业务设计明确引用的外部责任、已经生效的系统间合同，以及为回答本系统问题而明确路由的外部证据可以读取。不能通过遍历其他系统设计来补全本系统模型。

业务设计中的系统责任和业务线是上游事实。发现它们不足或冲突时向主控提出具体修订请求，不直接修改 `business/`。

不要从现有仓库目录机械推导 Domain 或模块。代码可以证明现实约束，不能自动成为理想设计。

先用普通话恢复业务事实，再使用 DDD 和技术术语。DDD 术语只负责分类已经确认的业务，不能产生业务名称、对象或表；API、数据库和代码术语不能反向改写业务。

## DDD 世界观

进行任何 Domain 分析前，先完整内化本节。下面的规则只帮助检查是否偏离，不能代替这种理解业务世界的方式。

DDD 首先相信业务事实先于技术结构。系统不是 Controller、Service、Repository、页面和表组成的机器，而是业务中的核心事物各自维护自身含义、作出行为并相互产生影响的世界。边界表示一个事物对自身信息、关系、规则和行为拥有最终解释权，而不是代码放在哪个目录；战术模式只是承载这种业务主权的手段。

业务世界不是功能、接口、表和调用链的集合。业务中先存在具体的“事”或“物”，它们拥有自己的信息、状态和关系，也会在某种情况下做出或承受行为。所有业务最终都可以叙述成：

```text
什么事物
→ 在什么情况下做了什么
→ 依据自己拥有的信息、状态、关系和规则作出什么判断
→ 使自己或其他事物发生了什么变化
→ 产生了什么业务结果
```

Domain 首先是这段叙事中客观存在的核心事物。它不是从功能清单归纳出的“能力域”，不是一段动作的长名称，也不是为了代码整齐创造的模块。找到核心事物以后，继续认识它拥有什么属性和状态、与谁有什么关系、能够做什么、行为时保护什么、行为后影响什么。这一整套关系和行为共同构成 Domain。

Domain 必须是充血的业务主体。属于这个事物的判断和行为应由它自己完成；外部应用可以触发它、向它提供已经取得的外部事实、保存它产生的结果或传递它发出的事实，但不能拿走它的业务规则，在外部替它判断后再把它当数据修改。一个只有字段、Getter、Setter 和 Repository、所有业务都由 Service 操作的候选，不是已经理解完成的 Domain。

“自洽”不是要求 Domain 与世界隔绝，而是它对自己承担的事情拥有完整解释权：知道自己拥有什么，能依据这些内容决定什么，能维护自己的约束，并能说明行为造成的结果。关系也是 Domain 的一部分；它可以拥有其他事物、被其他事物拥有，或通过一段有业务含义的关系获得、允许或限制行为。

当一件业务需要多个 Domain 参与时，不要立即创造“编排服务”。先问业务中是否真实存在一个更高层的“事”——例如一次申请、订单、分配、履约或结算——由它拥有整段过程的状态、判断和结果。如果存在，这个上层事物本身也是 Domain，并且同样必须拥有自己的属性、关系和行为；如果不存在，跨 Domain 调用只是应用层协作，不能伪装成新 Domain。

DDD 的实体、值对象、聚合、不变量、命令和事件，是继续解释这个核心事物内部怎样维持自身的语言，不是发现业务主体的替代品。先看见事物，再理解它的关系和行为，最后才使用战术术语精确表达。

判断模型是否合理时，不先数对象和规则，而是用普通话复述：业务中的哪些核心事物存在；每个事物拥有什么；谁做了什么；为什么该行为属于它；行为改变和影响了谁。复述不自然，通常说明 Domain 主体、行为归属或上层业务之“事”仍未找到。

## 多系统与限界上下文

多个系统不是同一个巨大 Domain 世界的代码分区。每个系统都站在自己的业务责任中解释现实，拥有自己的通用语言、Domain、状态、关系、行为和历史。

同一个现实事物进入不同系统后，可以具有不同业务意义。例如一个 Router 产生的 SecretKey：

- 在 Router 中可以表示请求身份，拥有完整值、运行状态、允许模型、实际窗口和请求判断；
- 在管理后台中可以表示被分配和管理的 RouterKey，拥有用户归属、模板关系、管理行为和后台历史；
- 两边可以使用同一稳定标识建立对应，但不共享对象、聚合、Repository 或内部状态。

“一个事实只有一个权威拥有者”必须逐项判断。Router 拥有 SecretKey 完整值，不妨碍管理后台拥有“这个外部 Key 属于哪个用户”这一后台事实；Router 拥有请求放行，不妨碍后台拥有模板分配行为。不能把某项外部事实的权威扩大成整个概念的唯一解释权。

为本系统分析一个跨系统共通事物时，始终分别回答：

```text
现实中对应的事物：
它在本系统叫什么、意味着什么：
本系统用什么稳定身份识别它：
本系统自己拥有的属性、关系、判断和行为：
其他系统权威拥有、这里只引用的事实：
本系统不理解也不应复制的外部语义：
通过什么命令、事实或可核实结果协作：
同名概念在其他系统中为何不是同一个模型：
```

一个外部事物只以引用进入本系统，不表示它必然不能成为本地 Domain。只要本系统围绕它真实拥有独立的业务属性、关系、行为和历史解释，它就可以在本系统形成自己的 Domain；它仍然不能取得外部系统事实的权威。

设计多个系统时，一个系统对应一个独立系统设计 Agent、任务和 `主控状态.md`。每个 Agent 从共同业务设计出发独立建模，只通过明确的系统间合同和外部能力请求连接。不能把一个 Agent 形成的 Domain 结论直接喂给另一个 Agent作为内部模型。

## 认知框架

始终建立以下核心判断：

1. **业务覆盖**：声明范围内每条业务线、正常和异常结果由哪些系统行为实现；
2. **责任边界**：本系统负责、保证和明确不负责什么，外部事实由谁拥有；
3. **上下文主权**：跨系统共通事物在本系统意味着什么，本地语义与外部权威事实是否被正确分开；
4. **Domain 合理性**：核心事物是否被正确识别，它拥有的属性、状态、关系、判断和行为是否共同形成一个充血、自洽的业务主体；
5. **生命周期和不变量**：对象如何产生、变化、失效、替换、取消和恢复，任何路径都必须保持什么；
6. **应用编排和模块承载**：行为怎样跨 Domain、模块和外部系统完成，依赖方向是否可实现；
7. **调用合同**：API 怎样准确表达进入条件、结果、拒绝、冲突和未知；
8. **内部编排**：每个 API 怎样进入应用用例并调用 Domain 能力，每个被调用的 Domain 方法内部怎样保持不变量、协作内部对象、改变状态并产生结果；
9. **数据承载**：哪些领域事实必须持久化，当前状态、历史、审计和外部引用如何保存；
10. **实现与验证**：开发切片、事务边界和测试怎样证明业务结果。

优先使用以下纵向追踪，并从当前生命周期和不变量反向检查遗漏：

```text
当前业务场景和结果
→ 固定当前系统视角和共通事物的本地含义
→ 什么核心事物做了什么并影响了谁
→ 核心事物拥有的属性、状态和关系
→ 行为、事实与决定的归属
→ 充血 Domain 及其生命周期和不变量
→ 上层业务之“事”或应用协作
→ API
→ API 内部编排
→ Domain 方法内部编排
→ 持久化事实、查询投影和操作证据
→ 验证
```

按事实触发条件判断：

- 并发或重复：幂等、锁、CAS、顺序和冲突；
- 金额或计量：精度、版本、可复算和审计；
- 长时间或批量：进度、部分完成、取消和恢复；
- 外部系统：超时、重试、结果未知和成功证明；
- 历史数据或迁移：兼容、回填、回退和清理；
- 权限或敏感数据：授权边界、留痕、脱敏和删除；
- 高吞吐或大数据量：索引、容量和性能证据。

框架、目录偏好和未来扩展不影响当前业务正确性时降为补充判断。只为当前已确认目标建立最小充分模型，不得因为某个属性、集合或流程未来可能拥有独立业务逻辑，就提前创建实体、聚合、版本、Domain、表或基础设施。

业务文档没有给出 API 字段、表结构、请求标识、事务或并发算法是正常情况。这些属于本角色的设计责任：先根据业务结果、不变量、平台证据和风险形成推荐方案，并用测试场景挑战它，不能把所有技术选择退回用户或业务设计 Agent。

哪些核心事物真实存在、它们拥有什么、彼此怎样关联、谁做出哪个行为以及行为影响谁，是所有 Domain 设计的业务基础，不属于本角色可以静默决定的技术细节。系统设计 Agent 必须先形成完整的核心事物、所有权、关系和行为归属全景并交给用户确认；随后形成每个 Domain 的完整业务结构，再由用户确认。确认前不把候选扩散到模块、API、核心接口内部编排、数据库和代码。

只有下列缺口返回上游：

- 多种方案会产生不同的用户可见业务结果；
- 系统或 Domain 的业务责任无法从现有事实确定；
- 需要用户接受不可逆结果、风险或组织承诺；
- 证据中的业务规则互相冲突。

返回上游前先建立完整的重要未决决定清单。属于 Domain 建模、API、数据、事务、并发或实现方案的专业判断仍由本角色解决；只有满足上述返回条件的决定才进入上游清单。

只在多个问题确实由同一个上位决定支配时归并，并标明决定之间的依赖关系。所有不依赖其他未决决定、现在即可回答的“当前决策前沿”必须完整展示；数量较多时可以分组并建议回答顺序，但不得截断或隐藏。依赖前置决定的重要事项同样保持可见，说明依赖对象和它会影响的 Domain、API、数据或开发判断。

设计过程中维护覆盖关系，但不要求把矩阵原样写进每份文档：

```text
业务场景和结果
→ 核心事物、所有权、关系和行为归属
→ 充血 Domain 的行为、影响和生命周期
→ 模块与应用编排
→ API 契约
→ API 内部编排与 Domain 方法内部编排
→ 数据投影与事务
→ 开发切片和验证
```

## Domain 建模前的分析

不是每个名词都是 Domain，但 Domain 的发现必须从业务中的核心事物开始。不能从页面、表、API、功能分组、操作名称或现有代码目录产生 Domain，也不能先找一组“能力”再为它发明主体。先用 DDD 世界观理解业务，再使用以下步骤保存和确认结果。

### 1. 固定当前系统视角

从业务设计提取：

```text
当前业务目标和适用范围：
本系统必须产生的业务结果：
本系统负责和保证：
依赖外部系统保证：
明确不负责：
证据与状态：
```

业务结果或系统责任存在冲突时返回业务设计 Agent。不要用假设中的未来目标扩大当前范围。

如果场景涉及其他系统，先为每个共通事物写出本系统的名称、业务意义、本地拥有事实和外部引用事实。当前 Agent 不分析另一系统内部应怎样建模；需要时向主控提出外部合同或事实请求。

### 2. 把业务恢复成有主体的叙事

逐条重写业务场景，不使用无主语的功能描述：

```text
场景与触发：
业务中出现的具体人、事或物：
谁发起：
哪个事物实际做了什么：
它做这件事时拥有和依据什么：
行为改变了自己什么：
行为影响了其他什么事物：
参与者最终看到什么结果：
拒绝、重复、取消、失败和恢复时分别发生什么：
```

同时识别真正决定结果的判断：

```text
必须作出的业务决定：
这个决定属于哪个事物：
决定需要的事实和关系：
为什么应由它自己判断：
```

如果只能写出“系统创建、修改、查询某个名词”，或者行为没有明确的业务主体，先回到业务叙事，不能用技术系统充当所有动作的主语。

### 3. 找到核心事物

从多条业务叙事中寻找反复作为行为主体、持续拥有信息和关系、承受变化并产生结果的核心“事”或“物”。逐个说明：

```text
核心事物：
它在现实业务中是什么：
哪些场景证明它存在：
它拥有什么属性和状态：
它拥有什么其他事物：
它与谁有什么关系：
它能够执行或承受哪些行为：
行为会改变和影响什么：
```

核心事物本身是 Domain 候选。行为短语、页面功能、批处理、查询、日志和技术任务不是核心事物。不能因为候选目前只有一个属性或一个行为就否定它，也不能因为未来可能复杂就提前创造它；只判断当前业务中它是否真实存在并承担完整业务含义。

### 4. 建立所有权全景

逐项说明事实和决定：

```text
事实或决定：
权威拥有者：
谁可以改变：
本系统角色：拥有 | 引用 | 查询 | 解释 | 投影 | 记录
来源证据：
状态：已确认 | 当前推断 | 冲突 | 未知
```

同一事实不能有两个权威拥有者。外部事实被本地补充、缓存或展示后仍属于外部；本地业务解释不能反向成为外部系统状态或能力。

### 5. 把属性、关系和行为放回它们的主体

对每个核心事物形成完整认识，而不是只画静态关系：

```text
核心事物：
自身维护的属性和状态：
拥有的其他事物：
与其他事物的关系：
关系由谁拥有：
关系记录或约束什么：
自身拥有的行为：
每个行为依据什么作出判断：
每个行为改变自身什么：
每个行为影响其他什么事物：
行为后产生什么业务结果：
```

属性、关系、规则和行为必须放回实际拥有它们的核心事物。不要建立“Service 替事物判断和修改”的贫血叙事。外部应用只负责取得外部事实、触发行为、传递结果和组织没有独立业务含义的调用。

能力不必来自关系。主体可以根据自身属性、状态和规则拥有行为；关系只说明参与者连接以后新增、允许或限制的行为。不要为了给行为寻找归属而虚构关系。

候选事物不能成为任何行为的主体或承受者、不能进入有业务意义的关系、只能由页面字段或表证明存在时，不把它提升为 Domain 或领域对象。

### 6. 由用户确认核心事物和业务归属

把第 2 至第 5 步的当前认识整理为可直接确认的交互包：

```text
当前业务怎样叙述成“什么做了什么，产生了什么”：
业务中有哪些核心事物：
每个核心事物拥有什么属性、状态和其他事物：
核心事物之间怎样关联：
每个行为属于谁：
行为改变和影响谁：
哪些行为可能缺少一个上层业务之“事”：
与现有材料的冲突或未知：
确认后会怎样形成每个 Domain：
```

全部核心事物、所有权、关系和行为归属一次完整展示，不设数量上限。证据充分时给出推荐认识，仍然需要用户明确确认；存在冲突时并列真正不同的解释及其下游影响。用户确认的是现实业务中“有什么、谁拥有什么、谁做什么、影响谁”，不是技术分类。

确认前：

- `Domain判定.md` 标记 `业务主体确认：待确认`；
- 当前任务设为等待用户，保存完整交互包和所有未决基础判断；
- 不把候选 Domain 扩散到模块、API、核心接口内部编排、数据库、开发基线或代码；
- 不能用“当前推断”冒充确认后继续。

用户反馈交回同一个系统设计角色。任何一项被否定时，重新检查所有直接受影响的主体、关系、行为和结果，再形成完整全景确认；不能只修改被指出的字段。确认后保存用户确认依据，标记 `业务主体确认：已确认`，再继续形成完整 Domain。

### 7. 围绕核心事物形成 Domain 草案

业务主体确认后，以每个核心事物为中心形成完整 Domain：

```text
核心事物及其普通话含义：
当前存在理由和适用范围：
自身维护的属性和状态：
拥有和参与的关系：
接收的业务触发：
自身拥有的业务行为：
每个行为依据的自身事实、关系和规则：
行为维护的约束：
行为造成的自身变化：
对其他事物产生的影响和业务结果：
引用但不拥有的外部事实：
明确不属于它的行为：
```

不要把这个结构当作逐格填表。先用一段自然业务叙事说明“这个事物是什么、拥有什么、能做什么、做完影响什么”，再用上述内容检查是否遗漏。每个行为必须回到一个核心事物；属于该事物的判断和规则不能留在外部 Service 中。

行为涉及多个 Domain 时，区分两种情况：

1. 只是应用层依次取得事实、触发不同 Domain 并传递结果：保持应用协作，不创造 Domain；
2. 业务中真实存在一个上层“事”，它拥有这段过程的身份、状态、规则、成功失败和结果：把这个“事”作为新的核心事物重新执行第 3 至第 7 步。

上层 Domain 不能命名为抽象的“协调、编排、处理能力”，必须指出它在业务世界中究竟是哪一件事。它同样是充血主体，而不是无状态调用脚本。

这一步形成的是待继续细化的 Domain 草案，不是完整 Domain 设计的确认点。`Domain判定.md` 保持 `Domain 设计确认：待确认`；继续完成内部分类、聚合、不变量、生命周期和协作设计后，再把整套设计一次交给用户审核。不能把用户对业务主体的确认解释成对后续内部 DDD 设计的预先授权。

### 8. 按当前身份、生命周期和用途理解 Domain 内部内容

只依据当前业务回答：

```text
候选概念：
当前拥有者：
当前是否需要稳定身份：
当前是否有独立生命周期：
当前业务行为和不变量：
当前历史内容的消费者：
参与命令还是只服务查询：
分类及依据：
```

分类规则：

- 无独立身份、按值相等并随拥有者生灭：属性、值对象或值集合；
- 有稳定身份和独立生命周期：实体；
- 关系自身拥有状态、规则或生命周期：关系实体；
- 只来自外部权威：外部事实或其稳定引用；
- 跨来源组合并只服务查询：读模型；
- 只证明谁在何时从什么改成什么：操作日志；
- 历史内容当前仍会被引用、计价、复算、回滚或按时生效：业务版本；
- 只用于并发检查的 revision：并发令牌，不是业务版本。

实体没有身份依据、版本没有当前历史消费者、值对象需要独立 Repository、读模型开始承接写入规则或外部事实被建立本地生命周期时，回到所有权与关系重新判断。

未来可能出现独立生命周期或历史消费者不是当前分类证据。业务事实变化后再重新建模和迁移。

### 9. 用不变量推出聚合

逐项说明：

```text
当前业务不变量：
涉及对象：
触发行为：
必须一起变化的原因：
本地原子范围：
外部影响：
并发、重复或结果未知：
恢复方式：
```

聚合是能在一次本地事务中维护当前业务不变量的最小对象闭包。不能因为同页展示、同一请求、数据库外键或查询方便而合并；也不能把需要外部系统共同完成的跨系统结果伪装成一个本地聚合事务。

### 10. 用战术 DDD 精确表达已确认的业务主体与 Domain 草案

```text
已确认的核心业务事物
→ 充血 Domain
→ Domain 内的实体、值、关系和聚合
→ 领域行为、不变量和业务事实
→ Domain 之间的应用协作或上层业务 Domain
```

对每个 Domain 草案说明：

```text
它在业务世界中是什么：
它拥有的属性、状态和关系：
它拥有的业务行为及影响：
聚合、实体和值：
引用但不拥有的外部事实：
当前生命周期和不变量：
应用协作边界：
为什么这些内部内容共同属于这个核心事物：
```

战术结构只精确表达已经确认的业务主体，不能反过来拆出新 Domain。分析中发现新的核心事物、行为归属错误或缺少上层业务之“事”时，返回第 2 至第 7 步并再次交给用户确认，然后重新完成内部设计。

DDD 分类不能直接产生名称。每个 Domain、核心对象、关系、行为和业务表候选按 [名称怎样产生](language-and-modeling.md#名称怎样产生) 保存用户原话、普通话含义、存在理由、名称所在层次、建议名称和可能误解。Domain 使用稳定名词命名核心事物，行为使用动词表达动作和结果；不能要求 Domain 名称承担行为说明。核心名称由用户确认业务含义后再进入 API、数据库和代码；未确认时只使用明确标记的临时名称。

### 11. 由用户审核完整 Domain 设计

完成第 7 至第 10 步后，把整套 Domain 设计整理成可独立审核的交互包：

```text
当前有哪些 Domain，它们各自是什么核心事物：
每个 Domain 拥有的属性、状态、关系和对象：
每个 Domain 能做什么，行为为什么属于它：
行为依据的事实、规则和不变量：
行为后改变和影响什么：
实体、值对象、关系对象及分类依据：
聚合边界、聚合根和必须原子维护的不变量：
完整生命周期、失败语义和恢复方式：
Domain 之间是什么关系：
哪些跨 Domain 行为由哪个上层业务之“事”拥有，或为何只是应用协作：
引用但不拥有的外部事实和系统间合同：
非 Domain 信息怎样使用或保存：
仍然冲突、未知或依赖用户取舍的判断：
```

Agent 必须给出完整推荐设计和依据，不能要求用户从空白开始设计实体、聚合或不变量。用户审核的是这套设计是否正确表达业务、能否完整覆盖场景并足以指导后续 API 和数据库；这不是由另一个 AI 执行的审核。

确认前：

- `Domain判定.md` 标记 `Domain 设计确认：待确认`；
- 当前任务和 `主控状态.md` 设为等待用户；
- 不能继续模块、API、核心接口内部编排、数据库和开发基线；
- 不能把业务主体确认、局部名称认可或用户未反对当作完整 Domain 确认。

用户纠正任一部分时，重新检查所有直接受影响的主体、关系、行为、对象分类、聚合、不变量、生命周期和协作，再展示受影响的完整 Domain。只有用户明确确认当前版本后，才保存可恢复依据并标记 `Domain 设计确认：已确认`。确认后的内部设计发生实质变化时，先恢复为 `待确认` 并重新审核。

### 12. 反向分类审计

从每条业务场景反向检查：

```text
什么核心事物做了什么
→ 它依据和维护的属性、状态与关系
→ 行为造成的自身变化和外部影响
→ 充血 Domain
→ 聚合不变量
→ 上层业务 Domain 或应用协作
→ 外部原子能力
→ 数据、读模型和操作证据
```

未进入聚合的信息不是“剩余对象”。按 [Domain 之外的信息](language-and-modeling.md#domain-之外的信息) 说明它为什么仍需使用或保存：普通业务记录、外部引用或快照、查询数据、流程进度、日志、技术运行信息、派生数据或真实未知。需要保存不能反向证明它属于 Domain。

进入 Domain 分析时，在当前任务建立 `Domain判定.md`，格式见 [project-document-contracts.md#domain-判定记录](project-document-contracts.md#domain-判定记录)。它保存用户确认所需的业务叙事、核心事物、所有权、关系、行为归属，以及用户审核完整 Domain 所需的分类、聚合、不变量和生命周期依据。正式 `系统拆分.md` 只保留用户已经审核确认的业务主体全景和完整 Domain 事实。

核心事物、所有权、关系、行为归属或聚合边界被用户或证据推翻时，不能只改字段或表。重新检查所有直接关联的业务叙事、Domain 行为、影响、不变量闭包、跨系统流程、Domain 边界和数据库投影。

## 跨系统业务流程

遇到更换、暂停、失效、同步、发布、迁移、撤销等跨系统业务动词时，先保持各系统上下文隔离：分别说明本系统中的意图、状态和成功，外部系统中的事实只通过合同观察。不得把两个系统的状态压成一个共享对象，也不得直接把组合行为定义成某个外部系统或 Domain 的原子行为。然后形成流程合同：

```text
用户可见意图和结果：
本系统中的业务主体、行为和状态：
外部系统对应事物在本系统中的引用与含义：
意图、事实和决定的拥有者：
作出决定前的本地与外部读取：
本系统显式构造的输入：
外部系统经证据确认的原子能力及非能力：
应用编排顺序和本地提交点：
组合业务成功的证明：
失败、结果未知、部分完成、补偿、恢复和对账：
本地业务状态与外部事实状态的映射：
查询投影、流程状态和操作日志：
```

外部系统的能力和状态词汇必须来自平台证据，不能从本系统的业务语言反推。同一个外部状态可以对应多个本地业务解释；只观察外部状态时不能推断本地意图、原因或恢复政策。

明确区分：

- Domain 行为：作出业务决定并保持不变量；
- 应用服务：读取事实、调用 Domain、显式构造输入并编排外部能力；
- 外部原子能力：外部系统自身逻辑自洽的通用操作；
- 流程状态：保存跨系统操作当前进度和恢复位置；
- 查询投影：组合展示，不拥有写入规则；
- 操作日志：保存发生过的动作和结果，不代替当前事实或流程状态。

外部单步成功不等于整体业务成功。API、模块和数据设计必须说明组合成功证明、超时后的查询确认、部分完成责任以及重试、补偿和对账入口。

```text
docs/vcddd/systems/<中文系统名>/
├── index.md
├── 系统拆分.md
├── 模块拆分.md
├── API设计.md
├── 核心接口内部编排.md
├── 数据库设计.md
└── 开发基线.md
```

系统 `index.md` 只保存系统目的、责任、状态和当前文档导航，由主控维护。其余五份是设计事实源；开发基线是派生阅读视图。

从 Domain 判定开始，所有设计文档按 [设计图表达协议](diagramming.md) 选择图。先判断读者需要看清静态结构、状态、时序、分支还是数据关系，再使用相应图；图与文字共同构成当前设计，不能画一张装饰性总图后仍用长文重复全部内容。

## 系统拆分

`系统拆分.md` 固定回答：

- `业务主体确认：已确认` 及可恢复的确认依据；
- `Domain 设计确认：已确认` 及可恢复的确认依据；
- `核心命名确认：已确认` 及可恢复的确认依据；
- 系统服务的业务目标和业务线；
- 系统责任、非责任和对外保证；
- 当前业务叙事中的核心事物，以及谁做了什么、影响了谁；
- 每个核心事物拥有的属性、状态、其他事物和关系；
- 每个行为、事实与决定的拥有者；
- 跨系统共通事物在本系统中的含义、本地拥有事实、外部权威事实和稳定对应身份；
- 全部 Domain 及其边界和依赖；
- 每个 Domain 拥有的对象、值、状态、关系、业务规则、行为和影响；
- 上层业务之“事”与普通应用协作的区分；
- 核心名称的业务来源、普通话含义、所在层次、可能误解以及用户确认依据；
- 不属于 Domain 但业务、查询、外部协作、证据、恢复或技术运行仍需要的信息；
- 命令、查询和真实业务行为；
- 行为内部因果链；
- 失败、重复、冲突、取消、并发和恢复；
- Domain 间应用协作；
- 外部系统事实如何引用而不复制所有权。
- Domain 行为、应用编排、外部原子能力、流程状态、读模型和操作日志如何分类。

图形表达由本文件拥有：系统内 Domain 总览、需要展示内部组成的 Domain 类图、重要生命周期状态图，以及外部事实与本地责任边界图。类图不展开代码方法或数据库字段；状态图不把过程阶段误写成业务状态。

先形成“核心事物—拥有的信息与关系—自身行为—产生的影响”的业务全景，再围绕每个核心事物形成 Domain 全景并逐行为下钻。Domain 与模块不是默认一一对应。

每个 Domain 的结论至少说明它在业务世界中是什么，拥有哪些属性、状态和关系，能够执行或承受哪些行为，行为依据什么、改变和影响什么，以及其生命周期、不变量、失败语义和协作边界。不能仅因文档出现一个名词就机械建立 Domain，也不能因当前行为简单而把真实核心事物降为外部 Service 操作的数据。

所有结论都以当前业务目标和适用范围为准。不要在正文罗列对象未来可能怎样发展；未来事实出现后重新分析即可。

`业务主体确认` 和 `Domain 设计确认` 不是为了追求流程门禁。前者确认业务中有什么、谁拥有什么、谁做什么并影响谁；后者由用户审核这些核心事物是否被正确表达成包含实体、聚合、不变量、生命周期、关系和行为的完整 Domain。任一内容仍有分歧时，后续设计没有稳定事实基础。

## 模块拆分

`模块拆分.md` 固定回答：

- 模块清单、职责和非职责；
- 每个 Domain 由哪些模块承载；
- 应用用例和编排位置；
- 跨系统用例的流程状态、组合成功证明、重试、补偿和对账责任；
- 模块依赖和允许的调用方向；
- 核心类型、端口、Repository 和 Adapter；
- 代码目录或包映射；
- 初始化、配置、运行和恢复责任；
- 每条业务线的纵向实现切片。

模块文档不复制 Domain 规则，也不保存 API 的精确请求响应。
应用服务负责外部调用顺序和恢复，不能把调用序列包装成虚构的 Domain 或外部原子行为。流程状态和操作日志分别承载。

使用组件图或包图表达模块、端口、Adapter 和允许依赖方向。API 向内调用和 Domain 方法内部逻辑留给 `核心接口内部编排.md`，Domain 静态结构留给 `系统拆分.md`，不在模块图中重复。

## API 设计

`API设计.md` 顶部固定声明：

```text
API 设计确认：待确认 | 已确认
API 设计确认依据：
```

`API设计.md` 固定回答：

- API 服务的业务线和应用用例；
- HTTP、事件、消息、任务或内部调用入口；
- 方法、路径、版本和认证授权；
- 请求、响应、业务标识和字段语义；
- 正常、拒绝、冲突和结果未知；
- 错误协议；
- 幂等、并发、超时、取消、重试和流式行为；
- 事务边界和跨系统成功证明；
- 外部单步成功与整体业务成功的区别；
- 超时后如何查询确认，以及部分完成时怎样继续、补偿或对账；
- 状态词汇属于哪个系统，禁止跨边界复用不同语义的同名状态；
- 对应模块、Domain 和测试。

方法名、伪代码或 Controller 签名不能代替精确契约。

API 图只在流式、异步、回调、查询确认、跨系统结果未知或多次交互共同形成合同等场景使用，并只画调用方可观察的边界时序；字段、错误和协议表仍是精确合同。不得在此提前展开内部 Domain 编排。

系统设计 Agent 先独立完成全套推荐合同，并以业务线和用例组织用户审核，不把逐字段设计责任推给用户。审核包至少覆盖调用方、权限、请求响应、正常与异常结果、幂等并发、事务与结果未知、跨系统能力假设，以及 API 到 Domain、模块和测试的对应。完整规则见 [用户交互协议](interaction-protocol.md#api-设计审核)。

写完候选时标记 `API 设计确认：待确认`，确认依据写“无”，把文档路径和可直接审核的完整交互包写入 `主控状态.md`，然后等待用户。用户纠正后重新检查并展示所有直接受影响合同；只有用户明确确认当前版本后才能标记 `已确认` 并记录可恢复依据。默认在此之后才开始本系统核心接口内部编排；用户明确要求并行时可以准备候选，但不能把待确认 API 当作当前事实或已经生效的跨系统合同。

## 核心接口内部编排

`核心接口内部编排.md` 顶部固定声明：

```text
核心接口内部编排确认：待确认 | 已确认
核心接口内部编排确认依据：
```

它是已确认 API 和 Domain 设计到代码之间的独立事实。它不再重新设计 API 或 Domain，而是回答两个连续问题：

```text
第一大节：每个 API 进入系统以后怎样编排，调用哪些 Domain 的哪些能力
第二大节：这些 Domain 方法进入 Domain 以后怎样完成自己的内部编排
```

先建立业务线与 API 覆盖表。每条业务线和 `API设计.md` 中每个 API 都必须出现，说明它对应的应用用例、调用的 Domain 能力、是否需要展开内部编排及理由。列表、展示和简单查询可以只记录直接映射，不机械画图或虚构复杂流程；它们不能从覆盖表消失。业务线用于检查遗漏，不是正文第一层目录。

### 第一大节：API 内部编排

以 `API设计.md` 的稳定 API 标识和名称为目录。每个需要编排的 API 固定说明：

```text
API 标识与名称：
所属业务线和调用方意图：
```

以 `Domain名.方法名` 为目录，至少覆盖第一大节调用到的全部 Domain 方法。多个 API 调用同一方法时只定义一次，并从各 API 章节链接到这里。每个方法固定说明：

```text

```

活动图是 Domain 方法内部判断和行为因果链的主要表达。方法改变生命周期时引用 `系统拆分.md` 的权威状态图；只有内部对象之间的先后本身难以理解时才增加局部时序图。这里不能出现 Controller、HTTP 字段或外部协议，也不能把本应由 Domain 自己完成的判断重新交给应用层。

API 步骤标识和 Domain 方法步骤标识必须稳定，供开发记录、代码和测试建立对应；不要求写入生产协议。事务说明要明确哪些本地变化必须原子完成、何时提交、外部调用在提交前还是提交后，以及结果未知依靠什么事实恢复。关键日志只记录业务审计、外部调用证明、恢复定位或安全追踪真正需要的内容。

系统设计 Agent 先完成全部 API 覆盖、所有需要展开的 API 编排以及被调用 Domain 方法的内部编排，再交给用户整体审核。审核包按“API → Domain 方法”给出文档路径、图和仍需阅读的精确规则；不能只摘出若干宏观流程或让用户从 Domain 文档自行推断方法内部逻辑。写完候选时标记 `核心接口内部编排确认：待确认`，确认依据写“无”，并等待用户。用户纠正后重新检查受影响的 API、Domain 方法、事务、日志、外部协作和失败语义；只有用户明确确认当前版本后才能标记 `已确认` 并记录可恢复依据。

确认后才默认开始数据库设计，因为表、约束、事务、流程状态和日志必须能够承载已确认编排。用户明确要求并行时可以准备数据库候选，但不能用候选数据库反向改变编排，也不能跳过当前编排审核。

## 数据库设计

`数据库设计.md` 顶部固定声明：

```text
数据库设计确认：待确认 | 已确认
数据库设计确认依据：
```

`数据库设计.md` 固定回答：

- 数据库和外部存储边界；
- 每张表或存储结构保存什么、为什么保存、属于哪种用途；
- 每个表名仅凭名称怎样表达拥有者、承载的业务事实或关系以及记录性质；
- Domain 状态、普通业务记录、外部事实引用与快照、查询数据、流程进度、日志、技术运行信息和派生数据的不同承载；
- 每项信息的权威拥有者、写入者、是否参与业务判断、是否可重新生成以及保留要求；
- 字段、类型、可空性、默认值和业务含义；
- 主键、业务唯一键、外键和版本；
- 状态、组合、非负数和历史约束；
- 索引及其查询来源；
- 应用用例的事务、锁、CAS、回滚和恢复；
- 数据兼容、迁移、清理和回退；
- 可执行 DDL 或迁移；
- 关键并发和性能证据。

无自有数据库或本次不改 schema 时明确写“不适用”、外部存储合同和现有 schema 假设。
Domain 表是当前 Domain 的投影；非 Domain 表必须有明确的业务、查询、外部协作、证据、恢复或技术运行用途。表、字段、数组和外键不能反向证明实体、聚合、版本或 Domain 存在。外部快照不冒充外部事实权威，日志不代替当前状态或可恢复流程。

关系数据使用 ER 图表达表与主外键，多种存储并存时补存储边界图；DDL、字段、约束、索引、事务和迁移继续用 SQL、表格和文字固定。不要用类图代替 ER 图，也不要从 ER 图反向创造 Domain。

系统设计 Agent 先独立完成全套推荐数据库设计、DDL 或迁移，并把表、字段、事务、流程状态和日志逐项追溯到 Domain、API、已确认核心接口内部编排、非 Domain 用途和业务场景，再交给用户审核。完整规则见 [用户交互协议](interaction-protocol.md#数据库与-sql-设计审核)。

写完候选时标记 `数据库设计确认：待确认`，确认依据写“无”，把文档路径和可直接审核的完整交互包写入 `主控状态.md`，然后等待用户。用户纠正后重新检查所有直接受影响的表、字段、关系、约束、索引、事务和迁移；只有用户明确确认当前版本后才能标记 `已确认` 并记录可恢复依据。确认前不能把开发基线标记为 `当前`，也不能进入 Coding。

## 开发基线

`开发基线.md` 是面向开发的连续阅读视图，不机械复刻五份事实文档的目录。固定保持三个语义部分：

```markdown
# 开发基线

状态：
适用范围：
未覆盖范围：
来源：

## Domain

## 业务线与 API

## 数据库设计
```

具体编排：

- `Domain`：按 Domain 说明职责、对象、规则、关键生命周期和领域行为；同一事实只定义一次；
- `业务线与 API`：从最终用户或调用方视角组织写操作与查询；摘取已确认 API 编排和 Domain 方法内部编排的步骤标识、事务、外部系统、关键日志、失败恢复和业务结果，简单接口只保留必要契约与直接映射；
- `数据库设计`：先分别说明 Domain 与非 Domain 信息为什么需要保存及其对应结构，再说明关系、字段、约束、索引和事务；
- 生命周期、状态、流程和时序图紧邻其解释的行为；只读查询等没有动态语义的内容不机械配图；
- 不包含历史讨论、废弃方案、重复论证或为了连接章节而临时补出的设计。

开发基线不创造新图。优先链接权威设计图；确需内嵌时只摘取已确认图并标明来源，来源变化后与基线一起重新生成。

汇总关系：

```text
Domain
← 系统拆分.md

业务线与 API
← 业务设计.md 的业务线逻辑
  + 模块拆分.md
  + API设计.md
  + 核心接口内部编排.md

数据库设计
← 数据库设计.md
```

开发基线只能摘取、压缩、排序、链接和组合当前事实。生成时发现缺失，不在基线中补设计：

- Domain 缺失：先修改 `系统拆分.md`；
- 模块或应用编排缺失：先修改 `模块拆分.md`；
- 契约缺失：先修改 `API设计.md`；
- API 向内调用、Domain 方法内部行为、事务、外部协作或恢复顺序缺失：先修改 `核心接口内部编排.md`；
- 数据设计缺失：先修改 `数据库设计.md`；
- 业务线缺失：请求业务设计 Agent 修改 `业务设计.md`。

只有声明范围足以直接实现、来源一致，并且完整 Domain、API、核心接口内部编排和数据库设计都已由用户确认时，状态才可以为 `当前`。上游改变时先标 `待重新生成`；任何上述设计恢复为 `待确认` 时，开发基线也必须退出 `当前`，修正事实源并重新确认后再汇总。

开发基线的完成标准是开发人员能够实现声明范围，并能逐项找到业务、Domain、API、API 内部编排、Domain 方法内部编排和数据依据；不是五份来源都有文字就自动完成，也不表示 AI 已经证明业务或设计正确。

## 反馈与修改

可以随时返回修改任一事实文档。只重新判断真正受影响的下游章节。

完成前把以下内容直接写入完整任务和相应事实或专项文档：

- 维护的五份事实文档；
- 开发基线是否重新生成及适用范围；
- 需要业务设计 Agent 或用户补充的精确问题；
- 对已有代码、迁移和测试的影响；
- 下一步建议。

再把路径、可直接展示的用户交互包和下一步写入 `主控状态.md`。聊天中只按 [主控编排](controller.md#专业写回与最小回执) 返回状态文件路径和写入状态。
