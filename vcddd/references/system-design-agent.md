## 目标

一次只站在一个系统视角，形成能独立指导领域理解、模块实现、调用契约和数据实现的事实文档，再把这些事实汇总成开发基线。

## 输入与边界

读取：

- 相关阶段性目标的 `业务设计.md`；
- 当前系统 `index.md`；
- 当前任务和待处理反馈；
- 直接相关代码、平台文档和验证证据。

业务设计中的系统责任和业务线是上游事实。发现它们不足或冲突时向主控提出具体修订请求，不直接修改 `business/`。

不要从现有仓库目录机械推导 Domain 或模块。代码可以证明现实约束，不能自动成为理想设计。

## 固定事实文档

```text
docs/vcddd/systems/<中文系统名>/
├── index.md
├── 系统拆分.md
├── 模块拆分.md
├── API设计.md
├── 数据库设计.md
└── 开发基线.md
```

系统 `index.md` 只保存系统目的、责任、状态和当前文档导航，由主控维护。其余四份是设计事实源；开发基线是派生阅读视图。

## 系统拆分

`系统拆分.md` 固定回答：

- 系统服务的业务目标和业务线；
- 系统责任、非责任和对外保证；
- 全部 Domain 及其边界和依赖；
- 每个 Domain 拥有的对象、值、状态和业务规则；
- 命令、查询和真实业务行为；
- 行为内部因果链；
- 失败、重复、冲突、取消、并发和恢复；
- Domain 间应用协作；
- 外部系统事实如何引用而不复制所有权。

先形成全局 Domain 全景，再逐行为下钻。Domain 与模块不是默认一一对应。

## 模块拆分

`模块拆分.md` 固定回答：

- 模块清单、职责和非职责；
- 每个 Domain 由哪些模块承载；
- 应用用例和编排位置；
- 模块依赖和允许的调用方向；
- 核心类型、端口、Repository 和 Adapter；
- 代码目录或包映射；
- 初始化、配置、运行和恢复责任；
- 每条业务线的纵向实现切片。

模块文档不复制 Domain 规则，也不保存 API 的精确请求响应。

## API 设计

`API设计.md` 固定回答：

- API 服务的业务线和应用用例；
- HTTP、事件、消息、任务或内部调用入口；
- 方法、路径、版本和认证授权；
- 请求、响应、业务标识和字段语义；
- 正常、拒绝、冲突和结果未知；
- 错误协议；
- 幂等、并发、超时、取消、重试和流式行为；
- 事务边界和跨系统成功证明；
- 对应模块、Domain 和测试。

方法名、伪代码或 Controller 签名不能代替精确契约。

## 数据库设计

`数据库设计.md` 固定回答：

- 数据库和外部存储边界；
- 每张表及其 Domain 状态或查询来源；
- 字段、类型、可空性、默认值和业务含义；
- 主键、业务唯一键、外键和版本；
- 状态、组合、非负数和历史约束；
- 索引及其查询来源；
- 应用用例的事务、锁、CAS、回滚和恢复；
- 数据兼容、迁移、清理和回退；
- 可执行 DDL 或迁移；
- 关键并发和性能证据。

无自有数据库或本次不改 schema 时明确写“不适用”、外部存储合同和现有 schema 假设。

## 开发基线

`开发基线.md` 是面向开发的连续阅读视图，不机械复刻四份事实文档的目录。固定保持三个语义部分：

```markdown
# 开发基线

状态：
适用范围：
未覆盖范围：
来源：

## Domain

## 业务线与 API

## 数据库设计
```

具体编排：

- `Domain`：按 Domain 说明职责、对象、规则、关键生命周期和领域行为；同一事实只定义一次；
- `业务线与 API`：从最终用户或调用方视角组织写操作与查询，说明涉及的 Domain、外部系统、编排顺序和业务结果；内容较多时可以在本节内拆分“业务操作”和“信息查询”；
- `数据库设计`：先给出 Domain 信息为什么需要保存以及对应的表，再说明关系、字段、约束、索引和事务；
- 生命周期、状态、流程和时序图紧邻其解释的行为；只读查询等没有动态语义的内容不机械配图；
- 不包含历史讨论、废弃方案、重复论证或为了连接章节而临时补出的设计。

汇总关系：

```text
Domain
← 系统拆分.md

业务线与 API
← 业务设计.md 的业务线逻辑
  + 模块拆分.md
  + API设计.md

数据库设计
← 数据库设计.md
```

开发基线只能摘取、压缩、排序、链接和组合当前事实。生成时发现缺失，不在基线中补设计：

- Domain 缺失：先修改 `系统拆分.md`；
- 模块或应用编排缺失：先修改 `模块拆分.md`；
- 契约缺失：先修改 `API设计.md`；
- 数据设计缺失：先修改 `数据库设计.md`；
- 业务线缺失：请求业务设计 Agent 修改 `业务设计.md`。

只有声明范围足以直接实现并且来源一致时状态为 `当前`。上游改变时先标 `待重新生成`，修正事实源后重新汇总。

## 反馈与修改

可以随时返回修改任一事实文档。只重新判断真正受影响的下游章节。

返回主控：

- 维护的四份事实文档；
- 开发基线是否重新生成及适用范围；
- 需要业务设计 Agent 或用户补充的精确问题；
- 对已有代码、迁移和测试的影响；
- 下一步建议。
