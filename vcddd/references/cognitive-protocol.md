## 目标

不要依靠“产品经理、架构师、开发者、审核员”等身份暗示工作。每个专业 Agent 必须由结果责任、核心判断、探索路线、风险触发器和结果合同约束。

专业 Agent 的工作不是逐项填满模板，而是让下一位读者能够据此完成自己的判断。

## 审核边界

业务设计和系统设计 Agent 不审核业务或设计，不输出“通过 / 不通过”。它们调查、分析、提出方案、暴露缺口和维护事实；业务含义是否符合真实需要只能由用户确认。

只有代码形成固定快照后才调用审核 Agent。代码审核判断实现是否符合已经确认的事实以及工程质量是否可接受，不反向证明业务或设计本身正确。

## 语言先于抽象

所有角色遵守 [业务语言与建模边界](language-and-modeling.md)。先用用户词汇和普通话说清现实中的人、事情、动作、规则与变化，再进入专业分类。

业务阶段只有元关键词可以组织内容，其他抽象词不能成为结论。Domain 阶段可以使用 DDD 术语，API、数据库和代码阶段可以使用各自必要的精确技术名称；后层术语不能反向改写前层业务。

Domain 阶段以后，优先用 [设计图表达协议](diagramming.md) 把已经形成的结构、关系、状态和时序外化，再用文字精确定义规则。图帮助发现遗漏和冲突，但图形语法、布局方便或现成 UML 模式不能反向创造业务对象、状态、模块或流程。

任何抽象结论都必须能指回具体来源、普通话含义和可由用户判断真假的业务描述。不能还原时删除抽象词，保留未知。

## 先确定结果合同

开始前明确：

```text
本次结果供谁使用：
使用者需要据此判断或完成什么：
错误或遗漏会造成什么：
必须形成的文档、代码；仅当对象是固定代码快照时才可能形成审核结果：
```

若完整任务没有说明，先从角色 reference 和目标推导；多个解释会改变工作方向时，把冲突写入任务和 `主控状态.md`，再向主控返回最小回执。

## 按三级关注组织注意力

### 核心判断

任何同类任务都必须建立。缺失时不能把范围声明为已经完成。

### 条件判断

只有事实触发风险时展开。常见触发器包括金额、权限、敏感信息、不可逆行为、批量处理、并发、重复请求、长时间任务、外部系统、迁移和法规。

每次展开都说明触发事实及其对结果的影响。不要因为 reference 提到某种风险就在所有项目中机械讨论。

### 补充判断

命名偏好、未来扩展、非当前优化和不改变业务结果的建议，只在核心判断和已触发条件判断稳定后处理。不得让它们占据主要篇幅或阻断主线。

## 只为当前目标设计

只依据当前已确认的目标、业务线、约束和证据形成业务、设计和实现。未来可能增加审批、独立管理、历史引用、容量或复杂规则，不能成为当前新增对象、状态、版本、Domain、模块、表或基础设施的依据。

当前设计只需最小充分：

- 完整实现声明范围的业务结果；
- 正确表达当前所有权、关系、生命周期和不变量；
- 能被当前代码与验证可靠实现；
- 不复制事实，也不引入没有当前消费者的复杂机制。

业务发展后重新划分对象、聚合、Domain、API 和数据是正常演进，不表示当前较小的设计错误。不得为了避免未来迁移而提前支付当前复杂度。

## 探索并收敛

对每个核心判断：

1. 从指定来源提取事实，不让用户重复整理已有材料；
2. 形成当前最能解释事实的答案；
3. 主动寻找反例、遗漏场景和竞争解释；
4. 只有存在实质不同的选择时形成少量候选；
5. 使用本角色的结果标准比较，不罗列没有影响的选项；
6. 给出当前结论、依据、状态和影响；
7. 无法判断时保留未知并请求正确的事实拥有者处理。

可以自由选择调查顺序、建模方法和解决方案。不得跳过核心判断，也不得为了填满结构制造事实。

## 保持可恢复的判断状态

尚未被正式事实文档吸收的内容保存在当前任务：

```text
关注问题：
级别：核心 | 条件 | 补充
触发事实：
当前答案：
依据：
状态：已确认 | 当前推断 | 存在冲突 | 尚未确定
竞争解释：
对本阶段结果和下游的影响：
下一步：
```

这不是要求公开内部推理。只保存能让另一个 Agent 恢复判断的证据、选项、结论和缺口，不保存思维流水。

答案稳定后写入对应事实文档，并从任务中的未决判断移除。简单任务不额外创建决策文档；需要长期追溯的重要竞争方案再按项目约定保存。

## 控制主次

优先处理会改变以下内容的问题：

1. 业务行为或最终结果；
2. 系统、Domain 或模块责任；
3. 对象生命周期或业务不变量；
4. API、数据和跨系统正确性；
5. 代码是否能够被验证为符合设计。

全部不会改变时降为补充判断。

不要用数量上限控制问题，也不要把未决判断平铺成互不相关的问题清单。先建立完整的重要未决决定清单：

1. 排除属于当前角色专业责任、应由 Agent 自行形成方案的事项；
2. 只有确实由同一个上位决定支配时才语义归并，不能为了减少数量合并不同取舍；
3. 标明决定之间的依赖关系，识别不依赖其他未决决定、现在即可回答的“当前决策前沿”；
4. 完整展示当前决策前沿；数量较多时按业务对象或影响范围分组，并建议回答顺序，不得截断或隐藏；
5. 依赖前置决定的重要事项也保持可见，但标明依赖对象和暂不要求回答的原因。

每个需要用户参与的决定使用决策包：

```text
需要决定的核心问题：
当前材料支持的答案：
推荐选择及理由：
真正不同的备选：
这个决定会解锁或改变什么：
依赖的决定：
状态：当前决策前沿 | 等待前置决定
```

重要与否以它是否改变业务结果、责任、生命周期、风险承诺或开发正确性判断，不以问题数量决定。完整清单和当前前沿都保存在任务判断状态中；上位决定或新证据出现后重新计算前沿。

## 分离思考与成文

关注地图决定如何调查，不决定最终文档目录。

先建立判断、挑战解释并收敛，再按照目标读者的理解顺序写文档。正式文档只保留当前事实、必要依据、明确未知和适用范围，不保留废弃方案、重复论证和想到问题的先后顺序。

## 用户参与

Agent 自己完成调查、归纳、候选形成和专业判断。只把下列内容交给用户：

- 证据无法证明的真实业务意图和组织现实；
- 多个合理方案之间的价值取舍；
- 高影响承诺、风险接受和不可逆决定；
- 原型或实现是否表达了预期结果。

系统设计中的事实与决定所有权、主体自有能力、事物关系及关系新增或约束的业务能力是例外：专业 Agent 负责调查和形成推荐认识，但必须由用户明确确认后，才能继续 Domain、API、核心业务流程和数据库推导。

缺少技术细节不等于需要用户决定。属于当前角色责任的建模、API、数据、并发或实现判断，由专业 Agent 给出方案和依据；固定代码快照的审核判断由代码审核 Agent 给出。只有它们会改变业务结果、责任边界、风险承诺或价值取舍时才上抛。

提问前先给当前认识、依据、推荐判断和不同选择的实际影响。
