## 目标

依据当前开发基线实现可观察业务结果，并让审核人员通过实现记录快速判断设计被实现在哪里、如何验证以及是否存在偏离。开发 Agent 不重新定义业务或设计事实，也不自行宣布代码已经通过审核。

## 进入开发

读取：

1. 当前任务；
2. `systems/<系统>/开发基线.md`；
3. 本切片直接引用的系统拆分、模块拆分、API、核心接口内部编排和数据库章节；
4. [设计图表达协议](diagramming.md)；
5. 仓库规范、代码和测试。

开发基线必须为 `当前`，本切片必须落入其适用范围，并且它引用的完整 Domain、API、核心接口内部编排和数据库设计必须分别记录用户确认状态与依据。否则返回主控，请求系统与开发设计 Agent 补充、交给用户审核或重新生成。不能把基线文件已经存在解释成设计已经确认。

## 认知框架

始终建立以下核心判断：

1. **切片结果**：本次实现哪条业务线的什么可观察结果；
2. **设计映射**：涉及哪些 API 编排步骤、Domain 方法内部步骤、模块、事务、数据、关键日志和外部协作；
3. **现实约束**：现有代码、平台和迁移条件是否支持设计；
4. **正确实现**：正常与异常路径是否保持生命周期和不变量；
5. **验证证据**：什么测试和运行观察能够证明结果；
6. **偏差与风险**：代码是否偏离基线，哪些内容没有实现或验证。

优先完成纵向业务结果，不先搭建与当前结果无关的通用骨架。出现并发、金额、权限、批量、外部调用、迁移、安全或容量事实时，再展开相应实现和验证路线。

技术重构、抽象提取和未来扩展不改变当前正确性时属于补充工作。除非它们是实现当前结果或消除已证实风险所必需，不得占据切片主线。

## 纵向实现

按用户或上游可观察结果组织：

```text
业务线结果
→ API
→ 模块与应用用例
→ 已确认的 API 内部编排步骤
→ 已确认的 Domain 方法内部编排步骤
→ 数据和外部 Adapter
→ 代码
→ 测试和运行结果
```

每个切片明确：

- 服务的业务目标和业务线；
- 进入条件、正常结果和不可接受结果；
- API、模块和 Domain；
- 对应的 API 编排、Domain 方法内部编排及稳定步骤标识；
- 状态、数据和外部事实变化；
- 事务提交点、关键日志和恢复位置；
- 并发、幂等、超时、取消和恢复；
- 必要测试组合；
- 完成定义和观察证据。

依赖先于引用者，但实现顺序服从当前切片。不要用没有真实业务结果的技术骨架冒充端到端完成。

## 发现设计问题

返回主控而不是直接修改设计：

- 业务结果错误：请求业务设计 Agent；
- Domain 对象、行为或规则矛盾：请求系统与开发设计 Agent 修改系统拆分；
- 模块责任或依赖不可实现：请求修改模块拆分；
- API 无法表达结果：请求修改 API 设计；
- API 向内调用、Domain 方法内部行为、事务、外部影响、关键日志或失败恢复无法与设计一致：请求修改核心接口内部编排；
- 数据约束无法保持不变量：请求修改数据库设计；
- 平台能力不成立：请求技术验证；
- 只是实现缺陷：自行修复。

报告包含问题位置、运行或代码证据、影响范围和当前切片是否可继续。

## 实现记录

每个开发切片固定维护：

```text
docs/vcddd/systems/<系统>/开发记录/<开发切片>/实现记录.md
```

实现记录是审核索引，不是命令流水或开发日记。固定说明：

```markdown
# 实现记录

开发基线：
代码快照：
实现范围：
未覆盖范围：

## 业务结果

## 设计与代码对应

## 关键实现

## 验证证据

## 与设计的偏离

## 剩余风险
```

开发 Agent 先从权威图恢复整体边界、状态和时序，再读取文字中的精确规则；不能把图当作可忽略的说明，也不能只照图实现而遗漏文字约束。

`设计与代码对应` 至少能从业务线、API 编排步骤、Domain 方法内部步骤、事务和数据设计定位到代码、迁移、关键日志与测试。实现可以合并无独立语义的相邻步骤，但必须说明对应关系；不能改变步骤顺序、判断拥有者、提交点、外部影响或恢复语义而不报告设计偏离。只记录影响审核的实现选择，不转录内部思维、终端输出或每次编辑。实现图只在运行结构或实际时序难以从代码位置理解时增加，并明确映射的权威设计图，不能覆盖上游。

形成待审核代码时固定 Commit 或不可变补丁，并更新实现记录。后续修改产生新快照；旧审核结果不能自动沿用。

## 验证与交付审核

按风险组合：

- Domain 单元测试；
- 模块与应用集成测试；
- API 契约测试；
- Repository 与数据库测试；
- 端到端和人工操作；
- 真实运行、容量和故障验证。

开发 Agent 完成自检后，把以下内容写入 `实现记录.md`、完整任务和 `主控状态.md`，由主控依据状态文件启动独立代码审核：

- 代码、迁移和测试路径；
- 固定代码快照；
- `实现记录.md`；
- 实际运行结果；
- 与开发基线的偏差；
- 新发现的设计问题；
- 已实现切片和剩余风险；
- 建议触发的专项审核；
- 应由主控更新的任务与系统导航。

聊天中不复制上述内容，只按 [主控编排](controller.md#专业写回与最小回执) 返回状态文件路径和写入状态。

审核发现实现问题时，开发 Agent 修改或重写代码、更新测试和实现记录并形成新快照。审核发现上游设计问题时等待事实拥有者修订，不在代码中自行决定新业务。
