## 语言顺序

始终按以下方向工作：

```text
用户原话、现实场景和已有证据
→ 普通人能够直接判断真假的业务描述
→ 用户确认
→ Domain 分析与 DDD 分类
→ API、数据库和代码
```

禁止从行业黑话、DDD 模式、表结构、框架或实现动作反向猜测业务。

用户或权威来源已经使用并明确指向现实事物的名称可以保留。Agent 自己引入的抽象词不能成为业务事实。

## 业务阶段的元关键词

业务发现和 `业务设计.md` 只允许使用帮助寻找事实的元关键词：

```text
谁
在什么情况下
为什么
做什么
发生什么变化
什么算完成
谁拥有
谁决定
与谁有什么关系
来源
状态
范围
未知
下一步
```

元关键词只能作为标题、问题或信息位置，不能充当答案。正文必须写实际的人、事物、动作、规则和结果。

“能力”只能作为“谁能做什么”的位置，答案必须使用具体动词。除非来自用户原话并已有明确定义，否则禁止用闭环、赋能、抓手、沉淀、治理、体系化、全链路、统一承载、能力建设等抽象词替代业务。

## 有效业务结论

业务结论必须满足：

1. 使用用户已有词汇或立即给出普通话定义；
2. 指出具体的人或事物；
3. 说明发生的动作、判断或变化；
4. 说明在什么情况下成立；
5. 用户能够直接回答“对 / 不对”；
6. 必要时能给出一个真实例子或反例。

去掉元关键词后，如果一句话没有留下具体的人、事情、变化或规则，它不是结论，必须重写或删除。

例如，不能写：

```text
建立统一配置能力，覆盖全生命周期，实现业务闭环。
```

应写成：

```text
运营人员给用户更换 Key 后，旧 Key 继续保留历史用量；
新 Key 承接之后的请求；更换未全部完成时显示停在哪一步并允许继续处理。
```

## Domain 阶段的 DDD 语言

进入 Domain 分析后可以使用 Domain、实体、值对象、聚合、领域行为、领域服务、生命周期和不变量等 DDD 术语。它们是分类已确认业务事实的语法，不是业务内容来源。

使用这些术语之前，先用 DDD 的方式理解业务叙事：

```text
业务中客观存在的核心事或物
+ 它拥有的属性、状态和关系
+ 它能够执行或承受的业务行为
+ 行为造成的自身变化和外部影响
= 一个需要作为完整主体理解的 Domain
```

业务最终总能回到“什么做了什么，产生了什么”。Domain 首先是这句话中客观存在的核心主体，不是行为短语、功能集合或一组数据。属性、关系、判断和行为共同属于这个主体；不能把规则和行为全部放在外部服务中，再把 Domain 留成只供读写的数据结构。

一个行为涉及多个 Domain 时，先寻找业务中是否存在一个真实的上层“事”拥有这段过程、状态和结果。只有这个“事”本身在当前业务中存在，才把它建模为上层 Domain；不能因为代码需要调用多个模块就创造“协调、编排、处理”Domain。

每个 DDD 判断都必须能够返回一条已确认的普通话业务描述：

- `实体`：业务为什么需要跨时间认出还是同一个东西；
- `生命周期`：它何时出现、允许怎样变化、何时不再使用；
- `不变量`：无论怎样操作都必须成立的具体规则；
- `聚合`：哪些变化为什么必须在一次本地提交中一起完成；
- `Domain`：业务中的哪个核心事物拥有这些属性、关系、判断和行为，并能作为一个完整主体说明。

DDD 没有合适分类时保留业务事实，不得删减、改写或强迫业务适配模型。DDD 用来发现和表达业务，不限制业务。

## 名称怎样产生

DDD 类型可以说明一个东西是什么，不能决定它叫什么，也不能证明它应该存在。

合格名称必须自解释：

- Domain 名称使用稳定名词，准确指向业务中的核心事物；不要求把全部行为压进名称；
- 领域行为名称使用动词，说明谁做什么以及产生什么业务结果；
- 只看业务对象或关系名称，就能知道它代表现实中的什么以及归谁所有；
- 只看表名，就能知道它保存哪项业务事实、关系、日志、快照、流程进度或技术状态；
- 页面名称和文案只需在实际页面语境中无歧义，不承担 Domain 或数据库名称的职责；
- 各层名称不阅读内部实现和长篇定义，也不会被误解成另一类业务。

Domain 名称回答“这是什么”，行为名称回答“它做什么”，表名回答“这里保存什么”。不能为了让 Domain 名称解释所有行为而把它写成长动作句；也不能用“管理、服务、能力、处理”掩盖尚未找到的核心事物。如果必须先阅读说明才能知道名称指向什么，优先回到业务主体、事实、所有权和关系重新判断。

每个 Domain、核心对象、关系和业务表名称都保存以下对应：

```text
用户原话或业务来源：
普通话含义：
谁拥有、与谁有什么关系：
为什么当前需要单独存在：
DDD 分类：
建议名称：
名称所在层次：Domain | 行为 | 对象或关系 | 页面 | 数据库
只看名称或结合其实际页面语境能够理解什么：
这个名称不能被误解为什么：
对应保存的信息或表：
```

名称优先来自用户和业务来源。新名称必须先给出普通话含义，并由用户确认核心业务含义。只有“统一管理、灵活配置、策略扩展、方便治理、未来演进”之类理由时，不创建对象、Domain 或业务表。

管理、配置、规则、策略、关系、记录、详情、信息、能力、服务、中心等泛化词不能单独承担业务含义。只有完整名称仍能让人直接理解具体业务时才可使用。

核心名称变化时，重新检查受影响的 Domain、API、表、字段和代码名称；不能只做文字替换而保留旧含义。

## Domain 之外的信息

不是所有需要使用或保存的信息都需要 Domain。未进入 Domain 不是遗漏，而可以是明确、正确的结论。

逐项按真实用途判断：

- 需要 Domain 维护的业务状态与规则；
- 业务需要保存、但没有独立业务决定和规则的普通记录；
- 外部系统拥有、本地只保存的标识、引用或最后观察快照；
- 为页面和查询组合的信息；
- 为跨系统操作保存的当前步骤和恢复位置；
- 证明谁在何时做了什么及结果如何的日志；
- 幂等、消息投递、任务执行等技术运行信息；
- 可以重新计算的统计或派生数据。

“需要建表”不能证明需要 Domain；“没有 Domain”也不能成为不保存业务所需信息的理由。

必须保持：

- 日志证明发生过什么，不代替当前业务状态；
- 外部快照不取得外部事实所有权；
- 查询数据不因为同页展示就成为聚合；
- 执行进度不因为需要恢复就自动成为业务 Domain；
- 技术运行信息明确标记为技术用途，不伪装成业务对象。

## 数据库怎样承载

数据库设计从“为什么必须保存”开始，而不是从“有哪些 Domain”开始。每张表或其他存储结构说明：

```text
保存的具体信息：
保存原因：
所属用途：
权威拥有者：
谁写入、怎样变化：
是否参与业务判断：
是否可以重新生成：
保留和清理要求：
来源的业务、Domain、外部合同或技术需要：
```

Domain 数据表是已确认 Domain 的投影。非 Domain 表则必须有明确的业务、查询、外部协作、证据、恢复或技术运行用途。两类都可以存在，但不能互相冒充。

表名必须表达它实际保存的东西及其用途。业务表名应能看出拥有者和承载的事实或关系；日志、快照、查询结果、流程进度和技术表应直接体现其记录性质，不使用虚构的业务对象为它们命名。
