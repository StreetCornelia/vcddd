## 作用

Domain 分析开始以后，结构、关系、生命周期、调用顺序、事务边界和数据承载通常比长段文字更适合用图表达。图不是正文装饰，而是设计事实的一部分：让用户、设计 Agent、开发 Agent 和审核 Agent 对同一结构与过程形成一致认识。

默认在 Markdown 中使用可版本管理的 Mermaid 源码：

- `classDiagram`：核心事物、实体、值对象、关系、聚合组成；
- `stateDiagram-v2`：生命周期、状态转换和终态；
- `sequenceDiagram`：参与者之间的先后、调用、提交和外部影响；
- `flowchart`：活动、判断、分支、回退和恢复；
- `erDiagram`：关系数据库结构；
- `flowchart` 的分组与依赖边：系统、组件、模块和端口关系。

项目已有 PlantUML 或其他可渲染、可版本管理的图源规范时遵循项目规范。不要为了坚持“UML”而用类图表达数据库、用时序图表达静态所有权；ER 图虽然不是 UML，仍是关系数据库的正确表达。

## 先判断图要回答什么

先写出读者要一眼回答的问题，再选择图：

| 读者问题 | 首选表达 |
| --- | --- |
| 有哪些核心事物，谁拥有谁，怎样关联 | 业务关系图或类图 |
| Domain、模块、端口和外部系统边界在哪里 | 组件图、包图或依赖图 |
| 一个事物从产生到结束怎样变化 | 状态图 |
| 一个 API 进入系统后怎样调用应用层、Domain、Repository 和外部系统 | 时序图 |
| 一个 Domain 方法内部怎样判断、改变状态、失败或结束 | 活动图或流程图 |
| 表怎样关联、主外键怎样连接 | ER 图 |
| 请求响应有哪些精确字段和错误 | 表格、Schema 和文字，不用图代替 |
| 不变量、幂等、事务隔离和结果未知究竟意味着什么 | 文字、规则表和场景表，不用图代替 |

一张图只回答一个主要问题。图太大而需要读者反复缩放、跨区寻找连线时，按 Domain、API 或 Domain 方法拆分；不要建立一张包含系统、Domain、模块、API、表和全部异常的“总图”。

## 图与文字的事实关系

- 图负责空间结构、时间顺序、状态变化和分支全景；
- 文字补充名称的业务含义、职责与非职责、不变量、精确条件、量化规则、错误语义、证据、假设和图刻意省略的内容；
- 表格负责字段、错误、失败矩阵、流程覆盖、索引、约束和设计到实现的对应；
- 图中每个节点和动作使用当前文档已经定义的业务名称，不用临时缩写或技术黑话改名；
- 图与正文必须表达同一个版本。发现冲突时文档恢复为待确认，不能自行选择图或文字中的一个继续；
- 图中遗漏某个异常分支可以由文字补充，但图不能画出与文字相反的成功、状态、所有权、提交顺序或重试语义；
- 图附近说明它回答的问题、适用范围以及明确不表达什么，避免读者把部署图误解为 Domain 图或把过程阶段误解为对外状态。

每种设计事实只由一份文档拥有。其他文档优先链接权威图；为连续阅读必须摘取时，标明来源并随派生文档重新生成，不能形成另一份独立演化的图。

## 各文档的图形责任

### `Domain判定.md`

在业务主体确认前，可以使用不带技术分类的业务关系图表达核心事物、所有权、关系和行为影响。不要提前画带 Repository、Service 或数据库字段的类图。

形成 Domain 草案以后，使用候选 Domain 关系图帮助用户核对边界。图必须清楚标记候选或待确认，不能因为已经画成正式 UML 外观而冒充结论。

### `系统拆分.md`

它拥有：

- 系统内 Domain 总览与 Domain 间关系图；
- 每个需要展示内部组成的 Domain 类图，表达聚合根、实体、值对象、关系和拥有方向；
- 每个具有重要状态变化的 Domain 状态图；
- 本系统与外部系统之间的事实拥有和合同边界图。

类图重点表达业务结构，不要求罗列所有代码方法、DTO 或数据库字段。状态图区分过程阶段、业务状态和终态；转换边使用业务行为命名。无法由图表达的不变量、拒绝理由、并发规则和外部事实边界紧邻图说明。

### `模块拆分.md`

它拥有模块、组件、端口、Adapter 和允许依赖方向的图。代码包结构与业务模块边界明显不同且会影响开发时，再补包图。

组件图不重新创造 Domain，也不展开核心业务时序。每个模块的职责、非职责和禁止依赖仍用文字固定。

### `API设计.md`

精确接口合同继续以字段表、Schema、错误表和协议说明为主。只有下列交互的边界行为难以通过接口表理解时增加时序图：

- 流式响应；
- 异步任务、回调或事件；
- 超时后查询确认；
- 跨系统结果未知或部分完成；
- 多次调用共同完成一个对外合同。

API 时序图只展示调用方、本系统和外部系统的可观察交互，不展开本系统内部 Domain 编排；内部实现由 `核心接口内部编排.md` 拥有。

### `核心接口内部编排.md`

它只拥有逐 API 的补充动态图：

- 每个 API 先用固定主流程表表达完整步骤，再按需增加一张时序图，展示 API 入口、应用用例、Domain 调用、Repository、事务提交和外部系统的先后；
- 分支或恢复仍无法从主流程与失败表看懂时，最多再增加一张活动图；
- 图中步骤标识必须与该 API 的 `S1、S2……` 一致；
- 长期状态变化、Domain 行为内部规则和对象协作引用 `系统拆分.md` 的权威类图、状态图和文字，不在本文件重画；
- 简单查询或直接映射不机械配图，但仍保留固定逐 API 文字结构。

图不能用宏观组件关系替代逐接口对应，不能先于主流程表成为阅读入口，也不能把多个 API 合并成一张“系统总流程”。关键业务证据可以作为注释出现，但日志要求仍回到对应步骤用文字说明。

### `数据库设计.md`

它拥有：

- 关系表和主外键的 ER 图；
- 多种数据库、对象存储、消息系统或外部安全存储并存时的存储边界图；
- 必要时从 Domain 聚合到持久化结构的投影关系图。

图只表达关系全景，不能代替逐表的存在意义、单行语义、字段解释、约束责任、查询证据、事务或生命周期。字段类型、可空性、唯一约束、检查约束、索引、事务、迁移与回退由[数据库设计固定模板](database-design-template.md)中的文字和表格固定；DDL 和 SQL 属于 Coding 实现，不进入设计文档。ER 图不能反向证明某个表就是 Domain 或聚合。

### `开发基线.md`

它不创造新图。按开发连续阅读需要，链接权威图；确需内嵌时只摘取已确认图并标明来源。来源图变化后，基线先标记待重新生成。

### `实现记录.md` 与审核记录

实现记录以“逐 API 编排步骤—引用的 Domain 行为—代码—日志—测试”对应表为主。只有运行时组件或实际时序无法从代码位置快速理解时，补充实际实现图，并明确它映射哪张设计图；不能用实现图覆盖上游设计。

审核记录引用设计图和对应代码证据，不重新绘制一套理想设计。实际实现与权威图不一致时记录偏差，并判断应修改代码还是返回上游重新确认。

## 多系统边界

每个系统的图只站在本系统视角：

- 其他系统显示为外部组件、外部参与者或黑盒 lifeline；
- 只画已确认合同、请求、事实和可观察结果；
- 不展开另一个系统内部 Domain、模块、事务或数据库；
- 同一现实事物在两个系统有不同意义时，分别使用各系统本地名称，并在边界处标明稳定对应身份；
- 跨系统总览图只表达系统责任和合同，不把多个系统合成一个共享 Domain 模型。

## 绘制与维护

1. 先完成该文档负责的分析，再选择能压缩理解成本的图，不让画图工具反向产生业务。
2. 为图写清标题、读者问题和适用范围。
3. 使用稳定业务名称、方向、基数、状态和编排步骤；必要时增加简短图例。
4. 把同一事实的补充说明放在图附近，不让读者跨越整篇寻找含义。
5. 用当前渲染环境检查语法与可读性；不能渲染时仍保留可审查的图源并明确验证缺口。
6. 修改结构、顺序、状态、事务或外部影响时，同时更新权威图、正文和受影响派生文档。
7. 图只呈现当前设计，不保留废弃候选叠层；推翻原因保存在任务或判定记录。

## 用户审核与下游使用

系统设计 Agent 的用户审核包必须链接完整文档，并指出本轮应重点查看哪些图以及每张图回答什么。用户确认 Domain、API、核心接口内部编排或数据库时，确认对象包含相应图和补充说明。

用户修改图中的关系、状态、顺序、事务或外部影响时，Agent 必须检查全部直接受影响的文字、API、数据和下游流程，不能只移动一个图节点。

开发 Agent 先从图恢复整体结构和时序，再读取文字中的精确规则；实现记录沿用图中的 API 标识、Domain 方法名、状态和编排步骤。实现符合性审核同时核对图形全景和精确文字，不能因为代码符合某张图就忽略正文约束，也不能只逐条核对正文而遗漏整体顺序或边界。
