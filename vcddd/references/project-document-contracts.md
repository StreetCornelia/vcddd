## 恢复模型

新启动的主控或专业 Agent 不依赖聊天历史，使用：

```text
角色 reference
+ work/<任务>/index.md
+ 任务列出的权威事实文档和直接证据
= 当前角色可继续工作的完整输入
```

角色 reference 规定怎样判断；任务恢复文档规定现在判断什么、读写哪里以及下一步；事实文档保存已经稳定的业务、设计和实现事实。三者不能互相替代。

## 入口文档

入口文档是导航和状态，不复制详细事实。

### `docs/vcddd/index.md`

固定说明：

```markdown
# VCDDD 项目入口

## 项目现实与范围

## 当前入口

- [业务目标](business/index.md)
- [系统](systems/index.md)
- [工作任务](work/index.md)

## 当前开发与审核

## 重要冲突与恢复
```

### `business/index.md`

列出用户已经建立的阶段性目标、状态、适用范围和 `业务设计.md` 入口。不把候选目标登记成正式目标。

### `systems/index.md`

列出系统名称、业务责任、状态和系统 `index.md` 入口。不在此重新描述 Domain、API 或数据库。

### 系统 `index.md`

固定说明系统目的、责任、当前状态，并链接当前的：

- `系统拆分.md`；
- `模块拆分.md`；
- `API设计.md`；
- `数据库设计.md`；
- `开发基线.md`；
- 存在开发切片时的 `开发记录/index.md`。

### `work/index.md`

列出当前、等待、暂停和完成的任务。每项至少说明任务状态、当前负责角色和 `work/<任务>/index.md` 入口。

## 任务恢复文档

字段保存的是可恢复语义，不是聊天摘要：

- 路径使用可点击的项目内相对链接或明确代码路径；
- `角色 reference` 使用稳定文件名，例如 `system-design-agent.md`；
- 已被事实文档吸收的答案从任务判断中移除并链接事实源；
- 未决决定保留所有者、依赖、影响和状态；
- 用户反馈被处理前保存原话，吸收后写处理结果并清空待处理区；
- `恢复动作` 写成下一位 Agent 可以直接执行的动作，不写“继续处理”。

## 角色进入与退出

### 主控调用角色前

先更新任务恢复文档：

1. 写入当前负责角色和角色 reference；
2. 写入必须读取、允许写入和禁止修改的路径；
3. 写入本次目标、完成条件、当前判断和待处理反馈；
4. 把交互状态设为“等待 Agent”；
5. 再用这些字段构造任务包。

任务包不得包含任务恢复文档没有记录的关键上下文。否则主会话一旦丢失，专业 Agent 无法重新启动。

### 专业 Agent 返回后

主控在让出用户回合前：

1. 持久化专业 Agent 的结果信封；
2. 链接实际维护的事实文档、代码或审核记录；
3. 更新未决决定、依赖和当前决策前沿；
4. 保存需要展示的用户交互包或清空交互等待；
5. 写明下一角色、必须重新读取的来源和恢复完成标准。

专业 Agent 只维护自己拥有的事实；主控维护任务恢复点和导航。

## Domain 判定记录

任务进入 Domain 分析时，在当前任务目录建立 `Domain判定.md`。所有权与关系必须由用户确认后才能继续推导对象、聚合、Domain、API 和数据库。

它是设计分析证据，不是新的系统事实源。固定保存：

```markdown
# Domain 判定

状态：
适用的当前业务目标与范围：
业务来源：
所有权确认：待确认 | 已确认
确认依据：
核心命名确认：待确认 | 已确认
核心命名确认依据：

## 业务原话与普通话结论

## 当前业务决定

## 所有权与关系

## 用户确认

## 概念分类

## 不变量与聚合

## 名称推导

## 非 Domain 信息

## 跨系统流程

## 当前 Domain 结论

## 未决决定
```

`业务原话与普通话结论` 保存不依赖行业黑话即可理解的业务事实。`所有权与关系` 完整记录谁拥有什么、各主体凭自身事实和规则能具体做什么、怎样关联、关系由谁拥有，以及关系新增、允许或限制什么行为。`用户确认` 保存确认范围、用户反馈及被否定后重新分析的结果。

所有权确认前只维护业务原话、当前业务决定、所有权与关系、用户确认和未决决定，任务状态为等待用户。确认后才继续概念分类、不变量、聚合和 Domain 推导。

`名称推导` 按 [业务语言与建模边界](language-and-modeling.md#名称怎样产生) 保存业务来源、普通话含义、DDD 分类、建议名称、只看名称能够理解的业务与具体行为、可能误解及用户确认结果。核心名称由用户确认后才能进入 API、数据库和代码。`非 Domain 信息` 保存业务仍然需要使用或记录、但不适合由 Domain 维护的信息及其真实用途。

只记录当前证据、关系、候选、结论和推翻原因，不保存思维流水。结论稳定后写入 `系统拆分.md`，并在其中声明 `所有权确认：已确认`、`核心命名确认：已确认` 和各自依据；任务恢复文档继续链接 `Domain判定.md`，但明确 `系统拆分.md` 是当前设计事实源。

## 语言验证记录

每次有效盲测写入 `docs/vcddd/work/<中文任务名>/语言验证/<中文对象>.md`。同一内容复测时建立新文件或清楚标识输入快照，不覆盖旧结果。

固定保存：

```markdown
# 语言验证：<对象>

目标读者：
对象类型：
实际展示位置：
输入快照或文件位置：
允许读取：
禁止读取：
结果状态：清楚 | 有歧义 | 无法从文字理解 | 盲测已污染

## 原始名称或文案

## 逐项理解

## 歧义与依赖的内部知识

## 普通话改写建议

## 返回的事实拥有者
```

记录只说明文字传达了什么，不保存预期答案，不判断业务正确性。事实拥有者在自己维护的文档或任务判断中记录处理结果，不能回写语言验证结果。

## 事实文档与恢复文档的边界

- `业务设计.md`、系统四份设计事实、代码和审核记录必须能独立支持各自读者完成判断；
- `work/` 保存当前任务怎样继续，不替代业务或设计；
- `Domain判定.md` 解释 Domain 结论怎样从已确认的当前所有权、能力和关系形成，不替代 `系统拆分.md`；
- `语言验证/` 保存不了解答案的 Agent 怎样理解名称或文案，不拥有也不修改被验证事实；
- `开发基线.md`、原型和报告都是派生阅读视图，不创建新事实；
- 文档结构用于恢复和阅读，不构成阶段门禁；任何步骤发现问题都可以返回事实拥有者修订。
