## 恢复模型

新启动的主控不依赖聊天历史，使用：

```text
docs/vcddd/index.md
+ work/index.md
+ work/<任务>/主控状态.md
= 可以继续路由和用户交互的完整输入
```

专业 Agent 使用：

```text
角色 reference
+ work/<任务>/主控状态.md
+ work/<任务>/index.md
+ 任务列出的权威事实文档和直接证据
= 当前角色可继续工作的完整输入
```

`主控状态.md` 规定当前通信；角色 reference 规定怎样判断；任务恢复文档规定完整目标、读写合同、判断和恢复；事实文档保存已经稳定的业务、设计和实现事实。四者不能互相替代。

## 入口文档

入口文档是导航和状态，不复制详细事实。

### `docs/vcddd/index.md`

固定说明：

```markdown
# VCDDD 项目入口

## 项目现实与范围

## 当前入口

- [业务目标](business/index.md)
- [系统](systems/index.md)
- [工作任务](work/index.md)

## 当前开发与审核

## 重要冲突与恢复
```

### `business/index.md`

列出用户已经建立的阶段性目标、状态、适用范围和 `业务设计.md` 入口。不把候选目标登记成正式目标。

### `systems/index.md`

列出系统名称、业务责任、状态和系统 `index.md` 入口。不在此重新描述 Domain、API 或数据库。

### 系统 `index.md`

固定说明系统目的、责任、当前状态，并链接当前的：

- `系统拆分.md`；
- `架构设计.md`；
- `模块拆分.md`；
- `API设计.md`；
- `核心接口内部编排.md`；
- `数据库设计.md`；
- `开发基线.md`；
- 首次 Coding 前形成并确认的 `工程编码规范.md`；
- 存在开发批次时的 `开发记录/index.md`。

系统涉及跨系统共通事物时，`系统拆分.md` 必须保存该事物在本系统中的名称和业务意义、本系统拥有的属性关系行为、外部权威事实、稳定对应身份和协作合同。其他系统的同名 Domain 只作为上下文映射，不复制其内部模型。

系统设计文档同时保存用户审核状态：

```text
系统拆分.md
  业务主体确认：待确认 | 已确认
  Domain 设计确认：待确认 | 已确认
  核心命名确认：待确认 | 已确认

架构设计.md
  架构设计确认：待确认 | 已确认
  架构设计确认依据：

模块拆分.md
  模块拆分确认：待确认 | 已确认
  模块拆分确认依据：

API设计.md
  API 设计确认：待确认 | 已确认
  API 设计确认依据：

核心接口内部编排.md
  核心接口内部编排确认：待确认 | 已确认
  核心接口内部编排确认依据：

数据库设计.md
  数据库设计确认：待确认 | 已确认
  数据库设计确认依据：

工程编码规范.md
  规范确认：待确认 | 已确认
  规范确认依据：
```

`已确认` 必须有可恢复的用户确认依据，不能由 Agent 根据文档已完成、代码已经如此、用户沉默或旧任务的概括认可自行填写。待确认文档可以保存完整候选并支持用户审核，但不能作为下游当前事实。用户明确要求并行准备时，下游候选必须标明依赖的待确认设计；只有 Domain、架构、模块、API、核心接口内部编排和数据库均确认后，开发基线才可以标记为 `当前`。工程编码规范也必须由用户确认并成为 `当前` 后才能进入 Coding。

`API设计.md` 中每个独立 API 合同必须声明唯一的 `API 标识：API-<系统内短名>`。标识表达稳定调用意图，不随标题文案变化；核心接口内部编排使用它建立一一对应关系。

`核心接口内部编排.md` 必须严格使用[核心接口内部编排固定模板](internal-orchestration-template.md)：

- 唯一固定入口为 `## 接口目录`；
- 此后每个二级标题固定对应一个 `## API-<标识>：<入口> — <名称>`；
- 每个 API 章节必须且只能按顺序包含 `业务结果 / 主流程 / 分支与失败 / 事务与外部影响 / Domain 调用 / 业务证据与验证`；
- 主流程固定用步骤表说明谁做什么、得到什么结果和下一步；
- API 标识必须与 `API设计.md` 完整一一对应，查询和简单接口也不能消失；
- 不允许“API 内部编排 / Domain 方法内部编排”双主轴，不允许接口组；
- Domain 内部规则、不变量、对象协作和生命周期链接 `系统拆分.md`，不在此复制。

候选交给用户前必须通过 `--orchestration-system <系统>`。业务线用于检查覆盖，不成为正文目录；图只补充逐 API 主流程，不代替固定文字和表格。

## 架构设计与模块拆分

`架构设计.md` 和 `模块拆分.md` 必须严格使用[架构设计与模块拆分固定模板](architecture-and-module-template.md)。

架构设计固定按顺序包含：

```text
架构目标与约束
总体架构
层次与主要组件
依赖与调用边界
数据、外部系统与运行协作
系统级技术机制
技术选择与理由
Coding 必须遵守的边界
允许 Coding 决定的内容
尚未确定的问题
```

模块拆分先给模块全景和模块目录，再为每个 `MOD-<标识>` 固定说明存在意义、职责与非职责、承载的 Domain 与数据、对外提供与依赖和代码范围；最后说明模块依赖规则、业务覆盖、Coding 必须遵守的边界和尚未确定的问题。

两份文档只固定系统级骨架和模块责任，不得出现逐 API 的类、文件、方法计划或模块内部私有调用顺序。已有代码时记录恢复现状所用快照、继承项、冲突、历史例外和推荐调整；没有代码时记录语言、框架、当前权威实践和最小推荐方案。

候选交给用户前必须通过 `--architecture-system <系统>`。只有用户明确确认当前完整候选后才能标记 `已确认`；实质边界变化后恢复为 `待确认`。

## 数据库设计

`数据库设计.md` 必须严格使用[数据库设计固定模板](database-design-template.md)。它以人能够审核的数据事实为正文，不以数据库建表语句为正文。

固定顶层结构为：

```text
数据承载全景
表目录
数据关系图
DBT-<标识>：<table_name> — <中文名称>（每张表重复）
跨表事务与一致性
查询投影与非 Domain 数据
数据安全与保留
数据库实现交接
```

每张表章节必须且只能按顺序包含：

```text
表的意义
产生、变化与使用
字段说明
身份、主键与唯一性
与其他表的关系
必须保持的约束
查询与索引
事务、并发与编排对应
历史、清理与迁移
尚未确定的问题
```

每张表在“表的意义”中给出数据库表注释原文。字段表覆盖所有实际字段，固定说明字段为什么存在、保存的事实或含义、事实来源、逻辑类型、必填和空值语义、默认值及含义、允许范围、变化时机、敏感性和数据库注释原文。主键、外键、时间、状态、版本及技术字段不能省略解释。

候选交给用户前必须通过 `--database-system <系统>`。`数据库设计.md` 禁止 SQL 代码块、DDL、ORM 实体和完整迁移；Coding 在设计确认后生成迁移与映射，并以实现记录和测试证明忠实落地。

## 工程编码规范

每个进入 Coding 的系统固定建立并由系统 `index.md` 直接链接：

```text
docs/vcddd/systems/<中文系统名>/工程编码规范.md
```

它由 Coding 角色维护，是系统级工程事实，不重新定义需要用户确认的 Domain、架构、模块、API、核心接口内部编排或数据库设计。工程规范自身也必须由用户确认；进入 Coding 时状态必须为 `当前`，固定包含：

```markdown
# <系统名>工程编码规范

最佳实践资料版本或取得时间：
```

`当前规则索引` 至少说明规则标识、级别、适用或触发条件和正文位置。规则级别为核心、条件或补充；规则状态为当前、候选或已替代。只有当前规则约束 Coding。纯工程且跨实施任务或跨开发批次稳定适用的认识写入规范；当前任务的局部选择留在实现或工程改进记录；改变业务或设计的内容返回事实拥有者。

已有代码时按固定主题逐项调查，使用仓库明确规范与工具配置、核心模块稳定做法和多个模块共同惯例作为证据；单个文件或偶发写法不能直接成为系统规则。完全没有代码时按确定的语言、框架和版本，从当前官方资料和成熟实践为全部主题提出推荐。缺失或冲突项必须给用户推荐方案、依据、替代项和权衡，不能只问空问题。

首版规范完整覆盖固定主题。当前系统不存在的事项写明“不适用、原因和重新触发条件”，不删除主题，也不预建虚构机制。只有整份规范和单项规则均为当前、规范确认已完成并有依据时，规则才能约束 Coding。

完整形成、渐进加载和演化规则见 [Coding 渐进实施与系统工程规范](coding-guidance.md)。

## 开发任务图、实施、测试与审核记录

每个开发批次先建立并确认 `开发任务图.md`。它严格使用[开发任务图固定模板](implementation-task-graph-template.md)，固定包含：

```text
批次范围与完成边界
代码产物清单
任务关系图
并行批次
共享写入与集成规则
开发任务
集成与统一代码快照
尚未确定的问题
```

状态为 `当前` 且 `任务图确认：已确认` 后才能创建实施 worktree。任务图覆盖全部业务与非业务生产代码，不要求每个任务存在业务结果、API 或 Domain，也不包含测试和正确性验证。

每个实施任务维护：

```text
开发记录/<开发批次>/实施任务/<TASK-标识>/实现记录.md
```

固定包含：

```markdown
# 实现记录：<TASK-标识>

开发任务图：
实施任务：
开发基线：
工程编码规范：
worktree 起始快照：
输出代码快照：
实现范围：
未覆盖范围：

## 任务代码责任

## 来源与代码对应

## 实际产生的代码

## 提供给后续任务的产物

## 与任务图或设计的偏离

## 剩余实现事项
```

实现记录不包含测试、验证证据或“通过”结论。全部任务合并后建立 `集成记录.md`，固定声明开发任务图、起始快照、任务 Commit、合并顺序、共享写入处理、未实现事项、统一生产代码快照、测试状态、工程改进状态和最终待审核快照。

统一测试使用[统一测试 Agent 合同](testing-agent.md)。每个独立测试角度维护：

```text
开发记录/<开发批次>/测试反馈/<测试角度>.md
```

固定声明测试角度、输入生产代码快照、基线、工程规范、测试代码范围、禁止修改的生产代码、覆盖与未覆盖对象、新增测试、执行入口、结果、失败证据、修正结果、问题责任、返回位置、测试代码快照和剩余风险。全部测试反馈完成后，新的测试结论 Agent 建立 `测试结论.md`，汇总生产与测试代码快照、失败责任、分歧、修正任务、复测范围、未覆盖风险和当前结论。

Coding 在任务规划、生产代码、SQL、统一测试、工程改进或审核中发现上游设计不合理时建立：

```text

```

```text
事实拥有者：
```

```text
开发记录/<开发批次>/工程改进/<轮次>-<分析角度>.md
```

固定字段为：

```text
分析角度：
```

至少保留一次独立的重复与抽象分析。工程改进记录不输出“通过 / 不通过”，不能修改测试断言掩盖生产代码问题。多个分析可以并行；修改同一文件、公共接口或相互依赖行为必须串行。

### `work/index.md`

列出当前、等待、暂停和完成的任务。每项至少说明任务状态、当前负责角色，并直接链接 `work/<任务>/主控状态.md`。主控状态再链接完整任务。

## 主控状态

每个活动任务固定维护 `docs/vcddd/work/<中文任务名>/主控状态.md`。这是主会话与专业 Agent 的唯一通信面，必须保持短小；完整分析、证据、未决决定和恢复判断保存在任务 `index.md`、专项记录和事实文档中。

固定格式：

```markdown
# 主控状态：<中文任务名>

任务文档：[完整任务](index.md)
当前负责角色：
角色 reference：
通信状态：待派发 | Agent 工作中 | 等待用户 | 可继续 | 阻塞 | 完成
当前讨论对象：
专业结果位置：
本轮变更：
用户交互包：
待处理用户反馈：
反馈处理结果：
下一步：
```

字段规则：

- `专业结果位置` 链接事实文档、任务章节、专项记录、实现记录或审核记录，不复制其正文；
- `本轮变更` 只列路径和变化性质，不粘贴 diff；
- `用户交互包` 保存可以原样展示给用户的完整内容；当前决策前沿不设数量上限，等待前置决定的事项也保持可见；
- 没有用户交互时写“无”；
- `待处理用户反馈` 只保存尚未吸收且属于当前任务的用户原话；多任务反馈的完整原话只在协调任务保存一次，各专业任务只保存主控切出的相关原文片段，不附主控解释；
- 专业 Agent 吸收反馈后清空原话，并在 `反馈处理结果` 中链接更新位置；
- `下一步` 必须可以直接执行，只写一个当前动作；并行任务分别维护各自状态文件。

主控派发或记录用户反馈时写此文件；专业 Agent 工作期间主控停止写入。专业 Agent 完成文档写回后更新此文件并只返回它的路径。两者不能同时写。

## 任务恢复文档

## 角色进入与退出

### 主控调用角色前

首次建立任务时，主控建立任务 `index.md` 和 `主控状态.md`；若任务还没有完整专业判断，只写已经确定的目标、来源、读写范围和未知，不代替专业 Agent 补结论。此后调用角色前只更新 `主控状态.md`：

1. 写入当前负责角色和角色 reference；
2. 链接完整任务；
3. 原样写入只属于当前任务的待处理用户反馈片段；
4. 把通信状态设为“Agent 工作中”；
5. 只把角色 reference 与 `主控状态.md` 路径发送给专业 Agent。

调度消息不得包含状态文件和任务文档没有记录的关键上下文，也不得复制完整任务内容。

### 专业 Agent 返回后

专业 Agent 在返回聊天前：

1. 更新自己拥有的事实文档、代码或专项记录；
2. 更新完整任务中的结果、未决决定、依赖、前沿和恢复动作；
3. 更新 `主控状态.md` 中的结果路径、变更路径、用户交互包和下一步；
4. 在聊天中只返回 `主控状态.md` 路径和写入状态。

主控收到后只读 `主控状态.md`，不重新吸收、概括或改写专业结果。专业 Agent 维护自己拥有的事实和完整任务；主控维护通信状态与全局导航。

## 设计图合同

Domain 之后的设计图遵守 [设计图表达协议](diagramming.md)。图源直接保存在拥有该事实的 Markdown 文档中，和正文一起版本管理：

- `系统拆分.md` 拥有 Domain 关系、类图和状态图；
- `架构设计.md` 拥有总体层次、主要运行组件和依赖方向图；
- `模块拆分.md` 拥有模块组件、包和依赖图；
- `API设计.md` 只拥有复杂边界交互图；
- `核心接口内部编排.md` 按需拥有逐 API 的内部时序图和分支或恢复活动图；Domain 行为内部图仍由 `系统拆分.md` 拥有；
- `数据库设计.md` 拥有 ER 图和存储边界图；
- `开发基线.md`、实现记录和审核记录只链接或明确摘取权威图，不建立竞争版本。

`主控状态.md` 的用户交互包必须链接完整设计文档，并列出本轮需审核的图及其读者问题；不能把图复制进状态文件形成第二份图源。任务恢复文档记录权威文档路径和受影响图，不保存图源码副本。

图与正文冲突时，对应设计状态保持或恢复为 `待确认`，完整任务记录冲突位置和受影响下游。用户对 Domain、API、核心接口内部编排和数据库的确认同时覆盖相应图与补充说明。

## Domain 判定记录

任务进入 Domain 分析时，在当前任务目录建立 `Domain判定.md`。它保存 Agent 怎样从有主体的业务叙事中找到核心事物、把属性、关系和行为放回主体，并形成用户确认的完整 Domain。它不是靠检查表推导 Domain 的表单。

它是设计分析证据，不是新的系统事实源。固定保存：

```markdown
# Domain 判定

状态：
适用的当前业务目标与范围：
业务来源：
业务主体确认：待确认 | 已确认
业务主体确认依据：
Domain 设计确认：待确认 | 已确认
Domain 设计确认依据：
核心命名确认：待确认 | 已确认
核心命名确认依据：

## 有主体的业务叙事

## 核心事物

## 属性、状态、所有权与关系

## 行为、判断与影响

## 多系统上下文映射

## 用户确认

## 完整 Domain 设计

## Domain 内部的 DDD 表达

## 不变量与聚合

## 名称推导

## 非 Domain 信息

## 跨系统流程

## 当前 Domain 结论

## 未决决定
```

`有主体的业务叙事` 使用普通话保存“什么在什么情况下做了什么，使谁发生什么变化并产生什么结果”。`核心事物` 保存业务中客观存在的事或物及其证据。`属性、状态、所有权与关系` 记录每个核心事物拥有什么、怎样关联以及关系由谁拥有。`行为、判断与影响` 把每个行为、使用的事实和规则、造成的变化和影响放回它所属的主体。`多系统上下文映射` 保存共通事物在本系统中的名称与含义、本地拥有事实、外部权威事实、稳定身份和系统间合同；不复制其他系统的内部 Domain。`用户确认` 保存业务主体确认和 Domain 设计确认的范围、用户反馈及被否定后重新分析的结果。

`完整 Domain 设计` 先用自然业务叙事说明每个 Domain 是什么核心事物、拥有什么、能做什么、影响什么，再说明上层业务之“事”与普通应用协作。`Domain 内部的 DDD 表达` 继续说明实体、值对象、关系实体和其他内部分类，`不变量与聚合` 保存聚合边界、生命周期、原子约束和失败语义。业务主体确认前不把候选写入下游；完成这些内部设计并由用户审核以前，`Domain 设计确认` 必须保持 `待确认`，不能继续模块、API、数据库和开发基线。

`名称推导` 按 [业务语言与建模边界](language-and-modeling.md#名称怎样产生) 保存业务来源、普通话含义、名称所在层次、DDD 分类、建议名称、可能误解及用户确认结果。Domain 用名词命名核心事物，行为用动词表达动作和结果，页面和数据库名称使用各自语境的标准；核心名称由用户确认后才能进入 API、数据库和代码。`非 Domain 信息` 保存业务仍然需要使用或记录、但不适合由 Domain 维护的信息及其真实用途。

只记录当前证据、主体、关系、行为归属、候选、结论和推翻原因，不保存思维流水。结论稳定后写入 `系统拆分.md`，并在其中声明 `业务主体确认：已确认`、`Domain 设计确认：已确认`、`核心命名确认：已确认` 和各自依据；任务恢复文档继续链接 `Domain判定.md`，但明确 `系统拆分.md` 是当前设计事实源。

## 事实文档与恢复文档的边界

- `业务设计.md`、系统六份设计文档、工程编码规范、代码和审核记录必须能独立支持各自读者完成判断；待确认设计或规范是完整候选，确认后才是当前事实；
- `work/` 保存当前任务怎样继续，不替代业务或设计；
- `主控状态.md` 只保存主控当前需要路由或展示的内容，不是专业结果档案；
- `Domain判定.md` 解释 Domain 结论怎样从已确认的核心事物、所有权、关系、行为和影响形成，不替代 `系统拆分.md`；
- `语言验证/` 保存不了解答案的 Agent 怎样理解名称或文案，不拥有也不修改被验证事实；
- `开发基线.md`、原型和报告都是派生阅读视图，不创建新事实；
- `工程编码规范.md` 是经用户确认的系统级工程事实，只规定怎样可靠、一致地实现，不重新定义业务或设计；
- `开发任务图.md` 保存全部代码产物、实施依赖和并行调度，由用户确认但不创造业务或设计事实；
- `实施任务/` 只保存各任务生产代码交接，`测试反馈/` 和 `测试结论.md` 只在全部生产代码形成以后保存验证证据；
- `工程改进/` 保存统一测试以后到最终待审核快照之间的分析与生产代码修改证据，不是正式审核；
- `API设计.md`、`核心接口内部编排.md` 和 `数据库设计.md` 分别保存自己的用户确认状态与依据；不能用开发基线或任务状态反推它们已经确认；
- 文档结构用于恢复和阅读，不构成阶段门禁；任何步骤发现问题都可以返回事实拥有者修订。
