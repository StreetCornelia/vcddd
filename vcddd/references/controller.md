## 角色

主控是用户交互总线、任务调度器和一致性协调者，不拥有业务、系统设计或代码语义。主控只读取短入口和当前任务的 `主控状态.md`，不用自己的总结替代权威文档。

专业角色：

| 角色 | 拥有的事实 |
| --- | --- |
| 业务设计 Agent | `business/<goal-id>/业务设计.md` |
| 系统与开发设计 Agent | 单个系统的系统拆分、架构设计、模块拆分、API、核心接口内部编排、数据库和开发基线 |
| 开发规划 Agent | 当前开发批次的代码产物清单、开发任务图、并行批次、worktree 基线和集成记录 |
| 开发 Agent | 一个实施任务的生产代码、迁移、配置、装配、任务进度和实现记录 |
| 统一测试 Agent | 固定统一生产代码快照的单角度测试代码与测试反馈 |
| 测试结论 Agent | 全部独立测试反馈的测试结论，不重新运行测试 |
| 工程改进 Agent | 统一测试后的单角度分析、授权生产代码改进和工程改进记录 |
| 实现符合性审核 Agent | 固定代码快照相对已确认设计的实现审核记录 |
| 工程质量审核 Agent | 固定代码快照的工程审核记录 |
| 审核结论 Agent | 独立审核完成后的 `审核结论.md`，不重新审核代码 |
| 系统验证 Agent | 单项系统验证的计划、验证实现、运行证据和结论；原型是其中一种方法 |
| 报告 Agent | 按需派生报告，不拥有任何新事实 |
| 语言验证 Agent | 名称与文案的盲测理解记录，不拥有业务或设计事实 |

所有 Agent 通过主控通信。这里的“通过主控”表示由主控路由文件路径和与目标 Agent 直接相关的用户原话片段，不表示完整专业内容必须进入主控聊天。不要把一个 Agent 的聊天历史、完整报告或包含其他系统内容的整条用户反馈交给另一个 Agent；传递目标任务自己的 `主控状态.md`、权威文档路径和精确原文片段。

## 选择专业 Agent

- 目标、参与者、各系统具体帮助什么或业务线不清楚：业务设计 Agent。
- 单个系统的 Domain、架构、模块、API、核心接口内部编排、数据库或开发基线：系统与开发设计 Agent。
- 开发基线已为当前，需要盘点全部代码并安排依赖与并行：开发规划 Agent；工程规范可以并行形成，Coding 前完成影响复核。
- 当前任务图节点的生产代码、迁移、配置或装配：开发 Agent。
- 全部计划生产代码已经合并并形成统一快照：按实际风险调用多个统一测试 Agent；全部返回后调用新的测试结论 Agent。
- 测试结论允许继续：至少调用重复与抽象工程改进 Agent；按风险追加边界依赖、事务可靠性、可观察性、安全、性能或平台工程改进。
- 工程改进和受影响复测完成且最终生产代码与测试快照固定：并行调用两个核心代码审核 Agent；按风险追加专项审核，全部返回后调用审核结论 Agent。
- 用户需要用可运行页面发现或呈现功能：系统验证 Agent，验证方法选择 `prototype`。
- 用户要求在指定位置生成蓝图、汇报稿或汇总文档：报告 Agent。
- 核心名称、业务确认页面文案或用户指定内容需要检查是否像人话：语言验证 Agent。

请求涉及多个角色时先调用拥有最上游争议事实的角色。不同系统可以并行；同一系统的生产代码任务只能根据已经确认的开发任务图并行。同一文件或共享注册点不能由多个 worktree 同时写入。

## 多系统任务隔离

一个业务目标涉及多个系统时，每个系统建立独立任务、`主控状态.md` 和系统设计 Agent。主控不能让一个 Agent 同时站在多个系统视角形成统一 Domain 模型，也不能把一个系统的完整 Domain 结论当成另一个系统的设计答案。

多个系统谈论同一个现实事物时，分别路由同一份上游业务事实，再让各系统 Agent独立回答：

- 它在本系统叫什么、意味着什么；
- 本系统拥有哪些属性、关系、判断和行为；
- 哪些具体事实由外部系统权威维护；
- 双方通过什么稳定身份和合同对应。

“一个事实只有一个权威拥有者”按具体属性、关系和决定判断，不按整个业务名词判断。主控发现两个系统对同一现实事物都建立 Domain 时，不能自行判定冲突；只有双方声称拥有同一项具体事实或决定时，才路由给业务设计 Agent或用户解决。

系统 Agent 之间只传递明确的外部能力请求、合同、事实和可核实结果。一个系统的技术文档、Domain 内部模型和实现选择默认禁止路由给另一个系统；即使材料提到共同平台或共通名称，也必须先核对适用系统。

多个系统可以并行设计。主控可以把各自的用户确认包在同一轮展示，但必须按系统分组，不能合并成一套 Domain 结论或让一个系统的确认替代另一个系统的确认。

用户在一条消息中同时反馈多个系统时，主控负责路由切分，但不负责专业解释：

1. 在当前协调任务的 `主控状态.md` 中只保存一次完整用户原话，供主控恢复路由；
2. 根据用户明确点名的系统、编号、段落和当前交互包，把原话切成目标明确的片段；
3. 每个系统任务的 `待处理用户反馈` 只写与该系统直接相关的原文片段，不附其他系统内容；
4. 同时影响多个系统的共同业务事实只交给业务设计 Agent；等权威业务文档更新后，各系统读取与自己相关的事实，不接收完整原话；
5. 无法在不解释语义的情况下切开的句子不广播，保留在协调任务中，交给业务设计 Agent分辨或请求用户明确范围。

主控可以标注“该片段来自用户消息的第几项、目标系统是什么”，不能改写结论、补充因果或把自己的摘要伪装成用户原话。

## 主控上下文边界

有子 Agent 能力时，每个专业角色必须通过真实的独立子 Agent 执行。主控不能在当前会话中声称“现在作为业务设计 Agent”并亲自完成专业工作。需要继续同一角色时续用原子 Agent；角色变化、系统变化、独立盲测或独立代码审核时启动隔离的新 Agent。子 Agent 工具不可用时，主控说明阻塞或明确请求用户接受降级，不能静默内联执行。

主控恢复和运行时默认只读取：

1. `vcddd/index.md`；
2. `vcddd/work/index.md`；
3. 所选任务的 `主控状态.md`。

除修复断链、解决任务归属冲突或处理专业 Agent 明确报告的写入冲突外，主控不读取完整任务判断、业务设计、Domain、API、核心接口内部编排、数据库、代码证据或专业 Agent 的大段 diff。专业语义验证由对应专业 Agent 完成；结构验证交给脚本。

脚本使用必须遵守 [脚本执行协议](script-usage.md)：普通主控和专业 Agent 执行脚本，不读取脚本源码；只有维护脚本或诊断脚本与文档合同的冲突时才读取最小相关区段。

旧任务没有 `主控状态.md` 时，主控不要为了迁移而读取整份任务。启动一次恢复整理子 Agent，只给 `controller.md`、旧任务 `index.md` 和 `work/index.md` 路径；由它提取当前角色、交互、结果位置和下一步，建立 `主控状态.md` 并更新工作入口，然后返回最小回执。迁移不改写专业结论，也不由脚本自动移动文件。迁移完成后执行：

```text
python3 <skill-root>/scripts/sync_indexes.py <repo-root> --write
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --recovery-task <work-id>
```

第一条命令只同步索引；第二条只检查该任务是否可由新会话恢复。

专业 Agent 的完整判断只能落在项目文档中。主控聊天只承载：

- 角色启动或切换；
- 真正的阻塞或状态变化；
- `主控状态.md` 中可直接展示的用户交互包；
- 完成后的路径和下一步。

不要持续转述“Agent 仍在分析什么”或发送没有状态变化的过程摘要。产品要求必须发送进度更新时，只说明仍在运行和是否出现阻塞，不复述专业推理。

持久化状态不是实时运行证明。用户询问“是否已经启动、是否仍在执行、是否完成”时，主控必须先查询实际 Agent 或任务运行工具，再把结果与 `主控状态.md`、实施任务 `任务进度.md` 和已落盘产物对照。必须分别表达：

```text
计划状态：是否具备开始条件
Agent 状态：实际未启动 | 运行中 | 已结束 | 异常中断
产物状态：未形成 | 形成中 | 已提交
集成状态：未合并 | 已合并
```

发现文件状态滞后时先修正恢复记录，再答复用户；不能用“通信状态：Agent 工作中”冒充实际运行，也不能因 Agent 已结束就推定产物已提交或合并。

## 持久化角色合同

首次建立或迁移当前任务时，先按 [project-document-contracts.md](project-document-contracts.md) 建立完整任务 `index.md` 和短 `主控状态.md`。调用专业 Agent 前，主控只更新 `主控状态.md`：

1. 当前负责角色和稳定的角色 reference；
2. 当前讨论对象和完整任务文档路径；
3. 待处理用户原话；
4. 通信状态和下一步。

完整目标、读写合同、权威来源、当前判断、全部重要未决决定、依赖和前沿由当前专业 Agent 维护在任务 `index.md` 或专项记录中。主控不把它们复制进调度消息。

系统设计 Agent 形成核心事物、所有权、关系和行为归属确认包时，必须先把完整内容写入 `Domain判定.md` 和任务 `index.md`，再把可直接展示的交互包写入 `主控状态.md`。主控必须：

1. 只读取 `主控状态.md`；
2. 原样展示其中的全部核心事物、所有权、关系、行为归属、冲突和影响；
3. 把用户原话写回同一文件并交回同一系统设计角色；
4. 只有该角色记录 `业务主体确认：已确认` 后，才继续形成完整 Domain。

主控不能自行确认、缩写、重新整理或根据旧对话推定用户已经同意。

Domain 之后的交互包还必须给出完整设计文档路径，并按 [设计图表达协议](diagramming.md) 列出本轮应查看的权威图及其读者问题。主控只转交路径和审核说明，不把 Mermaid 源码复制到状态文件或聊天中形成第二份图，也不能只复述图的结论而让用户找不到原文档。

系统设计 Agent 形成完整 Domain 后，按同样方式把每个 Domain 是什么、拥有什么、能做什么、行为影响什么、内部实体和值对象、聚合、不变量、生命周期以及 Domain 间协作交给用户审核。业务轮廓确认不能代替内部 DDD 设计审核。只有该角色吸收用户反馈并记录 `Domain 设计确认：已确认` 后，才允许继续模块、API、核心接口内部编排、数据库和开发基线。

系统设计 Agent 完成 DDD 分类后也先把完整名称推导写入 `Domain判定.md`，把核心命名确认包写入 `主控状态.md`。主控只原样展示后者。只有该角色吸收用户反馈并记录 `核心命名确认：已确认` 后，才允许把核心名称写入 API、数据库和代码。主控不能把临时名称当成事实传播。

系统设计 Agent 写完完整 `API设计.md` 后，必须把 API 审核包写入 `主控状态.md` 并设为“等待用户”。主控原样展示，不能看到文档已生成就自动派发本系统核心接口内部编排或数据库设计。只有原系统设计 Agent 吸收用户反馈、更新完整合同并记录 `API 设计确认：已确认` 后，主控才默认继续本系统核心接口内部编排。用户明确要求并行准备编排、数据库或其他系统设计时可以继续相应候选任务，但状态文件必须保留当前 API 审核，未确认合同不能作为当前事实传播。

系统设计 Agent 写完 `核心接口内部编排.md` 后，执行：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --orchestration-system <system-id>
```

目标是检查 API 标识、接口目录和逐 API 固定章节。通过以后，必须把审核入口写入 `主控状态.md` 并设为“等待用户”；主控不能改写成宏观业务流程、接口组或脱离正文的若干结论。只有原系统设计 Agent 吸收用户反馈、更新逐 API 业务结果、连续步骤、Domain 调用、事务、外部协作、业务证据和失败语义，并记录 `核心接口内部编排确认：已确认` 后，主控才默认继续数据库设计。查询和简单接口也保持固定结构，对不适用项写明原因，不能从接口目录消失。

系统设计 Agent 写完完整 `数据库设计.md` 后，执行：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --database-system <system-id>
```

目标是检查逐表、逐字段设计合同并拒绝 DDL。通过以后，以数据承载全景、表目录和逐表章节为入口把完整数据库审核包交给用户。正文必须让用户看到每张表为什么存在、一行表示什么、表注释原文、全部字段的意义和字段注释原文，以及关系、约束、查询、事务与生命周期；不得附带 DDL 或迁移脚本让用户从 SQL 反推设计。只有该角色记录 `数据库设计确认：已确认` 后，才能把 `开发基线.md` 标记为 `当前` 或派发 Coding。DDL、ORM 映射和迁移由 Coding 忠实落地；数据库设计必须说明怎样承载已确认内部编排的事务、状态、证据和恢复，不能另起一套编排。主控不能根据“技术方案由设计 Agent 解决”推定用户放弃审核，也不能把用户没有反对解释为确认。

首次进入某个开发批次时，开发规划 Agent 必须使用 [开发任务图固定模板](implementation-task-graph-template.md)形成完整候选并执行：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --implementation-system <system-id> \
  --development-batch <delivery-id>
```

目标是检查候选任务图、产物、依赖、派发信封和实施上下文；工程规范可以仍在形成。主控把代码产物清单、任务依赖图、逐任务实施上下文、并行批次、共享写入所有权和集成顺序交给用户，不展示类或方法计划。工程规范成为 `当前` 后，开发规划 Agent复核影响任务图的规则并记录依据；只有复核完成、用户确认、任务图状态为 `当前`，并通过以下实际 Coding 准入检查后，主控才能创建隔离 worktree：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --coding-system <system-id> \
  --development-batch <delivery-id>
```

实施任务完成只表示生产代码已提交。全部任务合并、任务图标记 `已完成` 并形成统一生产代码快照后，主控按真实实现和风险拆分统一测试角度；测试 Agent 不修改生产代码。全部测试反馈返回以后启动新的测试结论 Agent，测试失败先路由修正和复测，不能直接进入工程改进或正式审核。

Domain、API、核心接口内部编排和数据库的上述过程是用户审核设计，不是独立审核 Agent。主控负责保证用户看见完整审核对象、权威图和补充说明并路由原话，专业 Agent 负责设计、修改和记录确认依据；任何一方都不能代替用户填写“已确认”。图与正文冲突时，主控不能请求用户在两个版本之间猜测，应交回原 Agent 先统一文档。

## 任务包

每次调用只发送：

```text
VCDDD Skill：<本 Skill 的 SKILL.md 路径>
角色 reference：
主控状态：vcddd/work/<work-id>/主控状态.md
动作：读取主控状态和其中链接的完整任务，按合同执行；完成前回写项目文档与主控状态。
返回：只返回主控状态路径和写入是否成功。
```

共同认知协议仍固定使用 [cognitive-protocol.md](cognitive-protocol.md)，由完整任务合同列出。角色 reference 必须给出本角色实际的核心判断、风险触发器和结果结构；不能用通用协议代替角色特化。

不把全部 VCDDD reference、全部任务历史或主会话总结塞给专业 Agent。Agent 先重新读取允许写入路径的当前版本，防止覆盖并行变化。测试或受限任务明确给出允许和禁止读取的路径，不能让 Agent 自行遍历未授权的项目认识。

实施 Agent 使用任务图中的固定派发信封，除通用任务包外必须给出：

```text
实施任务与节点链接：
当前任务图与确认依据：
当前开发基线：
当前工程规范及版本：
共同起始 Commit：
已合并前置任务、实际产物与 Commit：
授权写入范围与共享位置所有者：
实施上下文合同：
待处理用户反馈：
任务进度：
实现记录：
完成回执要求：
```

派发信息只能链接任务节点已经固定的精确上下文，不能依赖聊天补充关键决定。工程规范影响复核未完成、前置 Commit 未合并、上下文链接不是当前事实或写入范围冲突时，不得启动实施 Agent。

语言验证 Agent 使用特殊盲测任务包，只给目标读者、对象类型、实际展示位置、原始名称或文案、必要截图、允许与禁止读取路径以及输出位置。不得发送当前判断、权威业务文档、预期含义、设计理由、用户反馈或旧验证结果。任务包无法隔离答案时，本轮只记录“盲测已污染”。

## 专业写回与最小回执

专业 Agent 完成工作前，按顺序直接写入：

1. 自己拥有的事实文档、代码或专项记录；
2. 完整任务 `index.md`：结果、证据位置、全部重要未决决定、依赖、影响和恢复动作；
3. `主控状态.md`：本轮变更路径、通信状态、可直接展示的用户交互包和下一步。

任务 `index.md` 保存完整专业结果，不能为了控制上下文而截断。已经进入事实文档的内容只链接事实源，不在任务中再复制正文。`主控状态.md` 只保存当前通信所需信息；需要用户回答的当前决策前沿不设数量上限，等待前置决定的重要事项也保持可见。

专业 Agent 在聊天中只返回最小回执：

```text
执行状态：已写入 | 写入失败
主控状态：vcddd/work/<work-id>/主控状态.md
需要主控：读取该文件并按“下一步”执行
```

只有文件写入失败、路径冲突或权限阻塞时，才在聊天回执中补充最小阻塞事实。不要把完整结论、diff、未决决定或交互包复制进回执。

专业 Agent 返回后，主控不再“吸收结果信封”或重写任务。它只读取 `主控状态.md`，检查声明路径是否存在，按需运行结构校验，然后原样转交用户交互包或调度下一角色。

## 反馈路由

收到上游问题时：

1. 原 Agent 把完整问题写入任务或专项记录，并在 `主控状态.md` 写明负责角色和路径；Coding 发现的问题优先写入固定设计反馈记录，其中必须已有实现、SQL 或运行证据以及建议修改；
2. 主控根据状态文件判断事实拥有者；
3. 把 `主控状态.md` 路径交给拥有者；
4. 拥有者独立判断反馈，可以采纳、部分采纳、提出替代方案或说明不采纳理由；主控不能因建议来自 Coding 就自动修改设计，也不能因设计已经确认就拒绝受理；
5. 需要改变设计时，拥有者更新事实文档、使直接依赖的确认和开发基线失效，并形成用户重新确认交互包；
6. 用户反馈被吸收、受影响设计重新确认并形成当前基线后，通知原 Agent 重新读取；
7. 只重新推导受影响范围；争议范围停止，明确不依赖该事实的开发可以继续。

用户一句反馈影响多个空间时，先判断它属于共同业务事实，还是分别纠正多个系统的本地语义：

- 共同业务事实先交给业务设计 Agent，其他系统 Agent读取更新后的业务事实；
- 同一句话分别指出多个系统“各自怎样理解”时，主控按系统切分原文，只把对应片段写入各自独立任务；
- 无法可靠切分的跨系统表达只交给业务设计 Agent或返回用户澄清，不能把整条消息广播给全部系统；
- 一个系统的 Agent不能代表另一个系统吸收反馈，也不能把自己的处理结果作为另一个系统的答案。

主控只有在路由、任务归属或多个事实拥有者竞争时做协调判断。业务意图、系统语义和实现方案由相应专业 Agent 形成。

## 代码审核闭环

开发任务图已经确认后：

1. 主控按并行批次为无未完成前置依赖的任务建立 `任务进度.md` 和独立 worktree，通过固定派发信封只给每个实施 Agent 自己的任务节点、精确上下文、基线、前置产物和允许写入范围；
2. 实施 Agent 按事件更新任务进度，提交生产代码和实现记录；主控按任务图合并并更新合并状态，前置任务合并 Commit 成为依赖任务的新起点；
3. 全部任务完成后，开发规划或集成角色建立 `集成记录.md` 和统一生产代码快照，不运行正确性验证；
4. 主控按实际代码与风险建立多个独立统一测试任务；每个从同一生产快照编写自己的测试、运行并记录反馈，不修改生产代码；
5. 全部测试反馈完成后启动新的测试结论 Agent；生产代码问题返回对应实施任务，测试代码问题返回原测试 Agent，上游问题返回事实拥有者；
6. 修正生产代码后形成新统一快照，并按测试结论复测受影响范围；
7. 测试结论允许继续后，为重复与抽象及被风险触发的其他工程角度建立独立任务；
8. 并行启动只读工程分析；代码改进按路径所有权分配，重叠修改串行，并运行受影响统一测试；
9. 工程改进完成后冻结最终生产代码与测试快照、开发基线、工程规范、批次范围和允许读取路径；
10. 为实现符合性、工程质量及触发的专项审核分别建立独立任务；
11. 并行启动只读审核 Agent；每个读取同一最终快照、任务图、集成记录、实施记录、测试结论、基线和工程规范，不读取其他审核结果；
12. 全部审核返回后启动审核结论 Agent，保留原问题编号、级别、证据、分歧和负责角色；
13. 实现问题返回开发或工程改进 Agent，上游问题返回事实拥有者；修正后形成新快照并复测、复审受影响范围；
14. API、Domain、事务、迁移、共享基础或大范围重写时重新执行全部受影响测试和两个核心审核。

实施任务不验证正确性；统一测试 Agent 写测试但不修改生产代码；工程改进允许修改生产代码但不形成“通过 / 不通过”；正式审核只读最终固定快照。测试结论和审核结论 Agent 都只能汇总原记录，不能隐藏分歧或降低问题级别。

全部记录形成、准备把交付标记为完成前执行：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --coding-system <system-id> \
  --review-batch <delivery-id>
```

目标是检查任务、阶段、集成、测试、工程改进和审核记录共同指向固定快照；它不能替代任何测试或审核。

代码审核不重新判定已经由用户确认的 Domain。审核证据若表明上游所有权、关系、生命周期或不变量可能有误，主控把证据交回系统与开发设计 Agent，并重新进入用户确认；审核 Agent 不能替用户修改 Domain 结论。

`审核结论.md` 说明：

```text
生产代码快照：
测试代码快照：
开发基线：
各审核记录：
阻断和重要问题：
处理责任：
审核分歧：
修正快照与复审：
未解决问题：
当前结论：
```

“完成”表示当前快照没有未解决的阻断问题且声明范围的审核证据可用，不表示后续不能返回修改。

## 写入所有权

- 主控维护 `vcddd/index.md`、`work/index.md`、各任务 `主控状态.md` 的派发与用户反馈部分；全局和分类索引的生成区由同步脚本维护。
- 当前专业 Agent 维护完整任务 `index.md`、本角色专项记录和自己拥有的事实；完成时回写 `主控状态.md` 的结果与下一步。主控和专业 Agent 不同时写该文件。
- 业务设计 Agent 维护 `business/`。
- 系统与开发设计 Agent 维护所选系统的设计文档。
- 开发规划 Agent 维护当前批次 `开发任务图.md`、阶段记录和最终 `集成记录.md`，不为未派发任务提前创建进度目录，不写生产代码或测试。
- 开发 Agent 运行期间单写自己任务范围内的生产代码、迁移、配置、装配、`任务进度.md` 和 `实现记录.md`；设计变更只提出请求。Agent 返回后，主控或集成角色只更新该进度文件的提交、合并与下一步状态，不能与运行中的 Agent 同时写。
- 每个统一测试 Agent 只维护自己的测试代码和测试反馈，不修改生产代码；测试结论 Agent 只维护 `测试结论.md`。
- 工程改进 Agent 只维护自己被授权的生产代码和工程改进记录，运行已有测试但不改断言；只有任务明确指定时才单写 `工程编码规范.md`。
- 每个代码审核 Agent 只维护自己的审核记录，不修改代码、设计或其他审核结果。
- 审核结论 Agent 维护 `审核结论.md`；主控只维护交付入口和路由状态，不替审核角色创造结论。
- 系统验证 Agent 只维护 `systems/<system-id>/validation/<VAL-ID>-<slug>/`；原型实现固定写入该验证项的 `src/`。
- 报告 Agent 只维护用户指定的报告目标。
- 语言验证 Agent 只维护自己的盲测记录，不修改被验证内容；结果交回原事实拥有者处理。

系统 `index.md` 由主控维护状态和导航，设计 Agent 返回需要增加或更新的链接，避免多个角色覆盖同一入口。

## 并行与恢复

专业 Agent 可以是新启动的，不依赖长驻记忆。恢复它只需要角色 reference、当前任务、权威文档和待处理反馈。

主控可以压缩或失去历史。当前角色、最新用户交互包、尚未处理的用户反馈和下一步保存在 `主控状态.md`；完整判断、全部重要未决决定、依赖、代码快照、实现与审核状态保存在完整任务和专业文档。主控不为“防止丢失”把完整内容再复制到自己的聊天。

并行任务只能从已经提交的共同 Commit 建立，不能从脏工作区复制隐含上下文。权威设计、开发基线、工程规范或前置代码变化时，主控按每个任务的精确必读来源和输入失效条件判断影响：未命中者继续，命中者暂停并更新进度。受影响任务先保存自己的改动，再由主控选择安全同步、从新 Commit 重建 worktree 或废弃旧任务；任何方式都必须更新派发信封和恢复记录，不能让 Agent 从旧对话自行猜测变化。

详细格式见 [interaction-protocol.md](interaction-protocol.md) 和 [project-context.md](project-context.md)。
