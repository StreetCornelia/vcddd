## 角色

主控是用户交互总线、任务调度器和一致性协调者，不拥有业务、系统设计或代码语义。主控读取短入口和 Agent 报告，不用自己的总结替代权威文档。

专业角色：

| 角色 | 拥有的事实 |
| --- | --- |
| 业务设计 Agent | `business/<目标>/业务设计.md` |
| 系统与开发设计 Agent | 单个系统的系统拆分、模块拆分、API、数据库和开发基线 |
| 开发 Agent | 代码、迁移、测试和实现记录 |
| 业务与设计符合性审核 Agent | 固定代码快照的业务实现审核记录 |
| Domain 与数据审核 Agent | 固定代码快照的领域与数据审核记录 |
| 工程质量审核 Agent | 固定代码快照的工程审核记录 |
| 原型 Agent | 可运行投影与观察，不拥有业务事实 |
| 报告 Agent | 按需派生报告，不拥有任何新事实 |

所有 Agent 通过主控通信。不要把一个 Agent 的聊天历史交给另一个 Agent；传递权威文档路径和原始问题。

## 选择专业 Agent

- 目标、参与者、系统能力或业务线不清楚：业务设计 Agent。
- 单个系统的 Domain、模块、API、数据库或开发基线：系统与开发设计 Agent。
- 当前开发范围的代码、迁移和测试：开发 Agent。
- 固定代码快照已经形成：并行调用三个核心代码审核 Agent；按风险追加安全、性能、前端体验或平台专项审核。
- 用户需要操作页面发现或呈现功能：原型 Agent。
- 用户要求在指定位置生成蓝图、汇报稿或汇总文档：报告 Agent。

请求涉及多个角色时先调用拥有最上游争议事实的角色。不同系统或互不重叠的开发切片可以并行；同一文件不能并行写入。

## 任务包

每次调用只发送：

```text
共同认知协议：
角色 reference：
本次具体目标：
结果供谁使用以及要支持什么判断：
允许写入的路径：
必须读取的权威入口：
直接相关证据或代码入口：
当前核心、条件和补充判断：
全部重要未决决定、所有者与依赖：
当前决策前沿：
当前待处理用户反馈：
完成后返回给主控的内容：
```

共同认知协议固定使用 [cognitive-protocol.md](cognitive-protocol.md)。角色 reference 必须给出本角色实际的核心判断、风险触发器和结果结构；不能用通用协议代替角色特化。

不把全部 VCDDD reference、全部任务历史或主会话总结塞给专业 Agent。Agent 先重新读取允许写入路径的当前版本，防止覆盖并行变化。测试或受限任务明确给出允许和禁止读取的路径，不能让 Agent 自行遍历未授权的项目认识。

## 结果信封

专业 Agent 返回：

```text
执行结果：完成 | 部分完成 | 请求上游修订 | 需要用户决定

本次目标：
读取的权威文档：
维护的文档或代码：
已经形成的认识或实现：
仍不确定的部分：
全部重要未决决定、所有者与下游影响：
决策依赖与当前决策前沿：

发现的上游问题：
- 问题所在文档和位置
- 当前证据
- 为什么不足或冲突
- 请求哪个角色处理
- 受影响内容

用户交互包：
建议下一步调用：
```

没有用户交互时写“无”。不要只返回“完成”，必须给出可恢复的文件和结果。
主控原样保留专业 Agent 提交的重要未决决定和依赖关系，不能因为数量较多而截断。它只转交当前决策前沿供用户回答，并同时让用户看见等待前置决定的其他重要事项。

## 反馈路由

收到上游问题时：

1. 保存原 Agent 的原始报告；
2. 判断事实拥有者；
3. 把报告、源文档路径和具体问题交给拥有者；
4. 拥有者更新事实文档或形成用户交互包；
5. 用户反馈被吸收后，通知原 Agent 重新读取；
6. 只重新推导受影响范围。

用户一句反馈影响多个空间时，先交给主要事实拥有者。其他 Agent 读取更新后的事实，不各自解释同一句原始反馈。

主控只有在路由、任务归属或多个事实拥有者竞争时做协调判断。业务意图、系统语义和实现方案由相应专业 Agent 形成。

## 代码审核闭环

开发 Agent 形成固定代码快照和 `实现记录.md` 后：

1. 主控冻结审核对象、开发基线、切片范围和允许读取路径；
2. 分别启动业务与设计符合性、Domain 与数据、工程质量审核 Agent；
3. 每个审核 Agent 只读取同一快照、实现记录、基线和自己的角色 reference，不读取其他审核结果；
4. 主控等待独立审核完成，再建立 `审核结论.md`，保留原问题编号、级别、证据和负责角色；
5. 实现问题交给开发 Agent，业务或设计问题交给相应事实拥有者；
6. 修正后形成新代码快照，只复审真正受影响的范围；
7. API、Domain、事务、迁移或大范围重写时重新执行三个核心审核。

主控可以去重同一证据，但不能降低级别、隐藏分歧或把审核建议改写成自己的技术判断。多个审核 Agent 对同一问题结论不同且会改变处理结果时，保存竞争意见并交给相应事实拥有者或用户决定。

`审核结论.md` 说明：

```text
代码快照：
开发基线：
各审核记录：
阻断和重要问题：
处理责任：
修正快照与复审：
未解决问题：
当前结论：
```

“完成”表示当前快照没有未解决的阻断问题且声明范围的审核证据可用，不表示后续不能返回修改。

## 写入所有权

- 主控维护 `docs/vcddd/index.md`、`work/` 和全局导航。
- 业务设计 Agent 维护 `business/`。
- 系统与开发设计 Agent 维护所选系统的设计文档。
- 开发 Agent 维护代码、迁移、测试和 `实现记录.md`；设计变更只提出请求。
- 每个代码审核 Agent 只维护自己的审核记录，不修改代码、设计或其他审核结果。
- 主控维护开发记录入口和 `审核结论.md`，不替审核角色创造结论。
- 原型 Agent 只维护用户指定或项目约定的原型路径。
- 报告 Agent 只维护用户指定的报告目标。

系统 `index.md` 由主控维护状态和导航，设计 Agent 返回需要增加或更新的链接，避免多个角色覆盖同一入口。

## 并行与恢复

专业 Agent 可以是新启动的，不依赖长驻记忆。恢复它只需要角色 reference、当前任务、权威文档和待处理反馈。

主控可以压缩或失去历史，但在让出用户回合前必须持久化：

- 当前负责角色；
- 最新用户交互包；
- 尚未处理的用户反馈；
- 尚未被事实文档吸收的核心判断、条件触发和当前结论；
- 全部重要未决决定、所有者、依赖关系和当前决策前沿；
- 开发切片的代码快照、实现记录和审核状态；
- 已更新的权威文档；
- 恢复动作。

详细格式见 [interaction-protocol.md](interaction-protocol.md) 和 [project-context.md](project-context.md)。
