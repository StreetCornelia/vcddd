## 目的

在任何生产代码形成前，把当前开发批次需要完成的全部代码工作拆成有明确先后关系的任务图。任务图覆盖业务和非业务代码；Domain 只在已确认设计真实涉及它时出现，不能为了套模板强行创建。

任务图回答：

- 全部需要产生哪些生产代码、迁移、配置和装配；
- 哪些任务提供后续任务实际消费的代码产物；
- 哪些任务可以在隔离 worktree 中并行；
- 哪些任务必须等前置代码合并后才能开始；
- 谁拥有共享写入位置；
- 全部编码完成后怎样形成统一生产代码快照。

任务图不写逐类、逐方法实现翻译，不包含测试用例、验证方式、运行证据或正确性结论。验证统一发生在全部生产代码形成以后。

## 形成顺序

严格按以下顺序形成任务图，不能先按期望的 Agent 数量分任务：

1. 读取状态为 `当前` 的开发基线、已确认设计、当前代码快照和仓库可执行约束；工程编码规范已经形成时同时读取，尚在形成时只记录已确认且会影响代码路径、共享写入或依赖的规则。
2. 从架构、模块、API、核心接口内部编排和数据库中盘点本批次全部代码产物；工程规范中的代码组织、生成文件、迁移、依赖和装配规则只用于修正任务边界，不让命名、注释、格式化等任务内部规则阻塞候选形成。
3. 按实际代码责任归类，但不要求每类都存在：
   - 工程基础；
   - 模块基础；
   - 数据与迁移；
   - 接口入口；
   - 业务实现；
   - 查询实现；
   - 外部系统集成；
   - 后台任务；
   - 系统级能力；
   - 装配与接线；
   - 现有代码改造；
   - 其他有明确来源的代码责任。
4. 为每项产物声明提供内容、消费的前置产物、主要写入范围和共享写入位置。
5. 合并必须共同完成的代码责任，拆开能够独立编写的责任。
6. 只根据真实产物依赖和写入冲突建立有向无环图。
7. 生成并行批次、worktree 基线和合并顺序。
8. 检查每项代码产物恰好由一个任务拥有，没有遗漏、重复所有权或循环依赖。

缺少代码仓库、版本快照或可恢复设计入口时不能猜测任务图。已有代码必须调查真实目录、注册入口、共享文件和构建方式；全新系统使用已确认架构与模块代码范围。

任务图候选可以与工程编码规范并行形成。工程规范尚未成为 `当前` 时，任务图必须保持 `待确认`，逐项记录“工程规范待复核”；工程规范确认后重新检查代码路径、生成物、共享位置、依赖、工具链和装配所有权。只有复核完成，任务图才能成为 `当前` 并创建 Coding worktree。

## 拆分规则

一个任务是一组必须共同完成的代码责任，不必独立产生业务结果，也不必涉及 API 或 Domain。

满足以下条件时拆开：

- 代码产物可以依据已确认合同分别编写；
- 主要写入范围不重叠；
- 一方只消费另一方明确提供的产物，不需要猜测其内部实现；
- 分开后各任务仍有清楚的代码交付边界；
- 任一任务失败不会使另一个任务已经形成的代码责任失去定义。

出现以下任一情况时合并或串行：

- 代码必须同时修改才形成有效责任；
- 共同维护同一事务、状态变化、不变量或失败语义；
- 大量修改同一核心文件、公共接口或注册入口；
- 一个候选任务只是另一个任务的少量辅助代码；
- 拆开后双方需要反复猜测内部结构；
- 拆分只是为了增加 Agent 数量。

只有已确认架构明确要求，或者至少两个真实后续任务共同消费且合同稳定时，才能建立独立公共基础任务。不能为未来可能复用预建工具库、公共基类、统一抽象层或扩展框架；只有一个当前消费者的工程代码留在消费者任务中，编码完成后再由工程改进判断是否抽取。

## 依赖与并行

每条边必须声明类型、提供产物和解除条件：

- `代码产物依赖`：后置任务直接引用前置任务产生的模块、接口、迁移、配置或其他代码；
- `数据结构依赖`：后置任务必须基于已经落地的结构或迁移代码编写；
- `装配依赖`：入口注册、依赖注入或启动装配需要前置实现已经存在；
- `写入冲突`：没有语义依赖，但会修改同一位置；它是调度约束，不能伪装成业务依赖；
- `集成汇合`：多个前置结果全部合并后才能形成统一生产代码快照。

设计文档已经确定的合同本身不自动制造代码先后关系。两个任务可以分别依据稳定合同编写且写入不重叠时，即使一个最终调用另一个，也可以并行；只有后置任务必须读取前置任务的实际代码产物时才建立实现依赖。

并行调度固定遵守：

1. 无未完成前置依赖的任务进入同一批次；
2. 同批任务从同一已记录基线 Commit 建立独立分支和 worktree；
3. 每个 Agent 只修改任务授权范围并提交自己的分支，不在任务 worktree 中合并其他分支；
4. 同一文件或共享注册点固定一个写入者，其他任务只声明需要的接线；
5. 任务完成只表示声明代码已经形成并提交，不表示正确性已经验证；
6. 集成角色按任务图合并；前置任务合并后的 Commit 是依赖任务的新基线；
7. 合并冲突若暴露责任、合同或设计问题，停止猜测并返回任务图或上游事实。

worktree 只从已经提交且可恢复的 Commit 建立，不能从另一个脏工作区复制未提交事实。运行中若开发基线、设计、工程规范或前置产物发生变化，主控先判断是否命中本任务的必读来源、不得重决策结论、写入范围或共享语义；命中时暂停受影响代码，更新任务图或派发信封并安全同步或重建 worktree。未核对新输入以前不得继续依据旧快照做决定。

`来源` 概括本任务的事实来源；`实施上下文合同/必须读取` 必须进一步链接到本任务实际使用的精确章节、API 标识、编排步骤、表规则或工程规则，不能只写整份文档名，也不能把全部历史交给 Agent 自行筛选。没有 Domain 的任务不出现 Domain 占位字段；没有 API 的任务也不强行引用 API。

`不得重新决定` 固定已经由用户确认、实施 Agent 只能忠实落地的结论。`允许自主决定` 固定仍属于本任务的等价实现空间。`前置代码产物与 Commit` 在候选阶段声明提供者和待填实际 Commit，在派发时替换为已经合并的真实产物与 Commit。`共享事务、不变量与失败语义` 只写本任务必须与其他任务共同保持的语义；不适用时写明原因。`输入失效条件` 说明哪些设计、规范、路径或前置产物变化会要求暂停、同步或重做任务图判断。`问题返回所有者` 指向精确事实拥有者，不能只写“返回上游”。

`代码产物清单` 至少说明产物标识、代码责任、来源、拥有任务和消费者。`并行批次` 按批次列任务、共同起始快照和解除条件。`共享写入与集成规则` 明确共享文件、唯一写入者和其他任务怎样交接接线请求。

`TASK-` 标识在同一开发批次唯一，只使用 ASCII 字母、数字、点、下划线和短横线，名称变化时保持稳定。

`任务类型` 只使用形成顺序中列出的固定分类；无法归入时使用“其他”并在代码责任中说明原因。`前置任务` 只写“无”或逗号分隔的 `TASK-` 标识。所有标识必须存在，不能依赖自身，任务关系必须是无循环的有向图。

`编码完成边界` 只说明生产代码、迁移、配置、注册或装配写到什么程度即完成，不写测试、验证或“通过”。测试代码不是开发任务的交付产物。

## 确认与执行

开发规划 Agent 可以在工程规范形成期间先完成候选并运行候选结构校验。用户只需审核代码产物是否完整、任务边界、先后关系、并行批次、上下文合同和共享写入所有权，不需要审核类或方法设计。工程规范成为 `当前` 后，开发规划 Agent 必须完成影响复核并填写依据；只有用户明确确认复核后的当前候选，任务图才能标记为 `当前`。

每个实施任务在派发前建立：

```text
delivery/<delivery-id>/tasks/<TASK-ID>/任务进度.md
```

任务进度只在等待条件变化、Agent 启停、形成代码产物、发生阻塞、提交或合并时更新。它记录计划状态、最近一次 Agent 事件、worktree 与 Commit、已完成产物、当前处理对象、剩余事项、阻塞、下一步和输出/合并 Commit；不记录思考过程、终端流水或无状态变化的“仍在工作”。

主控按固定派发信封为每个任务建立独立工作任务和 `主控状态.md`。派发前必须核对工程规范影响复核已完成、共同起始 Commit 包含全部前置 Commit、上下文链接仍指向当前事实、写入范围没有冲突。任一项不成立时不得创建 worktree。

执行期间：

- 用户询问某个 Agent 是否正在运行时，主控必须查询实际 Agent/任务运行状态；`主控状态.md` 和 `任务进度.md` 只是最近事件与恢复记录，不能替代实时运行证据；
- 计划状态、Agent 运行状态、代码产物状态和合并状态分别表达，不能用“Agent 工作中”推定代码仍在产生，也不能用文档已完成推定 Agent 仍在运行；
- 输入事实或代码快照变化命中 `输入失效条件` 时，受影响任务先暂停并更新进度，再安全同步或重建 worktree；不能依赖旧对话或旧工作区继续；
- 代码现实表明任务边界或依赖不成立时，开发规划 Agent 更新候选并让用户确认受影响部分；
- 设计或工程规范不成立时，写设计反馈并返回事实拥有者，不用任务图静默改变上游；
- 一个任务完成后记录输出 Commit 和实际提供产物；
- 全部任务按图合并后形成统一生产代码快照，再进入统一测试阶段；
- 未完成测试以前不得把编码完成解释为实现正确。
