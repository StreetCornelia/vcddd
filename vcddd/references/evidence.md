## 来源类型

| 来源 | 默认效力 |
| --- | --- |
| 用户当前明确决定 | 当前业务决定 |
| 已确认原型 | 确认范围内的功能事实 |
| 快速原型 | 候选功能与交互证据 |
| 当前业务政策或文档 | 核对范围后的事实候选 |
| 现有系统、代码和运行行为 | 当前现实，不自动证明应该如此 |
| 历史文档和旧设计 | 历史证据 |
| AI 综合解释 | 待纠偏推断 |
| PoC、测试和真实运行 | 指定条件下的技术或实现证据 |

不要因材料存在就把它当成完整需求，也不要把所有已有材料降级为普通候选。

证据具有系统适用范围。为 Router 形成的技术选型、运行验证和设计结论不能因为提到 Bifrost 就自动成为 Hub 的输入；一个系统中的 Domain 文档也不能证明另一个系统应采用相同模型。跨系统复用证据前必须说明它证明的是共同现实、外部合同，还是只属于原系统的本地解释。

## 确认原型

记录：

- 原型路径、链接或版本；
- 确认人、日期和可恢复记录；
- 被确认的页面、操作、输入和可见结果；
- 明确排除项；
- 未确认观察和视觉细节；
- 未覆盖路线和异常。

用户说“另一段对话已经确认”时，只提升当前点名和能恢复记录的范围。先检查当前附件、项目入口和直接相关任务；无法唯一定位时只请求最小定位信息，不搜索无关历史。

## 技术验证

只有讨论无法决定且结果可能推翻设计时建立 PoC。先说明：

- 命题和受影响设计；
- 支持、反驳和证据不足分别怎样观察；
- 必须真实的条件；
- 运行环境、版本和强度；
- 成本、权限和外部影响；
- 不验证的风险。

源码阅读和文档不能代替必须运行的命题。用户接受未验证风险不等于命题成立。

## 实现证据

测试和真实运行判断代码是否产生预期结果：

- Domain 规则和不变量；
- 模块与应用编排；
- API 契约和错误；
- 数据约束、事务和迁移；
- 端到端业务线；
- 页面、容量、故障和恢复。

证据保存复现条件、结果、限制和适用范围，不保存无意义的命令流水。

## 回写

证据本身不成为第四类事实：

- 业务或原型证据交给业务设计 Agent；
- Domain、模块、API 或数据库证据交给系统与开发设计 Agent；
- 实现缺陷交给开发 Agent；
- 证据推翻上游时先修改事实源，再局部更新下游和派生报告。

旧证据保留原适用范围；当前入口只导航到现行结论。
