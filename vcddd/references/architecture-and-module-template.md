## 用途与阅读边界

使用本模板形成系统级技术骨架和模块责任，不在 Coding 前翻译代码。

只回答：

- 系统采用什么总体技术形态；
- 主要层次、运行组件和依赖方向是什么；
- 哪些系统级机制支撑业务；
- 代码分成哪些责任模块；
- 每个模块为什么存在、负责和不负责什么；
- 哪些边界必须由所有 Coding 遵守。

禁止写入：

- 逐 API 的类、文件和方法清单；
- 模块内部的私有调用顺序；
- 可由 Coding 自主决定的局部封装；
- 对 `系统拆分.md`、`核心接口内部编排.md` 或 `数据库设计.md` 的重复解释。

## 形成方式

已有代码时：

1. 识别语言、框架、运行方式、仓库边界和明确架构说明；
2. 从构建配置、启动入口、核心模块和稳定依赖恢复当前架构与模块事实；
3. 区分明确规则、广泛稳定做法、局部历史写法和相互冲突的结构；
4. 不把当前代码自动视为理想设计；对冲突、缺失或明显不适合当前业务的部分提出推荐方案；
5. 把现状、推荐变化、影响和用户需要确认的决定完整交给用户。

必须实际读取目标仓库。只有用户概述、没有仓库路径或当前环境不能访问代码时，先请求代码入口或访问条件；不能从概述推断系统是单体、服务化或采用某种模块边界，也不能宣称已经完成现状恢复。

没有代码时：

1. 从已确认 Domain、API 编排、数据、事务、外部协作和运行约束形成最小架构；
2. 结合确定的语言、框架及版本，使用当前权威资料和成熟实践提出推荐方案；
3. 只引入当前业务和工程风险需要的组件，不为未来可能性预建框架；
4. 说明推荐理由、真正可选方案和主要权衡，交给用户确认。

不能跳过架构设计和模块拆分直接建立工程编码规范。对总体形态、层次、关键组件、模块责任或依赖方向中确有不同结果的选择，至少展示推荐方案、一个真实替代项和主要权衡。

## 架构设计模板

固定建立：

```markdown
# <系统名>架构设计

架构设计确认：待确认 | 已确认
架构设计确认依据：无
设计来源：
适用系统：
适用范围：
语言及版本：
主要框架及版本：
代码现实快照：无代码 | <Commit、标签或可恢复位置>

## 架构目标与约束

## 总体架构

## 层次与主要组件

## 依赖与调用边界

## 数据、外部系统与运行协作

## 系统级技术机制

## 技术选择与理由

## Coding 必须遵守的边界

## 允许 Coding 决定的内容

## 尚未确定的问题
```

各部分固定回答：

- `架构目标与约束`：当前架构必须解决的工程问题、业务约束、平台约束和明确不追求的目标；
- `总体架构`：单体、模块化单体、服务化或其他总体形态，以及选择原因；
- `层次与主要组件`：只说明一个层级及以上的职责和关系，不列内部类与方法；
- `依赖与调用边界`：允许和禁止的依赖方向、跨边界协作方式；
- `数据、外部系统与运行协作`：数据库、消息、缓存、任务、外部系统和部署单元怎样进入总体结构；
- `系统级技术机制`：事务承载、跨资源一致性、错误边界、日志监控、安全、配置等由什么统一机制支撑；
- `技术选择与理由`：记录会约束整个系统的技术选择、依据、替代项和代价；
- `Coding 必须遵守的边界`：列出实现不能自行改变的架构决定；
- `允许 Coding 决定的内容`：明确类、方法、文件、局部封装和等价框架 API 等自主空间；
- `尚未确定的问题`：保存仍需证据或用户决定的架构问题，不能用候选答案约束代码。

使用组件图表达总体层次、主要运行组件和依赖方向。图只展示系统级骨架，不展开逐接口内部编排。

## 模块拆分模板

固定建立：

```markdown
# <系统名>模块拆分

模块拆分确认：待确认 | 已确认
模块拆分确认依据：无
设计来源：
适用系统：
适用范围：
代码现实快照：无代码 | <Commit、标签或可恢复位置>

## 模块全景

## 模块目录

| 模块标识 | 模块名称 | 为什么存在 | 主要责任 | 承载的 Domain | 详细章节 |
| --- | --- | --- | --- | --- | --- |

## MOD-<标识>：<模块名称>

### 存在意义

### 职责与非职责

### 承载的 Domain 与数据

### 对外提供与依赖

### 代码范围

## 模块依赖规则

## 业务覆盖

## Coding 必须遵守的边界

## 尚未确定的问题
```

每个模块只回答：

- 为什么需要独立存在；
- 承担哪些业务或技术责任；
- 明确不承担哪些责任；
- 承载哪些已确认 Domain；
- 拥有或访问哪些数据和外部适配；
- 向其他模块提供什么系统级能力；
- 依赖哪些模块以及为什么；
- 在仓库中的代码根范围；
- Coding 不得跨越的责任和依赖边界。

不要规定模块内部类、方法、私有接口、局部调用顺序或预期封装。模块文档不复制 Domain 规则、API 字段、逐 API 编排或 SQL 设计。

使用组件图或包图表达模块和允许的依赖方向。业务覆盖只证明已确认业务能够落入模块，不把每条业务步骤翻译成代码结构。

## 用户确认

Agent 先形成可以独立阅读的完整推荐方案，再交给用户审核。交互包固定说明：

```text
当前总体架构：
为什么适合本系统：
模块怎样拆分：
必须遵守的边界：
从现有代码继承的内容：
建议改变的现有结构：
仍需决定的问题：
每个问题的推荐方案、替代项与主要权衡：
确认后 Coding 仍可自主决定的内容：
```

只有用户明确确认当前版本后，才能把相应确认状态改为 `已确认` 并记录可恢复依据。架构或模块边界发生实质变化时恢复为 `待确认`，受影响开发基线退出 `当前`。
