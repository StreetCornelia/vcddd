# 数据库设计固定模板

本模板约束 `vcddd/systems/<system-id>/design/数据库设计.md`。它的读者首先是审核业务和数据事实的人，其次才是实现数据库的人。正文必须让读者不阅读 SQL，也能回答：

- 为什么需要这张表；
- 一行记录究竟代表什么；
- 每个字段为什么存在、保存什么事实；
- 谁产生、修改和使用这些数据；
- 数据怎样支持已经确认的 API 编排、事务、恢复和查询；
- 哪些规则必须由数据库保持，哪些仍由 Domain 或应用层拥有。

数据库设计不是建表脚本的包装。`CREATE TABLE`、`ALTER TABLE`、索引 SQL 和可执行迁移属于 Coding 阶段的实现产物；它们必须忠实实现已确认设计，但不能代替用户对数据事实的审核。

## 形成顺序

按以下顺序形成候选：

1. 从业务、Domain、API 和逐 API 内部编排中列出必须持久化的事实；
2. 区分 Domain 状态、普通业务记录、外部事实引用或快照、查询投影、流程进度、业务证据和技术运行信息；
3. 先完成“数据承载全景”，说明为什么需要保存以及由谁拥有；
4. 再决定每张表的单行语义和独立存在的原因；
5. 最后逐字段说明具体事实、来源、变化时机和数据库注释原文；
6. 根据真实查询和并发事实补充约束、索引、事务、保留与迁移要求；
7. 运行固定结构验证，通过后才交给用户审核。

表结构只能承载已经识别的数据事实，不能反向创造 Domain、聚合、实体、版本或业务状态。未来可能出现的用途不能成为当前加表或加字段的理由。

## 逐表填写规则

每张表必须拥有稳定 `DBT-<系统内短名>` 标识。标识用于跨文档追溯，不随展示标题变化，也不能复用给另一张表。

“表的意义”必须把以下四件事分开写：

- 保存的事实是什么；
- 为什么需要持久化；
- 一行记录的边界是什么；
- 为什么这些字段应共同存在于一张表。

不能使用“保存相关信息”“记录数据”“支撑业务”等无法审核的句子。存在原因必须能指向一个当前业务结果、判断、查询、恢复、证据或技术运行需要。

`数据库表注释原文` 应独立说明这张表保存哪一类记录以及一行代表什么，不能只写表的中文名称。

技术表也必须解释意义。幂等、Outbox、任务执行、锁、消息消费位置等表不能只写实现名词，要说明它保护哪个业务动作、丢失后会造成什么后果，以及是否可以重建。

## 字段说明规则

每个实际字段都必须进入字段表，包括：

- 主键和外键；
- 创建、更新时间；
- 状态、版本、序号；
- 软删除、租户、来源、关联标识；
- JSON、数组、扩展字段；
- 仅为 ORM 或数据库机制服务的技术字段。

字段说明必须回答“为什么存在”和“值代表什么”，不能只把字段名翻译成中文。时间字段说明记录哪个事件的时间、由谁产生、使用哪种时区；金额说明币种和最小单位；状态说明允许值及其权威状态机；标识说明它识别谁、由谁分配、是否跨系统稳定。

`数据库注释原文` 是未来落入数据库 COMMENT 或等价元数据的完整中文文本。它应能脱离当前设计文档独立帮助排查数据，不能写“同上”“关联 ID”“状态”等模糊缩写。

JSON 或扩展字段必须列出当前允许结构、为什么不能建成普通字段以及演化约束。不得用无结构字段逃避逐字段设计。

## 约束、索引与事务规则

约束先写保护的事实，再写数据库和上层分别承担什么。数据库可表达的关键唯一性、引用完整性和范围兜底，不应只留给应用约定；数据库无法独立表达的跨记录或外部事实规则要明确责任位置。

索引必须来自已经识别的查询、排序、并发或约束，不从字段列表机械生成。证据不足时写“待观测”和启用条件，不预建未来索引。

事务章节只承载已确认的逐 API 编排：

- 对应到确切 API 标识和步骤；
- 说明哪些表读写必须共同成功；
- 说明并发下怎样防止违反事实；
- 说明本地提交和外部影响的顺序；
- 说明失败、超时和结果未知时保存什么恢复证据。

如果数据设计要求改变已经确认的步骤、事务或外部影响顺序，停止数据库推导，返回对应设计重新审核。

## 图与正文的关系

ER 图只提供关系全景，不能代替表的意义、字段说明或约束表。图中的表名、关系和基数必须与逐表章节一致。

多种存储并存且边界不直观时增加一张存储边界图。Domain 到持久化的投影确实复杂时可以增加投影关系图。没有这些图，正文仍必须可以完整审核。

## 禁止内容

`数据库设计.md` 中禁止：

- `CREATE TABLE`、`ALTER TABLE`、`CREATE INDEX` 等 DDL；
- SQL 代码块和完整迁移脚本；
- 用 ORM 实体代码代替字段说明；
- 只列字段名、类型和约束，不解释表与字段的意义；
- 从表名或外键反推 Domain；
- 为未来可能性预建表、字段、状态或索引；
- 把数据库产品语法选择包装成需要用户确认的业务事实。

DDL、ORM 映射、迁移、回填、回退和数据库注释的实际落地由 Coding Agent 在已确认设计之后完成，并进入代码、迁移文件、实现记录和测试证据。

## 提交用户审核

候选完成后运行：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --database-system <system-id>
```

验证通过只说明结构完整，不表示数据设计正确。系统设计 Agent 按“数据承载全景 → 表目录 → 逐表意义与字段 → 跨表事务和安全 → 实现交接”的顺序提交用户审核，并把完整 `数据库设计.md` 作为权威正文。

用户明确确认当前版本后，将确认状态改为 `已确认`，记录可恢复的确认依据。任何改变表存在意义、单行语义、字段事实、约束、事务或生命周期的实质修改都会使确认失效。
