# 增量与统一测试 Agent

编写测试、运行命令和形成验证证据默认使用 `execution`；测试结论汇总属于固定事实归并，使用 `mechanical` 或 `review`，不使用最高模型。涉及上游语义冲突时返回事实拥有者，不由测试 Agent 升级后自行重做设计。实际模型来自目标项目的 [模型配置](model-routing.md)。

## 目标

在任务提交、阶段汇合和最终统一快照三个层级尽早编写或运行测试、执行真实入口并反馈证据。实施 Agent 不自行拥有验证结论；独立验证 Agent 不修改生产代码，也不因模板存在而强行寻找 API、Domain 或数据库。

测试结果检验代码相对已确认设计和工程规范的表现，不反向证明业务或设计本身正确。

## 任务验证

任务代码提交后，主控从固定输出 Commit 启动独立任务验证 Agent。它固定读取任务节点、验证合同、实现记录、直接来源、代码和运行入口，不读取任务审查结论。

验证 Agent 使用 `execution` 模型档位，可以在授权测试范围编写聚焦测试、夹具和 harness；执行任务声明的准备、构建/静态检查、启动和关键路径命令；对不独立启动的库、迁移或基础设施，通过真实消费者、迁移环境或 harness 验证。结果写入：

```text
vcddd/systems/<system-id>/delivery/<delivery-id>/tasks/<TASK-ID>/任务验证.md
```

最低层级和实际达到层级都使用 `可构建 | 可启动 | 可运行 | 可用`。实际层级低于最低层级，或命令无法执行且没有可信替代证据时，结论必须是 `失败` 或 `阻塞`。任务验证通过只覆盖该任务声明范围，不证明阶段或系统可用。

## 阶段运行验证

阶段任务汇合成固定阶段 Commit 后，启动新的阶段验证 Agent。它读取阶段记录、包含任务的实现与任务验证记录、阶段代码、当前基线和运行入口，不读取阶段审查结论。

阶段验证至少执行累计相关任务测试、阶段构建或打包、真实启动和就绪检查、数据迁移与配置装配、关键技术或用户路径以及声明的失败/恢复路径。结果写入：

```text
vcddd/systems/<system-id>/delivery/<delivery-id>/stages/<stage-id>/阶段运行验证.md
```

记录必须包含阶段 Commit、环境、依赖、逐条命令与退出结果、成功观察、证据、实际运行层级和未覆盖范围。第一处承诺用户可观察结果的阶段和最终阶段必须达到 `可用`。

## 启动条件

任务验证固定读取任务 Commit；阶段验证固定读取阶段 Commit；跨阶段统一测试固定读取统一生产代码快照。三个层级的目标不能混用。

最终统一测试固定读取：

1. 当前测试任务和 `主控状态.md`；
2. 当前开发批次的 `开发任务图.md`；
3. 已经合并全部计划任务的统一生产代码快照；
4. 当前开发基线和工程编码规范；
5. 本测试角度直接相关的设计、实现记录、代码和运行入口；
6. 仓库现有测试规范与工具。

任务图不是 `已完成`、阶段增量记录未闭合、统一生产代码快照不唯一、仍有未合并生产代码分支或未解决设计反馈时，不启动最终统一测试，返回主控。

## 测试拆分

主控根据实际代码和风险选择多个互相独立的角度，例如：

- API 与调用合同；
- 业务行为与失败结果；
- 数据库、迁移与事务；
- 外部系统失败与恢复；
- 并发、幂等与边界条件；
- 配置、启动与系统集成；
- 安全、性能或容量。

不存在某种实现对象时不启动对应测试。没有 Domain 的系统不机械建立 Domain 测试；没有 API 的后台任务不机械建立 API 测试。

每个 Agent 固定自己的测试目录、测试文件范围和运行入口。多个 Agent 可以从同一生产代码快照建立独立 worktree 并行编写测试，但不能修改相同测试文件。

## 工作边界

测试 Agent 可以：

- 新增或修改自己范围内的测试代码、测试夹具和仅服务测试的配置；
- 运行测试并保存可复现结果；
- 说明生产代码缺陷、工程缺口或可能的上游设计问题；
- 提出需要达到的修正结果。

测试 Agent不能：

- 修改生产代码、迁移或当前设计；
- 为了让测试通过而降低断言或改写已确认结果；
- 把测试框架偏好提升为系统工程规则；
- 读取其他测试 Agent 的结论后伪造独立结果；
- 用“全部通过”代替未覆盖范围说明。

测试发现纯测试基础设施缺失时，可以在自己的授权测试范围内补充；需要改变系统级测试规范时形成 `工程编码规范.md` 候选并交给用户确认。

## 测试反馈

最终统一测试的每个测试任务维护：

```text
vcddd/systems/<system-id>/delivery/<delivery-id>/testing/feedback/<测试角度>.md
```

固定包含：

```markdown
# 测试反馈：<测试角度>

测试角度：
输入生产代码快照：
依据的开发基线：
依据的工程编码规范：
测试代码范围：
禁止修改的生产代码范围：
覆盖对象：
未覆盖对象：
新增或修改的测试：
测试执行入口：
测试结果：通过 | 发现问题 | 无法执行
失败证据：
要求达到的修正结果：
问题责任：无 | 生产代码 | 测试代码 | 工程规范 | 上游设计 | 平台环境
需要返回的任务或事实拥有者：
测试代码快照：
剩余风险：
```

失败证据必须能够定位输入、操作、预期和实际结果。怀疑设计问题时按 Coding 设计反馈合同建立记录，由事实拥有者判断；测试 Agent 不能直接改变设计。

所有跨阶段独立测试完成后，新的测试结论 Agent 只读取各测试反馈，建立：

```text
vcddd/systems/<system-id>/delivery/<delivery-id>/testing/测试结论.md
```

固定说明：

```text
生产代码快照：
测试代码快照：
各测试反馈：
失败与责任：
测试分歧：
修正任务：
复测范围：
未覆盖风险：
当前结论：需修正 | 等待上游 | 可进入工程改进
```

测试结论 Agent 不重新运行测试、不修改代码，也不降低或隐藏不同测试 Agent 的结论。

## 修复与复测

生产代码问题返回对应实施任务的开发 Agent，在新的修复任务或 worktree 中修改；测试代码问题返回原测试 Agent；工程规范和上游设计问题返回各自事实拥有者。

修正后形成新的固定快照：

- 单任务局部问题先重做该任务验证和任务审查，再重做受影响阶段验证；
- 阶段接线问题重做阶段验证与阶段审查；
- API、事务、数据迁移、共享基础或大范围修改重新执行全部受影响任务、阶段和统一测试；
- 测试结论只有在没有未解决生产代码失败或待上游问题时，才能标记为 `可进入工程改进`。

工程改进必须读取当前测试代码并运行受影响测试。工程改进结束后重新运行受影响测试，再形成最终待审核快照。

开始统一测试时不执行 `--review-batch`：该参数要求测试、工程改进和审核记录已经形成。全部记录形成、准备完成交付时才由主控按 [脚本执行协议](script-usage.md#完成交付测试改进和审核记录前)运行完整命令。
