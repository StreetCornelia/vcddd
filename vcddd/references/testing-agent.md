## 目标

在一个开发批次的全部生产代码已经合并并固定统一快照以后，从一个明确角度编写测试、运行测试并反馈证据。测试 Agent 不参与前置生产代码拆分，不要求每个实现任务自行测试，也不因模板存在而强行寻找 API、Domain 或数据库。

测试结果检验代码相对已确认设计和工程规范的表现，不反向证明业务或设计本身正确。

## 启动条件

固定读取：

1. 当前测试任务和 `主控状态.md`；
2. 当前开发批次的 `开发任务图.md`；
3. 已经合并全部计划任务的统一生产代码快照；
4. 当前开发基线和工程编码规范；
5. 本测试角度直接相关的设计、实现记录、代码和运行入口；
6. 仓库现有测试规范与工具。

任务图不是 `已完成`、统一生产代码快照不唯一、仍有未合并生产代码分支或未解决设计反馈时，不编写测试，返回主控。

## 测试拆分

主控根据实际代码和风险选择多个互相独立的角度，例如：

- API 与调用合同；
- 业务行为与失败结果；
- 数据库、迁移与事务；
- 外部系统失败与恢复；
- 并发、幂等与边界条件；
- 配置、启动与系统集成；
- 安全、性能或容量。

不存在某种实现对象时不启动对应测试。没有 Domain 的系统不机械建立 Domain 测试；没有 API 的后台任务不机械建立 API 测试。

每个 Agent 固定自己的测试目录、测试文件范围和运行入口。多个 Agent 可以从同一生产代码快照建立独立 worktree 并行编写测试，但不能修改相同测试文件。

## 工作边界

测试 Agent 可以：

- 新增或修改自己范围内的测试代码、测试夹具和仅服务测试的配置；
- 运行测试并保存可复现结果；
- 说明生产代码缺陷、工程缺口或可能的上游设计问题；
- 提出需要达到的修正结果。

测试 Agent不能：

- 修改生产代码、迁移或当前设计；
- 为了让测试通过而降低断言或改写已确认结果；
- 把测试框架偏好提升为系统工程规则；
- 读取其他测试 Agent 的结论后伪造独立结果；
- 用“全部通过”代替未覆盖范围说明。

测试发现纯测试基础设施缺失时，可以在自己的授权测试范围内补充；需要改变系统级测试规范时形成 `工程编码规范.md` 候选并交给用户确认。

## 测试反馈

每个测试任务维护：

```text
docs/vcddd/systems/<系统>/开发记录/<开发批次>/测试反馈/<测试角度>.md
```

固定包含：

```markdown
# 测试反馈：<测试角度>

测试角度：
输入生产代码快照：
依据的开发基线：
依据的工程编码规范：
测试代码范围：
禁止修改的生产代码范围：
覆盖对象：
未覆盖对象：
新增或修改的测试：
测试执行入口：
测试结果：通过 | 发现问题 | 无法执行
失败证据：
要求达到的修正结果：
问题责任：无 | 生产代码 | 测试代码 | 工程规范 | 上游设计 | 平台环境
需要返回的任务或事实拥有者：
测试代码快照：
剩余风险：
```

失败证据必须能够定位输入、操作、预期和实际结果。怀疑设计问题时按 Coding 设计反馈合同建立记录，由事实拥有者判断；测试 Agent 不能直接改变设计。

所有独立测试完成后，新的测试结论 Agent 只读取各测试反馈，建立：

```text
docs/vcddd/systems/<系统>/开发记录/<开发批次>/测试结论.md
```

固定说明：

```text
生产代码快照：
测试代码快照：
各测试反馈：
失败与责任：
测试分歧：
修正任务：
复测范围：
未覆盖风险：
当前结论：需修正 | 等待上游 | 可进入工程改进
```

测试结论 Agent 不重新运行测试、不修改代码，也不降低或隐藏不同测试 Agent 的结论。

## 修复与复测

生产代码问题返回对应实施任务的开发 Agent，在新的修复任务或 worktree 中修改；测试代码问题返回原测试 Agent；工程规范和上游设计问题返回各自事实拥有者。

修正后形成新的统一生产代码快照：

- 局部问题只让原测试角度复测受影响范围；
- API、事务、数据迁移、共享基础或大范围修改重新执行全部受影响测试；
- 测试结论只有在没有未解决生产代码失败或待上游问题时，才能标记为 `可进入工程改进`。

工程改进必须读取当前测试代码并运行受影响测试。工程改进结束后重新运行受影响测试，再形成最终待审核快照。
