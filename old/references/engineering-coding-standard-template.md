## 目的

在首次 Coding 前形成由用户确认的系统级工程规则。规范只规定代码怎样稳定、一致、可验证地表达已确认设计，不重新定义业务、Domain、API、事务业务语义或数据库事实。

同一系统只维护一份当前规范。所有开发规划、生产代码实现、统一测试、工程改进和代码审核都读取并遵守它。不要为每个实施任务重新发明风格，也不要把规范写成某次实现的类、方法和文件计划。

形成规范前先检查 `架构设计.md` 和 `模块拆分.md` 已经存在、由用户确认并覆盖当前系统。缺失时返回系统与开发设计 Agent，先按固定模板完成架构和模块；不能用工程规范中的“架构与代码组织”替代这两份上游事实，也不能提前生成或交付一份假设这些边界已经确定的工程规范候选。

工程规范可以与开发任务图候选并行形成。目录根、生成文件、迁移、依赖、共享装配和工具链等会改变代码产物、写入范围或任务依赖的规则，必须在 Coding 前触发任务图影响复核；命名、注释、错误包装、局部表达和格式化等任务内部规则不阻塞任务图候选形成。工程规范未成为 `当前` 或影响复核未完成时，不得创建 Coding worktree。

## 两条形成流程

### 已有代码

固定执行：

```text
识别语言、框架及版本
→ 按固定模板逐项调查仓库
→ 提取稳定工程风格
→ 标记冲突、缺失和历史例外
→ 对冲突与缺失提出当前最佳实践
→ 形成完整候选
→ 用户确认
→ 状态改为当前
→ Coding 遵守
```

每个模板项只能得到以下结论之一：

- `已有稳定规则`：有明确配置、仓库规范或多个核心位置一致证明；
- `现有做法冲突`：存在多种不能同时成为系统规则的做法；
- `当前没有体现`：没有相关代码、场景或足够证据；
- `明确不适用`：当前系统不存在该技术形态，并写明原因。

现有代码证据优先级固定为：

1. 仓库明确规范、构建配置和自动检查；
2. 核心模块长期、一致采用的方式；
3. 多个模块共同采用的稳定方式；
4. 局部或偶发代码只能作为历史例外，不能直接成为系统规范。

从代码发现的稳定做法也只是候选。代码证明“当前怎样写”，不能自动决定“以后必须怎样写”。把继承、修正和例外一起交给用户确认。

必须实际读取目标仓库的规范、配置、核心代码和代表性模块，并为每个固定主题留下可恢复证据。只有用户对现状的文字概述、没有仓库路径或当前环境不能读取代码时，先请求代码入口或访问条件；不能根据概述补写一份看似完整的存量规范，也不能把缺少访问误写成“当前没有体现”。

### 完全没有代码

固定执行：

```text
确认语言、框架及版本
→ 按固定模板逐项提出候选规则
→ 使用当前权威资料和成熟实践
→ 说明推荐、替代项与权衡
→ 形成完整候选
→ 用户确认
→ 状态改为当前
→ Coding 遵守
```

Agent 负责先提出完整推荐，不把“日志怎么写”“事务怎么做”等空问题交给用户从零发明。只让用户决定会形成系统长期规则的差异。

全新系统也必须先形成并确认架构设计和模块拆分，再依据这些边界形成工程规范。对会长期约束系统且确有不同结果的选择，完整候选必须同时展示推荐方案、至少一个真实可选方案和主要权衡；不能只给一组默认值后让用户整体确认。

## 调查和推荐规则

针对语言、框架、ORM、数据库驱动、日志库、测试框架和构建工具：

- 确认实际或预期版本；
- 优先使用当前官方文档、语言标准、框架维护者指南和成熟生态约定；
- 说明资料适用的版本和取得时间；
- 区分强制正确性要求、推荐实践和纯偏好；
- 不用“业界一般如此”代替依据；
- 只保留真正适合当前系统约束的方案。

现有做法冲突或模板项缺失时，固定向用户提供：

```text
当前情况：
推荐方案：
为什么适合当前系统：
依据及适用版本：
其他可选方案：
主要差异与代价：
适用条件与生命周期：
正确示例：
禁止或反例：
是否影响开发任务图：是 | 否
影响的代码产物、路径、共享写入或依赖：
建议采用：
请用户确认或调整：
```

多个问题按架构组织、事务数据、错误日志、可靠性安全、测试交付等主题分组展示。不能因为问题多而省略模板项，也不要让用户逐个回答不会改变系统规则的局部实现细节。

语言习惯、资源生命周期、事务、并发、数据映射、错误传播或封装规则仅用抽象标签无法让用户确认时，必须给当前语言或框架的最小代码示例和反例。示例只解释规则边界，不预先翻译当前系统的类、文件或方法计划。用户来自另一语言生态时，先说明对应概念和差异，再请求选择。

维护角色：Coding Agent

各主题至少回答：

- `架构与代码组织`：目录、包、层次、模块、依赖方向和跨模块调用；
- `Domain 与应用编排`：业务判断归属、Domain 代码表达、应用层责任和禁止的贫血实现；
- `命名与代码表达`：名称、类型、参数返回、空值、条件、注释、格式化和静态检查；
- `事务`：技术承载、传播、隔离、回滚、外部调用、跨资源一致性和重试关系；
- `数据访问`：SQL 或 ORM、Repository、查询写入、批量分页、锁、映射、迁移和注释；
- `错误处理`：错误分类、层间转换、API 映射、捕获、重试、错误码和禁止吞错；
- `日志与可观察性`：形式、级别、字段、记录时机、频率或抑制、关联标识、指标、追踪和脱敏；
- `外部系统协作`：客户端边界、超时、重试、降级、转换、错误、幂等、日志和测试替身；
- `并发、异步与幂等`：并发控制、幂等结果、消息、任务、重复执行、补偿和顺序；
- `配置与安全`：配置、环境差异、密钥、权限、输入、敏感数据和安全日志；
- `测试`：任务与阶段增量验证以及最终跨阶段统一测试共同使用的测试框架、目录、命名、隔离、数据、替身和风险触发角度；不存在的 Domain、API 或数据库测试写明不适用；
- `封装、复用与重复代码`：生产代码实施、真实重复、抽象条件、过度封装和工程改进；
- `工具链与交付验证`：格式化、Lint、类型或编译检查、迁移检查、测试和可重复交付入口。

当前系统不存在某项时写“不适用、原因和重新触发条件”，不能删除固定主题。固定模板保证 Agent 已经检查该问题，不代表必须预建相应技术机制。

工程规范定义验证和测试代码怎样写，但不能把反馈推迟到最终：单个实施 Agent 不拥有独立验证结论，任务 Commit 形成后由任务验证 Agent 立即补充聚焦测试或运行证据；阶段 Commit 形成后由阶段验证 Agent 验证组合运行；全部阶段闭合后，统一测试 Agent 只补充跨阶段和系统级风险。

## 单项规则模板

每项会约束 Coding 的规则固定写：

```text
规则标识：
状态：当前 | 候选 | 已替代
级别：核心 | 条件 | 补充
适用范围或触发条件：
当前规则：
来源：现有代码 | 语言最佳实践 | 框架最佳实践 | 用户决定
现有代码证据：无代码 | <配置、代码和快照>
采用原因：
适用生命周期或调用边界：
正确示例：
禁止或反例：
允许的实现空间：
禁止行为：
验证方式：
允许例外：
存量代码处理：
是否影响开发任务图：是 | 否
影响的代码产物、路径、共享写入或依赖：
关联配置、代码或替代规则：
```

规则级别固定为：

- `核心`：本系统所有 Coding 无条件读取和遵守；
- `条件`：索引声明触发事实，命中时读取和遵守；
- `补充`：不改变当前正确性的偏好，在核心和条件规则之后处理。

只有状态为 `当前` 且整份规范已经由用户确认的规则才能约束 Coding。

## 用户交互与确认

候选规范必须覆盖固定模板的全部主题。交互包固定说明：

```text
当前技术栈：
形成方式：
从现有代码继承的规则：
现有代码中的冲突和历史例外：
当前没有体现的规则：
建议采用的最佳实践：
每项重要选择的推荐、依据、替代项和权衡：
明确不适用的主题及原因：
确认后 Coding 必须遵守的内容：
仍然留给 Coding 自主决定的内容：
```

分轮交互中，每次明确选择都写入“形成过程与依据”的决策表，状态使用 `讨论中 | 已选择 | 被替代`。`已选择` 只表示该单项已经被用户选择，不表示整份规范已经确认，也不能提前约束 Coding。新一轮提问先读取该表和当前权威设计，不能让用户重复决定已经记录的事项；上游变化命中某项依据时，把该项恢复为 `讨论中` 并说明影响。

只有用户明确确认当前完整候选后，才能同时写：

```text
状态：当前
规范确认：已确认
规范确认依据：<可恢复的用户确认>
```

沉默、旧代码、Agent 判断或某个工具配置都不能代替用户确认。任何系统级规则的实质变化先写成候选并重新交给用户；确认前不得约束新的 Coding。

规范确认后，若已经存在开发任务图候选，必须把所有“是否影响开发任务图：是”的当前规则交给开发规划 Agent，重新核对代码产物、物理路径、生成物、共享写入、依赖、并行批次和装配所有权。复核结果写入任务图；没有影响也要明确记录依据。

## Coding 中补充规范

Coding 遇到现有规范没有覆盖的问题时：

1. 判断它是局部等价实现选择，还是会跨模块、跨实施任务、跨开发批次或长期重复使用的系统规则；
2. 局部选择由 Coding 自主决定，只记录在实现或工程改进记录；
3. 系统级问题先调查现有代码；没有稳定做法时根据当前技术栈提出最佳实践、替代项和权衡；
4. 把新规则写成候选并更新规则索引；
5. 取得用户确认后更新规范版本和确认依据，再让后续 Coding 遵守；
6. 涉及业务结果、Domain、API、事务业务语义或数据库事实时停止补规范，进入设计反馈闭环；
7. 影响存量代码时明确立即迁移、触及时迁移、允许例外或暂不迁移。

生产代码实施以忠实和清楚为先，不为未来复用提前抽象。任务和阶段审查先处理局部问题；全部生产代码形成并经过统一测试反馈后，独立工程改进 Agent 再检查跨任务的真实重复、职责混乱和合理抽象点。重构仍不得改变已确认设计和当前工程规范。
