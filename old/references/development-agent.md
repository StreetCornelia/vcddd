# 开发 Agent

开发规划默认使用 `planning`；边界明确的实施任务默认使用 `execution`；任务/阶段验证使用 `execution`，任务/阶段审查使用 `review`。任何角色都显式读取目标项目的 [模型配置](model-routing.md)，不能继承主对话最高模型。

## 目标

依据当前开发基线、工程编码规范和已经确认的开发任务图完成生产代码，并让每个任务和阶段尽早形成独立验证、运行证据和聚焦审查。开发 Agent 不重新定义业务或设计，不为了套模板强行创建 API 或 Domain，也不自行拥有正确性结论。

开发分为两种互相隔离的工作：

- `开发规划 Agent`：盘点全部代码产物，形成任务依赖图、并行批次、worktree 基线和共享写入所有权；
- `实施 Agent`：只执行任务图中的一个任务，提交声明范围内的生产代码并记录实际产物。
- `任务验证 Agent`：在固定任务 Commit 上执行验证合同、编写或运行聚焦测试并记录可运行证据，不修改生产代码；
- `任务审查 Agent`：只读固定任务 Commit，检查任务实现符合性和局部工程质量；
- `阶段验证/审查 Agent`：对阶段汇合 Commit 做真实运行验证和跨任务集成审查。

跨阶段统一测试仍在全部生产代码汇合后进行，但不是第一次验证。编码完成表示代码已经形成；任务能否合并由独立任务验证和审查决定，阶段能否继续由阶段验证和审查决定。

## 进入开发

开发规划固定读取：

1. 当前任务和 `主控状态.md`；
2. 状态为 `当前` 的开发基线；
3. 已确认的架构、模块、API、核心接口内部编排和数据库设计；
4. 当前代码快照、仓库规范和真实代码入口；
5. 已经形成的工程编码规范及其中会影响代码路径、生成物、共享写入或依赖的规则；规范尚未完成时记录待复核，不阻塞任务图候选；
6. [开发任务图固定模板](implementation-task-graph-template.md)；
7. [Coding 渐进实施与系统工程规范](coding-guidance.md)。

实施 Agent 固定读取：

1. 当前实施任务及 `主控状态.md`；
2. 状态为 `当前` 的 `开发任务图.md` 中自己的任务节点与完整实施上下文合同；
3. 固定派发信封和本任务 `任务进度.md`；
4. 当前开发基线和工程编码规范；
5. 实施上下文精确链接的设计章节；
6. 任务记录的 worktree 起始 Commit 和已经合并的前置代码；
7. 授权范围内的现有代码。

文件已经存在、代码已经采用某种写法或 Agent 推荐都不能替代用户对设计、工程规范和任务图的确认。

## 开发规划

严格按 [开发任务图固定模板](implementation-task-graph-template.md) 工作：

```text
盘点全部代码产物
→ 声明每项产物的提供者和消费者
→ 合并必须共同完成的代码责任
→ 识别真实代码依赖和写入冲突
→ 生成有向无环任务图
→ 形成并行批次与 worktree 基线
→ 用户确认
```

开发任务覆盖工程基础、模块基础、数据迁移、入口、业务实现、查询、外部集成、后台任务、系统级能力、装配和存量改造。类型只在真实存在时使用。

不按技术分层机械建立 Controller、Service、Repository、Domain 等任务，不把每个任务强行包装成业务切片，也不按期望 Agent 数量拆分。Domain 只在直接来源真实包含 Domain 行为时出现。

开发规划 Agent 不写生产代码。任务图引入新的总体架构、模块边界、统一机制或系统级工程规则时，先返回相应事实拥有者或形成工程规范候选，不能用调度计划暗中建立新设计。

任务图候选可以在工程编码规范形成期间先完成。工程规范成为 `当前` 后，开发规划 Agent 必须复核会影响代码产物、物理路径、生成物、共享写入、依赖和装配的规则并记录依据；复核前任务图不能成为 `当前`，也不能创建实施 worktree。

任务图候选交给用户前，开发规划 Agent 执行：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --implementation-system <system-id> \
  --development-batch <delivery-id>
```

目标是检查候选任务图、代码产物、依赖、派发信封和实施上下文。用户确认、任务图成为 `当前`、工程规范影响复核完成以后，主控创建任何 Coding worktree 前执行：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --coding-system <system-id> \
  --development-batch <delivery-id>
```

目标是检查实际 Coding 准入和已经派发任务的进度合同。参数定义与错误处理见[脚本执行协议](script-usage.md#开发任务图候选交给用户前)；候选检查失败由开发规划 Agent 修正任务图，Coding 准入失败由错误所指向的设计、工程规范、任务图或任务进度拥有者修正，主控不得先创建 worktree。

## 执行实施任务

实施 Agent 只完成任务节点的代码责任：

- 在记录的起始 Commit 建立独立分支和 worktree；
- 只修改任务授权范围；
- 忠实使用前置任务已经合并的实际代码产物；
- 实现节点声明的生产代码、迁移、配置、注册或装配；
- 不顺便修改相邻任务或共享文件；
- 共享接线由任务图指定的唯一写入者完成；
- 提交自己的代码分支并记录输出 Commit 和实际提供产物；
- 不合并其他任务分支，也不自行宣布依赖任务可以开始。

生产代码实施优先清楚和忠实：

- 不为未来可能复用预建接口、基类、工具库或扩展框架；
- 允许含义清楚的局部技术重复留到统一工程改进；
- 不允许同一业务规则、事务或失败语义在多个位置独立实现；
- 不用现有代码便利绕过已确认设计或工程规范；
- 规范不足时区分局部等价选择和系统级规则，系统级规则形成候选并由用户确认。

实施 Agent 不编写独立验证结论，但必须运行任务图已经声明的最低成本构建、类型检查、格式或静态检查，避免提交显然无法消费的代码，并把命令结果交给后续验证 Agent。独立任务验证 Agent 才负责按固定 Commit 编写/运行聚焦测试、启动或关键路径并形成结论。代码无法达到任务声明的最低运行层级时，任务不是“代码已完成”，应修正任务或返回规划/设计。

## 任务上下文与进度

每个任务节点必须有完整实施上下文合同，固定说明：

```text
必须读取：
不得重新决定：
允许自主决定：
前置代码产物与 Commit：
共享事务、不变量与失败语义：
输入失效条件：
问题返回所有者：
```

实施 Agent 不依赖聊天历史补全关键事实，也不遍历全部项目后自行挑选权威。派发信封必须给出当前任务图、开发基线、工程规范版本、共同起始 Commit、已合并前置产物、授权写入范围、当前反馈、进度文件和实现记录位置。

每个实施任务固定维护：

```text
vcddd/systems/<system-id>/delivery/<delivery-id>/tasks/<TASK-ID>/任务进度.md
```

固定字段：

```text
计划状态：等待前置 | 可开始 | 进行中 | 阻塞 | 代码已提交 | 验证中 | 需修正 | 可合并 | 已合并
最近一次 Agent 事件：未启动 | 已启动 | 已结束 | 异常中断
Agent 事件依据：
负责 Agent：
模型配置：
请求档位：
实际模型：
推理强度：
worktree：
起始 Commit：
当前 Commit：
已完成代码产物：
当前处理对象：
尚未完成：
阻塞与等待对象：
下一步：
输出 Commit：
合并 Commit：
最近更新时间：
```

任务进度是事件与恢复记录，不是开发日记。只在等待条件改变、Agent 启停、形成阶段性产物、发生阻塞、提交或合并时更新；不保存终端流水、推理过程或没有状态变化的过程摘要。实施 Agent 运行期间单写自己的进度文件；返回后由主控或集成角色更新提交与合并状态，双方不能同时写。

`最近一次 Agent 事件` 不是实时证明。用户询问 Agent 是否正在运行时，主控必须查询实际 Agent 或任务工具状态，再报告并修正已经过期的文件状态。计划、Agent、代码产物和合并状态不能互相推定。

worktree 必须从已提交的派发 Commit 建立。开发基线、设计、工程规范或前置产物变化命中 `输入失效条件` 时，实施 Agent停止受影响代码并更新进度；主控核对差异后安全同步或重建 worktree，更新派发信封与起始 Commit。未同步以前不得继续依据旧事实实现。

## 发现设计问题

忠于设计不等于压下实现证据。生成 SQL、迁移、配置或生产代码时：

- 语言、框架、ORM、文件组织或局部代码问题能保持当前语义：自行解决；
- 架构、模块责任、API、编排、Domain、数据、事务、外部影响或工程规范无法落地：停止受影响范围并形成具体反馈。

按事实所有者路由：

- 业务结果错误：业务设计 Agent；
- Domain 对象、行为、所有权或规则矛盾：系统与开发设计 Agent；
- 总体架构、主要组件或统一机制不成立：架构设计；
- 模块责任和依赖边界不成立：模块拆分；
- API 或内部编排无法表达结果：API 或核心接口内部编排；
- 表、字段、约束、迁移或事务承载不成立：数据库设计；
- 系统级工程规则缺失或冲突：Coding 形成工程规范候选并请求用户确认；
- 任务边界、依赖或共享写入判断错误：开发规划 Agent 更新任务图候选；
- 只是实现缺陷：当前实施 Agent 修正。

在当前交付单元的 `feedback/design/` 中建立与实施任务关联的记录，写明问题位置、权威设计、代码或 SQL 证据、影响、推荐修改、替代方案、可继续范围和事实拥有者。没有 Domain 的任务不使用 Domain 术语解释非 Domain 问题。

`来源与代码对应` 只记录本任务实际使用的设计和工程规则。任务没有 API、Domain、数据库或外部协作时不建立虚假映射。

实现记录是代码交接索引，不是开发日记、终端流水或测试报告。它不包含测试、验证证据或“通过”结论。

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --coding-system <system-id> \
  --development-batch <delivery-id> \
  --task-check <task-id>
```

目标是检查任务实现、验证和审查指向同一 Commit，达到最低运行层级并保持 Agent 独立；失败时不得合并。

## 集成与测试交接

开发规划或集成角色按任务图依次合并：

1. 同批无依赖任务从同一基线并行；
2. 任务验证和任务审查都通过以后才合并；
3. 前置任务合并后的 Commit 成为依赖任务的新起点；
4. 共享文件由唯一写入任务处理；
5. 冲突暴露新依赖时先更新任务图，不临场猜测；
6. 阶段任务汇合后固定阶段 Commit，在 `阶段记录.md` 登记阶段集成 Agent、`execution` 档位、实际模型与推理强度，再建立 `阶段运行验证.md` 和 `阶段审查.md`；
7. 阶段运行验证执行累计测试、构建、启动、就绪和关键路径；阶段审查检查跨任务接线、共享写入和错误传播；
8. 两者通过后阶段才请求用户确认或解除下一阶段；
9. 全部阶段闭合后建立 `集成记录.md`，记录任务/阶段 Commit、增量证据、合并顺序、未实现项和统一生产代码快照；
10. 把全部任务进度标记为 `已合并`，把任务图状态标记为 `已完成`。

阶段准备请求用户确认或派发依赖阶段前，主控执行：

```text
python3 <skill-root>/scripts/validate_project.py <repo-root> \
  --coding-system <system-id> \
  --development-batch <delivery-id> \
  --stage-check <stage-id>
```

目标是检查阶段记录、运行验证和阶段审查指向同一 Commit 且达到声明层级；失败时保持阶段阻塞。

以上任务、集成或交付状态写回以后，负责本次写回的开发规划或集成角色执行：

```text
python3 <skill-root>/scripts/sync_indexes.py <repo-root> --write
```

目标是同步交付与工作索引，不是证明代码正确。命令失败时由当前写回角色修正自己改变的状态拥有者；若错误属于其他事实源，保持当前交付未闭合并返回其拥有者。

集成角色不编写测试，也不宣布正确；阶段验证 Agent 拥有运行证据，阶段审查 Agent 拥有聚焦审查结论。统一生产代码快照形成后，主控按 [增量与统一测试 Agent](testing-agent.md) 启动跨阶段测试任务，补齐单任务和单阶段无法发现的组合风险。反馈中的生产代码问题返回对应实施任务修正，形成新快照后按影响范围复验、复审和复测。

测试结论允许进入工程改进后，再由多个工程改进 Agent 分析重复与抽象及风险触发角度。工程改进运行已经形成的受影响测试，最后固定待审核代码与测试快照。
