# 证据效力

验证命题和证据解释默认使用 `planning`，边界明确的原型/PoC 实现与运行使用 `execution`，索引和固定记录同步使用 `mechanical`。实际模型来自目标项目的 [模型配置](model-routing.md)；运行 Agent 不继承主对话最高模型。

## 来源类型

| 来源 | 默认效力 |
| --- | --- |
| 用户当前明确决定 | 当前业务决定 |
| 已确认原型运行 | 记录范围内的功能与交互证据，不自动成为系统事实 |
| 快速原型 | 候选功能与交互证据 |
| 当前业务政策或文档 | 核对范围后的事实候选 |
| 现有系统、代码和运行行为 | 当前现实，不自动证明应该如此 |
| 历史文档和旧设计 | 历史证据 |
| AI 综合解释 | 待纠偏推断 |
| PoC、测试和真实运行 | 指定条件下的技术或实现证据 |

不要因材料存在就把它当成完整需求，也不要把所有已有材料降级为普通候选。

证据具有系统适用范围。为 Router 形成的技术选型、运行验证和设计结论不能因为提到 Bifrost 就自动成为 Hub 的输入；一个系统中的 Domain 文档也不能证明另一个系统应采用相同模型。跨系统复用证据前必须说明它证明的是共同现实、外部合同，还是只属于原系统的本地解释。

## 系统验证工作空间

每项验证属于一个被验证系统，固定保存在：

```text
vcddd/systems/<system-id>/validation/<VAL-ID>-<slug>/
├── index.md
├── 验证计划.md
├── 验证结论.md
├── src/
├── fixtures/
├── scripts/
└── runs/
    └── <RUN-ID>/
        ├── 运行记录.md
        └── artifacts/
```

`index.md` 是验证状态的唯一拥有者，声明验证标识、所属系统、验证方法、命题、状态、结论入口和最近有效运行。单次运行状态只由该 `RUN-ID/运行记录.md` 拥有；运行记录固定保存源码 Commit、环境、入口、输入、观察、证据、适用与未覆盖范围，以及用户确认状态、依据和确认范围。系统和验证索引只保存脚本生成的状态投影。

验证方法包括 `prototype`、`executable-poc`、`contract-check`、`inspection`、`benchmark`、`simulation` 和 `minimal-e2e`。验证代码、原型代码、夹具和运行证据都保存在同一验证项中；生产代码不得导入 `validation/`。

验证项、运行记录、用户确认状态或验证代码更新后，执行：

```text
python3 <skill-root>/scripts/sync_indexes.py <repo-root> --write
python3 <skill-root>/scripts/validate_project.py <repo-root>
```

第一条命令同步验证索引；第二条使用基础检查验证目录、运行记录、源码 Commit 和用户确认绑定。系统验证没有专项参数。完整参数与失败处理见 [脚本执行协议](script-usage.md#系统验证或原型运行记录更新后)。

## 原型验证

原型是 `prototype` 验证方法，不是独立目录类型或系统事实源。记录：

- 验证项路径、原型源码 Commit 和运行编号；
- 确认人、日期和可恢复记录；
- 被确认的页面、操作、输入和可见结果；
- 明确排除项；
- 未确认观察和视觉细节；
- 未覆盖路线和异常。

原型源码写入验证项 `src/`，截图、录屏、用户反馈和观察写入具体 `runs/<RUN-ID>/`。用户说“另一段对话已经确认”时，只提升当前点名且能定位到 Commit、运行和范围的内容；无法唯一定位时只请求最小定位信息，不搜索无关历史。

## 技术验证

只有讨论无法决定且结果可能推翻设计时建立 PoC。先说明：

- 命题和受影响设计；
- 支持、反驳和证据不足分别怎样观察；
- 必须真实的条件；
- 运行环境、版本和强度；
- 成本、权限和外部影响；
- 不验证的风险。

源码阅读和文档不能代替必须运行的命题。用户接受未验证风险不等于命题成立。

## 实现证据

测试和真实运行判断代码是否产生预期结果：

- Domain 规则和不变量；
- 模块与应用编排；
- API 契约和错误；
- 数据约束、事务和迁移；
- 端到端业务线；
- 页面、容量、故障和恢复。

证据保存复现条件、结果、限制和适用范围，不保存无意义的命令流水。

## 回写

证据本身不成为第四类事实：

- 业务或原型验证证据交给相应事实拥有者；
- Domain、架构、模块、API 或数据库证据交给系统与开发设计 Agent；
- 实现缺陷交给开发 Agent；
- 证据推翻上游时先修改事实源，再局部更新下游和派生报告。

旧证据保留原适用范围；当前入口只导航到现行结论。
