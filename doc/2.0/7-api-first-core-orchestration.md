# VCDDD 2.0 阶段性成果（七）：以 API 为唯一主轴的核心接口内部编排

> 状态：已经进入运行时 Skill
>
> 日期：2026-07-30
>
> 前置文档：[Domain 思想与进入 Coding 设计前的认知基线](./5-domain-thinking-and-coding-transition.md)

## 1. 发现的问题

原有设计虽然要求“先按 API、再按 Domain 方法”展开，但它给一份文档建立了两个并列索引。Agent 为满足完整性，容易把 API、Domain 方法、事务、日志、失败、图和验证分别组织成大段资料。

这种文档可以包含很多正确信息，却要求读者自己跨章节拼装：

```text
这个接口先做什么
→ 得到什么
→ 接下来为什么走另一步
→ 最终产生什么结果
```

问题不只是语言冗长，而是文档没有唯一阅读主轴。

## 2. 新的事实边界

`核心接口内部编排.md` 只拥有：

> 一个已确认 API 进入系统以后，怎样按顺序调用应用用例、Domain、Repository 和外部能力，怎样形成分支、事务、外部影响和调用者可见结果。

相邻文档继续拥有自己的事实：

- `API设计.md`：请求、响应、协议和错误合同；
- `系统拆分.md`：Domain 行为、规则、不变量、对象协作和生命周期；
- `模块拆分.md`：模块、端口、Adapter 和依赖；
- `数据库设计.md`：数据事实及其持久化承载；
- `工程编码规范.md`：事务框架、日志形式、代码组织和测试实现。

核心接口内部编排只引用这些事实，不复制或重新设计它们。

## 3. 全文只有一个主轴

```text
接口目录
→ API-1 完整编排
→ API-2 完整编排
→ API-3 完整编排
```

不能使用：

```text
第一部分：所有 API
第二部分：所有 Domain 方法
```

也不能把多个接口合成“创建类 API”“修改类 API”。每个 API 都有稳定标识和独立章节；简单查询也保留相同结构。

## 4. 每个 API 的固定阅读顺序

```text
业务结果
→ 主流程
→ 分支与失败
→ 事务与外部影响
→ Domain 调用
→ 业务证据与验证
```

主流程使用连续步骤回答：

```text
谁执行
→ 做什么
→ 得到什么结果
→ 下一步是什么
```

事务、失败、外部影响和日志必须引用这些步骤，不能各写一套脱离主流程的长篇说明。图只能补充主流程表，不能代替人类可读的文字路径。

## 5. 为什么需要低自由度模板

“需要说明 API、Domain、事务、日志和失败”只是信息清单。模型仍然可以自行决定顺序、层级和表达方式。

核心接口内部编排承担设计确认、Coding 输入和实现审核，结构一旦漂移就会让三个阶段共同失去稳定索引。因此这里适合使用低自由度模板：

- API 设计先给每个接口稳定 `API 标识`；
- 每个 API 章节固定六个三级标题；
- 主流程、失败、事务和 Domain 调用使用固定表头；
- API 标识必须与 API 设计按顺序一一对应；
- 候选交给用户前执行专门结构校验；
- 结构不合格时不能通过摘要代替正文请求确认。

## 6. 当前思想基线

> 核心接口内部编排不是设计资料的集合，而是逐接口、可连续阅读的业务执行说明。读者打开一个 API 章节，就应当直接知道调用者为什么调用、系统先后做什么、每一步产生什么、失败在哪里、事务在哪里结束以及最终返回什么；不需要跳到另一套 Domain 方法目录自行组装答案。
