# 2.0：以数据事实为中心的数据库设计

## 问题

数据库设计如果没有确定模板，AI 很容易把“完整”理解成“给出尽可能多的数据库技术细节”，于是正文迅速滑向：

- 大段 `CREATE TABLE` 和索引语句；
- 字段名、类型、可空性与约束清单；
- ER 图和数据库产品细节；
- 从 SQL 中才能推断出的表用途与业务含义。

这些内容看似精确，却把最需要用户审核的问题藏了起来：为什么需要这张表，一行究竟代表什么，每个字段保存什么事实，以及这些数据怎样服务已确认的业务编排。

这不是生成能力不足，而是任务缺少阅读主轴和固定交付合同。只说“完成数据库设计”时，模型会按自己最熟悉的技术产物补全；DDL 又天然具有强结构和高细节密度，因此会挤占真正的数据设计。

## 设计决定

2.0 将 `数据库设计.md` 定义为“可由人审核的数据事实规格”，而不是建表脚本。

正文只有一个详细阅读主轴：表。

每张表先回答：

1. 为什么必须存在；
2. 一行记录表示什么；
3. 为什么这些字段要共同存在；
4. 谁产生、改变和使用这些数据；
5. 每个字段为什么存在、保存什么事实；
6. 哪些约束、查询、事务和生命周期必须保持。

所有实际字段都进入固定字段表，技术字段也不例外。字段除了类型、空值和默认值，还必须给出事实来源、变化时机、敏感性以及未来应落入数据库的注释原文。

## 设计与实现的边界

数据库设计拥有：

- 数据持久化的原因和边界；
- 表的存在意义与单行语义；
- 字段事实、关系、约束和查询依据；
- 数据怎样承载逐 API 编排中的事务、并发和恢复；
- 历史、清理、安全与迁移要求。

Coding 拥有：

- 具体 DDL 语法；
- ORM 映射；
- 迁移文件和执行编排；
- 回填、回退程序；
- 数据库注释的实际落地；
- schema 与设计一致性的测试。

Coding 可以在不改变设计语义的范围内选择数据库产品细节和工具。一旦实现便利要求改变表的意义、字段事实、约束或事务，就必须返回设计重新确认。

## 渐进应用

系统设计 Agent 只有在开始数据库阶段时才读取数据库固定模板。它先从已确认的业务、Domain、API 和逐 API 编排抽取需要持久化的事实，再形成表和字段，不从已有技术习惯反推业务模型。

候选交给用户前运行 `--database-system <系统>`。验证器只做确定性结构检查：

- 文档是否以数据承载全景和表目录开场；
- 每张表是否有稳定标识和固定章节；
- 字段说明是否使用完整表头；
- 是否覆盖目录中的每张表；
- 是否混入 SQL 代码块或 DDL；
- Coding 阶段读取的数据库设计是否已经由用户确认。

结构通过不代表语义正确。用户仍然审核为什么保存、如何解释和怎样承载业务。

## 预期结果

用户不再需要从数百行 SQL 中猜测设计意图。系统设计能够先稳定数据事实，Coding 再忠实生成可执行 schema；当实现技术变化时，只要数据语义没有变化，就不必重新讨论业务设计。
