# VCDDD 2.0 阶段性成果（五）：Domain 思想与进入 Coding 设计前的认知基线

> 状态：从真实使用与修正中形成的思想基线
>
> 日期：2026-07-29
>
> 用途：保存不应随对话压缩而丢失的认知，不定义不可回退的固定流程

## 1. 本文的位置

本文提炼 VCDDD 2.0 在真实项目使用和多轮修正中形成的思想性结论。它不是聊天摘要，也不记录每次修改经过；它保存的是后续参与者需要继承的世界观、判断方向和人机协作认识。

本文尤其用于解决两个问题：

1. 长对话结束或更换会话以后，新的 Agent 怎样恢复我们已经形成的认知，而不重新走一遍争论；
2. 从业务和 Domain 设计进入 Coding 相关设计时，哪些 DDD 思想仍然必须继续约束模块、API、数据库和代码。

新的 Coding 设计会话不需要读取形成这些结论的完整历史。它只需要读取当前 Skill、项目当前事实文档，以及本文中与 Coding 设计直接相关的部分。原会话可以继续保留为思想形成的历史依据。

## 2. VCDDD 要保护的不是流程，而是对业务世界的理解

代码生成和重写越来越便宜以后，最值得保护的内容不是某套目录、类结构或框架习惯，而是系统怎样表达业务世界。

这包括：

- 业务中实际存在什么；
- 谁拥有什么；
- 谁能够做什么；
- 行为依据什么事实和关系；
- 行为会改变或影响什么；
- 哪些判断由谁拥有最终解释权；
- 不同事物怎样协作并产生完整结果；
- 当前为什么采用这种认识；
- 新事实出现后应该有意修改哪里。

因此，VCDDD 不是把需求翻译成代码的流水线。它是一套让人和不同职责的 AI 持续理解、设计、实现并修正同一个系统的协作方式。

文档、图、原型、API、数据库、代码和测试都是当前业务认识的不同投影。它们可以帮助形成认识，也可能暴露旧认识的问题，但任何一种投影都不能仅凭“已经存在”自动成为业务真相。

## 3. 业务的基本叙事：什么做了什么，产生了什么

所有业务最终都可以回到一个朴素结构：

```text
什么人、事或物
→ 在什么情况下做了什么
→ 依据自己拥有的信息、状态、关系和规则作出什么判断
→ 使自己或其他事物发生了什么变化
→ 产生了什么业务结果
```

这不是一种文档格式，而是一种理解业务的方式。

如果一句业务描述没有明确主体，只说“系统支持配置”“完成统一管理”“实现整体更新”，它仍然没有说明业务世界中谁在做事。功能、页面、接口和任务名称可以描述执行入口，却不能替代业务主体。

前序业务设计不需要使用 DDD 术语，但必须把事实准备成这种有主体、有关系、有动作、有影响的叙事。这样，非开发人员可以直接判断业务是否符合真实需要，后续 Domain 设计也不需要从页面或功能清单猜测业务主体。

## 4. Domain 首先是业务中的核心事物

在当前 VCDDD 对 DDD 的理解中，Domain 分析的起点不是能力、流程、判断清单或技术边界，而是业务中客观存在的核心“事”或“物”。

一个核心事物本身就是 Domain。继续建模不是为了证明它配不配成为 Domain，而是为了把它认识完整：

```text
Domain
├── 自己维护的属性和状态
├── 自己拥有的其他事物
├── 与其他事物的关系
├── 自己能够执行或承受的行为
├── 行为时使用的事实、关系和规则
├── 始终需要维护的约束
└── 行为造成的自身变化和外部影响
```

Domain 名称回答“这是什么”。它应当是稳定、清楚的业务名词，而不是为了说明所有功能写成一条很长的动作句。

领域行为回答“它做什么”。行为名称应使用明确动词，说明动作和结果。

判断一个 Domain 是否被认识正确，不能只看它是否有身份、状态机、不变量或 Repository。更重要的是能否用自然业务语言回答：

- 这个核心事物是什么；
- 它拥有什么；
- 它能做什么；
- 为什么这些行为属于它；
- 行为后改变了什么；
- 它会对其他事物产生什么影响。

## 5. Domain 是拥有关系和行为的充血主体

Domain 不是数据容器。属于核心事物的业务判断、规则和行为必须由它自己维护。

外部应用可以：

- 获得外部事实；
- 把业务触发交给 Domain；
- 保存 Domain 产生的新状态；
- 把 Domain 产生的事实传递给其他参与者；
- 组织没有独立业务含义的调用顺序。

外部应用不能：

- 取出 Domain 的数据后替它完成业务判断；
- 绕过 Domain 直接修改本应由它维护的状态和关系；
- 把所有行为都放在 Service 中，只留下字段和读写方法；
- 用技术调用链代替业务中真实存在的过程。

所谓 Domain 自洽，不表示它与外部世界隔绝，而表示它对自己承担的事情拥有完整解释权。它知道自己拥有什么，能够依据自身状态、关系和规则处理触发，维护自己的约束，并产生明确影响。

## 6. 关系是 Domain 的内部事实，也是行为的重要来源

“谁拥有什么”是 Domain 分析的重要业务基础，因为属性和行为必须有明确归属。

需要看清：

- A 拥有什么信息和状态；
- A 是否拥有 B；
- A 与 B 通过什么关系相连；
- 关系由谁维护；
- 关系成立后允许、限制或新增了什么行为；
- 行为改变关系时由谁作出判断。

但能力不一定来自关系。一个 Domain 也可以根据自己拥有的属性、状态和规则形成自有行为。不能为了给行为寻找解释而虚构关系。

所有权和关系必须由用户确认，因为它们描述的是现实业务怎样成立，不是 AI 可以独立决定的技术结构。基础关系错误以后，后续 Domain、API、数据库和代码即使内部自洽，也只是在精确实现错误认识。

## 7. 多系统不是一个统一的 Domain 世界

一个业务目标可能同时涉及管理后台、Router、Hub 和外部平台，但它们不是同一个巨大模型的技术分区。每个系统都从自己的业务责任解释现实，拥有自己的通用语言、Domain、关系、行为和历史。

同一个现实事物可以在多个系统中分别形成 Domain。例如 Router 产生的 SecretKey：

- 在 Router 中，它可以是请求身份，拥有完整值、运行状态、允许模型、实际窗口和请求判断；
- 在管理后台中，它可以是 RouterKey，拥有用户归属、模板关系、管理行为和后台历史；
- 两者通过稳定身份对应，但不是同一个对象、聚合或内部模型。

“一个事实只有一个权威拥有者”需要落到具体事实和决定：

- Router 拥有 SecretKey 的完整值；
- 管理后台可以拥有这个外部 Key 属于哪个用户；
- Router 拥有请求是否放行；
- 管理后台可以拥有为这个 Key 选择哪个模板。

一方对某项事实拥有权威，不表示它对整个业务概念拥有唯一解释权。

因此，多系统设计必须：

1. 每个系统由独立 Agent 从自己的视角建模；
2. 同一个现实事物分别说明在各系统中叫什么、意味着什么；
3. 各系统只拥有自己的属性、关系、判断和行为；
4. 不共享 Domain 对象、聚合、Repository 或内部状态；
5. 只通过稳定身份、命令、事实和可核实结果协作；
6. 一个系统的技术证据和设计结论不自动适用于另一个系统。

限界上下文的意义不是为同一模型划代码边界，而是允许不同系统对同一现实事物拥有各自正确、有限的解释。

## 8. 多个 Domain 参与时，先寻找更高层的业务之“事”

一个行为需要多个 Domain 参与时，不能立即得出“需要编排 Domain”或“需要一个协调服务”。

首先判断业务中是否真实存在一个更高层的“事”，由它拥有：

- 这件事情本身的身份；
- 当前进行到哪里；
- 参与哪些 Domain；
- 下一步允许发生什么；
- 什么算成功、失败、取消或结果未知；
- 怎样恢复或结束；
- 最终产生什么业务影响。

如果这样的业务之“事”真实存在，它本身就是一个上层 Domain，也必须是拥有自身属性、关系和行为的充血主体。

如果业务中不存在这样的事，只是技术上需要先调用 A 再调用 B，那么它是应用协作，不应为了代码组织创造一个虚假的 Domain。

上层 Domain 不是无状态调用脚本。应用服务也不能因为调用了多个 Domain 就获得新的业务主权。

## 9. 当前业务足够正确，比预测未来更重要

业务会发展。今天只是一个属性的内容，未来可能产生自己的身份、生命周期、规则和行为；今天简单的一段关系，未来也可能成长为独立业务。

这不构成现在提前建模的理由。

当前设计只需要满足：

- 能完整覆盖现在已经确认的业务场景；
- 核心事物、关系和行为归属清楚；
- 当前业务规则能够自洽执行；
- 当前数据能够正确记录业务；
- 当前名称能够准确表达所承载的内容。

未来出现新的业务事实时，再重新识别核心事物、调整 Domain、迁移数据和修改实现。不能用未来可能性制造现在并不存在的实体、版本、聚合、Domain、表或基础设施。

## 10. DDD 用来找到业务，不用来限制业务

实体、值对象、聚合、不变量、命令、事件和状态机都可以帮助表达已经理解的业务，但它们不是所有事实必须填写的表格。

不是所有需要使用或保存的信息都值得由 Domain 维护。例如：

- 操作日志；
- 外部事实的引用或观察快照；
- 只服务页面组合的查询数据；
- 技术任务和消息投递状态；
- 没有独立业务判断的普通记录；
- 可以重新计算的统计或派生数据。

这些内容可以有数据库表，但不必为它们创造 Domain。

DDD 分类不合适时，应保留真实业务事实并选择合适的承载方式，而不是删除事实、扭曲名称或强迫业务适配模型。

## 11. 语言必须服从所处层次

行业黑话容易把执行方式伪装成业务结论。业务发现阶段应优先使用用户词汇、现实场景和普通话，只允许少量元关键词帮助寻找事实。

DDD 术语只在 Domain 分析和开发设计中使用，用来精确表达已经确认的业务，不用来创造业务。

不同层次的名称承担不同责任：

| 层次 | 名称要回答什么 |
| --- | --- |
| Domain | 这是什么核心业务事物 |
| 领域行为 | 谁做什么、产生什么结果 |
| 对象或关系 | 它代表什么、归谁所有或连接谁 |
| 页面文案 | 用户在当前页面语境中能否无歧义理解 |
| 数据库 | 保存什么业务事实、关系、日志、快照或技术状态 |

一个 Domain 名称不需要装下全部行为。一个页面按钮也不需要承担架构定义。名称是否清楚，应按其真实读者和使用场景判断。

数据库和 Domain 的名称都应使人能够直接知道它承载的业务内容，但这种“直接知道”不等于把行为说明塞进 Domain 名称。

## 12. 各层文档有独立意义，也有自然推导顺序

VCDDD 当前形成四个主要认知层次。

### 11.1 业务设计

面向非开发人员。

读者应能独立理解：

- 系统为什么存在；
- 能做什么和不做什么；
- 谁在什么场景下做什么；
- 系统怎样参与；
- 事情怎样变化和结束；
- 正常、拒绝、重复、失败和恢复时会发生什么。

它本身是一份完整业务说明，不只是给下一阶段提供输入。

### 11.2 系统与开发设计

面向开发人员审核。

它需要明确：

- 系统和模块边界；
- 核心 Domain、关系、行为和生命周期；
- API 怎样表达业务意图与结果；
- 每条业务线的核心流程怎样调用 Domain、提交事务、影响外部系统、记录关键证据并处理失败恢复；
- 数据库怎样保存领域状态和非 Domain 信息；
- 开发切片怎样覆盖业务场景。

它相当于详细 PRD 与实现设计的结合，也必须能够独立完成开发前审核。

这里需要区分两种审核：独立 AI 审核 Agent 只用于代码；Domain、API、核心业务流程和数据库 / SQL 则由设计 Agent 先完成完整推荐方案，再由用户审核。用户不是替 AI 从空白开始设计，而是决定当前版本能否成为开发事实。

Domain 的审核对象不只是“有哪些 Domain”的业务轮廓，还包括实体、值对象、聚合、不变量、生命周期、领域行为和协作边界。API 的请求响应、错误与并发合同，以及数据库的表、字段、关系、约束、事务和迁移，也都不能由 AI 在文档生成后自动视为确认。

核心业务流程是 API 与数据库之间的独立事实。它按业务线组织而不是按接口组织：每条业务线都要说明核心结果由哪些流程完成，但只展开真正包含业务判断、状态变化、事务、外部协作、关键日志或失败恢复的流程。稳定的流程步骤继续映射到代码和测试，使审核者能够判断实现是否保持了已确认的业务顺序。

### 11.3 代码与实现记录

代码根据当前开发基线形成。

实现记录保存：

- 哪项业务和设计由哪些代码承载；
- 哪些测试证明了哪些结果；
- 实现过程中发现了什么矛盾；
- 是否存在主动偏离和剩余风险。

它不是命令流水账，而是快速判断代码是否忠实执行设计的索引。

### 11.4 代码审核记录

只有代码形成固定快照以后才进行审核。

多个独立 Agent 从实现符合性、工程质量以及按风险触发的专项角度审核同一代码快照。审核只判断代码是否符合已经确认的业务和设计，不重新决定业务应该怎样。

前置业务和 Domain 设计必须由人参与确认。AI 审核不能证明业务正确，因此在代码形成以前增加审核 Agent 通常只会增加耗时和虚假权威。

这四层存在自然顺序，但不是不可回退的门禁。任何一层发现问题，都可以返回拥有相应事实的上一层补充或替换；修改源事实以后，只重新推导真正受影响的内容。

## 13. 人与 AI 的决定权不同

AI 应主动完成：

- 阅读已有材料和证据；
- 形成完整、可批判的当前解释；
- 发现遗漏、矛盾、反例和隐藏前提；
- 提出有依据的推荐；
- 完成 Domain 内部建模、API、数据库、事务和技术方案；
- 把实现发现返回正确的事实层；
- 维护可恢复文档。

人必须参与决定：

- 真正目标和利益；
- 业务中实际存在哪些核心事物；
- 谁拥有什么；
- 事物之间是什么关系；
- 行为究竟属于谁；
- Domain 对业务世界的完整表达是否正确；
- 多个合理业务结果之间怎样选择；
- 不可逆风险和组织承诺是否接受。

用户需要确认的重要问题不应被任意数量截断。应减少的是重复传输、无关历史和 AI 能独立解决的技术问题，而不是隐藏第四个或第五个仍会改变业务结果的重要决定。

## 14. 专业 Agent 不是身份扮演，而是独立认知单元

只给 Agent 一个“产品经理”“架构师”或“审核员”身份，不足以让它稳定工作。一个专业角色需要明确：

- 它最终要对什么结果负责；
- 它首先关注什么；
- 什么问题会触发深入调查；
- 可以沿哪些路线探索；
- 什么问题不属于它；
- 什么事实必须交给用户；
- 它读哪些权威文档；
- 它维护哪些事实；
- 下一位参与者怎样恢复。

这些内容共同形成认知协议。协议提供稳定方向和结果导向，但不能把思考压缩为死板问题清单。主问题必须优先，次要条件只在被事实触发时展开。

不同阶段适合由独立子 Agent 负责。每个 Agent 只读取自己的角色协议、当前任务和固定事实文档，在自己的范围内形成完整闭环。

主控只负责：

- 与用户交互；
- 把单一任务的用户原话交给当前专业 Agent；
- 一条反馈涉及多个系统时保存一次完整原话，并按系统切出互不污染的原文片段分别路由；
- 把专业 Agent 形成的交互包原样展示；
- 路由上游修订请求；
- 维护短状态和任务入口；
- 启动、续用和切换专业 Agent。

主控不重新完成专业工作，也不依赖自己的长聊天历史保存项目事实。

“主控是传声筒”不表示把整段话广播给所有 Agent。主控必须控制每个 Agent 看见的上下文：系统明确的反馈只进入该系统；共同业务事实先进入业务设计；无法可靠切分的内容先澄清。专业 Agent 不应通过用户同一条消息顺便获得另一个系统的模型、纠正和设计方向。

## 15. 文档是跨会话共享记忆

长会话不是项目的长期记忆。真正能够支持换会话和换 Agent 的，是项目中明确维护的当前事实、决定依据、未决问题和下一步。

每份阶段文档必须能独立服务自己的读者；同时，上一层足够完整时，应能自然支持下一层继续工作。

项目文档需要同时保留：

- 当前有效认识；
- 重要选择成立的理由和适用范围；
- 尚未解决的问题；
- 被接受但未验证的风险；
- 发生过的重要语义变化；
- 当前任务位置和下一步。

不需要保留：

- 全部聊天逐字稿；
- AI 的原始思维流水；
- 已经被当前事实文档吸收的重复解释；
- 与当前任务无关的旧目标全文。

因此，主会话可以持续压缩，也可以更换。只要专业 Agent 正确维护文档，新会话不需要继承旧会话的完整上下文。

## 16. 原型、证据和报告的正确位置

业务最初可以来自：

- 用户想法和讨论；
- 已确认原型；
- 为发现功能制作的快速网页原型；
- 现有系统和代码；
- 运行行为；
- 文档、截图和外部证据。

快速原型不一定发生在需求确认之后。人有时必须先看到一个可操作页面，才能发现真正需要的功能。此时原型是业务发现工具。

已经由其他对话确认的原型，则是其确认范围内的功能事实来源，不需要重新制作来“验证需求”。

报告和蓝图只是投影。它们可以从当前事实文档摘取、压缩、排序和绘图，但不能为了让报告完整而临场创造 Domain、API、数据库或系统方案。缺少内容时，应返回事实拥有者补充源文档。

## 17. 进入 Coding 设计时仍需保留的 DDD 思想

Coding 相关设计与前面的业务探索不需要共享全部讨论历史，但必须继续承认以下内容：

1. 模块承载 Domain，不定义 Domain；
2. 应用服务触发和协作 Domain，不夺走 Domain 行为；
3. API 表达业务意图、结果和失败，不只暴露 CRUD；
4. 数据库是领域状态和其他必要信息的投影，不反向定义业务主体；
5. 一个行为必须能追溯到拥有它的 Domain；
6. 跨 Domain 流程需要区分真实上层业务之“事”和普通应用协作；
7. 代码中的关键判断不能绕过 Domain；
8. 实现发现业务矛盾时返回设计，不静默用代码形成新事实；
9. 实现记录建立业务设计到代码和测试的对应；
10. API 确认后，按业务线形成并确认核心业务流程，明确 Domain 调用、事务、外部影响、关键日志和失败恢复；
11. 完整 Domain、API、核心业务流程和数据库 / SQL 设计分别经用户审核确认后，才形成当前开发基线；
12. 代码形成后才由独立 Agent 审核实现符合性和工程质量。

Coding 设计 Agent 不需要重新发现业务，也不需要重新判断用户已经确认的 Domain 是否正确。它需要做的是把当前 Domain 的属性、关系、行为、不变量和协作方式忠实映射为模块、API、数据、代码结构和测试，并把完整技术设计交给用户审核；AI 的专业判断责任不等于 AI 有权替用户确认。

## 18. 新 Coding 设计会话的最小恢复方式

建议新开一个专门的 Coding 设计会话。新会话不读取本次完整聊天历史，按以下顺序恢复：

1. 读取当前版本的 `vcddd/SKILL.md`；
2. 读取目标项目的 `docs/vcddd/index.md`、当前任务和主控状态；
3. 读取当前系统已经确认的 `业务设计.md` 与 `系统拆分.md`；
4. 只在需要理解本次方法思想时读取本文第 3 至第 11 节；
5. 进行 Coding 设计时重点读取本文第 17 节；
6. 把新的设计事实和未决问题继续写回项目文档，不依赖新会话历史。

原会话继续作为思想演化的历史保留；新会话承担新的专业目标。两者通过项目文档连接，而不是通过复制全部聊天连接。

## 19. 当前思想基线

可以把目前形成的认识压缩为：

> VCDDD 先用普通业务语言看见现实中的核心事物、关系、行为和影响，再用 DDD 让每个核心事物成为能够维护自身状态、规则和行为的充血 Domain；用独立专业 Agent 和可恢复文档保存不同阶段的完整事实；让人决定业务意义，让 AI 主动完成专业设计与实现；允许任何新证据返回正确的事实层，并只在代码形成以后审核代码是否忠实表达当前业务世界。
