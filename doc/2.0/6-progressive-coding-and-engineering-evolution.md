# VCDDD 2.0 阶段性成果（六）：忠于设计的 Coding 与渐进式工程收敛

> 状态：Coding 后半段的阶段性设计，已经进入运行时 Skill
>
> 日期：2026-07-30
>
> 前置文档：[Domain 思想与进入 Coding 设计前的认知基线](./5-domain-thinking-and-coding-transition.md)

## 1. 本文的位置

前面的工作已经使业务设计、Domain、API、核心接口内部编排、数据库和开发基线成为能够被用户理解与确认的当前事实。进入 Coding 以后，不再需要继续发散业务意义，而需要解决另一个问题：

> 怎样让 AI 忠实实现已经稳定的业务，同时主动形成足以支撑真实系统的工程方案，并让这些工程认识在后续 Coding 中持续生效。

Coding 不是机械翻译设计，也不是再次进行业务发现。它必须同时承担两项责任：

1. 让代码忠实表达已经确认的业务世界；
2. 对框架、代码组织、可靠性、日志、测试、安全、性能和运行等非业务问题形成专业解决方案。

这两项责任具有不同开放程度：

```text
业务、Domain、API、事务结果和数据事实
→ Coding 不再发散，只能忠实实现

工程结构、技术机制、代码表达和运行保障
→ Coding 主动调查、比较、实现并持续收敛
```

## 2. 事务属于已确认的业务实现设计

数据库事务是一种技术机制，但事务保护的完整性、提交边界、部分成功、外部影响顺序、结果未知和恢复方式会直接改变业务结果。

因此，事务不等到代码形成以后再临场决定。Domain 之后的业务实现设计完整说明：

- 一次业务行为需要哪些变化共同成立；
- 什么时刻可以宣布业务成功；
- 哪些本地变化必须原子提交；
- 外部调用发生在提交前还是提交后；
- 失败时回滚什么；
- 不能回滚的影响怎样恢复、补偿或对账；
- 重复、并发、超时和结果未知怎样解释。

Coding 可以自主选择事务装饰器、显式 Unit of Work、锁、CAS、Outbox、重试或其他技术机制，但不能改变已确认的事务范围、提交点、外部顺序和失败语义。

事务与数据库设计的关系因此是：

```text
业务完整性与成功语义
→ 核心接口内部事务编排
→ 数据库结构、约束和并发承载
→ 系统工程实现规则
→ 代码与测试
```

## 3. 每个系统拥有自己的工程编码规范

业务目标可能涉及多个系统。每个系统有独立的限界上下文、技术栈、运行方式和风险，因此工程编码规范也以系统为边界：

```text
vcddd/systems/<system-id>/coding/工程编码规范.md
```

它不是项目级通用教材，也不属于需要用户逐项确认的业务设计。它保存这个系统的 Coding 以后都需要遵守的当前工程认识，例如：

- Domain、应用层和基础设施层怎样编码；
- 模块依赖和应用用例怎样组织；
- 已确认事务在代码中怎样开启、传播和提交；
- 并发、幂等、错误、重试和恢复怎样实现；
- 日志、指标和追踪使用什么结构、时机和频率；
- 数据访问、迁移和外部 Adapter 遵守什么边界；
- 安全、性能、容量、配置和运行怎样保证；
- 测试怎样证明业务结果和工程风险；
- 命名、目录、类型和基础代码表达遵守什么规则。

不同系统不默认共享同一份规范。同一仓库拥有多个系统时，每份规范明确适用代码范围；共同平台规则可以被引用，但必须说明在本系统怎样生效。

## 4. 工程规范怎样在真实 Coding 中形成

系统第一次进入 Coding 时，AI 不应该凭空写一套完整工程圣经。它先读取：

- 当前开发基线和直接设计来源；
- 仓库已有代码、配置、测试与运行入口；
- 已经存在的语言和框架约定；
- 当前切片真正触发的工程风险。

由此形成最小可用规范，明确区分：

- 已经成立并继续采用的规则；
- 现有代码违反但需要迁移的规则；
- 只服务当前切片的局部选择；
- 证据不足、暂不能约束代码的候选；
- 已经被新认识替代的历史规则。

Coding 过程中出现原规范无法表达的新工程问题时，AI 判断它是否会在本系统后续 Coding 中重复生效：

- 只属于当前切片：写入实现或工程改进记录；
- 跨切片稳定适用：写入工程编码规范；
- 证据不足：登记为候选；
- 改变业务或设计：返回事实拥有者。

这样，工程规范来自真实代码和风险，但不会让偶然实现自动升级为永久规则。

## 5. AI 怎样渐进加载工程指引

工程规范会持续增长。如果每次 Coding 都完整加载全部设计历史、全部规则和全部代码，旧问题和无关细节会占据主要注意力。

因此，工程规范首先提供“当前规则索引”。每项规则说明：

- 规则标识；
- 级别；
- 适用或触发条件；
- 正文位置。

规则分为：

- `核心`：本系统全部 Coding 始终读取；
- `条件`：只有并发、金额、外部调用、批量、迁移、安全、容量等事实触发时读取；
- `补充`：不改变当前正确性的偏好，在主线稳定后处理。

Coding Agent 的恢复顺序是：

```text
当前任务和开发基线
→ 工程规范索引与核心规则
→ 当前切片直接设计来源
→ 被事实触发的条件规则
→ 当前代码、测试和运行证据
→ 必要时追溯历史改进与审核
```

这不是让 AI 忽略未读取的规则。索引必须使 Agent 能够判断当前事实是否命中规则；索引无法完成这个判断时，规范本身需要先被修复。

## 6. 首次实现不以提前抽象为目标

首次 Coding 的主线是：

> 忠实、清楚、可运行和可测试地形成一个纵向业务结果。

AI 不需要在第一次看见相似代码时立即封装，也不为尚未出现的未来复用预建接口、基类、框架或扩展点。局部技术重复可以暂时存在，等真实代码形成后再判断。

但这不允许同一个业务规则分裂：

- 同一权限判断不能在 Controller 和 Domain 分别实现；
- 同一状态转换不能在多个 Service 各写一份；
- 同一事务或失败语义不能由多个入口独立解释；
- 复制会立即造成安全、数据或恢复风险时不能等待后续重构。

“是否抽象”不能只看行数或出现次数。合理抽象需要证明：

- 多处代码承担同一责任；
- 它们具有同一变化原因；
- 能形成清楚名称、合同和测试边界；
- 抽取确实降低不一致或验证成本。

表面语法相似但业务意义不同、只有一个消费者、封装后需要大量分支或只减少少量行数的代码，不应被强行合并。

## 7. 忠于设计不等于禁止反馈设计

Coding 会接触设计阶段没有的实现证据：真实 SQL、数据库能力、迁移数据、框架限制、并发行为、测试失败和运行结果。这些证据可能说明已经确认的数据库甚至 Domain 设计并不合理。

因此 Coding 同时承担两项责任：

- 在设计成立时忠实落地，不重新扩散业务想法；
- 在新证据表明设计不成立时，主动提出问题和具体修改建议。

先区分工程问题和设计问题。SQL 方言、ORM 写法、迁移工具和代码组织能在不改变语义的情况下解决，仍由 Coding 决定。若表、字段、约束、事务无法保持数据事实，或者 Domain 的所有权、关系、聚合、不变量和生命周期在代码中相互矛盾，就不能靠隐藏字段、触发器、重复判断或特殊分支绕过去。

Coding 为此形成设计反馈记录，至少保存：

- 问题对应的权威设计；
- 实现、SQL、测试或运行证据；
- 为什么当前设计不成立或代价不可接受；
- 影响的业务结果和代码范围；
- 推荐修改；
- 必要的替代方案与权衡；
- 当前停止位置和可以继续的范围；
- 应修改的权威文档与事实拥有者。

Coding 有建议权，没有上游事实写入权。系统或业务设计 Agent 独立判断建议，需要改变设计时重新提交用户确认并生成新开发基线。这个闭环同时避免两种错误：Coding 静默改变设计，以及 Coding 以“忠于设计”为由机械实现一个已经被证据推翻的方案。

## 8. 首次实现以后进行工程改进

首次实现通过自检以后固定一个可定位快照。新的独立 Agent 从单一工程角度分析这个真实快照，而不是在写代码前猜测所有可能问题。

至少执行“重复与抽象”分析。再根据系统规范和当前风险选择：

- 边界与依赖；
- 事务、并发、错误与恢复；
- 日志、指标与追踪；
- 测试质量；
- 安全与敏感信息；
- 性能、容量与资源；
- 配置、部署和平台运行。

这些 Agent 与正式审核不同：

- 工程改进可以提出并实施修改；
- 它不输出“通过 / 不通过”；
- 它保持业务与设计事实不变；
- 它把系统级工程认识写回规范；
- 它把局部选择、修改和验证保存在当前交付单元的工程改进记录。

多个 Agent 可以对同一快照并行分析，但不能并行修改同一个文件、公共接口或相互依赖的行为。重叠修改需要由一个 Agent 或连续 Agent 在最新快照上串行完成。

## 9. 工程改进与正式审核必须分离

如果审核 Agent 一边判断、一边修改代码，审核对象会持续变化，最终无法回答哪个快照被审核、哪个问题已经被证明解决。

因此形成两个不同闭环：

```text
首次实现快照
→ 工程分析和可修改的工程改进
→ 最终待审核快照

最终待审核快照
→ 只读实现符合性审核
+ 只读工程质量审核
+ 风险触发的专项审核
→ 审核结论
```

正式审核发现问题以后，再启动开发或工程改进角色形成新快照；原审核角色只对受影响范围复审。审核不能顺手重构移动中的代码。

## 10. 交付记录保存实现演化

每个交付单元按照任务、阶段和最终统一交付三个不同层次保存：

```text
delivery/<delivery-id>/
├── plan/
│   └── 开发任务图.md
├── stages/
│   └── <stage-id>/
│       ├── 阶段记录.md
│       ├── 阶段运行验证.md
│       └── 阶段审查.md
├── tasks/
│   └── <TASK-ID>/
│       ├── 任务进度.md
│       ├── 实现记录.md
│       ├── 任务验证.md
│       └── 任务审查.md
├── feedback/design/
│   └── <序号>-<事实对象>.md
├── integration/
│   └── 集成记录.md
├── testing/
│   ├── feedback/
│   └── 测试结论.md
├── improvement/
│   └── <轮次>-<分析角度>.md
└── review/
│   ├── 实现符合性.md
│   ├── 工程质量.md
│   └── 审核结论.md
```

任务进度只保存最近事件、代码产物、Commit、模型选择和集成状态；实现记录保存单个任务的最终代码交接。任务 Commit 形成后立即由独立 Agent 生成 `任务验证.md` 与 `任务审查.md`，两者通过后才能合并。阶段记录拥有共同起点、起点等价性、任务输出、唯一阶段 Commit 和用户确认门禁；阶段 Commit 形成后立即生成 `阶段运行验证.md` 与 `阶段审查.md`，两者通过后才能确认或解锁依赖阶段。只有全部阶段闭合以后才建立最终集成记录，并进入跨阶段统一测试、工程改进和最终审核。

`integration/集成记录.md` 是全部生产任务汇合后的唯一集成事实，保存：

- 当前开发任务图与起始代码快照；
- 已合并任务、任务 Commit、阶段 Commit、合并顺序及增量验证与审查证据入口；
- 共享写入处理与仍未实现事项；
- 唯一统一生产代码快照；
- 统一测试和工程改进状态；
- 最终待审核快照。

设计反馈只在实现证据推翻或质疑上游设计时建立，保存问题、证据、修改建议、上游处理和重新确认结果。工程改进记录保存输入快照、分析角度、修改或保留理由、实际修改、工程规范更新、验证结果和输出快照。两者都不是终端流水或原始推理。

正式审核记录只判断最终固定快照。实现、工程改进和审核各自拥有自己的事实，不能互相覆盖。

## 11. 当前 Coding 思想基线

当前认识可以压缩为：

> 业务与系统设计负责完整确定系统要表达的业务世界，包括事务和数据库怎样承载业务结果；Coding 在这些事实内自由形成工程方案，并把跨切片稳定适用的认识保存为系统级工程编码规范。实现证据表明设计不合理时，Coding 给出问题、证据和推荐修改，由事实拥有者与用户重新确认。首次实现优先忠实和清楚，不预测性抽象；真实代码形成后再由独立工程改进 Agent 从多个角度收敛，最后以固定快照接受只读审核。这样既不让代码扩散业务，也不把 Coding 降为缺少工程判断的机械翻译。
